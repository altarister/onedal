# 최소 금액을 세 배차망 공통으로 — 계획 (onedal-ab 검토 반영)

기사님 원문: *"화물24시, 인성, 픽커 모두 적용될 수 있도록 공통으로 처리되도록 수정되어야 할 것 같아.
24시 플러그인에 있는 것을 모든 배차망이 공통으로 사용할 수 있도록"*
앞선 원문(최소 금액 칸 만들 때): *"배차망 모두 통일해서 가는 것이 맞을 것 같다"*

## ② 지금은 이렇게 돈다

최소 금액의 원천은 DB `user_filters.min_fare` 한 칸이다. 관제웹 🔍 필터 «어떤 콜»의 막대(0~10만, 0 = 끔)가 고친다.
서버가 피기백 필터 `minFare` 로 원달앱에 내려 준다. 원달앱이 목록 줄을 거르는 자리는 배차망마다 다르다.

| 배차망 | 원달앱의 요금 조건 (지금) | 최소 금액이 걸리나 |
|---|---|---|
| 화물24시 `Hwamul24Parser.shouldClick` | `fare ≥ minFare` **그리고** (단가표가 서면) `fare ≥ 배송거리 × 단가` · 상한 | ✅ 늘 |
| 인성 `InsungParser.judge` | 단가표가 서면 `fare ≥ 배송거리 × 단가` **만**. 단가표·차종·배송거리 중 하나라도 없을 때만 `fare ≥ minFare` | ❌ 평소엔 안 걸림 |
| 픽커 `KakaoPickerParser.decideAxes` | `fare ≥ pickerAlarmMinFare`. 이 값은 DB `user_settings.picker_alarm_min_fare`(관제웹에 칸 없음, 기본 1만)에 콜할인율을 곱한 것이다(`computePickerAlarmMinFare`, 할인율 100%면 0) | ❌ 안 걸림 |

원달앱 화면 셋이 `pickerAlarmMinFare` 를 «하한»으로 보여 준다 — `NetworksScreen:106·263`(«1차 하한 N원») · `DashboardScreen:117-120` · `MainViewModel:96·117·140-144`(설명문).
서버 `OrderEvaluator` 는 픽커의 요금 하한을 «앱이 이미 걸렀다»며 건너뛴다(`skipFareFloor`). 인성·24시는 첫짐(STANDBY)일 때만 `minFare` 로 한 번 더 본다 — 이중 안전망이라 그대로 둔다.

| 사용자 | min_fare | 콜할인율 | picker_alarm_min_fare | 앱이 받는 픽커 하한 |
|---|---|---|---|---|
| af0a… | 20,000 | 100% | 4,000 | 0 (할인율 100%) |

## 바꾸는 모습 — 식은 한 벌, 부르는 곳은 세 파서의 첫 요금 축

**공통 한 벌:** 새 파일 `core/engine/FareFloor.kt` (있는 폴더에 파일만 더한다) — `passes(fare, minFare)`, `minFare ≤ 0` 이면 끈 것이라 통과.

**부르는 자리:** 세 파서의 판정 함수 안, 지금 요금 축이 있던 자리. 목록 순회(`HijackService`)에 두지 않는다.
- 까닭: 성적표(«첫 번째로 걸린 축»)와 버린 콜의 «떨어진 까닭»은 파서의 판정 함수 한 곳이 세야 한다.
  `HijackService` 목록 순회 주석이 *«여기서 필터를 다시 읽어 판단하면 decide 와 두 벌이 된다»* 로 못 박아 두었다.
  목록 순회에서 따로 세면 필터 꺼짐(`isActive=false`)도 그 자리가 다시 읽어야 해 또 두 벌이 된다.
- 기사님 «공통으로 처리»는 **식이 한 벌**이라는 뜻으로 읽는다 — 배차망마다 금액 비교를 다시 쓰지 않는다.

**배차망 파서에서 바뀌는 것:**
- 24시: `order.fare >= filter.minFare` → `FareFloor.passes(order.fare, filter.minFare)`. 단가표·상한은 남는다
- 인성: 단가표가 서도 `FareFloor.passes` 를 **함께** 본다 (24시와 같은 «최저가 그리고 단가»). 단가표가 없을 때의 대체 판정은 이것으로 흡수된다
- 픽커: `decideAxes` 요금 축이 `pickerAlarmMinFare` 대신 피기백 `minFare` 를 `FareFloor.passes` 로 본다. 로그 «하한 N» 도 그 값

**원달앱 화면 (화면에 보이는 것이 바뀐다):** 위 화면 셋의 «픽커 하한 N원»을 «최소 금액 N원»(피기백 `minFare`)으로 바꾼다 — 화면은 1만 원이라 하는데 실제로는 막대가 걸리는 어긋남을 막는다.

**서버:** `OrderEvaluator` 의 «픽커는 앱이 이미 걸렀다 (픽커 알람 하한)» 문구를 «최소 금액»으로 맞춘다.
`pickerAlarmMinFare` 피기백·`picker_alarm_min_fare` 칸·`computePickerAlarmMinFare` 는 원달앱이 더는 읽지 않는다 — 이번 수정에서 지우지 않는다.

## 단계와 «무엇이 참이면 끝인가»

1. 빨간불: 세 배차망에 `fare < minFare` 인 콜 한 줄씩(인성은 단가표 통과 콜) → 지금은 인성·픽커가 통과시킨다는 JVM 검사가 빨갛다. 세 파서 판정 함수에 `FareFloor.passes` 호출이 있는지 무는 검사도 빨갛다
2. `FareFloor` + 세 파서 → 1의 검사 초록, 기존 `filterVerdict` 문제지는 요금 축 기대만 바뀐다
3. 픽커 채점기(`pickerAlarmGrade.mjs`)가 읽는 «하한 N» 값 출처를 최소 금액으로 → 채점기 검사 초록
4. 원달앱 화면 셋 문구 → 화면 문구를 읽는 검사가 있으면 초록
5. 서버 문구 → 서버 규칙 검사 초록
6. 게이트 전부 → 초록 · 원달앱 설치

## ⑤ 기사님 하루에 무엇을 하나

- 좋은 콜: 막대를 픽커 요금대(5천~1만)보다 높게 두면 **픽커 콜이 줄어든다**. **인성도** 단가로는 이득인 짧은 관내 콜(막대 2만·콜 1.8만)이 새로 잘린다 — 하루 6콜에 관내콜을 끼우는 자리와 닿는다. 막대를 낮게 두면 둘 다 그대로다.
- 노이즈: 인성은 단가표가 서도 «너무 싼 짧은 콜»을 막대가 막아 준다 → 줆. 24시는 지금과 같다.
- 기사님 손: 요금 하한을 고치는 자리가 관제웹 막대 하나로 모인다(픽커 하한은 관제웹에 칸이 없었다). 원달앱 화면도 그 값을 보여 준다.
- 관제웹 «버린 콜»의 떨어진 까닭 분포가 바뀐다 — 인성·24시에서 요금이 차종·지역보다 먼저 세어질 수 있다(축 순서는 파서 안 자리대로).

🔴 **요금 체계가 다른 배차망에 한 값을 건다.** 픽커는 5천 원대가 보통이고 인성·24시는 2만 원 이상이다.
지금 실물은 픽커뿐이라 막대를 픽커 요금대에 두면 당장은 된다. 인성·24시가 실물이 되는 날 다시 본다.
콜할인율 100%(«전부»)여도 막대는 그대로 하한으로 걸린다 — 지금 픽커 하한은 할인율 100%면 0 이었다. 막대 0 이 «끔»이다.

## 검토 (onedal-ab)

- 공통 자리 = 목록 순회 → **파서 안 첫 요금 축**으로 고침 (두 벌 금지 주석 둘)
- 필터 꺼짐 문제 → 파서 안이면 사라짐
- 픽커 하한을 읽는 원달앱 화면 셋 → 이번 일에 넣음
- 인성 관내 콜이 새로 잘리는 위험 → ⑤ 에 넣음
- 서버 `skipFareFloor`·첫짐 재확인 → 이중 안전망이라 그대로
