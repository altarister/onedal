# 시니어 서버 개발자 심층 리뷰: 1DAL 백엔드 아키텍처 분석 및 개선 방향

**작성 일시**: 2026-09-17  
**작성 관점**: 시니어 백엔드 아키텍트 / Principal Systems Engineer 관점  
**핵심 목표**: 초저지연(Sub-100ms) 판정 처리, 동시성 락(Lock) 및 I/O 블로킹 제거, 무중단 스케일아웃(가로 확장) 지원, 고성능 인프라 완성

---

## 📌 총평 및 아키텍처 진단

현재 1DAL 백엔드는 **"1명의 개발자가 1대의 차량을 위해 빠르게 비즈니스 로직을 구현한 전형적인 모놀리식 프로토타입"**입니다. 현장 도로 위 실측 오류를 방어하는 비즈니스 규칙(규칙 ③, ④, ⑤)은 정교하게 구축되어 있으나, **백엔드 시스템 엔지니어링 관점에서는 동시성 병목, 단일 스레드 I/O 블로킹, 외부 API 의존성 등 구조적인 성능 한계**를 지니고 있습니다.

기사 수가 5~10명으로 늘어나거나 대량의 콜이 쏟아지는 순간 서버가 먼저 멈추거나 지연(Lag)을 일으킬 수 있는 핵심 취약점과 개선 방향을 정리합니다.

## 1. 런타임 & 프로세스 아키텍처

### ⚠️ 문제점 (취약점)
1. **운영 환경에서의 JIT 실시간 컴파일러(`tsx`) 구동**
   - `ecosystem.config.cjs`에서 프로덕션 서버를 `args: 'tsx src/index.ts'`로 구동하고 있습니다.
   - `tsx`는 개발 편의용 도구이며, 운영 환경에서 실행 시 불필요한 메모리 점유, 초기 구동 지연, V8 엔진의 JIT 인라인 캐싱 효율 저하를 초래합니다.
2. **동기식 SQLite(`better-sqlite3`)와 단일 이벤트 루프의 충돌**
   - `better-sqlite3`는 동기식 C++ 네이티브 바인딩입니다.
   - DB에 쿼리를 실행하는 수 밀리초 동안 **Node.js의 메인 스레드(이벤트 루프)가 완전히 블로킹(Freeze)**됩니다. 초당 1회씩 들어오는 GPS 로깅, 필터 연산, 장부 조회가 겹치면 메인 스레드가 멈추어 소켓 통신과 앱 응답이 밀립니다.

### 💡 개선 및 구현 방향
- **AOT(사전 컴파일) 프로덕션 번들 파이프라인 구축**:
  - `esbuild` 또는 `tsup`을 도입하여 빌드 타임에 단일 최적화 자바스크립트 파일(`dist/index.js`)로 컴파일하고, 운영에서는 순수 `node` 바이너리로 실행하여 메모리를 절감하고 처리 속도를 극대화합니다.
- **Worker Thread 기반 DB 쓰기 및 지오메트리 연산 분리**:
  - 무거운 Turf.js 지오메트리 연산(폴리곤 교집합, 마름모)과 SQLite 쓰기 작업을 메인 스레드에서 분리하여 **Worker Thread 또는 백그라운드 작업자**로 넘겨 메인 이벤트 루프 지연(Lag)을 0ms로 유지합니다.

## 2. 데이터베이스 & 동시성 모델

### ⚠️ 문제점 (취약점)
1. **SQLite의 물리적 단일 라이터(Single Writer Lock) 한계**
   - SQLite WAL 모드가 동시 읽기는 지원하지만, **쓰기 트랜잭션은 전 시스템에서 오직 1개만 허용**됩니다.
   - 여러 기사의 GPS 수집, 스크랩 로그, 판정 이력이 동시에 쓰기를 시도하면 `SQLITE_BUSY (database is locked)` 에러가 발생하거나 큐에 쌓여 지연이 급증합니다.
2. **상태 저장형(Stateful) 인메모리 세션 스토어**
   - 기사의 활성 세션과 필터(`userSessionStore.ts`, `filterManager.ts`)가 서버 프로세스의 메모리 객체로 관리됩니다.
   - PM2가 메모리 초과(1GB)로 재시작되거나 배포가 진행되면 실시간 세션 메모리가 순간적으로 소실되며, 서버를 여러 대로 늘리는 스케일아웃이 원천적으로 불가능합니다.

### 💡 개선 및 구현 방향
- **인메모리 쓰기 버퍼(Write-Behind Buffer) 도입**:
  - 매초 들어오는 GPS 로그나 통계 데이터를 디스크에 즉시 쓰지 않고, 메모리 버퍼 큐에 모아두었다가 2~3초 주기로 일괄 커밋(Bulk Insert)하여 디스크 I/O 횟수를 95% 이상 감축합니다.
- **Redis 기반 분산 세션 & 캐시 레이어 분리**:
  - 세션과 필터 상태를 Redis 같은 외부 인메모리 저장소로 분리하여, **서버 프로세스가 다운되거나 재기동되어도 기사의 운행 세션이 즉각 100% 무손실 복구**되도록 무상태(Stateless)화합니다.

## 3. 외부 API 통합 & 지오메트리 캐싱

### ⚠️ 문제점 (취약점)
1. **카카오 모빌리티 API 직렬 동기 호출 병목**
   - 새 콜이 들어올 때마다 외부 카카오 API에 HTTP 요청을 보내고 응답을 대기합니다. 카카오 API 응답이 200~300ms 지연되면 우리 시스템의 판정도 그대로 밀립니다.
   - 네트워크 일시 단절이나 카카오 호출 제한(Rate Limit 429) 발생 시 판정 전체가 중단되는 구조적 취약점이 있습니다.
2. **단순 반경 200m 베이스 캐시의 조악함**
   - 현재 `baseRouteCache`는 단순 위경도 직선거리 200m만 비교합니다. 고가도로 위와 아래, 고속도로 진입 전후 등 실제 도로 토폴로지(위상)가 다른 위치가 동일 좌표로 오인되어 캐시가 오염될 위험이 있습니다.

### 💡 개선 및 구현 방향
- **S2 Geometry / H3 육각 타일 기반 공간 인덱스 캐시**:
  - 구글 S2 또는 우버 H3 공간 인덱스를 적용하여, 단순 거리가 아니라 차량의 진행 방향(베어링 각도)과 도로 링크가 일치할 때만 캐시를 재사용하도록 정밀화합니다.
- **서킷 브레이커(Circuit Breaker) & 로컬 비상 판정 폴백**:
  - 카카오 API 지연(1초 초과) 또는 장애 감지 시 즉각 외부 호출을 차단하고, 로컬 하버사인 거리 기반의 비상 추정 엔진으로 0.01초 만에 즉각 폴백 판정을 내려 기사의 30초 결재 타이머를 보장합니다.

## 4. 통신 프로토콜 & 모바일 통신 효율

### ⚠️ 문제점 (취약점)
1. **HTTP/1.1 피기백(Piggyback) 폴링의 무선 네트워크 낭비**
   - 안드로이드 앱이 매초 `POST /api/scrap`을 날리고 응답에 서버 명령을 실어 보내는 방식은 매 요청마다 수백 바이트의 불필요한 HTTP 헤더를 왕복시킵니다.
   - 이는 이동 중인 스마트폰의 무선 모뎀을 24시간 풀가동시켜 폰의 발열과 배터리 소모를 가속화합니다.
2. **단방향 폴링으로 인한 긴급 취소 지연**
   - 서버가 똥콜을 감지하여 긴급 취소 명령을 내리고 싶어도, 앱이 다음 스크랩 요청을 보낼 때까지 최대 1초 동안 명령 전달이 지연됩니다.

### 💡 개선 및 구현 방향
- **gRPC (HTTP/2) 또는 바이너리 웹소켓 양방향 푸시 전환**:
  - Protobuf 기반의 초경량 바이너리 통신으로 전환하여 패킷 크기를 80% 이상 줄이고 완벽한 양방향 스트리밍을 구축합니다.
  - 위험 콜 감지 시 서버에서 안드로이드 앱으로 0.005초 만에 다이렉트 긴급 취소 시그널을 푸시합니다.

## 6. 비표준 세션 분리 모델 및 저장소 경계 불일치 취약점

### ⚠️ 문제점 (취약점)
1. **상식과 불일치하는 세션 계층 분리 (`UserSession` vs `DeviceSession`)**
   - **일반적인 아키텍처 상식**: 멀티 디바이스 서비스에서는 `UserSession` 객체 하위에 소속 기기 컬렉션(`session.devices`)이나 기기 상태가 포함되어 관리될 것으로 기대합니다.
   - **1DAL 실제 구현**:
     - 사용자 세션(`userSessionStore.ts`): 기사의 주문 상태(`myOrders`, `pendingOrdersData`, `activeFilter`, `pendingDecisions`)만 관리.
     - 기기 세션(`routes/devices.ts` & SQLite `user_devices`): 모듈 스코프의 인메모리 `activeDevices: Map<string, DeviceState>` 및 SQLite DB 테이블에 별개로 분리 관리.
   - **결함 발생 메커니즘**: 엔지니어가 일반적 상식에 따라 `session.devices.get(deviceId)`를 호출하면, 런타임에 `TypeError: Cannot read properties of undefined (reading 'get')` 예외가 발생하여 배차 판정 및 토스트 팝업이 먹통이 됩니다.
2. **인메모리 세션 상태와 SQLite DB 간의 데이터 비대칭성 (이중성)**
   - 가상/체험 모드(`SIMULATION`) 콜은 관제탑 동선 및 합짐 클러스터링 계산을 위해 Node.js RAM(`session.myOrders`)에는 적재되지만, 실제 DB 오염을 방지하기 위해 SQLite `orders` 테이블에는 저장되지 않습니다.
   - 하지만 서버 엔진 내부의 여러 하위 모듈(예: 마일스톤 생성기 `birthFirstStep`, 주행 상태 기록기)은 "메모리에 주문이 존재하면 당연히 DB에도 `orders` 행이 존재한다"는 일반적인 영속성 가정을 전제로 코딩되어 있어, SQLite 외래키/조회 예외가 연쇄 폭발합니다.
3. **취소·페널티 로직의 파편화 (SSOT 부재 위험)**
   - 콜이 종료되는 5가지 경로(웹 취소 결재, 폰 화면 이탈, 30초 타임아웃, 긴급 리셋, 신규 콜 선점)에서 각각 취소 처리를 수행할 경우, 가상 콜 필터링 누락 시 기사에게 실제 '취소 10회 페널티'가 누적되고 DB에 유령 취소건이 기록됩니다.

### 💡 개선 및 구현 방향
- **단일 통합 세션 파사드(Session Facade) 및 기기 모드 접근자 표준화**:
  - `getDeviceMode(deviceId, userId)`와 같이 저장소 위치(메모리 Map vs SQLite)를 은닉하는 단일 진실 공급원(SSOT) 접근자를 제공하고, `UserSession`에 가상 기기 인터페이스를 바인딩하여 잘못된 프로퍼티 접근을 컴파일 단계에서 차단합니다.
- **취소·종료 파이프라인의 SSOT 캡슐화 (`cancelCount.ts`)**:
  - 호출부 어디에서도 가상 모드 여부를 분기하지 않도록, `countCancel(order)` 및 `countKeep(order)` 코어 내부에서 `order?.isSimulated`를 완전 캡슐화하여 페널티 및 DB 누수를 원천 차단합니다.
- **영속성 계층 격리 어댑터 도입**:
  - DB 저장이 필요한 실물 콜과 메모리 전용 가상 콜을 구분하는 `Persistable` 플래그를 모델 레벨에서 강제하고, DB 접근 함수 앞단에서 인터셉트하여 예외 없이 안전하게 무시(No-Op)하도록 가드합니다.

## 📋 단계별 백엔드 리팩토링 로드맵

| 단계 | 과제 | 적용 기술 | 기대 효과 |
| :---: | :--- | :--- | :--- |
| **1단계** | 프로덕션 빌드 현대화 | `esbuild` / `node dist/index.js` | CPU/메모리 40% 절감, 기동 속도 3배 향상 |
| **2단계** | 세션 파사드 및 SSOT 캡슐화 | `SessionFacade` / `cancelCount` 일원화 | 계층 혼동 런타임 크래시 0건 달성 |
| **3단계** | 이벤트 루프 블로킹 해소 | Worker Thread 지오메트리 오프로딩 | 메인 이벤트 루프 지연 0ms 유지 (소켓 렉 제거) |
| **4단계** | DB 디스크 I/O 최적화 | 인메모리 링버퍼 Bulk Insert | SQLite 쓰기 락 충돌(`SQLITE_BUSY`) 95% 제거 |
| **5단계** | 외부 API 회복탄력성 | 카카오 API 서킷브레이커 & 로컬 폴백 | 카카오 장애 시에도 판정 중단 없는 무중단 서비스 |
| **6단계** | 초저지연 양방향 통신 | gRPC / WebSocket 다이렉트 푸시 | 무선 트래픽 80% 절감 및 긴급 취소 지연 제로화 |
