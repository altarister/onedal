# 37. 못 알아본 화면에 사진을 붙인다 — «그 화면이 무엇이었나»를 한 장으로 특정한다

기사님 말씀:
- *"이미지랑 추가된 문자들을 모두 가지고 있는 거지?"* → 지금은 사진이 없고 글 앞 200자만(같은 화면 하루 한 번) 남는다.
- *"그럼 그 페이지를 어떻게 특정하지?"* → *"나 기획해"* — 원달앱이 못 알아본 화면을 만나면 그 순간 사진을 찍어 운영센터 «이상 기록»에 같이 붙인다.

배경 원칙(기획 35): 어떤 배차망이건 모든 페이지 · 모든 팝업을 배차망 정의 표에 적는다. 표에 없는 화면은 리뉴얼 신호이고, **캡처를 붙여 표에 한 줄 더한다.**
지금은 그 «캡처»를 기사님이 폰에서 손으로 찍어야 한다. 이 기획은 원달앱이 그 캡처를 스스로 남기게 한다.

## 끝의 모습

> 운영센터 «점검 › 앱 이상 기록»의 «모르는 화면» 줄을 누르면 그 순간의 폰 화면 사진 한 장과 원달앱이 읽은 글 200자가 펼쳐진다.
> 사진은 가리지 않은 원본이다. 그래서 사진은 운영센터 허락이 있는 사람만 보고(볼 때마다 운영센터 기록 한 줄), 30일이 지나면 사진 파일이 지워진다(줄은 남는다). 이 둘은 검사가 지킨다.
> 원달앱이 사진을 찍는 일 때문에 콜 잡기 · 픽커 상세 사진 판독이 늦거나 실패하지 않는다.

## 무엇을 · 언제 · 어떻게 찍나

### 언제 찍나

| 조건 | 정함 | 까닭 |
|---|---|---|
| 글 보고와 같은 문턱 | `UnknownScreenReport.record` 가 «운영센터 올림»을 낸 때만 찍는다 — 실물 배차망 앱 · 10자 이상 · 같은 배차망 · 같은 지문 하루 한 번 | 문턱이 하나면 «사진 없는 줄 / 줄 없는 사진»이 안 생긴다. 하루 장수도 지금 줄 수를 넘지 않는다 |
| 넘어가는 찰나 거르기 | 보고 순간이 아니라 **1초 뒤에** 찍는다. 그때 원달앱의 지금 화면 판별(`telemetryManager.currentScreenContext`)이 여전히 «모르는 화면»일 때만 | 픽커 «콜을 누른 직후 넘어가는 틀»은 0.3~0.7초다(기획 35). 1초 뒤 다른 화면으로 판별됐으면 찰나였다 |
| 상세 사진 판독과 부딪히지 않기 | 1초 뒤 찍기 직전, **상세 사진 판독 중(`session.isVerifyingSnapshot`)이면 찍지 않는다** · 찍은 뒤 0.4초 안에 상세 판독이 걸리면 판독이 먼저다(사진 찍기 쪽이 물러선다) | 접근성 사진은 0.33초에 한 번(`ScreenReader.kt:21`). 모르는 화면 사진이 픽커 상세 판독 바로 앞에 찍히면 판독 사진이 «너무 잦음»으로 실패하고 그 콜을 놓친다 |
| 찍지 않을 때 | 글 보고만 보낸다(지금과 같음) | 사진은 곁다리 — 글 보고를 잃지 않는다 |

**«조금 뒤 다시 보기는 안 된다»(HijackService.kt 주석)와 부딪히지 않나** — 그 주석은 *화면 노드(글자)를 다시 읽는 것*이 캐시 때문에 안 된다는 말이다. `takeScreenshot` 은 노드가 아니라 **화면 픽셀**을 찍으므로 1초 뒤의 실제 화면이 찍힌다. 1초 뒤 판별 값은 그사이 온 이벤트로 이미 갱신된 값을 읽기만 한다(다시 읽기 아님). 그래서 1초 뒤 찍기로 정한다.

**운행 중 기사님 손** — 사진은 화면에 아무것도 띄우지 않는다(접근성 사진은 셔터 소리 · 알림이 없다). 기사님 화면 · 손은 그대로다.

**콜 잡기를 늦추나** — 찍기는 원달앱 사진 실행기(`1dal-ocr` 한 줄 스레드)에서 돌고, 보내기는 이상 보고 실행기에서 돈다. 화면 읽기(메인 스레드)는 막지 않는다. 다만 같은 한 줄 스레드라, 사진을 JPEG 로 줄이는 동안(어림 수십 ms) 상세 판독이 그 뒤에 줄 선다 → 위 «부딪히지 않기» 조건으로 상세 판독 중 · 직전에는 아예 찍지 않는다. 한 번에 걸리는 시간은 3단계 시험에서 로그로 잰다.

### 무엇으로 찍나

- 접근성 `takeScreenshot(Display.DEFAULT_DISPLAY)` — 픽커 상세 판독과 같은 길 · 같은 권한(`canTakeScreenshot` 이미 켜짐). 새 권한 · 새 동의 없음.
- 안드로이드 11 미만 폰: 찍지 않고 글만(지금과 같음). 원달앱 `FirstRunCheck` 가 이미 «안드로이드 11 = 픽커 사진 읽기 최소 판»으로 본다.
- 실패(오류 코드 · 비트맵 변환 실패 · 보안 화면이라 검게 나옴): 사진 없이 글만 보내고 로그 한 줄.
- 크기: 전체 화면을 **540폭으로 줄여 JPEG 60 품질**(폰 안 판독 사진과 같은 값 · `ScreenReader.kt:30 · :267`). 자르지 않는다(어느 페이지 위에 뜬 팝업인지 보려면 전체가 필요). 어림 50~120KB/장(540×1170 · 확인 못 함 — 3단계에서 실측).

### 사진을 어떻게 싣나

- **글 보고와 한 번에** 보낸다 — 1초 뒤 찍고, `sendAnomalyReport(..., screenshotBase64 = …)` 한 번. 못 찍으면 그때 글만 보낸다. 그래서 글 보고가 1초 늦게 닿는다(운영센터 기록일 뿐이라 운행에 영향 없음).
- 따로 두 번 보내는 길(글 먼저 → id 받아 사진 따로)은 쓰지 않는다 — `ApiClient` 가 응답 id 를 안 읽고, 새 주소가 하나 더 생긴다.

| 하루 몇 장(어림) | 상한 = 같은 배차망 · 같은 지문 하루 한 번이라 **줄 수와 같다.** 로컬 DB 는 오늘 3줄. 실주행 픽커에서 모르는 화면은 «넘어가는 틀 · 정렬 시트 · 팝업» 몇 가지가 지문을 바꿔 가며 되풀이된다 — 넉넉히 폰 한 대 하루 50장 · 3대(가족판) 150장 × 100KB = **하루 약 15MB · 30일 약 450MB.** 1초 뒤 거르기로 넘어가는 틀이 빠지면 더 준다. (모의 주행 로그 빈도는 실제의 약 15배 — 쓰지 않았다) |
| 지우는 규칙 | 서버가 하루 한 번(이미 도는 하루 단위 일이 있으면 거기에, 없으면 기동 뒤 한 시간마다 확인) 보관 날수가 지난 사진 파일을 지우고 그 줄의 `screenshot_path` 를 비운다. 줄은 안 지운다. 🔴 README «서버가 켜질 때 조건을 보고 표를 지우는 코드를 새로 만들지 않는다»와 — 이것은 표가 아니라 사진 파일이고, 켜질 때 한 번이 아니라 보관 날수 규칙이다. 그래도 «되돌릴 수 없는 일»이라 기사님께 여쭌다 |
| 실서버 준비 | `~/onedal-shots` 폴더를 처음 한 번 기사님이 만든다(APK 폴더와 같음). 폴더가 없으면 서버는 사진만 버리고 글은 저장 · 경고 로그 |

### 새 설정값인가 (README ⑤-4)

- `SHOTS_DIR` 는 서버 환경 값(`RELEASES_DIR` 와 같은 자리) — 기사님 설정창 값이 아니다.
- **보관 날수는 설정값으로 만들지 않고 코드 상수 하나로 둔다(30일 · 정해짐)** — 읽는 곳이 서버 지우기 한 곳뿐이고 화면에서 고칠 일이 없다. 기사님이 «설정창에서 바꾸고 싶다»고 하시면 그때 다섯을 채운다:

| | 설정값으로 만든다면 |
|---|---|
| ① 스키마 | 운영센터 전역 값 표(회원 설정 아님) 한 칸 |
| ② 값 | 30 — 배차망이 화면을 바꾸면 그 주 안에 표에 한 줄 더하므로 한 달이면 넉넉하다 |
| ③ 시점 | 서버가 하루 한 번 지울 때 읽는다 · 운영센터에서 쓴다 |
| ④ 화면 | 운영센터 «점검 › 앱 이상 기록» 머리에 «사진 보관 30일» · 고칠 수 있음 |
| ⑤ 읽는 곳 | 서버 지우기 하나 — «이 사진을 지워도 되나» |

## 🔴 운영센터 화면 — 이상 기록 줄이 어떻게 늘어나나

- 표의 «까닭» 칸 끝에 사진이 있는 줄만 **«📷»** 표시.
- **줄을 누르면 그 줄 아래가 펼쳐진다** — 왼쪽(폰 폭에서는 위) 사진 한 장(폭 맞춤 · 누르면 원래 크기), 오른쪽 글 200자 전부(`detail_parsed_text` — 지금은 운영센터에 아예 안 나간다). 다시 누르면 접힌다.
- 사진은 펼칠 때 `GET /api/ops/anomalies/:id/shot` 로 받아(머리 칸 인증 · blob) 띄운다. 표를 열 때 100장을 한꺼번에 받지 않는다.
- 펼친 아래에 «이 화면을 표에 한 줄 — 배차망 · 페이지 · 그 위에 뜬 것»을 적는 칸은 **이번에 만들지 않는다**(기획 35 «모을 것» 일과 이어지지만 화면이 더 는다 — 따로).
- 공유 모양 `OpsAnomaly` 에 `text`(글 200자) · `hasShot`(사진 있나) 두 칸이 는다(shared `ops.ts:82`).
- 🔴 관제웹 화면은 안 바뀐다 — 관제웹 · 운영센터 · 운행일지 소스 어디도 회원용 `/api/telemetry/anomalies` 를 부르지 않는다(grep 0).

## 단계 — 무엇이 참이면 끝인가

사진을 가리지 않으므로 **«30일 지우기»와 «운영센터만 본다»는 첫 사진이 들어오는 날부터 돌아야 한다** — 지우기를 받기와 같은 1단계에 둔다. 단계마다 파일 · 줄은 아래 «줄별 안».

| 단계 | 무엇 | 운행 · 화면 | 끝 |
|---|---|---|---|
| 1 | 서버가 사진을 받아 레포 밖 폴더에 쓰고 · 30일 지난 사진 파일을 지우고 · 회원 문에는 사진을 안 낸다 | 운행 무변화 · 화면 무변화 | 서버 새 검사 둘(`anomalyShots` · `anomalyShotGuards`) + 고친 검사 둘(`telemetry` · `memberIsolation`) 초록 · 기존 DB 사본으로 부팅 |
| 2 | 운영센터 이상 기록 줄에 📷 · 누르면 사진 + 글 200자 펼침 · 사진은 운영센터 문으로만 · 볼 때 기록 한 줄 | 🔴 운영센터 화면 바뀜(합의됨) · 관제웹 무변화 | 서버 `opsRoutes` 검사에 사진 문 · 기록 줄 · 운영센터 검사 초록 · 내 PC 운영센터에서 시험 사진 한 장이 펼쳐짐 |
| 3 | 원달앱이 1초 뒤 조건을 보고 찍어 글과 한 번에 보낸다 | 운행 무변화(콜 흐름에 손대지 않음) | 원달앱 새 검사(`UnknownScreenShotTest`) 초록 · 폰 시험에서 운영센터에 사진이 뜨고 같은 시간 상세 판독 «스크린샷 실패 code=3» 0 줄 |

## 순위 검산

**찍는 때 — 셋을 나란히**

| | 보고 순간 바로 | 1초 뒤 · 조건 확인 (정함) | 찍지 않고 글을 늘림(200 → 전부) |
|---|---|---|---|
| 페이지 특정 | 됨 — 다만 넘어가는 찰나면 반쯤 그려진 화면 | 됨 — 1초 머문 화면만 | 안 됨 — 글만으로는 «어느 페이지 위의 무엇»을 못 가른다(로컬 세 줄이 그 예) |
| 픽커 상세 판독과 부딪힘 | 🔴 있음 — 넘어가는 틀 바로 뒤가 상세 판독(150ms 뒤)이다 | 없음 — 판독 중 · 직전엔 안 찍는다 | 없음 |
| 사진 장수 | 줄 수와 같음 | 줄 수 이하 | 0 |
→ 1초 뒤가 첫째. «바로»는 좋은 콜을 잃을 수 있어 둘째도 아니고 뺀다.

**저장 자리 — 둘을 나란히**

| | 서버 디스크 레포 밖 폴더 + 이미 있는 칸에 파일 이름 (정함) | DB 안 바이트 |
|---|---|---|
| 새 칸 | 없음 | 없음(같은 칸에 넣는다 해도 칸 이름과 내용이 어긋남) 또는 새 칸 |
| DB 크기 · 백업 | 그대로 | 하루 약 15MB씩 는다 |
| 배포가 지울 위험 | 레포 밖이라 없음(APK 와 같음) | 없음 |
| 지우기 | 파일 지우고 칸 비우기 | 표를 만져야 함 |
→ 디스크 폴더가 첫째.

**올리는 순서 — 둘을 나란히**

| | 서버(1 · 2단계) 먼저 → 원달앱(3단계) (정함) | 원달앱 먼저 |
|---|---|---|
| 옛 서버 + 새 원달앱 | 생기지 않음 | 🔴 사진 실은 본문이 100KB 를 넘으면 옛 서버가 413 으로 거절 → **글 보고까지 잃는다** |
| 새 서버 + 옛 원달앱 | 사진 칸이 비어 올 뿐 — 지금과 같음 | — |
→ 서버 먼저.

**단계 순서** — 3을 1보다 먼저 하면 위 413 문제. 2를 1보다 먼저 하면 보여 줄 사진이 없어 운영센터 펼침을 시험 못 한다. 지우기를 받기보다 늦게 두면 가리지 않은 사진이 기한 없이 쌓이는 날이 생긴다 — 그래서 1단계에 같이 둔다.

### 올리는 순서

1. 실서버 `~/onedal-shots` 폴더 — 기사님 손 한 번(`mkdir -p ~/onedal-shots`). 없어도 서버는 글만 저장하고 경고 한 줄.
2. 1단계 + 2단계(서버 · shared · 운영센터)를 한 번에 `main` 으로 → 실서버 자동 배포. 🔴 push 는 기사님이 말씀하실 때만 · 직전 «지금 운행 중이신가».
3. 실서버에서 `/api/telemetry/anomalies` 가 1MB 본문을 받는지 · 기동 로그에 사진 지우기 주기가 떴는지 확인(읽기는 기사님 허락 범위 안에서).

## 확인 못 한 것

- **실서버 SCREEN_UNKNOWN 줄 수 · 배차망별 · 글 길이** — 실서버 DB 읽기를 자동 권한 확인이 막았다. 기사님이 운영센터에서 «많이» 보신 줄의 수는 아직 모른다 → 1단계 올리기 전에 다시 센다(하루 장수 어림을 고친다).
- **실서버 디스크 여유** — 같은 까닭으로 `df` 를 못 봤다. 30일 약 450MB(넉넉한 어림)가 들어가는지 올리기 전에 본다.
- **사진 한 장 크기** — 540폭 전체 화면 JPEG 60 의 실제 크기(어림 50~120KB)는 3단계 폰 시험에서 잰다. 폰 안 `files/snapshots/` 는 잘린 판독 사진이라 그대로 못 쓴다.
- `ops/src/api/ops.ts` 의 요청 함수 모양 — 이번에 못 읽어 2단계 `anomalyShot` 의 줄 번호는 그 단계에서 정한다(인증은 `Authorization` 머리 칸이라는 것만 확인).
- 카카오 픽커가 어떤 화면에 보안 표시(사진 막기)를 거는지 — 상세 판독이 되므로 상세는 아니다. 다른 화면은 3단계 시험에서 «검게 나옴» 로그로 본다.
