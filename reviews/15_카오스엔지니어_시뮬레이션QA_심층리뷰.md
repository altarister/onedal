# [전문가 리뷰 ⑤] 카오스 & 모빌리티 시뮬레이션 QA 엔지니어의 품질 검증 심층 진단

**작성 일시**: 2026-09-17  
**전문가 관점**: 모빌리티 자율주행·내비게이션 시뮬레이션 QA 및 카오스 엔지니어링 전문가 (Simulation / Chaos Test Specialist)  
**핵심 목표**: 목숨을 건 도로 위 실측 테스트 탈피, 10,000회 가상 극한 주행 시뮬레이션 자동화, 회귀 버그 0% 무결점 배포

---

## 📌 총평 및 QA 방법론 진단

현재 1DAL의 버그 대장(#1~#160)을 보면, **기사님이 실제 트럭을 몰고 고속도로를 달리며 겪은 사고와 오류들을 사후에 고치는 '피와 땀의 수동 실측 방식'**에 의존하고 있습니다.

하지만 이 방식은 **극도로 위험하고 비효율적**입니다. 
- 기사가 시속 100km로 달리는데 새 배포 버전에서 경유지 순서 버그가 터져 엉뚱한 나들목으로 빠지거나, 
- 30초 안전취소 타이머가 멈춰 패널티를 먹는 사고는 기사의 생명과 직결됩니다.

자율주행차나 항공기 소프트웨어처럼, **실제 도로에 나가기 전에 컴퓨터 가상 환경에서 10,000번의 극한 상황(카오스)을 주입해 100% 검증을 끝내는 '가상 모빌리티 시뮬레이션 QA 파이프라인'** 구축 방안을 제시합니다.

---

## 1. 수동 도로 실측의 한계 & 카오스 엔지니어링(Chaos Engineering)

### ⚠️ 현재 검증 방식의 치명적 맹점
1. **재현 불가능성(Non-Reproducibility)**:
   - 도로 위의 교통 상황, GPS 오차, 신호등, 날씨는 매 순간 바뀝니다. "지난주 목요일 판교 IC에서 겪었던 그 버그"를 동일한 조건으로 다시 재현하여 디버깅하는 것이 불가능합니다.
2. **극단적 엣지 케이스(Edge Case) 검증 불가**:
   - 터널 속 통신 단절 10초, 지하 3층 주차장 진입, 배차망 콜 1초에 200건 폭풍 유입, 스마트폰 배터리 5% 쓰로틀링 등 극한의 상황을 실제 주행 중에 인위적으로 만들어 테스트할 수 없습니다.

### 💡 카오스 주입(Fault Injection) 가상 환경 구축
- **가상 도로 주행 시뮬레이터 (`Virtual Mobility Simulator`)**:
  - 실제 고속도로 궤적(GPX 데이터)을 초당 10배속으로 서버에 주입하며 가상 차량을 주행시킵니다.
- **인위적 결함 주입 (Chaos Injection)**:
  - 주행 시뮬레이션 중 임의의 시점에 **'소켓 강제 단절(Network Drop)'**, **'카카오 API 3초 지연(Latency Injection)'**, **'GPS 좌표 500m 순간 점프(GPS Jitter)'**를 강제로 터뜨려도 시스템이 죽지 않고 정상 복원되는지 자동 검증.

## 2. CI/CD 가상 배차망 대량 스트레스 테스트 파이프라인

### 💡 자동화 테스트 파이프라인 아키텍처
코드 변경 사항이 GitHub에 푸시될 때마다 GitHub Actions에서 자동으로 돌아가는 3단계 품질 게이트웨이:

```
[코드 커밋] 
   ↓
[1단계: 단위 테스트] Jest & Vitest 로직 검증 (1초)
   ↓
[2단계: 가상 배차망 카오스 시뮬레이션 (Virtual Fleet Simulation)]
   - 10대의 가상 트럭이 서울-부산, 수도권 순환로를 시속 300km 모의 주행
   - 10,000건의 가상 화물 콜을 무작위 난사
   - 경유지 역주행(U-Turn), 30초 취소 타임아웃, LIFO 적재 위반 여부 수학적 검증
   ↓
[3단계: 품질 합격 판정] 단 1건의 미처리 예외(Crash)나 헛걸음 경로가 없을 때만 실서버 배포 승인!
```

## 3. 골든 시나리오(Golden Scenarios) 회귀 테스트 자산화

### ⚠️ 과거 버그의 망령 방어
- 버그 대장에 기록된 뼈아픈 과거 실측 사고들을 영구적인 **'골든 테스트 시나리오'**로 코드화해야 합니다:
  1. **#32, #36, #60 시나리오**: 4개 콜 다중 합짐 시 이미 상차한 정거장이 경유지에 다시 나타나지 않는가?
  2. **#90, 0903 시나리오**: 굽은 길(신둔-사음동) 통과 시 1번과 2번 경유지가 1초 간격으로 뒤집히지 않는가?
  3. **#144 시나리오**: 기사가 3단 시트를 손으로 만지는 중에도 새 판정이 뜨면 최우선으로 떠오르는가?
  4. **#159 시나리오**: 전진 방향 동(신둔면)이 상차 반경에 걸려 하차지 목록에서 지워지지 않는가?

- **효과**: 개발자가 코드를 한 줄 고쳤을 때, 과거 160개의 버그 중 단 하나라도 재발(Regression)하면 배포 파이프라인이 즉각 빨간불을 띄우며 배포를 차단합니다.

## 4. 모바일 폰 팜(Device Farm) 실기기 호환성 테스트

### ⚠️ 안드로이드 파편화(Fragmentation) 극복
- 기사들이 쓰는 스마트폰은 제각각입니다:
  - 갤럭시 S21, S22, S23, S24, 갤럭시 폴드, 저가형 갤럭시 A 시리즈 등.
- 화면 해상도, 안드로이드 OS 버전(Android 12~15), One UI 버전에 따라 3단 시트의 높이, 버튼 폰트 크기, 접근성 서비스 바인딩 속도가 완전히 달라집니다.
- **해결책**: AWS Device Farm 또는 사내 모바일 기기 테스트 랙을 구축하여, 주요 갤럭시 단말기 5종에서 UI 깨짐과 터치 씹힘이 없는지 자동 스크린샷 비교(Visual Regression Testing) 검증.

## 5. 시뮬레이션 환경 격리(Simulation Isolation) 및 런타임 은폐 결함 방어

### ⚠️ 카오스 테스트 관점의 2대 치명적 맹점
1. **단위 테스트 그린(Green) 뒤에 숨겨진 런타임 크래시**:
   - 프론트엔드 단위 테스트가 컴포넌트 트리를 완전히 마운트하지 않고 정규식 검사나 단편적 Mock에 의존할 경우, 700개가 넘는 테스트가 전부 성공하더라도 실제 브라우저 마운트 시 `ReferenceError`가 터져 관제탑 화면이 즉각 올스톱(화이트스크린)됩니다.
   - **카오스 방어**: 모든 핵심 컴포넌트에 대해 가상 DOM 트리 렌더링 스모크 테스트를 필수 게이트로 지정하고, 최상단 `ErrorBoundary`가 에러를 흡수해 주행 중 화면 전체가 먹통이 되는 사태를 차단해야 합니다.
2. **가상 시뮬레이션과 실제 운영 상태의 격리 파괴 (State Contamination)**:
   - 개발 및 체험 모드(`SIMULATION`)에서 발생한 가상 콜의 취소 이벤트가 도메인 코어의 SSOT(`cancelCount.ts`)를 거치지 않고 누수되어, 실제 기사의 취소 페널티(10회)를 소진시키거나 SQLite DB에 유령 데이터를 남기는 상태 오염 발생.
   - 세션 계층 분리(`UserSession` vs `DeviceSession`) 경계를 오인하여 런타임 `TypeError`가 발생할 때, 전체 배차 루프가 중단되지 않도록 안전 폴백 메커니즘 구축 필수.
