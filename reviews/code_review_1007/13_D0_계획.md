## 🔴 기사님께 여쭐 것 — 셋 (배포 방식 · 늦어짐 · 운행 중 막기)

**A. 배포 스크립트를 레포 파일로 옮기고 «실패하면 되돌리기»를 넣나 (P8-01 · P8-08)**
지금: 배포는 ① 코드를 먼저 새것으로 갈아 끼우고(`git reset --hard origin/main`) ② 관제웹을 빌드하고 ③ 서버를 다시 띄우고 ④ 30초 안에 서버가 답하는지 본다. 구멍 둘:
- 관제웹 빌드가 도중에 죽으면(2026-09-01 메모리 부족이 그 꼴) 빌드 도구가 시작할 때 비운 화면 폴더가 빈 채로 남는다 → **실서버 관제웹이 바로 하얀 화면**. 디스크 코드는 이미 새것이라, 서버가 다시 뜨는 순간 검사 안 된 새 서버가 뜬다.
- ④ 에서 새 서버가 안 뜨면 «실패»로 끝나고 되돌리기가 없다 → 옛 서버는 이미 내려갔고 새 서버는 계속 죽는다 → **실서버가 꺼진 채**.
- 가: 배포 순서를 `onedal-web/scripts/deploy.sh` 한 파일로 옮기고(배포 파일은 그것을 부르기만), 시작할 때 지금 판 번호를 적어 두고 어디서 실패하든 그 판으로 되돌려 서버를 다시 띄운다. 관제웹 · 운영센터는 새 폴더에 빌드한 뒤 성공하면 바꿔 끼운다(빈 화면 폴더가 생기지 않음). DB 는 자동으로 되돌리지 않는다(되돌리면 그 사이 운행 기록이 사라짐 — 백업은 지금처럼 남고 복원은 사람 손).
- 나: 지금 배포 파일 안에서 고친다 — 같은 동작이지만 로컬에서 그 순서를 그대로 돌려 볼 수 없다.
- 추천: 가 — 같은 스크립트를 로컬 검사에서 돌려 «빌드가 깨지면 화면 폴더 그대로 · 서버가 안 뜨면 옛 판으로 되돌아감»을 실제로 보일 수 있다.

**B. push 뒤 GitHub 에서 검사를 먼저 돌리고, 통과해야 배포하나 (P8-03 · P8-02)** — 배포가 몇 분 늦어진다.
지금: push 와 배포 사이에 검사가 없다. 실서버는 서버 코드를 타입 검사 없이 바로 돌린다. 게이트를 건너뛴 push 는 그대로 실서버에 간다.
- 가: GitHub 실행기에서 서버 tsc · jest · 관제웹 tsc -b · `pnpm test:web` 을 돌리고, 배포는 그 뒤에만. 배포가 몇 분 늦어진다(jest 가 가장 길다 — 처음 돌려 보고 실제 시간을 알린다). 배포 파일만 고친 push 도 돌게 감시 경로에 배포 파일 한 줄을 더한다.
- 나: 지금처럼 검사는 사람 손.
- 추천: 가 — 여러 세션이 같은 main 에 올린다. 한 세션이 게이트를 건너뛰어도 실서버에 안 간다.

**C. 운행 중이면 배포를 멈추나 (P8-09)**
지금: 배포는 늘 서버를 다시 띄운다(«무중단 갱신»이라는 주석과 달리 한 대짜리라 몇 초 끊긴다). 다시 뜨면 메모리에 있던 결재 대기 · «심사 중» · 기다림이 사라진다. 막는 것은 «올리기 직전 기사님께 운행 중인지 여쭘» 하나뿐이다.
- 가: 배포 맨 앞에서 서버에 «지금 운행 중인가»(진행 중 콜 · 심사 중 콜 · 결재 기다림 · 걸린 기다림 수)를 묻고, 하나라도 있으면 **코드를 갈아 끼우기 전에** 배포를 멈춘다(GitHub 빨간불 · «운행 중이라 멈춤» 한 줄). 운행이 끝난 뒤 GitHub 에서 «다시 실행»을 누르거나 다음 push 때 간다. 이 질문은 서버 안(localhost)에서만 답한다 — 밖에서 운행 여부가 보이지 않게.
- 나: 지금처럼 사람 손.
- 추천: 가 — 운행 중 배포는 결재 대기 콜을 잃는 길이다. 사람이 잊어도 막힌다.
- 🔴 **멈춘 배포는 어디로 가나** (onedal-71): «멈추고 끝»이면 그 커밋을 다시 올리는 손이 없다 — 기사님은 push 했으니 올라간 줄 아시고 실서버는 옛 판인 채 남는다(main 과 실서버가 말없이 갈라짐 · 폰 위치 · 머리줄 차종과 같은 «있는 것처럼 보이는 연결»).
  - C-가: 운행 중이면 **기다린다** — 배포가 1분마다 «운행 중인가»를 다시 묻고 풀리면 그때 올린다. 상한 4시간을 넘기면 빨간불(«4시간 운행이 안 끝나 멈춤»). GitHub 작업 시간 상한(`timeout-minutes` · ssh 명령 상한 `command_timeout`)도 그에 맞춘다. 기다리는 동안 새 push 가 오면 앞의 기다림은 거두고 새 것이 기다린다(`concurrency` · 진행 중 취소) — 두 배포가 겹쳐 돌지 않게. 기다리는 동안 GitHub 실행 시간이 든다.
  - C-나: 멈추고 끝 + 갈라짐을 화면에 보인다(관제웹이나 운영센터에 «실서버 판 ≠ 최신 커밋») — 화면이 는다.
  - 추천: C-가(onedal-71 · 저 같음) — «운행이 끝나면 올라간다»가 기사님 기대와 같고 화면이 늘지 않는다.
- 함께 정할 것: 운행 중이어도 꼭 올려야 할 때(서버가 이미 죽어 있는 등) — 가-1: GitHub 수동 실행에 «운행 중이어도 올림» 체크 하나 / 가-2: 없음(운행이 끝나기를 기다림). 추천 가-1 — 서버가 죽어 있으면 «운행 중» 답도 안 오므로 그때는 저절로 간다. 체크는 서버가 살아 있는데 급할 때만.

## 단계 — 각 줄 «무엇이 참이면 끝인가» · 검증(동작으로)

🔴 원칙(기사님 «글자 가»): 배포 파일 글자를 세는 검사는 만들지 않는다. 확인은 **실제로 막히는 것을 보이는** 동작 시험으로 한다. 실서버는 만지지 않는다 — 첫 실전은 A·B·C 답을 받은 뒤의 첫 배포다.

1. **배포 순서를 `onedal-web/scripts/deploy.sh` 로 (A 가)** — 지금 `deploy.yml` 의 [0]~[5] 를 옮기고 셋을 더한다: ① 시작에 `PREV=$(git rev-parse HEAD)` · ② `trap` 하나로 어디서 실패하든 `git reset --hard $PREV && pnpm install` → 서버를 다시 띄움(옛 판) → 그 뒤 health 를 다시 봐 «되돌림 성공 / 되돌림도 실패»를 적고 exit 1 · ③ 관제웹 · 운영센터는 `--outDir dist.new` 로 빌드 → 성공하면 `dist` 와 바꿔 끼움. [4] 주석 «무중단 갱신» → «다시 띄움 — 한 대라 몇 초 끊긴다»(D10 몫이 넘어온 것). `deploy.yml` 의 ssh 단계는 `git fetch` 뒤 새 판의 `deploy.sh` 를 부르기만.
   - 끝 · 검증(동작): 서버 검사 하나가 **임시 git 저장소 · 가짜 `pm2` · `pnpm` · `curl`**(PATH 앞에 둔 작은 대본들)로 `deploy.sh` 를 실제로 돌린다 — ⓐ 관제웹 빌드가 실패하는 판 → 끝난 뒤 HEAD 가 PREV · `dist` 안의 옛 파일 그대로 · exit≠0 ⓑ 새 서버가 health 에 답하지 않는 판 → HEAD 가 PREV · 가짜 pm2 가 옛 판으로 다시 띄워짐 · exit≠0 ⓒ 멀쩡한 판 → HEAD 가 새 판 · `dist` 바뀜 · exit 0. 각 경우를 망가뜨리는 변이(trap 을 뺌 · dist.new 대신 dist 에 바로 빌드)로 🔴.
   - 못 잡는 것: 실제 EC2 의 메모리 · pm2 · 네트워크 — 첫 배포 로그로 본다.
2. **«지금 운행 중인가» 문 (C 가)** — 서버에 `GET /api/health/busy`(localhost 에서 온 요청만 답함 · 밖에서는 404). 답: 진행 중 콜 · 심사 중 콜 · 결재 기다림 · 걸린 기다림(`state/waits`) 수와 `busy: true/false`. 🟡 `routes/health.ts` · 서버 부팅 자리를 만지므로 **onedal-24 의 D13(서버 파일 나누기)과 겹치는지 먼저 묻는다**.
   - 끝 · 검증(동작): jest — 진행 중 콜이 있는 세션을 만들면 busy · 없으면 아님 · 밖에서 온 요청(원격 주소)이면 404. 세는 칸 하나를 빼는 변이로 🔴.
3. **배포 맨 앞에서 운행 중이면 기다림 (C 가 · C-가)** — `deploy.sh` 의 [0] 앞에서 `curl -s localhost:4000/api/health/busy`. `busy: true` 면 «운행 중이라 기다림 — 진행 중 N · 심사 중 N …» 찍고 1분 뒤 다시 묻는다(코드는 안 갈아 끼움). 4시간이 넘으면 exit 1. `deploy.yml` 에 `concurrency: { group: deploy, cancel-in-progress: true }` · `timeout-minutes` · `command_timeout`. 서버가 답하지 않으면(죽어 있음) 그대로 배포. 가-1 이면 GitHub 수동 실행 입력 `force` 가 참일 때만 건너뜀.
   - 끝 · 검증(동작): 1단계 검사에 ⓓ — 가짜 curl 이 처음 두 번 `busy: true` 뒤 `false` 를 주면: busy 동안 HEAD 그대로 · pm2 안 불림 → 풀린 뒤 새 판으로 감(기다리는 간격은 검사에서 짧게 줌). 상한을 넘기도록 계속 busy 면 HEAD 그대로 · exit≠0. ⓔ 가짜 curl 이 답하지 않으면 배포가 간다.
4. **GitHub 검사 작업 (B 가)** — `deploy.yml` 에 `check` 작업(ubuntu · pnpm install · 서버 `tsc --noEmit` · `npx jest` · 관제웹 `tsc -b` · `pnpm test:web`)을 두고 `deploy` 작업은 `needs: check`. 감시 경로에 `.github/workflows/deploy.yml` 한 줄.
   - 끝 · 검증(동작): 실제로 보이는 길은 GitHub 뿐이다 — 기사님이 push 를 허락하신 첫 배포에서 ① `check` 가 돌고 ② 통과 뒤에만 `deploy` 가 도는 것을 GitHub 화면 · `gh run view` 로 본다. 로컬에서는 같은 명령 넷을 차례로 돌려 초록인지만 본다(그 자체가 게이트와 같다). «일부러 실패하는 검사 → 배포 안 감»은 push 가 필요해 기사님 허락 없이는 보이지 않는다 — 허락하시면 별도 가지에서 한 번(main 아님 · 배포 안 됨)으로 `needs` 가 막는 것만 본다.
   - 못 잡는 것: GitHub 실행기의 better-sqlite3 빌드 실패 같은 실행기 사정 — 첫 실행에서 드러난다.

순서: 2(onedal-24 와 겹침 확인 뒤) → 1 → 3 → 4. 1~3 은 한 커밋씩 · 4 는 배포 파일이라 push 전에는 실서버에 아무 일도 없다. **push 는 기사님이 먼저 말씀하실 때만 · 올리기 직전 «지금 운행 중이신가» — C 가 들어가도 첫 배포만은 사람이 확인한다.**

③ DB 값 대조: 없음 — 표 · 칸을 바꾸지 않는다(배포 백업 동작 그대로).
④ 순위 검산: 해당 없음.

## 남은 것

- 🟡 «운행 중»을 모든 사용자 중 하나라도로 센다 — 운영센터로 기사가 여럿 붙는 날(여러 기사 목표)에는 배포할 틈이 없어진다. 그때 «배포 창»(정한 시각) 같은 다른 길을 정한다 — 지금 고칠 일 아님(onedal-71).

- DB 자동 복원은 하지 않는다 — 되돌림은 코드만. 새 판이 스키마를 바꿨다가 되돌아간 경우는 옛 코드가 새 칸을 모른 채 도는데, `ensureColumns` 는 칸을 더하기만 하므로 옛 코드는 그대로 돈다(칸을 지우는 판이면 다르다 — 그런 판은 지금 규칙상 없다).
- 리허설 배차망(onedal-sim) 빌드는 지금처럼 실패해도 계속(관제 서버와 무관).
