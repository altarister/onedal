# 1DAL 코드 레벨 정밀 리뷰 실행 계획 (10-07)

기사님 말씀: «우리 프로젝트에 전체적인 코드 리뷰를 진행할 거야 — 각 파트마다 리뷰할 수 있도록 계획을 짜 봐».

## 0. 이 리뷰가 지난번(reviews/code_review · 09-17)과 다른 점

- 지난 계획서는 파일 경로가 지금 코드와 다르다(`AccessibilityService.kt` · `parser/` · `filter/` · `timer/` 는 지금 없음). 이번은 **10-07 의 실제 파일을 세어** 파트를 나눴다(아래 1).
- 지난 리뷰 뒤 생긴 큰 덩어리가 셋이다. 리뷰를 거치지 않은 코드라 먼저 본다.
  - **블루투스 공급 고리**(reviews/49 · 50): 관제앱 `SupplyService.java` · 원달앱 `BleLink.kt` · 서버 `/supply` · `phoneSupply` · `decisions` · `phoneStatus`
  - **운영센터**(`ops/`) · 서버 `routes/ops.ts`
  - **배차망 화면 정의 표**(shared `networkPages.ts` → 생성 파일)
- 이번은 **관점 여덟(코드 품질 · 상태 관리 · 성능 · 렌더링 최적화 · 주석 · 검사 품질 · 보안 · 버그 꼴)** 을 모든 파트에 걸고(아래 2), 관점마다 지금 숫자를 세어 출발점으로 둔다. 버그 꼴은 일반론 대신 **이 레포에서 실제로 난 병**에서 뽑는다(아래 2-1).

## 2. 관점 여덟 — 무엇을 보나 (기사님 «코드 품질 · 상태 관리 · 성능 · 렌더링 최적화 · 주석까지 전반적으로»)

계획은 두 축이다. **파트(어디를 · 아래 3)** × **관점(무엇을 · 이 장)**. 한 파트를 읽을 때 그 파트에 걸린 관점을 모두 한 번에 본다. 찾은 것마다 관점 이름(Q1~Q8)을 붙여, 끝의 종합 표를 파트로도 관점으로도 묶을 수 있게 한다.

### Q1 코드 품질 · 오류 · 로그 — 읽고 고치기 쉬운가 · 실패가 보이는가
- 본다(품질): 한 파일 · 한 함수가 너무 큰가(함수 100줄 · 파일 800줄을 넘으면 «왜 한 덩어리인가»를 적는다) · 같은 일을 하는 코드가 두 벌인가(«공통 최대» — shared 로 갈 것) · 죽은 코드 · 쓰지 않는 칸 · 타입 구멍(`any` · `as any` · `!`) · 오류를 삼키는 `catch {}` · 이름이 하는 일과 맞나 · 한 파일이 여러 일을 하나(결합도)
- 본다(오류 · 로그): 실패가 기사님 화면 · 소리에 닿는가(조용히 삼키지 않나) · 로그 한 줄로 콜 하나를 따라갈 수 있는가(`pnpm log call`) · 하루 로그 양 · 1초마다 찍히는 줄(F 와 겹침) · 로그 줄 안의 말이 용어집 말인가
- 지금(10-07 셈): 800줄 넘는 파일 — 서버 9 · 관제웹 8(목업 넷 포함) · shared 4 · 원달앱 2(`HijackService.kt` 2,289 · `KakaoPickerParser.kt` 1,270) · 시뮬 1 · `any` — 서버 376 · 관제웹 45 · shared 22 · 운영센터 0 · 빈 catch — 서버 `catch {}` 2 · 원달앱 `catch (_: Exception) {}` 11
- 재는 도구: `pnpm audit:dead` · `lint:gate` · 파일 · 함수 길이 셈 · `any` · 빈 catch grep · 서버 로그(`pnpm log` 요약 · 태그별 줄 수)
- 끝: 그 파트의 800줄 넘는 파일마다 «나눌 자리 / 한 덩어리가 맞는 까닭» 한 줄 · `any` 는 «받는 경계(외부 JSON)라 맞음 / 타입으로 바꿀 것»으로 가름

### P0 검사 품질 — 맨 먼저 (기사님 «잘 만든 검사가 있어야 하는데 지금은 너무 그냥 만든 것 같아 술술 뚫리는 것 같다»)
- 까닭: 뒤 파트들의 찾은 것을 «검사가 이미 무나»로 가르는데, 그 검사를 믿을 수 없으면 모든 파트의 판단이 흔들린다. 고칠 때도 «고쳤다 = 초록»이 참이려면 검사가 먼저 서야 한다.
- 지금은 이렇게 돈다(10-07 · 셈):

| 자리 | 검사 파일 | 소스 글자를 읽는 검사 | 비율 |
|---|---|---|---|
| 서버 jest(`server/tests`) | 352 | 233(`rules/` 301 중 217) | 66% |
| 원달앱 단위(`onedal-app/app/src/test`) | 151 | 62 | 41% |
| shared · 관제웹 vitest | 112 | 14 | 13% |

  «소스 글자 검사»는 함수를 돌리지 않고 «이 파일에 이 글자가 있나 · 이 줄이 저 줄보다 앞인가»를 본다. 글자만 남기고 동작을 망가뜨리면(조건 뒤집기 · 인자 바꾸기 · 다른 자리로 옮기기) 초록이다.
- 재는 법 셋:
  1. **핵심 규칙 표**: 운행을 지키는 규칙 스무 개 안팎을 README 「이건 버그가 아니라 규칙이다」 · 각 CLAUDE.md · 오늘까지의 결정에서 뽑는다(예: 잡은 콜을 서버가 안 버림 · 안전취소 타이머는 앱이 스스로 · 목적지 없는 필터는 잡기 보류 · 만석이면 잡기 보류 · 자동은 한 폰만 · 관제웹 없음 → 알람 · 결재는 decide 한 곳 · 같은 결재는 한 번만 실행 · 내일 콜은 확정 안 함 · 체험은 확정 막음 · 증명 전 쓰기는 버림 · 옛 원달앱 거절 · 취소 셈 한 곳 · 빈 목록은 싣지 않음). 규칙마다 «지키는 검사 이름 · 종류(동작 / 글자)»를 적는다.
  2. **변이 표본**: 규칙마다 «글자는 그대로 두고 동작만 망가뜨리는» 변이 **하나**(조건 뒤집기 · 비교 바꾸기 · 반환값 고정 · 호출 한 줄 빼기)로 시작한다. «잡힘»이면 다음 규칙으로, «뚫림»일 때만 둘째 변이를 넣어 뚫림이 한 자리인지 본다. 돌리는 검사는 그 규칙의 검사 파일만이다(서버 `npx jest <파일>` · 원달앱 `--tests <클래스>` · vitest `<파일>`) — 전체를 돌리지 않는다. 변이는 돌린 즉시 되돌리고, 끝에 `git diff` 가 비어 있는지 본다. **같은 작업 트리에서 변이 측정과 다른 검사를 동시에 돌리지 않는다** — 변이가 남은 순간을 다른 검사가 읽어 거짓 찾은 것이 생긴다(P0 R14 측정 섞임 · e48ae3be). 동시에 해야 하면 git worktree 를 따로 쓴다.
  3. **글자 검사 가르기**: 소스 글자 검사를 둘로 가른다. «구조 규칙»(예: `decide` 밖에 결재 쓰기 0 · 생성 파일 머리 · 손 글자 0)은 글자로 보는 것이 맞다. «동작 대신 글자»(예: «이 함수가 이 문자열을 부른다»로 동작을 갈음)는 동작 검사로 바꿀 후보다. 표본은 핵심 규칙을 지키는 글자 검사 전부 + 나머지에서 30개(서버 20 · 원달앱 10 · 이름 순 고르게)다.

## 4. 진행 방식

1. **한 파트씩.** 파트를 시작할 때 그 파트 파일을 «읽을 목록»으로 먼저 세고(파일 · 줄), 다 읽으면 «읽음»으로 지운다. 안 읽은 파일이 남으면 그 파트는 끝이 아니다.
2. **찾은 것마다 관점(Q1~Q8)과 버그 꼴(A~O, 있으면)을 붙인다.** 같은 찾은 것이 둘에 걸리면 둘 다 적는다.
2-1. **찾은 것은 고침과 떼어 둔다.** 리뷰 중에는 코드를 고치지 않는다. 찾은 것은 산출물 표에 «코드로 본 것(파일:줄 · 재현 길)» 과 «판단(왜 문제인가 · 임기응변인가 구조인가)»으로 나눠 적는다.
3. **찾은 것마다 확인 한 번.** 「이 길이 실제로 도나」를 호출 자리 grep · 검사 · 로그 중 하나로 확인한다. 확인 못 한 것은 «추정»으로 따로 둔다. 그리고 «검사가 이미 무나(검사 이름) / 안 무나»를 한 칸 적는다 — 안 무는 찾은 것이 고칠 때 검사를 함께 만들 자리다.
4. **무게는 기사님 하루로.** 찾은 것마다 «좋은 콜 · 노이즈 · 기사님 손» 중 무엇에 닿는지와 «실주행에서도 나나 · 시험 도구에서만 나나»를 적는다. 운행 동작 · 새 설정값 · 관제웹 화면이 바뀌는 고침은 «🔴 기사님 결정»으로 표시한다.
5. **파트가 끝나면 그 파트 산출물을 다른 세션에 리뷰 받는다**(읽기만 · «코드로 본 것 / 판단만»).
6. **P0 만 바로 고쳤다**(검사 더하기라 운행 동작이 안 바뀜 · 결과 `00_P0_검사품질_결과.md`). **P1~P8 은 리뷰와 «고침 계획»까지만 쓰고 코드는 안 고친다**(기사님 «P1~P8 까지 파트 고침 계획을 모두 세우자 — 모아서 덩어리별로 한 번 더 분류하자»).
   - 파트 산출물 하나에 두 장: «찾은 것» 표 + «고침 계획»(찾은 것마다 어느 파일 어느 자리를 무엇으로 · 새 검사 · 🔴 기사님 결정 여부 · 운행 영향)
   - 파트 산출물 이름: `0N_PN_<이름>_결과.md`(찾은 것 · 고침 계획 함께)
7. **P1~P8 이 다 끝나면 `09_덩어리.md`** — 여덟 파트의 고침 계획을 모아 **파트를 가로질러 덩어리로 다시 묶는다.** 묶는 기준은 «한 번에 고쳐야 같이 맞는 것»이다.
   - 예: 같은 원천 칸을 여러 파트가 건드림(내일 상차 목록 — P1 원달앱 · P3 서버 필터) · 같은 꼴의 병(1초 주기 비용 — P2 · P3 · P4) · 같은 검사 다시 만들기(글자 검사 → 동작) · 같은 기사님 결정에 걸림(관제웹 화면 바뀜끼리)
   - 덩어리마다 «들어 있는 찾은 것 · 고칠 파일 · 운행 영향(좋은 콜 · 노이즈 · 손) · 🔴 기사님 결정 · 순서(먼저 해야 다른 덩어리가 서는 것) · 크기» 한 줄씩
   - `09_덩어리.md` 도 다른 세션 리뷰를 받는다.
8. **기사님이 덩어리를 고르신다.** 고르신 덩어리만 그 덩어리 계획서(줄별)를 써서 승인을 받고, 하나씩 고친다 — 덩어리마다 다른 세션 리뷰 → 게이트 → `pnpm drive e2e` → 결과 문서.
