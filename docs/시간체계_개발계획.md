## 0. 조사 결과 — 지금 코드의 실태

계획을 세우기 전에 코드를 읽었다. **네 가지가 나왔고, 그중 둘은 계획을 바꿀 만한 것이다.**

### 🔴 발견 ① `arrivalMarginMin` 은 DB에 없다. 코드 상수로 산다

`JudgmentConfig.unknown.arrivalMarginMin` 은 인터페이스에 있고 기본값 30 이다.
그런데 **`JUDGMENT_FIELDS` 표에 없다.**

```
표에 있는 것   merge 4개 · unknown 4개(pickupDwell·dropoffDwell·pickupOffset·restMargin)
              · weights 4개 · color 2개                        = 14개
표에 없는 것   unknown.arrivalMarginMin                        ← 이것 하나
```

그 표가 **DB 컬럼도 관제웹 폼도 기본값도 전부 만든다.** 표에 없으니
컬럼이 안 생기고, 폼에도 안 뜨고, 값은 언제나 `DEFAULT_JUDGMENT` 의 **30 고정**이다.

`OrderEvaluator.ts:182` 와 `dispatchEngine.ts:279` 가 `session.judgment.unknown.arrivalMarginMin`
을 넘기고는 있지만, 그 값은 항상 30 이다. **기사님이 고칠 방법이 없다.**

> 이것이 규칙 ⑤-4 가 경고한 *"일단 만들고 나중에 노출한다"* 의 실물이다.
> 다행히 **고치기는 쉽다 — 표에 한 줄 더하면 컬럼·폼·기본값이 따라온다.**

### 🔴 발견 ② 관제웹은 판정 기준을 받아 놓고 **시간 계산에 안 쓴다**

`client-app/src/stores/judgmentStore.ts` 가 소켓으로 `judgment-init`·`judgment-updated`
를 받아 들고 있다. 그런데 시간 파생 호출에는 **안 넘긴다.**

```ts
// DepartureCountdown.tsx:71 · PinnedRoute.tsx:150
deriveRouteTimeline(routeStops, orders, reportsOf, milestonesOf, now, routeComputedAt)
//                                                                    ↑ rules 인자가 없다 → DEFAULT_DEADLINE_RULES
```

**지금은 우연히 문제가 안 난다** — 서버도 관제웹도 30 을 쓰니까(발견 ①).
🔴 **그런데 ①을 고쳐 DB 값이 40 이 되는 순간, 서버는 40 관제웹은 30 으로 갈라진다.**
같은 콜에 서버와 화면이 다른 시각을 말하게 된다.

> → **①과 ②는 반드시 같은 단계에서 함께 고친다.** ①만 하면 사고가 난다.

### 발견 ③ 단독 경로는 **이미 저장되고 있다**

기획 §4-2 의 *"첫짐 때 저장한 값이 있으니 비교하면 얻을 수 있다"* 는 맞다.

```
orders.kakaoSoloDurationMin   이 콜 혼자 갈 때의 배송 주행   (routeComposer.ts:84)
orders.totalDurationMin       지금 경로 전체 (접근 포함)      (routeComposer.ts:78·95)
```

**새 컬럼이 필요 없다.** 기획 ①스키마의 *"단독 경로를 어디에 저장할지"* 는 이미 답이 있다.

### 발견 ④ `unknown_slack_minutes` 는 고아 컬럼

DB 에는 있는데(값 90) `JUDGMENT_FIELDS` 에 없어 **아무도 안 읽는다.**
옛 `마감 미확인 여유 = 90분` 의 잔재로 보인다 — 기획 §2 규칙 ⑤-5 가 *"그런 단일 상수를
만들지 않는다"* 고 폐기한 값이다. **지우는 건 이 계획의 범위 밖이다** (시간 계산에 영향 없음).

## 1. 다섯 단계 — 이 순서로 간다

```
1. 지금 값을 DB 로 올린다        (구조만 — 값은 그대로 30)
2. 관제웹이 그 값을 쓰게 한다     (①과 함께. 안 하면 갈라진다)
3. 시한을 주행 × 1.5 로 바꾼다    (값 교체 — 구조는 안 건드린다)
4. 버퍼를 파생시켜 화면에 낸다
5. 합짐 할인율에 시간 하강을 넣는다
```

### 🔴 순서를 이렇게 잡은 이유

**구조를 바꾸는 일과 값을 바꾸는 일을 같이 하지 않는다.**
`judgment.ts:75` 에 이미 같은 원칙이 적혀 있다 — *"구조를 바꾸는 일과 값을 바꾸는 일을
같이 하지 않는다. 색이 바뀌면 원인을 못 가린다."*

1·2 를 마치면 **화면에 보이는 시각이 하나도 안 바뀐다.** 그게 맞는지 확인하고 3 으로 간다.
3 에서 시각이 바뀌면 원인은 3 뿐이다.

## 2. 단계별 상세

### 단계 1 — 지금 값을 DB 로 (구조만)

| 무엇 | 어디 |
|---|---|
| `JUDGMENT_FIELDS` 에 `arrival_margin_minutes` 한 줄 추가 | `shared/src/judgment.ts` |
| (자동) DB 컬럼 생성 | `db.ts:412` `ensureColumns` 가 표를 읽는다 |
| (자동) 관제웹 판정 기준 폼에 칸 등장 | 폼이 표를 읽는다 |

```ts
{ col: 'arrival_margin_minutes', path: ['unknown', 'arrivalMarginMin'], group: '모를 때',
  label: '🕒 도착 약속 여유', unit: '분', min: 0, max: 120, int: true,
  why: '통화 전 추정 약속 = 도착 예상 + 이만큼' },
```

**값은 30 그대로.** 이 단계에서 화면은 아무것도 안 바뀐다.

- 검사: 폼에 칸이 뜬다 · DB 컬럼이 생긴다 · 기본값 30
- ⚠️ **기존 DB 사본으로 부팅 스모크** (빈 DB 는 `ensureColumns` 문제를 숨긴다 — server/CLAUDE.md)

### 단계 2 — 관제웹이 그 값을 쓰게 (🔴 1과 함께)

`deriveRouteTimeline` · `deriveCallTiming` 호출 네 곳에 `rules` 를 넘긴다.

| 파일 | 줄 |
|---|---|
| `DepartureCountdown.tsx` | 71 (`deriveRouteTimeline`) · 95 (`deriveCallTiming`) |
| `PinnedRoute.tsx` | 150 (`deriveRouteTimeline`) |
| `PinnedRouteCard.tsx` | `timing` 을 만드는 자리 |

`judgmentStore` 의 `unknown` 을 `DeadlineRules` 로 옮기는 함수를 **한 곳에** 둔다 —
네 곳이 각자 매핑하면 그게 다음 갈라짐이다 (규칙 ③).

```ts
// shared — 서버도 관제웹도 이걸 쓴다
export function deadlineRulesOf(j: JudgmentConfig): DeadlineRules
```

서버의 `OrderEvaluator.ts:182` · `dispatchEngine.ts:279` 도 이 함수로 바꾼다
(지금은 손으로 객체를 짓고 있어 필드가 늘 때마다 두 곳을 고쳐야 한다).

- 🔴 검사: **판정 기준을 40 으로 바꾸면 서버 로그와 화면이 같이 40 을 쓴다**
  (이 검사가 없으면 ①의 위험이 그대로 남는다)

### 단계 3 — 시한을 `주행 × 1.5 + 픽업` 으로 (값 교체)

`timing.ts` 의 두 자리가 `margin` 을 더하고 있다.

```ts
// 664   deriveCallTiming
const margin = rules.arrivalMarginMinutes ?? 30;
pickupPromisedArrivalAt = new Date(capturedMs + (approachMinutes + margin) * 60_000)...

// 793   deriveRouteTimeline
const margin = rules.arrivalMarginMinutes ?? 30;
promisedUntil = new Date(etaMs + margin * 60_000)...
```

여기를 **비율**로 바꾼다.

```ts
// 새 파생 — 한 곳에서만 만든다
export function arrivalMargin(deliveryDriveMin: number | null, rules: DeadlineRules): number
    → deliveryDriveMin != null ? Math.round(deliveryDriveMin * rules.arrivalMarginPct / 100)
                               : rules.arrivalMarginMinutes      // 주행을 모르면 고정값 폴백
```

| 무엇 | 값 |
|---|---|
| `arrival_margin_pct` (새 칸) | **50** |
| `arrival_margin_minutes` (단계 1에서 만든 것) | 30 — **주행을 모를 때의 폴백으로 남는다** |
| `unknown_pickup_dwell_minutes` | 15 → **20** |

⚠️ **`deliveryDriveMin` 이 무엇인지가 함정이다.** 시한은 **배송 주행(상차지→하차지)** 만
본다(기획 §1). `routeStops.driveMinutes` 는 **누적**이라 접근이 섞여 있다.

```
상차 정거장의 driveMinutes  = 접근 주행           ← 이게 아니다
하차 − 상차                 = 배송 주행           ← 이것이다
orders.kakaoSoloDurationMin = 배송 주행 (단독)     ← 합짐 전에는 이것과 같다
```

**합짐이 붙으면 둘이 갈라진다.** 어느 쪽을 시한의 재료로 쓸지 정해야 한다 —
기획 §2 가 *"시한은 콜 받는 순간 임시로 정해지고 경로가 바뀌어도 다시 세지 않는다"* 고
했으므로 **`kakaoSoloDurationMin`(잡을 때의 단독 주행)** 이 맞다. 계산도 안정적이다.

- 검사: `주행 110분 → 여유 55분` · `주행을 모르면 30분` · **20분 콜에서 여유 10분**
  (기획 §1 의 "짧은 콜이 빡빡해진다" 를 검사로 못박아 둔다 — 놀라지 않게)
- ⚠️ 이 단계에서 **화면의 모든 약속 시각이 바뀐다.** 여기서만 바뀌어야 한다

### 단계 4 — 버퍼를 파생시켜 화면에 낸다

🔴 **저장하지 않는다. 파생시킨다** (규칙 ③).

```ts
// shared/src/timing.ts — 타임라인이 이미 모든 재료를 갖고 있다
export function callBuffer(entry: RouteTimelineEntry, order, rules): number | null
    → 시한(order) − (entry.driveMinutes + entry.leadMinutes + 상차 정차)
```

단계 4-1 에서 만든 `driveMinutes`·`leadMinutes` 가 그대로 재료가 된다
([이번 커밋](../onedal-web/shared/src/timing.ts) 에서 이미 실어 보내고 있다).

화면 (기획 §7 의 넷 중 셋):

| 무엇 | 어디 |
|---|---|
| 그날 합짐 예산 | 첫짐 KEEP 직후 — `DepartureCountdown` 옆 |
| 임시/확정 구분 | 시한 표시에 `~` |
| 합짐 비용 · 막은 콜 | **단계 5 이후** — 후보 카드가 필요하다 |

- 검사: 기획 §4-2 시나리오 A(버퍼 44분) · §4-3 시나리오 B(−8분, 못 붙임) 를
  **값으로 재현**한다. 두 시나리오가 이미 숫자로 검산돼 있어 그대로 테스트가 된다

### 단계 5 — 합짐 할인율 시간 하강

🔴 **`merge` 국면에만.** `first` 는 지금 그대로 (기획 §7-0 — 의도된 비대칭).

**타이머를 만들지 않는다.** 경과 시간에서 파생시킨다 (규칙 ③).

```ts
// 5분마다 10%p, 바닥에서 멈춘다
discountAt(elapsedMin, base, stepMin, stepPct, maxPct)
    → Math.min(maxPct, base + Math.floor(elapsedMin / stepMin) * stepPct)
```

- **기준 시각** — `merge` 진입 시각 = 첫짐 KEEP 시각. 지금 국면 전환 시각이 안 남는다
  (`filterManager.ts:405` 는 로그만 찍는다) → **세션에 `phaseEnteredAt` 을 둔다**
- **다시 계산되는 시점** — 앱이 `POST /api/scrap` 으로 5초마다 오므로 그때 파생하면 된다.
  값이 바뀔 때만 피기백으로 새 필터를 내린다 (지금 구조 그대로)
- 🔴 **바닥은 하나만** — `maxPct` 로 막는다. 합짐 하한가로도 막으면 같은 바닥이 두 곳이 된다

새 값 셋 (`PHASE_FIELDS` 에 넣을지 `JUDGMENT_FIELDS` 에 넣을지 정해야 한다):

| | 값 | 근거 |
|---|---|---|
| 하강 주기 | 5분 | 기사님 |
| 하강 폭 | 10%p | 기사님 |
| 최대 할인 | **미정** 🔴 | 기획 §7 — 없으면 시세의 20% 까지 간다 |

- 검사: `0분 → base` · `5분 → base+10` · `바닥에서 멈춘다` · **`first` 는 안 움직인다**
- ⚠️ 앱이 5분마다 필터가 바뀌는 것을 견디는지 — `pnpm e2e:app`

## 3. 위험

| | 무엇 | 어떻게 막나 |
|---|---|---|
| 🔴 높음 | ①만 하고 ②를 빠뜨리면 **서버와 화면이 다른 시각**을 말한다 | 같은 단계로 묶었다. 검사로 못박는다 |
| 🔴 높음 | 단계 3 에서 **모든 약속 시각이 바뀐다** | 1·2 를 먼저 끝내 "안 바뀜"을 확인하고 간다 |
| 중간 | 짧은 콜이 빡빡해진다 (20분 → 여유 10분) | 검사에 명시. 실측으로 확인 (기획 §1) |
| 중간 | `deliveryDriveMin` 을 누적 주행으로 잘못 쓰면 접근이 섞인다 | `kakaoSoloDurationMin` 으로 고정 |
| 낮음 | 5분마다 필터가 바뀌어 앱이 흔들린다 | `pnpm e2e:app` |

## 5. 시작 전에 정해야 하는 것

| | 질문 | 없으면 |
|---|---|---|
| 🔴 | **최대 할인율** (단계 5) | 시세의 20% 짜리 콜을 잡는다 |
| 🔴 | `merge` 시작점 — 0% 인가, 설정값(10%)인가 | 하강 시작 위치가 안 정해진다 |

**단계 1~4 는 위 넷 없이도 시작할 수 있다.** 단계 5 만 막혀 있다.
