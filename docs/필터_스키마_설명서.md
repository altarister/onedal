# 필터 스키마 설명서

> **작성 2026-08-15** · 기사님: *"필터 관련 DB 스키마 보여줘. 거기에 지금 추가 혹은 삭제할
> 것들을 대입해 보고, 그 값들을 **어떻게 어느 시점에 꺼내 쓰거나 수정할지** 기준을 세우고
> **어떻게 보여질지**까지가 확인되어야 수정을 진행할 거야."*
>
> 이 문서는 루트 `CLAUDE.md` 규칙 **⑤-4**(*값을 만들기 전에 네 가지가 먼저 확정된다*)의
> ① 스키마 ② 값 ③ 시점 ④ 화면 을 채운 것이다. **여기가 채워지기 전에는 코드를 고치지 않는다.**

# 1. 지금 있는 것 — `user_filters` (실제 DDL)

```sql
CREATE TABLE user_filters (
    user_id                TEXT PRIMARY KEY,
    destination_city       TEXT    DEFAULT '파주',
    destination_radius_km  INTEGER DEFAULT 10,
    corridor_radius_km     INTEGER DEFAULT 5,
    min_fare               INTEGER DEFAULT 30000,
    max_fare               INTEGER DEFAULT 1000000,
    pickup_radius_km       REAL    DEFAULT 10,
    excluded_keywords      TEXT    DEFAULT '[]',
    is_active              BOOLEAN DEFAULT 0,
    is_shared_mode         BOOLEAN DEFAULT 0,
    load_state             TEXT    DEFAULT 'EMPTY',
    driver_action          TEXT    DEFAULT 'WAITING',
    vehicle_rates          TEXT    DEFAULT '{"오토바이":700, … ,"특수화물":3000}',
    agency_fee_percent     REAL    DEFAULT 23.0,
    max_discount_percent   REAL    DEFAULT 10.0,
    eyeline_pct            INTEGER DEFAULT 10,
    phase_settings         TEXT    DEFAULT ''
);
```

## 1-1. 칸을 성격으로 나누면 **네 무리**다

| 무리 | 칸 | 성격 |
|---|---|---|
| **A 사냥 조건** | `destination_city` · `destination_radius_km` · `corridor_radius_km` · `pickup_radius_km` · `excluded_keywords` | 어디서 무엇을 잡을까 |
| **B 돈** | `vehicle_rates` · `agency_fee_percent` · `eyeline_pct` · ~~`min_fare`~~ · ~~`max_fare`~~ · ~~`max_discount_percent`~~ | 얼마면 잡을까 |
| **C 지금 상태** | `is_active` · `is_shared_mode` · `driver_action` · ~~`load_state`~~ | 지금 무엇을 하고 있나 (설정이 아니다) |
| **D 국면별 묶음** | `phase_settings` (JSON) | 국면마다 A·B 를 따로 |

## 1-2. 🔴 지금 **A 와 D 가 겹쳐 있다**

`phase_settings` 는 이미 다섯 국면치 값을 갖고 있다 (현재 실제 저장값):

```json
{ "first": { "destinationCity":"파주시", "pickupRadiusKm":5, "detourAllowKm":1,
             "dropoffRadiusKm":5, "discountPct":10 },
  "merge": { …, "detourAllowKm":5, "dropoffRadiusKm":3, "discountPct":10 },
  "drive": { …, "detourAllowKm":0, … },
  "local": { …, "discountPct":20 },
  "home":  { …, "detourAllowKm":10, … } }
```

그런데 **평면 칸도 그대로 남아 있다** — `destination_radius_km=1`, `pickup_radius_km=1.0`.
같은 뜻이 두 곳에 있고, 지금은 **국면 전환 때 JSON 이 평면을 덮어쓰는** 방식으로 산다.

> 명세 §5: *"기존 평면 컬럼은 **P4 에서 정리**"* — 계획은 있으나 아직 안 했다.
> 이 문서는 그 정리를 전제하지 **않는다.** 지금 구조 위에서 더한다.

# 2. 무엇을 더하고 무엇을 뺄까

## 2-1. ➕ 더할 것 — `judgment_config` (JSON 한 칸)

**컬럼을 11개 늘리지 않는다.** `vehicle_rates` · `phase_settings` 와 같은 방식이다
(명세 §2-4-7 이 이미 정한 규약).

```sql
ALTER TABLE user_filters ADD COLUMN judgment_config TEXT DEFAULT '';   -- v9
```

지금 **코드에 박혀 있어 못 바꾸는 값 11개**가 여기로 들어온다:

```jsonc
{
  // 첫짐(단독) 색 기준 — 분
  "solo":  { "honeyMaxMin": 40, "shitMinMin": 90 },

  // 합짐 색 기준 — 🔵는 둘 다(AND), 🟡는 하나만 넘어도(OR)
  "merge": { "honeyMaxMin": 30, "honeyMaxKm": 15,
             "shitMinMin": 60,  "shitMinKm": 30 },

  // 🔴 모르는 값을 채울 **일반값** — 불리한 값이 아니다 (규칙 ⑤-2)
  "unknown": { "dwellMin": 15, "slackMin": 120 },

  // 상하차 정차 시간 — 방법별 기본 + 짐 점수당 추가
  "dwell": {
    "base":     { "지게차": 10, "수작업": 15, "호이스트": 20, "검수": 90 },
    "perPoint": { "지게차": 0.3, "수작업": 1.5, "호이스트": 1.0, "검수": 0 }
  }
}
```

### 값의 근거 (규칙 ⑤-4 ②)

| 값 | 지금 | 새 값 | 근거 |
|---|---|---|---|
| `unknown.dwellMin` | **20** | **15** | 실제 신고 **수작업 44건 · 지게차 12건 — 78% 가 수작업(15분)**. 20분은 수작업보다 높고 호이스트와 같다. 지금 주석은 *"낙관하지 않는다"* 라며 **비관을 명시**한다 |
| `unknown.slackMin` | **60**(똥 기준을 돌려씀) | **120** | `shared/timing.ts` 에 이미 `DEFAULT_DELIVERY_SLACK_MINUTES=120` 이 있다. 같은 뜻인데 두 값이 따로 살고 있었다 |
| 나머지 | 그대로 | 그대로 | 지금 값을 그대로 옮긴다. **이관과 값 변경을 같이 하지 않는다** — 색이 바뀌면 원인을 못 가린다 |

## 2-2. ➖ 뺄 것 — **이 문서에서는 빼지 않는다**

| 칸 | 상태 | 왜 지금 안 빼나 |
|---|---|---|
| `min_fare` · `max_fare` | 앱 구버전 호환 | 명세 **P4**. 앱 재설치가 필요해 별건 |
| `max_discount_percent` | `eyeline_pct` 가 대체 | 〃 |
| `load_state` | 쓰는 곳 2곳뿐 | 적재는 `getActiveCalls()` 에서 파생된다. P4 에서 함께 |
| 평면 A 칸들 | `phase_settings` 와 중복 | 명세 P4. **한 번에 둘을 건드리지 않는다** |

🔴 **더하는 일과 빼는 일을 같은 커밋에 섞지 않는다.** 색이 바뀌었을 때 원인이 둘이 된다.

## 2-3. ⛔ DB 로 올리지 **않는** 값

| 값 | 어디 | 왜 코드에 두나 |
|---|---|---|
| 데스밸리 `30초` / `35초` | `dispatchConfig` | **안전장치.** 규칙 ② — 설정으로 열면 `0` 으로 꺼질 수 있다 |
| GPS 점프 `5km` · 로그 `200m` · 속도 `200km/h` | `geoService` | 진단용. 기사님이 조정할 성질이 아니다 |
| 트림 `0.5km` · 도착 감지 `500m` | `geoService` | 물리 감지. 바꾸려면 실측 근거가 필요하다 |
| 적재 칸 `5` · 차종별 칸 | `shared/pricing` | **차의 물리 규격.** 차가 바뀌면 `user_settings.vehicle_type` 이 정한다 |

# 3. 언제 읽고 언제 쓰는가 (규칙 ⑤-4 ③)

## 3-1. 두 그릇 — 이 규칙을 깨면 화면이 거짓말한다

```
baseFilter    DB · "평소"      ← user_filters 한 줄
activeFilter  메모리 · "오늘"   ← 로그인 때 1회 복사, 이후 완전 격리
```

`judgment_config` 도 **같은 규칙을 따른다.** 오늘만 빡빡하게/느슨하게 쓸 수 있어야 한다.

## 3-2. 생명주기

| 시점 | 무엇이 일어나나 | `judgment` 는 |
|---|---|---|
| **로그인** | DB → 메모리 1회 복사 | DB 값을 읽어 `session.judgment` 로. 비어 있으면 **기본값 시드** |
| **콜 평가** | 서버가 색을 정한다 | `session.judgment` 를 **읽기만** 한다 |
| **재탐색** | 같은 콜을 다시 잰다 | 🔴 **같은 값을 읽는다** — 지금은 자기 숫자(10km/30분)를 써서 색이 바뀐다 |
| **🟢 오늘만** | 메모리만 바꾼다 | `session.judgment` 갱신 · DB 불변 |
| **📌 계속** | 메모리 + DB | 둘 다 갱신 |
| **자정(영업일 전환)** | 오늘값 = 평소값 | DB 값으로 되돌아간다 |
| **국면 전환** | 국면 조각을 평면에 펼친다 | **건드리지 않는다** — 판정 기준은 국면과 무관하다 |

## 3-3. 🔴 읽는 곳은 **한 곳**이어야 한다

지금은 두 곳이고 숫자가 다르다:

```
OrderEvaluator      똥 = 60분 이상 OR 30km 이상   (dispatchConfig)
recalculateKakao    똥 = 30분 초과 OR 10km 초과   (dispatchEngine.ts:203 에 직접)
```

**같은 콜이 재탐색만 해도 색이 바뀐다.** DB 로 옮겨도 재탐색이 자기 숫자를 쓰면 그대로다.
→ 이관보다 **먼저** 통일한다.

# 4. 어떻게 보이는가 (규칙 ⑤-4 ④)

## 4-1. 색이 곧 결정이다

기사님(2026-08-15): *"KEEP 버튼의 내용보다는 **파란색, 녹색이면 코드를 믿고 바로 잡을 거야**."*

```
🔵 꿀    시간·거리 둘 다 여유 안        →  바로 잡는다
🟢 보통  꿀도 똥도 아님                 →  바로 잡는다
🟡 똥    시간 또는 거리가 한계를 넘음    →  본다
🔴 실패  연산 실패 (잡지 마라)
```

**설명 문구는 그다음이다.** 색을 틀리는 것이 이 시스템의 가장 큰 사고다.

## 4-2. 카드에 함께 보일 것

```
🔵 꿀   우회 +1.1km · 주행 +6분 · 상하차 30분 ⓘ미확인
                                            └ 일반값으로 계산했다는 표시
```

- 숫자는 **일반값으로 계산**하되(규칙 ⑤-2), `미확인` 배지를 함께 단다 →
  숫자가 거짓말하지 않으면서 색은 나온다
- 통화로 확정하면 배지가 사라지고 숫자가 실측으로 바뀐다

## 4-3. 필터 설정 팝업 — **판정 기준** 섹션

```
┌ 필터 설정                       × ┐
│ 제외 단어  [착불, 수거]            │  ← 다섯 탭 공통
│ 판정 기준  ▾                      │  ← 🆕 여기. 역시 공통(탭 밖)
│    첫짐   🔵 ≤ 40분   🟡 ≥ 90분    │
│    합짐   🔵 ≤ 30분 & ≤ 15km      │
│           🟡 ≥ 60분 | ≥ 30km      │
│    미확인 상하차 15분 · 여유 120분  │
│ 첫짐● 합짐 운행중 관내 복귀         │
│ …                                │
│ [평소값] [오늘만 적용] [계속]      │  ← 저장 버튼은 기존 것을 그대로 쓴다
└──────────────────────────────────┘
```

- **탭 밖**에 둔다. 다섯 국면 공통이므로 탭 안에 있으면 *"이 탭에만 걸리나"* 로 읽힌다
  (제외 단어와 같은 이유 — 명세 §4-2)
- 접어 두되(`▾`) **접힌 채로도 지금 값이 한 줄 요약**으로 보인다
- 편집 가능. 저장은 기존 `오늘만` / `계속` 이 그대로 처리한다

## 4-4. 어디로 내려보내나

| 대상 | 보내나 | 왜 |
|---|---|---|
| 앱 (REST 피기백) | ❌ | **앱은 색 판정을 하지 않는다** (규칙 ⑤-1). `AutoDispatchFilter` 평면을 안 건드리므로 **앱 재설치가 필요 없다** |
| 관제웹 (소켓) | ✅ | `filter-updated` 페이로드에 `judgment` 를 `activeFilter`·`baseFilter` 의 **형제로** 추가 |

## 남은 결정 하나

**합짐 판정에서 거리(`shitMinKm: 30`)를 어떻게 할까.**

명세 §3 은 *"경유를 넓혀도 비용이 아니다 — 후보가 늘 뿐"* 이라 한다. 그런데 코드는
**30km 를 넘으면 시간과 무관하게 똥**(OR)이다. 2026-08-15 의 `+31.1km` 콜이 여기 걸렸다.

| 안 | 뜻 |
|---|---|
| ㉮ 거리를 색에서 뺀다 | 명세대로. 시간만 본다 |
| ㉯ 느슨하게 | 예: 30 → 50km |
| ㉰ 지금 유지 | |

이것만 정해지면 ①~④가 다 닫힌다.
