## 2. 확인된 사실 — 근거와 함께

| # | 사실 | 근거 |
|---|---|---|
| ① | 리스트에 그 카드가 **11:50 부터 또렷이** 있었다 — `수지 성복 → 강남 대치2  13,783` | 서버 로그의 앱 화면 중계 `🧾 [화면 LIST]` |
| ② | **상차 성복동은 필터 안**이다 — 현위치에서 5.5km, 상차 반경 10km | `pickupGroups.용인시 수지구` 에 포함 · `pickupArea.at` = 현위치 |
| ③ | 성복동은 **지도 점도 찍힌다** — `dongDotsOf` 에 20개 동 전부 나온다 | `shared/src/filterArea.ts` 를 그때 필터로 직접 실행 |
| ④ | **하차 대치2동은 필터 밖**이다 — 강남구가 목록에 아예 없다 | `destinationKeywords` 31개 · `destinationGroups` (광주 20·분당 8·처인 2·중원 1) |
| ⑤ | **서버 하차 목록이 0개였던 순간은 한 번도 없다** | 로그 전 구간 스캔 — 11:43~11:54 내내 29~31개 |
| ⑥ | 🔴 **앱은 하차 목록을 0개로 들고 있다.** 상차는 19개로 정상 | A24 앱 저장소 `OneDalPrefs.xml` 의 `activeFilter` 직접 확인 |
| ⑦ | 앱은 **라이브를 본다** (`isLiveMode=true`). `localPcIp` 는 저장만 된 값이다 | 같은 파일 |
| ⑧ | 서버 응답에 **필터 본문이 안 실린다** — `filterVersion` 이 같으면 생략 | 앱이 저장한 `api_scrap_res` 원문 127자: `{success, apiStatus, deviceControl, filterVersion}` |
| ⑨ | 앱 알람 판정은 **하차 목록이 비면 «제한 없음»으로 통과**시킨다 | `KakaoPickerParser.kt:477` — `destKeywords.isEmpty() ‖ order.dropoff.isBlank() -> true` |
| ⑩ | 앱이 **스스로 상세까지 들어간다** — 기사님이 누른 것이 아니다 | A24 logcat: `🔔 [알람] … (앱이 상세까지 들어간다)` · `⏱️ [상세 대기] … 연 쪽: 알람` |
| ⑪ | 상세를 읽은 **뒤에는 필터를 다시 안 본다** | `PreConfirmSequence.kt` — `verify` 성공 즉시 `sendConfirmOnce`·`sendDetail` |

**즉 사슬은 이렇다.** 서버 31개 → (앱에 안 내려감) → 앱 0개 → `isEmpty()` 라 전부 통과 →
알람 → 앱이 상세 자동 진입 → 필터 재검사 없이 서버 전송.

## 3. 🔴 이미 틀린 것으로 밝혀진 가설 — 다시 파지 말 것

| 가설 | 왜 틀렸나 |
|---|---|
| «기사님이 리스트에서 눌렀다» (`MANUAL_CLICK` 이라서) | `MANUAL_CLICK` 은 **픽커 상세 OCR 파서가 붙이는 이름**이다 (`PickerDetailOcrParser.kt:103·114`). 기사님은 안 누르셨다 |
| «미리보기라 필터를 안 지나는 게 설계다» | 설계는 맞지만 **이 사건의 원인이 아니다.** 앱이 자동으로 연 것이고, 알람 단계에서 걸렸어야 한다 |
| «서버가 빈 하차 목록을 보냈다» | 사실 ⑤ — 서버는 한 번도 0개가 아니었다 |
| «경기 광주 «대치리» 와 «대치2동» 이 «대치»로 충돌했다» | 하차 목록 31개에 «대치» 들어간 낱말이 **하나도 없다** |
| «성복동에 지도 점이 없다» | 사실 ③ — 점은 찍힌다. 기사님이 보신 «점 밖»은 **하차지**였다 |
| «앱이 로컬 서버를 본다» | 사실 ⑦ — `isLiveMode=true`, 라이브를 본다 |

## 4. ⬜ 아직 모르는 것 — 여기서 시작한다

**서버는 31개를 갖고 있는데 앱은 왜 0개인가.** 상차(19개)는 멀쩡히 들어왔다.
둘은 같은 `APP_FILTER_KEYS` 로 **같은 응답**에 실려 나간다 (`routes/scrap.ts` 의 `appFilter` 조립).

볼 곳 셋 — **③이 가장 의심된다.**

1. 서버 조립 — `appFilter` 에서 하차만 빠지는 길이 있나 (`onedal-web/server/src/routes/scrap.ts:235`)
2. 전달 — `filterVersion` 이 **목록 내용을 반영하나.** 내용이 바뀌어도 버전이 같으면 영영 안 내려간다
3. 🔴 **앱 저장** — 응답을 `OneDalPrefs.activeFilter` 에 넣는 Kotlin 코드에서 **하차만 다르게 다루는 자리**.
   상차(`pickupKeywords`)는 최근에 추가된 키이고 하차는 오래된 키다 — 옛 코드가 남아 있을 수 있다

## 5. 고칠 자리 (원인과 별개로 둘 다 필요하다)

| | 무엇 | 왜 |
|---|---|---|
| 🔴 1 | 앱: `destKeywords.isEmpty()` 를 «전부 통과»가 아니라 **«고장 — 안 잡는다»** 로 | 규칙 ④ — *«필터가 비어 있으면 «전부 통과»가 아니라 «고장»으로 다룬다»*. 서버가 무엇을 보내든 앱이 스스로 막는다 |
| 2 | 앱: 상세 OCR 로 하차지를 **알아낸 그 자리**에서 필터를 한 번 더 본다 | 리스트에서 무엇을 놓쳤든 거기서 걸린다 (사실 ⑪) |
| 3 | 서버: `filterVersion` 이 목록 내용까지 반영하는지 | 안 하면 갈라진 채로 영영 간다 |
