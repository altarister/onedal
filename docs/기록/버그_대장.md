# 버그 대장 — 클래스로 센다

> 2026-08-18 신설. 기사님: *"발견된 버그를 정확히 진단할 수 있어야 재발 방지가 된다.
> 이 루틴을 끊어 버리고 싶어."*
>
> **버그를 하나씩 세면 "또 새 버그"로 보이고, 클래스로 세면 "저번 그거"가 보인다.**
> 같은 클래스가 두 번 나오면 인스턴스가 아니라 **그 클래스를 없애는 수정**을 한다.

## 규칙 — 순서를 뒤집는다

```
진단  →  이 버그를 잡았을 검사를 먼저 만든다 (빨간불 확인)  →  수정  →  초록불
```

검사가 **빨간불이 안 뜨면 진단이 틀린 것**이다. 그때는 고치지 말고 진단으로 돌아간다.

## 왜 통과했는가 — 우리 검사의 사각 (2026-08-18 측정)

| 관문 | 무엇을 보는가 | 값이 틀린 걸 잡나 |
|---|---|---|
| `tsc` | 타입이 맞나 | ❌ |
| `jest` | 함수가 규칙대로 도나 | ❌ (DB 를 여는 테스트가 **0개**였다) |
| `scenario` | **소켓으로 방송된 상태**가 맞나 | ❌ (DB 행은 씨앗 고를 때만 썼다) |
| `audit:socket`·`audit:dead` | 배선이 이어져 있나 | ❌ |
| **`scenario` 장부 검사** 🆕 | **실제로 저장된 행·화면 문구** | ✅ |

→ 2026-08-18 이전에는 **타입이 맞고 소켓 방송이 맞으면 값이 증발해도 전부 초록불**이었다.

## 클래스 — 형태와 「또 있나」 훑는 법

아래 표의 **클래스** 칸에 쓰는 이름들이다. 새 버그를 만나면 **먼저 여기서 형태를 찾는다** —
같은 형태면 인스턴스가 아니라 그 클래스를 없애는 수정을 한다.

| 클래스 | 형태 | 또 있나 훑는 법 |
|---|---|---|
| **같은 판단이 두 곳에** | 같은 뜻을 앱과 서버가 각각 정의하거나, 한 파일 안에서 분기마다 따로 판단한다 | ① 판단을 담은 **이름으로 전 레포를 훑는다** — 두 곳 이상에서 같은 뜻을 계산하는가<br>② **호출부 개수를 센다**<br>③ 규칙 검사가 «호출부 전부»를 훑는가, 한 곳만 보는가 |
| **파생값이 죽은 채 방치** | 함수는 불리는데 세션에서 사라진 필드를 읽어 **몇 달째 아무 일도 안 한다** | **`pnpm audit:dead`** 가 이 클래스 전용 도구다 |
| **시간차 · 경합** | 앱·서버·관제웹이 같은 사건을 **다른 시각에** 알고, 그 사이에 결정을 내린다 | ① 서버 로그에서 «앱 보고» 주기를 잰다<br>② 앱 화면 전환 ↔ 서버 인지 ↔ 관제웹 카드 삭제 **세 시각을 한 줄에** 놓는다<br>③ 그 사이에 내려지는 결정을 센다 (취소·필터 교체·카드 삭제) |
| **위치가 진실이 아니다** | 서버가 아는 «지금 내 위치»가 실제와 다른데, 그 위에서 경유·도착·경로가 계산된다 | 궤적(`gps_tracks`)과 부여받은 경로를 대조한다 |
| **화면은 메모리, 장부는 비어 있음** | 화면에는 보이는데 재시작하면 사라진다 — 저장 경로를 안 거쳤다 | **`pnpm ledger`** 로 «화면이 말하는 것»과 «장부에 남은 것»을 대조 |
| **한 화면 두 세상** | 같은 화면의 두 조각이 서로 다른 계산을 본다 | 파생의 출처를 센다 — 하나여야 한다 |
| **앱이 화면에서 잘못 읽는다** | 파서가 노드를 잘못 묶거나 못 읽는다 | 원하는 지명의 콜을 밀어넣어 통과하는지 본다 |
| **한 신호에 뜻이 둘** | 같은 값을 두 곳이 반대로 해석한다 (빈 배열 = «전부 금지» ↔ «전부 허용») | 그 값을 읽는 곳을 전부 찾아 뜻을 맞춘다 |

## #50 · 폰마다 다른 숫자를 "필터"의 숫자인 척 그렸다 (2026-08-23)

**클래스: `한 벌짜리 자리에 여럿인 값을 놓는다`**

#49 를 붙인 지 몇 분 만에 기사님이 짚으셨다.

기사님: *"`👁️ 방금 6건 → 통과 0 · 도착지 4 · 차종 1 · 경로순서 1` **이것이 필터에
들어가면 안 될 것 같아.** 폰이 2개 이상이어도 상관없는 건가?
**1번 폰은 작동하는데 2번 폰은 작동하지 않는다면?**"*

- 🔴 **필터는 한 벌, 성적표는 폰마다다.** 필터는 서버가 만들어 **모든 폰에 똑같이**
  내려보낸다. 스캔 성적표는 **그 폰이 방금 무엇을 봤나**라 폰마다 다르다
- 한 벌짜리 카드에 폰마다 다른 값을 놓으면 **하나를 골라야 한다.** 코드가 그렇게 돼 있었다:
  ```ts
  const tally = devices.filter(d => d.filterTally && d.filterTally.seen > 0).pop()?.filterTally;
  ```
  `.pop()` 은 **배열 순서상 마지막 폰**이다 — 아무 뜻도 없는 기준이다.
  1번 폰이 잘 잡고 있어도 2번 폰이 뒤에 있으면 화면은 **2번 폰의 `통과 0`** 을 보여 준다.
  기사님은 그걸 *"필터가 안 잡는다"* 로 읽으신다
- 🔴 **주어가 빠진 것이 진짜 결함이다.** `👁️ 방금 6건` 에는 **누가** 봤는지가 없다.
  폰이 하나일 땐 안 보이지만, 하나일 때 안 보이는 것이 둘일 때 사고가 된다
- 고침: 성적표를 **폰 카드 안**으로 옮겼다 (`DeviceControlPanel`). 폰 이름·화면 상태·
  `수집/수락/취소` 가 이미 거기 있다 — 주어가 자동으로 붙는다. 폰이 셋이면 줄도 셋이다
- 고침: 고르는 자리를 **없앴다.** `summarizeTally(tally)` 는 **폰 하나의 성적표만** 받는다.
  합치거나 고르는 코드가 들어설 자리가 아예 없다 (`client-app/src/lib/filterTally.ts`)
- 아직 안 훑은 폰은 **줄이 안 뜬다** — `0건`이라고 적지 않는다. 모르는 것과 없는 것은 다르다
- ⚠️ 동점이면 선언 순서를 유지한다. 스캔마다 `도착지 2 · 차종 2` 의 앞뒤가 뒤집히면
  화면이 깜빡이는 것으로 읽힌다
- 검사: `server/tests/rules/filterTally.test.ts` (8건, 자리 규칙 2건 신설) ·
  `client-app/src/lib/filterTally.test.ts` (5건, 순서·null)
- ⚠️ **자리 규칙은 서버 쪽 한 곳에만 뒀다.** 앱→서버→화면 왕복을 통째로 보는 검사가
  거기라서다. 두 벌이면 나중에 한쪽만 고쳐진다

> **#49 와 같은 뿌리다.** #49 는 *"화면이 말을 안 한다"*, #50 은 *"화면이 **누구** 얘긴지
> 안 밝히고 말한다"* 였다. 값을 화면에 올릴 때는 **그 값의 주어가 하나인지 여럿인지**를

## #56 · 서버가 **끝내는 법을 몰랐다** — Ctrl+C 에 강제 종료로 끝났다 (2026-08-26)

**클래스: #40 의 다른 얼굴** — 「껐다고 믿은 서버가 안 꺼진다」

기사님: *"지금 서버 죽여 보니… `Previous process hasn't exited yet. Force killing...` 이거 이상한데."*

- 증상: Ctrl+C 를 누르면 `tsx` 가 정중히(SIGTERM) 요청했다가 **안 나가서 SIGKILL** 로 끝냈다
- 뿌리: 종료 절차가 **하나도 없었다.** `process.on('SIGINT'|'SIGTERM')` 도, `close()` 도 없음.
  Node 는 **열린 손잡이가 하나만 있어도 안 죽는다** — 서버가 쥐고 있던 것:
  ① 듣고 있는 HTTP 소켓(keep-alive 포함) ② Socket.IO 연결 ③ **1초 인터벌 두 개**
- 고침 (종료 경로만 — 부팅 경로는 안 건드림):
  ```
  io.close() → closeAllConnections() → httpServer.close() → db.close()
  3초 안에 못 끝내면 process.exit(0)  ← 종료 코드를 tsx 가 아니라 우리가 정한다
  setInterval(…).unref()             ← 타이머가 서버를 붙잡지 않는다
  ```
- 🔴 **`closeAllConnections()` 가 핵심이다.** keep-alive 연결은 «놀고 있어도» 살아 있어서,
  이걸 안 하면 `close()` 콜백이 **영영 안 온다.** 여기서 제일 오래 매달린다
- 실측: SIGTERM → **0.23초에 자진 종료.** 포트·프로세스·DB 잠금 잔재 없음
- 검사: `server/tests/rules/gracefulShutdown.test.ts` (4건)

> **#40 과 #56 은 같은 병의 앞뒤다.** #40 은 Ctrl+C 가 **닿지 않은 것**(`a & b & c` 라
> 백그라운드로 갔다), #56 은 **닿았는데 안 나간 것**. 둘 다 결과는 하나 — *"내가 끈 서버가
> 살아 있다."* #40 때는 4시간 40분 동안 지워진 콜을 화면에 보냈다.
>
> 🔴 그래서 **`bootedAt` 확인은 계속 필요하다.** 이 고침은 «잘 나가게» 만든 것이지
> «확인하지 않아도 되게» 만든 것이 아니다.

## #76 · **거짓 계약을 문서에 적었다** — 「대기 = 필터 꺼짐」이 성립한 적이 없다 (2026-08-30)

**클래스: 「한 값이 여러 사실을 답한다」(신설)** — #33「같은 값을 두 곳에서」의 **뒤집힌 짝**이다.
저건 한 사실을 두 값이 답하는 것이고, 이건 **한 값이 여러 사실을 답하는 것**이다.

기기 모드를 셋으로 늘리며 용어집에 *"대기면 콜 필터가 꺼진다"* 고 적었다. **거짓이었다.**
`updateActiveFilter(isActive:false)` 를 받은 **바로 그 함수 안에서** 불변식이
*"선점 중인 콜 0건이면 다시 켠다"* 로 되켠다.

`activeFilter.isActive` 가 답하던 사실이 **넷**이었다:

```
① 기사님이 필터를 켰는가     기기 모드
② 앱이 누르는가              (실은 앱의 currentMode 가 답하는데 여기 섞여 있었다)
③ 지금 콜을 물어도 되는가    선점 잠금 · 불변식이 푼다
④ 필터를 믿을 수 있는가      scrap.ts — 부트스트랩·만석·미접속·고장
```

넷은 **AND** 여야 하는데 서로 **덮어썼다.** ③이 ①을 덮고 있었다.

🔴 **값이 둘일 땐 넷이 같은 말이라 아무도 못 봤다.** 값을 하나 늘리는 순간 갈라진다 —
이것이 «값 늘리기»가 실은 «축 쪼개기»인 이유다.

**고침**: ①을 `session.filterEnabledByMode` 로 떼어내고 불변식이 그것을 넘지 못하게.
`undefined` 는 «켬» 이다 — 모드를 한 번도 안 고른 사용자를 망가뜨리지 않는다.

**또 있나 훑는 법**: 한 불리언에 **쓰는 곳이 셋 이상**이면 의심한다. 특히 «되돌리는»
불변식이 붙은 값 — 그 불변식은 **자기가 아는 한 사실**만 알고 나머지를 덮는다.

⚠️ **내가 기사님께 먼저 드린 답이 틀렸다.** 기사님이 보신 것은 덱 칩(정차를 세는 쪽)인데
