# 버그 대장 — 클래스로 센다

> 2026-08-18 신설. 기사님: *"발견된 버그를 정확히 진단할 수 있어야 재발 방지가 된다.
> 이 루틴을 끊어 버리고 싶어."*
>
> **버그를 하나씩 세면 "또 새 버그"로 보이고, 클래스로 세면 "저번 그거"가 보인다.**
> 같은 클래스가 두 번 나오면 인스턴스가 아니라 **그 클래스를 없애는 수정**을 한다.

## 규칙 — 순서를 뒤집는다

```
진단  →  이 버그를 잡았을 검사를 먼저 만든다 (빨간불 확인)  →  수정  →  초록불
```

검사가 **빨간불이 안 뜨면 진단이 틀린 것**이다. 그때는 고치지 말고 진단으로 돌아간다.

## 왜 통과했는가 — 우리 검사의 사각 (2026-08-18 측정)

| 관문 | 무엇을 보는가 | 값이 틀린 걸 잡나 |
|---|---|---|
| `tsc` | 타입이 맞나 | ❌ |
| `jest` | 함수가 규칙대로 도나 | ❌ (DB 를 여는 테스트가 **0개**였다) |
| `scenario` | **소켓으로 방송된 상태**가 맞나 | ❌ (DB 행은 씨앗 고를 때만 썼다) |
| `audit:socket`·`audit:dead` | 배선이 이어져 있나 | ❌ |
| **`scenario` 장부 검사** 🆕 | **실제로 저장된 행·화면 문구** | ✅ |

→ 2026-08-18 이전에는 **타입이 맞고 소켓 방송이 맞으면 값이 증발해도 전부 초록불**이었다.

`evolveOrder` 한 곳을 거치게 하고, 검사가 우회를 막는다.

### 3 은 닫혔다 — 값을 고른 게 아니라 **축을 버렸다** (2026-08-18)

기준값을 얼마로 할지 한참 헤맸다. 시뮬레이터 데이터로 표를 만들다 폐기했고
(가짜 데이터에 맞춘 색이 된다), 기사님 경험을 숫자로 받으려 했다.

그런데 기사님의 답은 **"그 값이 첫짐에 완전 필요 없다"** 였다.
첫짐에서 오래 걸린다는 건 나쁜 게 아니라 **그게 일감**이다. 잴 자가 틀렸던 것이다.

→ 운행시간 축을 지우고 **단가**로 바꿨다. 앱이 `요금 ≥ 거리 × 단가` 로 하한을 이미
넘긴 콜만 올리므로, 서버가 답할 것은 **적정가를 넘었는가** 하나다.
새 기준값을 만들지 않았다 — 적정가·하한가는 요율 판정이 이미 쓰던 값이다.

**교훈: 값이 안 정해지면 값을 더 고민하지 말고 "이 축이 맞는가"를 의심한다.**
`pnpm scenario` 의 색 몰림 검사가 이걸로 초록불이 됐다 (40/40).
