> 혼합해 이야기하고 있는 거 같아. 둘이 어떻게 다른지 어떻게 구분해야 할지까지 생각해서
> 개발 계획서를 명확하게 만들고 보고해."*
>
> 지적이 맞다. 그리고 **혼동의 출처는 명세 안에도 있다** — 아래 §1-3 참조.

# 1. 둘은 무엇이 다른가

## 1-1. 시간축이 가른다 — 경계는 **선빵**이다

```
콜이 배차망 화면에 뜬다
        │
        │  ①  🔍 콜 필터    "이 콜을 집을까?"        ← **앱이** 쓴다
        ▼
    앱이 집는다 (선빵)  ────────────────────────────  경계
        │
        │  ②  🎯 판정 기준    "집은 이 콜이 좋은가?"    ← 서버만 쓴다
        ▼
    데스밸리 30초 · 색이 뜬다 · 기사님이 결재
```

- **선빵 이전** = 콜 필터. 놓치지 않는 게 목적이라 **느슨**하다
- **선빵 이후** = 판정 기준. 정확히 구분하는 게 목적이라 **정밀**하다

루트 `CLAUDE.md` 규칙 ⑤ 그대로다 — *"앱은 느슨하게 올리고, 서버는 정밀하게 구분한다."*

## 1-2. 표로

| | 🔍 **콜 필터** | 🎯 **판정 기준** |
|---|---|---|
| 언제 | 선빵 **전** | 선빵 **후** (데스밸리 30초) |
| 누가 쓰나 | **앱** (서버가 만들어 내려보냄) | **서버만** |
| 답하는 질문 | *집을까?* | *좋은가?* |
| 결과 | 집는다 / 넘긴다 | 🔵 🟢 🟡 색 |
| 앱에 내려가나 | ✅ 피기백으로 | ❌ **절대 안 내려간다** |
| 국면(첫짐·합짐·운행중…)마다 다른가 | ✅ `phase_settings` | ❌ 한 벌 |
| 바꾸는 화면 | 🔍 **필터 팝업** | ⚙️ 설정 → **판정 기준** 탭 |
| 사는 곳 | `user_filters` (+`phase_settings`) | 🆕 `user_judgment` |

## 1-3. 🔴 명세 §2-4-8 이 둘을 한 칸에 묶어 놓았다

명세의 표는 이렇게 되어 있다:

| 필드 | 앱 (1차 필터) | **서버 (데스밸리 판정)** |
|---|---|---|
| 도착 도시 | ❌ | ✅ 키워드·시 별칭 생성 |
| 경유 허용 | ❌ | ✅ 회랑 폭 → 키워드 |
| 단가 할인율 | ✅ | ✅ 요율 판정 |

**"서버" 칸에 성격이 다른 둘이 섞여 있다:**

```
키워드·별칭·회랑 만들기   →  이건 여전히 "무엇을 잡을까" 다.
                             서버는 필터의 **제조자**이고 앱이 **사용자**다.
요율 판정                →  이것만 "잡은 걸 어떻게 볼까" 다.
```

→ 서버가 한다고 다 판정이 아니다. **서버는 콜 필터를 *만들고*, 판정 기준으로 *색을 낸다*.**
   내가 두 일을 "서버가 한다"로 뭉쳐 말한 것이 혼동의 원인이었다.

## 1-4. 헷갈리기 쉬운 하나 — 눈높이(단가 할인율)

앱도 쓰고 서버도 쓴다. 그런데 **중복이 아니다**:

```
앱     하한으로 쓴다     요금 ≥ 거리 × 단가 × (1−눈높이)   →  통과 / 탈락
서버   정도로 쓴다       적정가의 몇 % 인가                →  색의 재료
```

같은 숫자를 **문턱**으로 쓰느냐 **눈금**으로 쓰느냐의 차이다.
그러므로 눈높이는 **콜 필터**에 속한다. 판정 기준 테이블에 넣지 않는다.
(규칙 ⑤-1 *"돈은 앱이 이미 걸렀다 — 서버가 다시 세지 않는다"* 와 어긋나지 않는다.
 서버는 다시 **거르지** 않고, 이미 통과한 것의 **정도만** 본다.)

# 2. 값을 어디에 둘 것인가

## 2-1. 🔍 콜 필터 — **지금 그대로 둔다**

| 값 | 사는 곳 | 앱이 쓰는 형태 |
|---|---|---|
| 도착 도시 | `user_filters` · `phase_settings` | 키워드·시 별칭으로 변환돼 내려감 |
| 상차 반경 | 〃 | 그대로 (`상차거리 ≤ 반경`) |
| 우회 허용 | 〃 | ❌ (회랑 → 키워드로만) |
| 하차 반경 | 〃 | ❌ (회랑에 합쳐짐) |
| 눈높이 | 〃 | 단가표로 변환돼 내려감 |
| 제외 단어 | `user_filters` | 그대로 |
| 허용 차종 | 파생 (적재에서) | 그대로 |

**이번 작업에서 건드리지 않는다.**

## 2-2. 🎯 판정 기준 — 🆕 `user_judgment` 테이블

```sql
CREATE TABLE IF NOT EXISTS user_judgment (
    user_id TEXT PRIMARY KEY,

    -- 📦 합짐 색 (분 · km)
    merge_honey_max_minutes  INTEGER DEFAULT 30,
    merge_shit_min_minutes   INTEGER DEFAULT 60,
    merge_honey_max_km       REAL    DEFAULT 15,
    merge_shit_min_km        REAL    DEFAULT 30,

    -- 🚚 첫짐 색 (분)
    solo_honey_max_minutes   INTEGER DEFAULT 40,
    solo_shit_min_minutes    INTEGER DEFAULT 90,

    -- 🔧 모를 때 쓰는 일반값 (분)
    unknown_pickup_dwell_minutes   INTEGER DEFAULT 15,
    unknown_dropoff_dwell_minutes  INTEGER DEFAULT 10,
    unknown_slack_minutes          INTEGER DEFAULT 90,

    -- ⚖️ 가중치 (상대값 · 0 이면 색에 반영 안 함)
    weight_drive_time   REAL DEFAULT 1,
    weight_detour_dist  REAL DEFAULT 1,
    weight_deadline     REAL DEFAULT 1,
    weight_slots        REAL DEFAULT 1,

    -- 🎨 색 경계 (총점)
    color_honey_min   INTEGER DEFAULT 70,
    color_normal_min  INTEGER DEFAULT 40,

    FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

### 왜 JSON 한 칸이 아니라 **컬럼**인가 (기사님 지적 반영)

기사님: *"나중에 라이브 하고 뭔가 필요한 값이 있으면 **마이그레이션이 많이 힘들 듯** 한데."*

| | 값이 하나 늘었을 때 |
|---|---|
| JSON 한 칸 | 기존 행의 JSON엔 그 키가 **없다** → 읽는 곳마다 `?? 기본값` → **규칙 ③이 경고한 폴백**이 새로 자란다 |
| **컬럼** | `ensureColumns()` 한 줄 + `DEFAULT` → **기존 행이 자동으로 채워진다.** 폴백 코드가 필요 없다 |

이 레포엔 이미 `ensureColumns()` 가 있다. **컬럼 추가는 이미 풀린 문제다.**

> 명세 §2-4-7 의 *"컬럼을 15개로 늘리지 않는다"* 는 `phase_settings`(5국면 × 5필드 = **25개**)
> 얘기였다. 판정 기준은 **국면과 무관하게 한 벌**이라 경우가 다르다. 모순이 아니다.

## 2-3. 값의 **뜻**은 어디에 두나 — `shared` 의 표 하나

기사님: *"수정할 때마다 문서를 읽어야 할 건데.. **문서가 항상 최종본이 아닐 수 있고**."*

```
DB              지금 값이 얼마인가            ← 진실
shared 표       라벨 · 단위 · 최소/최대 · 근거  ← 화면이 이걸 읽어 폼을 그린다
docs 문서       왜 그 값으로 정했나 (경위)     ← 값은 안 적는다
```

```ts
// shared/src/judgment.ts
export const JUDGMENT_FIELDS = [
  { key: 'merge_honey_max_minutes', group: '합짐', label: '🔵 꿀 기준 시간',
    unit: '분', min: 0, max: 240, why: '이 시간 이하로 늘면 만점' },
  { key: 'unknown_pickup_dwell_minutes', group: '모를 때', label: '상차 미확인',
    unit: '분', min: 0, max: 120, why: '찾기 + 상차 + 결박 (기사님 2026-08-15)' },
  …
] as const;
```

🔴 **값이 하나 늘면 이 표에 한 줄 + DB 컬럼 하나.**
화면 코드도 서버 판정 코드도 **안 고친다.** (`PHASE_FIELDS` 가 이미 같은 패턴이다 — 표가 화면을 그린다)

# 3. 흐름 (기사님 1~5번 그대로 · 두 곳만 조정)

```
1. 부팅        user_judgment 없으면 만들고 기본값 시드
2. 접속·새로고침 DB → session.judgment
3. 콜 수신     그 세션 값으로 scoreMerge() → 색
4. 값 변경     ⚙️ 설정 → 「판정 기준」 탭 → 폼 → [적용]  →  한 번에 서버로
5. 저장        트랜잭션 하나로 DB + 세션 동시 갱신
```

## 조정 ①  **"오늘만"을 만들지 않는다**

콜 필터는 **평소(DB) ↔ 오늘(메모리)** 두 그릇이고 로그인 때 1회 복사한다.
판정 기준까지 그러면 *"새로고침하면 오늘 바꾼 게 날아가나?"* 가 생긴다.

판정 기준은 **도로에서 데이터를 모아 조정하는 성격**이라 하루만 바꿀 일이 없다.
→ **그릇 하나. 바꾸면 계속 적용.** 기사님 2번이 그대로 단순해진다.

## 조정 ②  탭 이름은 **「판정 기준」**

지금 탭: `기본 설정` · `요율/필터` · `기기 설정`
`판정/필터` 는 `요율/필터` 와 한 글자 차이라 *"필터 값을 바꾸려면 어느 탭이지?"* 가 된다.

**그리고 화면이 갈리는 것 자체가 §1 의 구분을 몸으로 가르쳐 준다:**

```
🔍 필터 팝업            → 콜 필터   "무엇을 잡을까"
⚙️ 설정 → 판정 기준 탭   → 판정 기준   "잡은 걸 어떻게 볼까"
```
