## 왜 그룹으로 묶나

증상 하나씩 쫓으면 **같은 뿌리를 여섯 번 고치게 된다.** 실제로 오늘 하루에
`isAlreadyLoaded`(합짐에만) · `isActive`(켜는 곳만 흩어짐) · `LIST`(앱/서버 정의 다름) ·
`broadcast`(서버만 줄임) 넷이 **전부 같은 모양**이었다 —
**같은 판단이 두 곳에 있고 한쪽만 고쳤다.**

그래서 아래는 증상이 아니라 **원인 그룹**이 목차다. 한 그룹을 확인하면 그 안의 증상이
전부 같이 판정된다.

---

## A. 같은 판단이 두 곳에 — 한쪽만 고치면 되살아난다

**형태**: 같은 뜻을 앱과 서버가 각각 정의하거나, 한 파일 안에서 분기마다 따로 판단한다.

| 증상 (기사님 보고) | 두 곳이 어디였나 | 상태 |
|---|---|---|
| 앱은 리스트로 갔는데 관제탑이 계속 기다림 | 앱 `LIST`+`LIST_COMPLETED` / 서버 `LIST` 만 | 🟢 |
| 앱 만졌더니 사냥이 죽은 채로 남음 | `isActive` 끄는 곳 1 / 켜는 곳 4, 취소 경로 3개 누락 | 🟢 |
| 합짐 하나 내리니 경로가 꼬임 | `isAlreadyLoaded` 가 합짐에만, 단독 분기에 없음 | 🟡 |
| `filter-updated` 초당 5번 | 서버 1회 발신 / 관제웹 5개 훅이 각자 구독 | 🟢 |

**한 번에 확인하는 법**
```
① 판단을 담은 이름으로 전 레포를 훑는다 — 두 곳 이상에서 같은 뜻을 계산하는가
② 호출부 개수를 센다 (calculateSoloRoute 3곳 · 타이머 키 3파일 …)
③ 규칙 테스트가 "호출부 전부"를 훑는가, 한 곳만 보는가
```
🔴 **아직 안 센 것**: 앱과 서버가 각각 정의하는 것이 `LIST` 말고 또 있는가
(상태 목록 · 종료 판정 · 화면 종류 · 차종 이름).

## B. 파생값이 죽은 채 방치 — 호출부는 멀쩡한데 늘 `null`

**형태**: 함수는 불리는데 세션에서 사라진 필드를 읽어 **몇 달째 아무 일도 안 한다.**
`tsc` 가 못 잡는다(`session: any`).

| 증상 | 무엇이 죽어 있었나 | 상태 |
|---|---|---|
| 지나온 구간이 안 빠짐 | `getActivePolyline` → 늘 `null` | 🟢 (74회 동작 확인) |
| 도착 감지가 안 돎 | `getLastDropoffCoord` → 늘 `null` | 🟢 |

**한 번에 확인하는 법** — `pnpm audit:dead` 가 이 그룹 전용 도구다.
🔴 **아직 안 한 것**: 관제웹(client-app)에는 같은 검사가 없다. 서버만 본다.

## C. 시간차 · 경합 — 두 쪽이 서로 다른 순간을 진실로 안다

**형태**: 앱·서버·관제웹이 같은 사건을 **다른 시각에** 알게 되고, 그 사이에 결정을 내린다.

| 증상 | 시간차의 정체 | 상태 |
|---|---|---|

| 주행 중 잘못된 지명 콜이 올라옴 (가설 ㉯) | 서버는 매초 트림, 앱은 다음 보고 때 새 필터를 받음 | 🔴 |

**한 번에 확인하는 법**
```
① 서버 로그에서 [앱 보고] 주기를 잰다                    → 이미 측정: 중앙 4.8s
② 앱 화면 전환 ↔ 서버 인지 ↔ 관제웹 카드 삭제 세 시각을 한 줄에 놓는다
③ 그 사이에 내려지는 결정이 무엇인지 센다 (취소 · 필터 교체 · 카드 삭제)
```
🔴 **이 그룹이 가장 안 봐 왔다.** 위 넷이 전부 같은 뿌리일 가능성이 높다.

# 확인 결과 (2026-08-14 · A·B·D 훑음 · 코드 수정 없음)

## 🔴 A-1. **오늘 고친 버그가 합짐 판정 경로에 그대로 남아 있다** — 가장 큰 것

`OrderEvaluator.ts:110~137` 이 **경유지를 손으로 조립한다.** `composeMergedRoute` 를 안 쓴다.

```ts
const allPickups = [
    { x: activeMain.pickupX!, ... },              // 🔴 이미 상차했어도 넣는다
    ...activeSubs.map(c => ({ x: c.pickupX!, ... })),   // 🔴 여기도
    { x: securedOrder.pickupX!, ... },            // 후보 콜 — 이건 맞다
];
```

**이게 새 콜을 평가하는 주 경로다.** 상차를 마친 뒤 합짐 후보가 뜨면,
다녀온 상차지를 전부 경유지로 넣고 거리·시간을 잰다.

`composeMergedRoute` 의 주석이 그 결과를 이미 적어 두었다 —
*"거리와 시간이 부풀고, 그 값으로 우회 예산을 재니 **합짐 판정이 통째로 틀어진다.**"*

같은 파일 103행에 **전에도 한 번 놓쳤다**는 기록이 있다:
*"EE 리팩터링에서 composeMergedRoute 를 쓰는 곳만 통일하고 여기를 놓쳤다."*
**같은 파일이 같은 이유로 두 번 놓쳤다.**

→ 기사님 증상 ①(합짐 하나 완료 후 오작동)·②(잘못된 콜이 올라옴) 둘 다와 이어질 수 있다.
   판정이 부풀면 꿀콜이 똥콜이 되고, 순서가 틀어진다.

# 수정안 + 증명 방법 (2026-08-14 · 착수 전 정의)

## 먼저 — **"고쳤다"의 등급을 정한다**

오늘 반복된 문제는 **L1·L2 만 하고 "고쳤다"고 말한 것**이다.
앞으로 각 수정은 **어느 등급까지 갔는지** 반드시 함께 적는다.

| 등급 | 무엇을 증명하나 | 도구 | 한계 |
|---|---|---|---|
| **L1 규칙** | 코드의 *모양*을 고정 (되돌리면 깨진다) | `jest` 코드 스캔 | 🔴 **동작을 증명하지 않는다** |
| **L2 값** | 순수 함수에 값을 넣어 결과 확인 | `jest` | 조립된 시스템은 아니다 |
| **L3 시나리오** | 진짜 서버를 띄워 콜 생애를 돌림 | `pnpm scenario` | 앱은 없다 |
| **L4 실물** | 기사님 운행에서 그 줄이 찍힘 | 서버 로그 파일 | — |

🔴 **L4 를 못 본 것은 "고쳤다"가 아니라 "고쳤을 것이다"** 라고 적는다.

## ① `OrderEvaluator` 경유지 손조립 제거 — **가장 먼저**

**바꿀 것** — 손조립을 지우고 `composeMergedRoute` 를 쓴다.
그 함수의 `extra` 파라미터가 *"후보 콜은 아직 안 실었으므로 상차지를 남긴다"* 라고
**정확히 이 호출부를 위해** 만들어져 있는데 정작 여기가 안 쓴다.

```ts
const result = await composeMergedRoute({
    calls: activeCalls,          // 이미 상차한 콜의 상차지는 함수가 알아서 뺀다
    extra: securedOrder,         // 후보 콜 — 상차지를 남긴다
    driverLocation: session.driverLocation,
    priority: routingOptions.defaultPriority,
    carType: routingOptions.carType,
});
if (!result) { /* 좌표가 없다 — 기존 실패 경로 */ }
```
반환 타입은 같다(`calculateDetourRoute` 를 그대로 돌려준다). 쓰는 필드는 `distDiffKm` 하나.
⚠️ `null` 을 돌려줄 수 있으므로 방어가 하나 는다.

**증명**

| 등급 | 무엇을 확인 |
|---|---|
| L1 | `OrderEvaluator` 안에 `calculateDetourRoute(` 직접 호출과 `allPickups` 손조립이 **없다** |
| L1 | 경유지를 조립하는 곳은 `routeComposer` **하나뿐**이다 (전 레포 훑기) |
| L2 | `composeMergedRoute` 에 `ORDER_PICKED_UP` 콜 + 후보를 넣으면 → 실은 콜의 **상차지가 waypoints 에 없고**, 후보의 상차지는 **있다** |
| L3 | 시나리오에 **"상차 후 합짐 후보 평가"** 단계를 새로 넣는다 — 지금 없다 |
| L4 | 로그에 `🛣️ [경로] 이미 상차한 콜 N건의 상차지를 경유지에서 제외` 가 **평가 때도** 찍힌다 |

🔴 L2 를 카카오 호출 없이 하려면 **경유지 조립부를 순수 함수로 떼야 한다**
(`buildSoloRouteUrl` 을 뗀 것과 같은 방식). 그게 이 수정의 실제 작업량이다.

## ② 아무도 안 쏘는데 열려 있는 문 둘

**바꿀 것 — 기사님 결정 필요**

| 문 | 안 | 밖 |
|---|---|---|
| `update-my-location` | **지운다** (앱은 REST 피기백이라 소켓을 안 쓴다) | `processDriverMovement` 로 태운다 |
| `dispatch-complete` | **지운다** (완료는 마일스톤 `DELIVERED` 가 한다) | 남긴다 |

지우는 쪽을 권한다 — **문이 둘이면 안전장치를 우회하는 길이 생긴다.**
다만 되돌리기 어려우니 확인을 받는다.

**증명** — L1 ④의 검사가 그대로 증명이 된다(검사가 0건이 되면 문이 닫힌 것).

---

## ③ `pnpm audit:dead` 를 관제웹까지

**바꿀 것** — 지금 서버만 본다. 관제웹의 ① 안 쓰는 export ② `any` 로 받는 공유 상태를 추가.

**증명** — L1. **만들자마자 무언가를 잡아야 한다.** 0건이면 검사가 안 도는 것을 의심한다
(`audit:dead` 는 만들 때 네 건을 잡았다).

---

## ④ `pnpm audit:socket` 의 네 번째 방향 — **가장 값싸다**

**바꿀 것** — `서버 on` 중 **아무도 emit 하지 않는** 이벤트를 보고한다.
Socket.IO 내장(`disconnect`·`connect`·`error`)은 사유와 함께 allowlist 에 둔다
(`audit:dead` 의 `KEEP` 과 같은 방식 — **사유 없이는 못 넣는다**).

**증명** — 🔴 **만들자마자 지금 있는 2건(`update-my-location`·`dispatch-complete`)을 잡아야 한다.**
안 잡히면 검사가 틀린 것이다. ②를 고친 뒤 0건이 되는 것까지가 한 짝이다.

> ③④를 먼저 했으면 ①②가 자동으로 걸렸다. 앞으로를 위해 **가장 값싼 투자**다.

---

## ⑤ 서버가 받은 위치를 기록한다 — D 그룹 확인의 전제

**바꿀 것 — 기사님 결정 필요 (빈도)**

지금 `session.driverLocation = currentGPS` 는 **검증도 로그도 없다.**
매초 들어오므로 그대로 찍으면 로그가 부풀 것이다. 셋 중 하나:

| 안 | 남기는 것 | 하루 분량(대략) |
|---|---|---|
| ㉮ 이동이 있을 때만 | 좌표·이동거리·출처 | 중간 |
| ㉯ **뒤로 갔을 때만** | 후퇴한 거리 | 아주 작음 · **D 그룹만 겨냥** |
| ㉰ 매번 | 전부 | 큼 |

㉯를 권한다 — D 그룹의 증상(순간이동·파이프 둘·11669km/h)은 **전부 "뒤로 갔다"로 나타난다.**
평소엔 조용하고 문제가 났을 때만 남는다.

**증명**

| 등급 | 무엇을 확인 |
|---|---|
| L2 | 뒤로 가는 좌표열을 넣으면 경고가 나오고, 앞으로만 가면 안 나온다 |
| L4 | 기사님 운행 로그에 **경고가 하나도 없다** → D 그룹이 그제서야 🟢 가 된다 |

---

## 착수 순서 (권고)

```
④ 소켓 검사 사각지대   ← 값싸고, ②를 자동으로 잡는다
② 열린 문 둘 닫기      ← ④가 0건이 되는 것으로 증명
① OrderEvaluator      ← 지금 매 합짐마다 틀린 판정을 내고 있다 (가장 큰 손해)
⑤ 위치 기록           ← D 그룹 확인의 전제
③ 관제웹 죽은 코드 검사
```

🔴 **①은 L3(시나리오 단계 신설)까지 하고 나서야 "고쳤을 것이다"라고 적는다.**
L4 는 기사님이 상차 후 합짐을 한 번 잡으셔야 나온다.
