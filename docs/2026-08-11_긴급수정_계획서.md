# 긴급 수정 계획서 — 세션 복구 · 적재 반영

작성 2026-08-11 · 대상 브랜치 `phase0-2-cleanup-and-status-fix` · **배포 보류 중**

---

## 1. 왜 이 문서가 있는가

Phase 8.5 재설계를 마친 뒤, 실제 서버(`scen.db`, 포트 4012)에 소켓으로 붙어
콜 하나의 생애를 끝까지 돌리는 시나리오 검증을 했다. 화면 로직은 정상이었지만
**서버 쪽에서 배포하면 안 되는 결함 네 개**가 나왔다.

네 개 중 셋은 **같은 실수의 반복**이다 — 파생 계산은 고쳤는데 **그 입구의 관문을 안 고쳤다.**
그래서 이 문서는 개별 수정뿐 아니라 **같은 실수가 다시 나지 않게 하는 구조**까지 범위에 넣는다.

## 2. 확인된 사실

전부 실제 서버에서 재현했다. 추측이 아니다.

| # | 증상 | 재현 결과 | 심각도 |
|---|---|---|---|
| **A** | 상차한 콜이 새로고침하면 사라진다 | `ORDER_PICKED_UP` 로 두고 재접속 → HTTP 0건 · 소켓 0/0 · `dispatchPhase=STANDBY` · 차종 `1t` 포함 개방 · `capacityConfidence=CONFIRMED` | 🔴 치명 |
| **B** | 어제 잡은 콜이 통째로 사라진다 | 어제 19:55 상차 콜이 **상태로 한 번, 날짜로 또 한 번** 걸러짐 | 🔴 치명 |
| **C** | 잔여 용량이 짐 신고를 무시 | 파레트 2개 → 5개(2.5배)로 바꿔도 `["오토바이","다마스","라보","승용차"] ESTIMATED` 고정. 필터 재파생을 강제해도 동일 | 🔴 높음 |
| **D** | 불일치 경고가 절대 안 뜬다 | 통화 2개 vs 현장 5개 → `cargo-mismatch` **0건** | 🔴 높음 |
| **E** | 짐을 저장해도 필터가 재파생 안 됨 | `save-cargo-report` 가 `updateActiveFilter` 를 호출하지 않음 | 🟡 중간 |
| **F** | **착불 현금을 받아도 기록할 곳이 없다** | 관제웹은 안내 문구뿐 · `unpaidAmount`/`settlementStatus` 를 **쓰는 경로가 없음**(읽기만). 기사님 답변으로 드러남 | 🔴 높음 (돈) |

### 정상 동작으로 확인된 것 (건드리지 않는다)

6단계 진행 파생(`0→6`) · 상태 전이 · 멱등성(중복·역행 보고 무시) · 완료 후 필터 복귀
(`GATHERING→STANDBY`) · 방출 · 합짐 2건 다중 경유지 경로 · `filter-init` 1회 · `handler-error` 0건

> ⚠️ 검증 중 `dispatchPhase` 가 안 풀린다고 본 것은 **검사기가 `filter-updated` 를
> `filter-update` 로 잘못 듣던 것**이었다. 제품은 정상이다. 이 문서에 남겨 같은 오판을 막는다.

## 3. 근본 원인

### A·B — 상태 목록을 손으로 두 벌 관리했다

[`dispatchEngine.ts:626`](../onedal-web/server/src/services/dispatchEngine.ts) 복구 쿼리:

```sql
status IN ('ORDER_CONFIRMED','ORDER_COMPLETED','ORDER_RELEASED','ORDER_CANCELED','ORDER_FORCE_CANCELED')
--          ORDER_PICKED_UP · ORDER_DELIVERED 가 없다
AND o.timestamp >= ?   -- 오늘 자정
```

Phase 8.3 에서 상태 두 개를 새로 만들면서 이 목록에 추가하는 걸 빠뜨렸다.
`shared` 에 이미 `EVALUATING_STATUSES` · `TERMINAL_STATUSES` 가 있는데도
**여기만 손으로 나열해서** 둘이 갈라졌다.

### C·D — 단위 체계를 옮기면서 관문 두 개를 안 고쳤다

`sizeClass`(소·중·대) → `unit`(파레트·라면박스…) 전환 때 **계산 함수는 고쳤다.**

```ts
// shared/src/index.ts:167 — ✅ 제대로 고쳐져 있다
export function cargoPoints(r) {
    if (r.unit) return unitPoints(r.unit, r.quantity);   // 새 단위 우선
    if (!r.sizeClass) return 0;
    ...
}
```

그런데 **그 함수를 부르기 전의 관문 두 곳이 옛 필드에 남았다.**

```ts
// server/src/core/helpers.ts:48
if (chosen?.sizeClass) { points += cargoPoints(chosen); }   // 🔴 항상 false
else { points += 차종추정; anyEstimated = true; }

// shared/src/index.ts:179
if (!declared?.sizeClass || !actual?.sizeClass) return null;  // 🔴 항상 null
```

화면(`StopCallSheet`)은 `sizeClass` 를 **한 번도 보내지 않는다**(전수 확인).
그래서 두 관문 모두 영원히 닫혀 있다.

**결과:** `CargoMismatchBanner` · `resolve-cargo-mismatch` · 🚨 UI 가 전부 도달 불가능한 코드다.
그리고 합짐 2건이면 만재로 추정해 `["오토바이"]` 만 남는다 —
Phase 8.4 가 *"놓치던 합짐 기회를 연다"* 고 한 것의 **정확히 반대**가 되어 있다.

## 4. 이번에 지킬 원칙

세 번째 반복이므로, 고치는 것으로 끝내지 않는다.

1. **목록을 손으로 나열하지 않는다.** 상태 목록은 `shared` 의 단일 출처에서 파생시킨다.
2. **관문은 필드가 아니라 계산 함수로 건다.** `if (x.sizeClass)` 가 아니라 `if (cargoPoints(x) > 0)`.
   그러면 단위 체계를 또 바꿔도 관문은 안 깨진다.
3. **새 상태를 추가하면 테스트가 깨지게 만든다.** 결정을 강제하는 테스트를 둔다.
4. **찾은 방법을 레포에 남긴다.** 이 결함들은 `tsc`·`jest` 를 전부 통과했고
   **시나리오를 돌려서만** 나왔다. 그 검사기를 재사용 가능하게 넣는다.

### T1. 복구 대상 상태를 단일 출처로 (A) — 🔴 최우선

**바꿀 것**

`shared/src/index.ts` 에 추가:

```ts
 *
 * 🔴 손으로 나열하지 않는다. 2026-08-11 에 Phase 8.3 이 만든
```

`ALL_ORDER_STATUSES` 런타임 배열이 없으면 함께 만든다 (타입만으로는 런타임에 못 쓴다).

**적용처 — 2곳이 아니라 3곳이다** ⚠️ *(계획 재검증에서 추가로 발견, 2026-08-11)*

| # | 파일 | 지금 | 바꾼 뒤 |
|---|---|---|---|
| 1 | `server/services/dispatchEngine.ts:626` | 5개 하드코딩 | `RESTORABLE_STATUSES` 로 `IN (?,?,…)` 바인딩 |
| 2 | `server/routes/orders.ts:36` | `('ORDER_CONFIRMED','ORDER_COMPLETED')` | 동일 |
| 3 | **`client-app/pages/Dashboard.tsx:44`** | `isTerminal(s) \|\| s === 'ORDER_CONFIRMED'` | `!isEvaluating(s)` |

3번을 처음에 놓쳤다. **서버 두 곳만 고치면 관제웹이 다시 걸러낸다.**

```ts
// Dashboard.tsx:44 — HTTP 이력을 합치는 곳
orders.filter(o => isTerminal(o.status) || o.status === 'ORDER_CONFIRMED')
//                                          🔴 ORDER_PICKED_UP 이 두 조건 다 아니다 → 버려진다
```

바로 아래 줄에서 소켓 `liveCalls` 가 덮어쓰므로 **평소에는 깜빡임으로만 보인다.**
하지만 소켓 sync 가 늦거나 유실되면 상차한 콜이 화면에서 사라진다.
무엇보다 **같은 목록이 세 군데 손으로 적혀 있다**는 것이 이번 사고의 본질이다.

**검증** — `ORDER_PICKED_UP` 상태로 재접속했을 때
소켓 `active` 에 남고 · `dispatchPhase=GATHERING` 유지 · 차종이 개방되지 않을 것.
**추가로** 소켓을 끊은 채 HTTP 만으로도 진행 중 목록에 뜰 것.

**리스크** — 종결 콜이 세션 메모리에 더 많이 올라온다.
`getActiveCalls()` 가 `isTerminal` 로 거르므로 적재·경로 계산에는 영향이 없다
(복구 코드가 이미 `getActiveCalls()` 기준으로 궤적을 복원함을 확인했다).
`ORDER_DELIVERED` 가 `TERMINAL_STATUSES` 에 들어 있는 것도 확인했다.
다만 **메모리 사용량과 부트스트랩 시간**은 다시 재보고, 필요하면 T5 의 상한으로 조절한다.

**받아들임 기준**
- [ ] 상차 후 새로고침 → 진행 중 탭에 그대로
- [ ] 하차 후 새로고침 → **완료됨 탭**에 그대로 (지금은 `ORDER_COMPLETED` 만 남는다)
- [ ] 부트스트랩 시간이 수정 전 대비 2배를 넘지 않을 것

### T3. 불일치 관문을 계산 함수로 (D) — 🔴

`shared/src/index.ts:179`

```ts
export function cargoMismatchRatio(declared?, actual?): number | null {
    if (!declared || !actual) return null;
    const d = cargoPoints(declared);
    const a = cargoPoints(actual);
    if (d === 0 || a === 0) return null;   // 한쪽이라도 짐 정보가 없으면 비교 불가
    return a / d;
}
```

**부수 작업** — `socketHandlers.ts:197` 로그가 `report.sizeClass` 를 찍어 항상 `-` 로 나온다.
`unit × quantity` 로 바꾼다. (기능 아님, 로그 신뢰도)

**⚠️ 하차지는 여전히 `null` 이 나온다 — 그게 맞다** *(재검증에서 확인)*

`StopCallSheet` 는 부피를 **상차지에서만** 보낸다.

```ts
unit:     isPickup ? eff.unit     : undefined,
quantity: isPickup ? eff.quantity : undefined,
```

기사님 설계 그대로다 — *"하차지 통화 시 물건의 크기와 부피 성질은 이미 파악된 상태이고
시간과 상하차 방법만 관심사."* 그래서 하차지 `cargoPoints` 는 0 이고 비교가 성립하지 않는다.

**이걸 문서에 못박아 둔다.** 안 그러면 나중에 "하차지 불일치가 안 뜬다"를 버그로 오인해
`unit` 을 하차지에도 받게 만들 것이다. 불일치 판정은 **상차지 전용**이다.

**검증** — 상차지에서 통화 2개 → 현장 5개 저장 시 `cargo-mismatch` 가 `ratio=2.5` 로 도착할 것.
`CargoMismatchBanner` 가 뜨고 `resolve-cargo-mismatch` 왕복이 될 것.
하차지 저장으로는 **아무 일도 일어나지 않을 것**(정상).

### T5. 영업일 최소 안전판 (B 일부) — 🔴 치명이지만 설계가 필요

Phase 7(영업일) 본체는 시각 표준 통일(7.5)이 선행이라 이번 범위 밖이다.
대신 **가장 위험한 구멍만** 막는다.

```
미완료 콜(ORDER_CONFIRMED · ORDER_PICKED_UP) → 날짜와 무관하게 복구
종결 콜                                      → 지금처럼 오늘 것만
```

전날 상차해서 다음날 배송하는 운행이 이것만으로 살아난다.

**상한을 둔다** — 무기한이면 몇 달 전 미완료 콜이 되살아난다.
3일은 임의값이므로 **기사님 확인이 필요하다.**

**⚠️ 어느 시각 필드로 재는가** *(재검증에서 발견한 구멍)*

초안은 상한을 `capturedAt` 으로, 기존 필터는 `timestamp` 로 써서 **두 필드가 섞여 있었다.**
이건 Phase 7.5 가 정리하려는 바로 그 문제(시각 포맷 4종)를 새로 만드는 짓이다.

→ **기존 쿼리와 같은 `o.timestamp` 하나로 통일한다.** 정확해서가 아니라
   **이미 그 필드로 걸러 온 동작을 바꾸지 않기 위해서**다.
   `timestamp` 는 앱이 준 값이라 신뢰도가 낮지만, 그 교정은 Phase 7.5 의 일이다.
   섞어 쓰면 T5 를 지울 때 무엇을 지워야 하는지 알 수 없게 된다.

**⚠️ T5 는 복구 코드의 전제 하나를 무효화한다**

`dispatchEngine.ts` 복구부 끝에 이런 주석이 있다.

```
// (복구 쿼리가 오늘 것만 가져오므로 어제 상태가 살아날 우려도 없다)
```

T5 가 어제 미완료 콜을 되살리므로 **이 문장이 거짓이 된다.**
주석을 고치는 데 그치지 말고, 그 전제에 기대던 로직이 있는지 확인한다 —
상태는 `getActiveCalls()` 에서 매번 파생되므로 괜찮을 것으로 보이지만,
**"괜찮을 것"으로 넘기다 이번 사고가 났다.** 복구 직후 파생 결과를 시나리오로 확인한다.

> 이 안전판은 Phase 7 이 들어오면 **삭제한다.** 임시라는 것을 코드 주석에 명시한다.

### ① T5 상한 = **3일** — 확정

```
복구 대상에서 밀려난 미완료 콜이 있으면
  · 서버 로그에 경고 (콜 ID · 상태 · 며칠 지났는지)
  · 관제웹에 한 줄 배너 — "3일 넘은 미완료 콜 N건이 화면에서 빠졌습니다"
```

조용한 소실은 만들지 않는다. 기사님이 모르는 채로 콜을 잃는 일이 이번 사고의 본질이었다.

### ② 착불 현금은 **하차 완료를 누르기 전에** 받는다 — 확정

**🔴 그런데 그 기록 수단이 없다** — 이 답변으로 드러난 공백이다.

### T8. 착불 수령 기록 (F) — 🔴 돈이 걸린다

**어디에** — 하차 완료 단계(`DELIVERED`)의 주 버튼 **바로 위**.
기사님이 현금을 받는 그 순간, 완료를 누르기 직전에 눈에 들어와야 한다.

```
착불 111,000원
  [ 받았음 ]   [ 못 받음 · 미수 ]

```

**무엇을 남기나** — `orders.settlementStatus`(수령/미수) · `unpaidAmount` · `settledAt`.

0 원으로 조용히 넘기지 않는다.

**범위 밖** — 입금 확인, 사무실 정산 대사. 그건 Phase 8 정산의 일이다.
