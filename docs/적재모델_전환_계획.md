# 적재 모델 전환 — 라면박스 체계 (⑤-4 문서, 코드 전 확정용)

> 원천: [용어집](용어집.md) §5·§7 (기사님 확정 2026-08-17).
> ⑤-4 규칙: **스키마·값·시점·화면 넷이 확정되기 전에 코드를 시작하지 않는다.**
> 이 문서 끝의 질문 4개에 답이 달리면 그때 코드로 간다.

## 왜 바꾸나 — 지금 코드는 세 번째 체계다

같은 값이 세 벌 존재해 왔다:

| 체계 | 어디에 | 1t | 라보 | 다마스 | 승용차 | 상태 |
|---|---|---|---|---|---|---|
| 30점 축 (08-09) | `VEHICLE_CAPACITY` — **지금 코드** | 30 | 15 (½) | 10 (⅓) | 6 (0.2) | 돌고 있음 |
| 5칸 체계 (08-13) | 메모리·문서 | 5칸 | 2칸 (0.4) | 1칸 (0.2) | 1칸 (0.2) | 코드에 못 들어감 |
| **라면박스 (08-17)** | **용어집 — 확정** | **100** | **40 (0.4)** | **30 (0.3)** | **5 (0.05)** | 이걸로 통일 |

비율이 실제로 다르다 — 라보 ½→0.4, 다마스 ⅓→0.3, 승용차 0.2→0.05.
**적재가 판정 색의 한 요소이므로, 이 차이는 색을 바꾼다.**

## ① 스키마 — 값이 어디 사는가

**제안: `shared/src/vehicles.ts`·`cargoUnits.ts` 의 상수표** (지금 자리 그대로, 숫자만 교체).

- 근거: 차의 물리·짐의 부피는 **도로에서 조정할 값이 아니라 측정된 사실**이다.
  기사님이 조정하는 것(가중치 `weights.slots`)은 이미 `user_judgment` DB에 있다.
- 용어집 §5·§7 이 원천 — 숫자를 고치려면 용어집을 고치고 코드가 따라간다.
  `glossary.test.ts` 방식으로 **용어집 표와 코드 상수가 같은지 검사**를 붙인다.
- 대안(DB + 설정 탭)은 ④ 질문에서 기사님이 고르시면 그렇게 한다.

## ② 값 — 근거는 용어집

### 차종 용량 (`VEHICLE_CAPACITY` → 박스 단위)

| 차종 | 지금(30점) | 새 값(박스) | 근거 |
|---|---:|---:|---|
| 오토바이 | 0 | **1** | 용어집 §7 (조수석 0점 규칙은 폐기 — 용어집이 1로 확정) |
| 승용차 | 6 | **5** | 용어집 §7 |
| 다마스 | 10 | **30** | 〃 |
| 라보 | 15 | **40** | 〃 |
| 1t | 30 | **100** | 파레트 2개(80) + 여유 20 |
| 1.4t~25t·특수 | 톤당 30 | **❓ 질문 2** | 용어집에 없음 |

### 짐 단위 (`CARGO_UNIT_POINTS` → 박스 단위)

| 단위 | 지금(점) | 지금을 1t 비율로 | 새 값(박스) | 차이 |
|---|---:|---:|---:|---|
| 파레트 | 15 | ½ t | **40** | 비율 같음 (2개=80, +여유20=만재) |
| 라면박스 | 0.25 | 1/120 t | **1** | 120개→**100개**가 1t |
| 마대 | 1 | 박스 4개 | **1** | 🔴 **4배 줄어듦** |
| 톤백 | 30 | **만재** | **40** | 🔴 **만재→0.4대** — 콜을 더 받게 됨 |
| 쇼핑백 | 0.1 | | **0.2** | |
| 서류봉투 | 0.02 | | **0.2** | |
| 기타 | 0 (=모름) | | **0 (유지)** | "환산 불가" 표시 — 차종 추정으로 폴백 |

- 선택지 5개(파레트·라면박스·마대·서류봉투·기타)와 옛 단위 읽기(톤백·쇼핑백)는 **그대로** —
  기사님 2026-08-12 결정. 숫자만 바뀐다.
- 콜의 짐 추정(통화 전, 표시 차종으로): 1t 콜 = **80박스(1t짐)**, 라보 콜 = **❓ 질문 1**

## ③ 시점 — 언제 읽고 쓰는가 (지금과 같다, 단위만 바뀜)

| 언제 | 무엇 |
|---|---|
| 콜 평가 시 | 잡은 콜들의 박스 합 → 남은 용량 → 판정의 적재 요소 |
| 통화 신고 시 | 신고 단위×수량으로 갱신 (DECLARED → ACTUAL 이 이김) |
| 필터 파생 시 | 남은 용량 → 허용 차종 목록 (`getRemainingCapacityTypes…`) — 앱 피기백 |
| 하차 완료 시 | 그 콜의 박스만큼 용량 복귀 |
| 사이클 종료 시 | 0 으로 리셋 |

DB 마이그레이션: **없음** (테스트 단계). `stop_cargo_reports` 의 unit·quantity 는 원자료라 그대로 —
점수 환산은 읽을 때 하므로 옛 행도 새 표로 다시 계산된다.

## ✅ 기사님 확정 (2026-08-17) — 넷 다 답을 받아 구현 완료

1. 콜의 짐 추정 = **차종 용량 그대로** (라보 40 · 다마스 30 · 승용차 5), 1t 콜만 80
2. 큰 차종 = **톤당 100박스 비례**
3. 화면 표기 = **박스만**
4. 오토바이 짐 = **1박스** (조수석 무점유 규칙 폐기)

구현하며 확정된 것 하나 더:
- **그릇 ≠ 짐** — 내 1t 트럭의 그릇은 `TRUCK_CAPACITY_SLOTS = 100`, "1t" 콜의 짐은
  `VEHICLE_CAPACITY['1t'] = 80`. 옛 축은 한 표가 둘을 겸했는데 이제 갈라졌다
  (`typesFittingIn` 이 그릇을 짐 표로 읽으면 자투리 20박스를 영영 못 쓴다)
- **상하차 정차 재보정** — 점수당 분을 물리 기준으로: 수작업 = 박스당 22.5초(옛 라면박스
  기준 보존), 지게차·호이스트 = 파레트 기준 보존. 같은 짐이면 옛 축과 같은 분이 나온다.
  단 수작업 파레트 2개는 60분→45분 (박스 기준으로 통일한 결과)
- 같은 뜻의 표 두 벌(`VEHICLE_SLOTS` 5칸 · `VEHICLE_CAPACITY` 30점)을
  `VEHICLE_CAPACITY` 하나로 합쳤다 (규칙 ③)
