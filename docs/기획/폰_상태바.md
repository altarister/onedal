# 폰 상태 바 — 관제웹이 폰에 대해 보여 주는 모든 것

> **2026-09-02 기사님과 함께 정리.** 코드에서 요소를 전수로 꺼내 컬럼을 붙였다.
> 🆕 표시는 **아직 코드에 없다** — 만들 것이지 있는 것이 아니다.
> 화면 파일은 `client-app/src/components/dashboard/DeviceControlPanel.tsx` 다.

기사님: *"폰 상태 바인데 여기서 설정을 하니까 문제인 것 같고,
통신 방법이 수동인데 즉시 반영을 원하는 것이 문제인 듯한데."*

이 한 문장이 이 문서의 출발점이다. 상태 바에는 **폰이 말해 준 사실**과
**우리가 정한 목표**가 섞여 있었고, 둘을 같은 모양으로 그려서 목표가 사실처럼 보였다.

> **필터 판에서 이 컬럼을 그대로 쓰면** 딤드 설계가 한 번에 된다.

### 컬럼이 묻는 것

| 컬럼 | 묻는 것 |
|---|---|
| **앱** | 이 사실의 **원천이 앱인가** — 폰이 켜지고 망에 붙고 화면을 읽는 것은 전부 앱발이다. 서버가 가공해도 원천은 앱이다 |
| **서버** | 서버가 **자기만 아는 것**을 보탰나 — 등록해 둔 이름, 서버 시계. 앱은 모르는 값이다 |
| **관제** | 관제웹이 **바꾸는가** |

🔴 **«서버가 판정한다»와 «서버가 원천이다»는 다르다.** 서버가 `OFFLINE` 을 찍어도 그 원천은
*"앱이 말을 안 했다"* 이므로 앱발이다. 이 구분을 흐리면 **어디를 고쳐야 하는지**가 흐려진다.

## 2. 포함 관계 — 한 줄기

```
1 폰 이름
├ 5 앱 버전 🆕
└ 2 살아있나 ────── 3 조용한가 🆕 · 4 누적
  └ 6 화면 켜짐 💤
    └ 7 접근성 (이름 색)
      └ 8 배차망
        └ 9 화면명          ← 6과 한 배지로 표시한다
          ├ 10 앱 작업 단계 🆕
          └ 11 성적표

12 모드   ← 딴 줄기. 유일하게 «우리가 정한 것»
```

**위가 꺼지면 아래는 뜻이 없다.** 접근성이 ⚪면 8~11 은 옛 값이고, 화면이 💤면 9~11 이 없다.

### 🔴 6번이 7번 **위**에 있어야 하는 이유 (2026-08-22 기사님 확정)

화면이 꺼지면 노드가 0인 것이 **당연하다.** 그걸 «접근성 고장»이라 하면 폰을 끌 때마다
거짓 경고가 뜬다. 그래서 서버는 화면이 꺼져 있으면 접근성 판정을 **건너뛴다**
(`devices.ts` — `if (session.isScreenOn === false) { session.blindSince = undefined; return; }`).

그래서 «안 읽힘»의 이유가 **둘로 갈려 있다** — 💤(폰을 켜세요)와 ⚪(접근성을 켜세요).
할 일이 다르므로 갈라 두는 것이 맞다.

### 표시는 합치되 값은 가른다

6+9 를 배지 하나로 그리고(`[💤 화면 꺼짐]`), 8+11 도 «신선할 때만» 한 덩이로 그린다.
🔴 **표시를 합치는 것이지 값을 합치는 것이 아니다** — 값을 합치면 위의 판정이 무너진다.

### ✅ 1단계로 만든 것 (2026-09-02 · 관제웹·서버만 · 앱은 한 줄도 안 고쳤다)

**6+9 를 배지 하나로** — 고르는 일은 `shared/screenLabels.ts` 의 `deviceScreenBadge` 하나가 한다.
화면이 꺼지면 배지가 통째로 `💤 화면 꺼짐` 이 되고 **배차망·화면명은 함께 나가지 않는다** —
그 값은 화면이 꺼지기 **전에** 읽은 것이라, 함께 그리면 «읽지도 않고 단언하는» 것이 된다.
⚠️ **끊김이 화면 꺼짐보다 위다.** 말이 없는 폰에 «화면이 꺼졌다»고 적는 것도 단언이므로,
`OFFLINE` 이면 예전처럼 그린다 (끊김은 폰 이름의 빨간 깜빡임이 말한다).

**3번 «조용한가»** — 규칙 ⑤-4 의 다섯을 먼저 확정하고 만들었다.

| | 확정한 것 |
|---|---|
| ① 스키마 | `DeviceSession.prevSeen`(직전 보고 시각) — **메모리 세션만**, DB 에 안 적는다 |
| ② 값 | **30초** (기사님 확정 2026-09-02). 지어낸 값이 아니라 **생존신고 60초의 절반**이다 — 앱은 일이 생기면 그때 보내고(수초) 아무 일도 없으면 60초마다 보내므로, 간격이 그 중간값으로 나오는 일이 거의 없다 |
| ③ 시점 | `touchDeviceSession` 에서 `lastSeen` 을 덮기 **직전** 한 곳 |
| ④ 화면 | 폰 이름 바로 옆 `👀`/`⏱️` (표의 «2 안»). **화면이 꺼져 있어도 그린다** — 최대 60초를 기다려야 하는 것이 바로 그때다 |
| ⑤ 읽는 곳 | **관제웹의 이 배지 하나뿐** (`deviceQuietIcon`). 서버 판정도 앱도 안 읽는다 — «콜을 줄까»를 이걸로 정하기 시작하면 한 값이 두 질문을 답한다 |

**🖥️ 화면이 바뀐 보고는 서버 로그에 한 줄 남는다** (기사님 지시 2026-09-02:
*"페이지 바뀌거나 할 때 post 로 서버로 값을 보내는 거지? 그때 콘솔을 꼭 넣어서 트래킹 할 수 있게 해 줘."*)

```
🖥️ [화면 바뀜] 1234 · 픽커 홈 → 콜 리스트 · 직전 보고와 3.2초 만
```

간격이 함께 찍히므로 *"앱이 알아채는 데 얼마나 걸렸나"* 가 그 줄에서 바로 읽힌다 —
2026-09-02 에 정지 화면이 18.3초 걸린다는 것도 이 숫자로 알았다.
🔴 **판정(«조용/움직임»)은 로그에 안 적는다.** 사실(초)만 적는다 — 판정하는 곳은 하나여야 한다.

### ✅ 0단계 — 다섯을 정했다 (2026-09-02 · 규칙 ⑤-4)

**① 작업 단계는 다섯 칸** (기사님 확정). 앱 안엔 상태가 여섯인데, 관제에서 뜻이 있는 것만 추렸다.

| 칸 | 언제 | 화면 |
|---|---|---|
| 대기 | 아무 콜도 안 잡고 있다 | `대기` |
| 상세 보는 중 | 콜을 눌러 상세에 들어갔다 | `상세` |
| 팝업 | 상·하차지·적요를 걷는 중 | `팝업 2/3` |
| 판결 대기 | 서버 판결을 기다린다 | `판결 대기` |
| 안전취소 | 위약금 없이 무를 수 있는 30초 | `안전취소 12초` |

🔴 **«왜 멈췄나»가 그 한 칸에서 보여야 한다** — 간단히 세 칸으로 줄이면 «어느 팝업에서
막혔나»를 못 본다. 기사님은 운전 중 1~2초에 읽으시므로 **글자는 짧게, 숫자는 크게.**

**② 모드 «대답»은 값 그대로** — 필터처럼 «버전»을 쓰지 않는다. 필터가 버전을 쓰는 것은
본문이 커서 아끼려는 것인데, 모드는 글자 하나라 아낄 것이 없다. 앱이 매 보고에
«나 지금 ALARM이다»를 싣고, 서버가 **«내가 보낸 것»과 대조**하면 「적용중」이
저절로 파생된다 (규칙 ③ — 상태를 저장하지 말고 데이터에서 파생시킨다).

**③ 「적용중」이 안 풀릴 때는 10초 뒤 버튼만 다시 눌리게 한다** (기사님 «10초쯤»).
🔴 **글자는 «반영 안 됨»이라 쓰지 않는다** — 홈에 있는 폰은 실제로 나중에 반영되므로
그건 거짓말이 된다. `적용중 · 마지막 통신 42초 전` 처럼 **사실만** 적는다.

**④ 화면**은 위 표 그대로(10번 칸 · 9번 안). **⑤ 읽는 곳**은 관제웹의 그 칸 **하나뿐**이다 —
서버 판정은 계속 **목표값**으로 돈다. «적용 안 된 폰은 콜을 안 준다» 같은 것이 붙으면
한 값이 두 질문을 답하게 된다.

## 3. 방향은 둘뿐이다

기사님: *"post 방식의 통신을 하고 있어서 요청하지 않으면 변하지 않는 것도 알고 있는 거지?"*

### 앱 → 관제 (1~11) — **즉시 만들 수 있다**

```
앱이 알아챔 → POST → 서버가 받자마자 → 소켓 푸시(1초) → 관제웹
```

앱이 **변화를 알아채는 순간 쏘면** 된다. 오늘 홈에서 늦은 것은 *전달이 느려서가 아니라
앱이 못 알아채서*였다 — 그래서 9번만 반영 시간을 «앱이 알아챌 때»라고 적었다.

> ⚠️ **왜 못 알아채나**: 안드로이드 접근성은 화면을 캐시하고 그 캐시는 **이벤트가 와야** 버린다.
> 이벤트 없이 다시 읽으면 아까 그 화면을 준다. 2026-09-02 에 «몇 박자 뒤 다시 읽기»를
> 넣었다가 **18.3초 → 18.3초**, 전혀 안 나아져서 되돌렸다. 자세한 것은 `todo.md` 최상단.

### 관제 → 앱 → 관제 (12) — **왕복이라 즉시가 불가능하다**

```
①클릭 → ②서버가 들고 있음 → ③앱이 가지러 옴 → ④앱이 «받았다» 대답 → ⑤관제에 표시
        └────────── 이 사이가 «적용중» ──────────┘        └ 여기서 활성
```

②~④ 동안 서버는 *«보냈다»* 만 알고 *«적용됐다»* 는 모른다.
**그래서 버튼이 그 사이를 «적용중»으로 보여야 한다.**

지금은 ①에서 곧장 바뀐 것처럼 그린다 — 코드에도 그렇게 적혀 있다:
`// 즉각적인 UI 피드백을 위해 로컬 상태 선갱신 (낙관적 업데이트)` (`useDevices.ts`).
**폰이 받았는지 모르는 채로 «바뀌었다»고 그리는 것**이라, 2026-09-02 오전에 고친
«읽지도 않고 화면을 단언하던 것»과 같은 병이다.

🔴 **④가 지금 없다.** 앱이 «내가 이 모드다»를 대답하지 않는다.
필터에는 그 대답(`filterVersion`)이 있는데 모드에만 없는 **비대칭**이다.

## 4. 아직 없는 것 셋 — 전부 «앱 안에는 있는데 안 보낸다»

| | 앱 안의 값 | 지금 서버가 아는 것 |
|---|---|---|
| **5 앱 버전** | `AppInfo.versionLabel()` | `DeviceSession.version` 칸은 **있는데 아무도 안 채운다** |
| **10 작업 단계** | `isAutoActive` · `collectState`(팝업 3장) · `isDetailScrapSent` · `isWaitingForDecision` · 30초 타이머 · `isPreview` | `isHolding` **불리언 하나**로 눌려서 올라온다 |
| **12 모드 대답** | 앱이 받아서 적용은 한다 | **대답이 없다** |

🔴 셋 다 **앱을 고쳐야** 하므로 **한 번의 재배포에 모아서** 넣는다.

## 5. 이 표를 다시 쓸 때

- 요소가 늘면 **포함 관계 어디에 들어가는지**를 먼저 정한다. 위가 꺼지면 뜻이 없는가?
- «관제 ✓» 가 붙는 요소는 **반드시 왕복**이고, 따라서 **«적용중» 상태를 가진다**
- «앱 ✗» 인데 앱 안에 값이 있으면, 그것은 **구멍**이지 설계가 아니다
