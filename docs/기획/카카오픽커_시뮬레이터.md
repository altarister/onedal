## 0. 왜 만드나

픽커는 **되돌릴 창이 없다** (버튼 취소 없음 · 전화만 · 하루 5번).
그래서 앱의 픽커 경로를 실물로 시험하려면 한 번 한 번이 비싸다.

| 앱의 픽커 경로 | 지금 시험하는 법 | 시뮬이 생기면 |
|---|---|---|
| 리스트 수집 (`KakaoPickerParser.groupListNodes`·`parse`) | 실물 폰 · 단위검사(덤프 문제지) | 책상에서 원하는 카드를 흘린다 |
| 알람 → 상세 진입 → 미리보기 전송 (`sendPickerPreview`) | 실물에서 콜을 기다린다 | 문제지로 바로 |
| 「수락하기」 → 잡은 콜로 승격 (`reportPickerAccepted`) | **하루 5번 중 하나를 쓴다** | 몇 번이든 |
| 운행 단계 인식 (`KakaoPickerKeywords.stageOf`) | 실제 배송을 한 건 끝까지 | 버튼으로 단계를 넘긴다 |
| 🔴 **오더카드 요금을 안 누르는가** (`isListCardAnchor` · 09-13 라이브 오배차) | 재현 수단이 없다 | 오더카드를 켜서 일부로 띄운다 |

🔴 **시뮬은 앱의 픽커 경로를 시험하는 도구다 — 픽커를 흉내 내는 것 자체가 목적이 아니다.**
그러니 그리는 기준은 «실물과 똑같은 모양»이 아니라 **«앱이 읽는 글자·위치가 실물과 같은가»** 다.

## 1. 🔴 먼저 막힌 자리 — 앱은 시뮬 화면을 늘 «인성»으로 읽는다

앱 코드를 읽어 보니 이렇다 (폰에서 재현은 안 해 봤다):

```kotlin
// TargetApp.kt
"com.onedal.simulator" -> INSUNG          // 시뮬 패키지 = 인성으로 못박힘

// HijackService.kt → NetworkSwitchGate
// 화면 패키지의 배차망 ≠ 라디오 선택  →  라디오를 그 배차망으로 갈아탄다
```

그래서 시뮬에 픽커 화면을 그려도 **앱은 라디오를 인성으로 되돌리고 인성 파서로 읽는다.**
👉 **화물24시 시뮬도 같은 자리에 걸려 있을 것이다** (코드를 읽어서 한 추정이다 — 폰으로 확인할 것).

**고르셔야 할 것 — 셋 중 하나:**

| | 방법 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A** (추천) | `codeOfPackage("com.onedal.simulator") = null` — 시뮬에서는 **라디오가 원천** | 한 줄. 인성·24시·픽커 시뮬이 모두 풀린다 | 시뮬에서는 자동 전환이 없어진다 — 시뮬 첫 화면에서 고른 배차망과 앱 라디오를 기사님이 맞춰야 한다 |
| B | 시뮬 앱을 배차망별 패키지로 나눈다 (`com.onedal.simulator.picker` …) | 실물과 똑같이 «패키지가 곧 배차망» | 앱 셋을 따로 설치. 시뮬 첫 화면 한 장으로 합친 09-11 결정과 어긋난다 |
| C | 시뮬 화면에 배차망 표식 글자를 숨겨 두고 앱이 읽는다 | 자동 전환 유지 | 🔴 앱 판별에 **시뮬 전용 낱말**이 들어간다 — 공통 코드에 화면 글자를 박지 않는다(배차망_통합 §9-4) |

⚠️ A·B 모두 **`onedal-app/app/`(스캐너 영역)** 을 고친다 — 시뮬 담당 영역 밖이다. 스캐너 담당에게 알리고 넘긴다.

## 2. 🔴 둘째로 막힌 자리 — 픽커 파서는 «글자»와 함께 «위치»를 읽는다

인성 파서와 달리, 픽커 파서는 **화면 픽셀 위치**에 기대고 있다:

| 앱이 기대는 것 | 실물 값 (1080 폭 폰) | 시뮬이 맞춰야 할 것 |
|---|---|---|
| 요금 닻 = 쉼표 든 숫자 + **중심 X ≥ 600px** | 오른쪽 정렬 | 요금을 오른쪽 끝에 |
| 한 카드 = 요금 중심 **±60px 띠** (줄 간격 ±35 · 다음 카드 ±163) | | 카드 높이·줄 간격을 **기기 픽셀로** 맞춘다 |
| 「리스트 설정」 머리줄 **아래**의 요금만 리스트 카드 | 오더카드는 머리줄 위 | 머리줄을 오더카드 띠와 카드 목록 **사이**에 |
| 글자 노드가 **낱개**로 온다 (네이티브 TextView) | | 🔴 웹뷰는 글자를 뭉쳐 올리기도 한다 — **글자마다 요소 하나** |

CSS px → 기기 px 배율(폰 해상도·밀도)이 섞이므로 **눈대중으로 맞추지 않는다.**
→ 3단계의 **덤프 대조**(`uiautomator dump`로 시뮬 화면과 실물 덤프 `log/카카오픽커/화면덤프`를 나란히)가 완료 조건이다.

## 3. 만들 화면 — 실물 캡처와 앱 낱말에 1:1로 묶는다

🔴 **앱이 이미 쓰는 낱말은 한 글자도 바꾸지 않는다** — 바꾸면 시뮬이 앱을 시험하는 게 아니라 속이게 된다.
열 이름의 번호는 `ex_images/카카오픽커/실물_2026/` 캡처 번호다.

### 3-1. 수락 전

| 화면 | 실물 | 앱이 알아보는 낱말 (원천) | 담을 것 |
|---|---|---|---|
| 홈 | 01 | `시작하기` (`STAGE_WORDS`) | 「시작하기」 버튼 하나 → 리스트 |
| **리스트** | 02·11·13 | `리스트 설정` (`listRequired`) | 위 탭(퀵 배송·도보배송·대리·한차배송) · 「퀵 오더카드 대기 중…」 띠 · 머리줄 `리스트 설정 / 높은 가격순 / 20km` · 카드들 · 뜬 메뉴 `서포트모드·카드설정·수요지도` · 아래 탭 `신규 / 내 오더 N` |
| 리스트 카드 | 02 | 요금 `^\d{1,3}(,\d{3})+$` · `KM_REGEX`/`M_REGEX` · `TAG_WORDS` · `ITEM_SIZES` | 윗줄 `퀵 [단거리] [준비 N분\|준비 완료] 소형 [예약 17:00]` + 오른쪽 도착 **시** / 아랫줄 `15.2km 분당 서현1` + 도착 **동** / 오른쪽 요금 |

### 3-2. 수락 후 — 기사님이 손으로 넘긴다

앱은 알람 모드에서 「수락하기」를 **절대 안 누른다**(`clickSafe`). 그러니 시뮬에서도 **계약은 사람 손가락**이다.
「밀어서 …」는 실물이 스와이프지만 시뮬에서는 **끌기와 탭 둘 다** 받는다 (시험용).

| 단계 (`Stage`) | 실물 | 앱 낱말 | 시뮬 화면 |
|---|---|---|---|
| (수락 직후) | 15 | — | 「내 오더」 탭으로 넘어간다 · `신규 / 내 오더 1` |
| `TO_PICKUP` | 16·18 | `픽업 준비` · `픽업지 근처에` | `픽업 준비 N분 남음` → `픽업 준비 완료` · `배송 N분 남음` · 상단 `배정 취소` |
| `AT_PICKUP` | 17 | `밀어서 픽업 완료` | 시트: `오더 확인 <번호>` · 배송지 · 배송 물품 · 고객 요청 · 「밀어서 픽업 완료」 |
| (취소 시도) | 19 | — | `배정 취소 불가` 팝업 |
| `TO_DROPOFF` | 21 | `배송 시간` · `물품 파손` | `배송 시간 N분 남음` · `물품 파손/분실을 주의해 이동해주세요` |
| `AT_DROPOFF` | 22 | `밀어서 사진 촬영` | 시트 + 「밀어서 사진 촬영」 |
| (사진·문자) | 24~30 | — | **한 장으로 줄인다** — 「배송 완료」 버튼 하나. 카메라·문자앱은 픽커 밖이라 앱이 안 읽는다 |
| `DONE` | 31 | `물품이 안전하게 전달` | `배송 완료 N P` · 오늘 배송·수익 → 리스트로 |

🔴 **주의: 「배송」 한 낱말을 아무 데나 쓰지 않는다.** 앱은 `배송 시간`으로 배송 중을 가르는데,
픽업 이동 화면에도 `배송 33분 남음`이 있다 — 시뮬이 문구를 바꾸면 **앱 검사가 아니라 시뮬 버그**를 보게 된다.

## 4. 데이터 — 무엇을 더하나

### 4-1. `CallItem` 에 픽커 칸 (`core-simulator/src/types.ts`)

화물24시가 한 방식 그대로 — **선택 칸으로 더하고 인성·24시는 무시한다.**

```ts
// ── 카카오픽커 전용 (Optional) ──
itemSize?: '초소형' | '소형' | '중형' | '대형';
pickerTags?: string[];         // 단거리 · 급송 · 반나절 · 승 · 착불 …
prepMinutes?: number | null;   // 준비 N분 — null 이면 「준비 완료」
reservedAt?: string;           // 예약 17:00 · 내일
pickupDeadline?: string;       // 17:04까지 픽업
deliveryDeadline?: string;     // 17:18까지 배송
deliveryFee?: number;          // 배송비
promotion?: number;            // 프로모션 — 최종수익 = 배송비 + 프로모션
orderNo?: string;
pickupBuilding?: string;
dropoffBuilding?: string;
```

🔴 **요금 칸(`fare`)은 새로 만들지 않는다** — 최종수익이 곧 `fare` 다. 칸 둘에 같은 돈을 적으면 언젠가 갈라진다.
최종수익을 `deliveryFee + promotion` 에서 **만들어 쓰는** 쪽으로 한다 (규칙 ③).

### 4-2. 줄임 표기 (`core-simulator/src/format.ts`)

`formatHwamul24Region` 옆에 `formatPickerRegion` — 픽커는 **시 이름 앞 두 글자 + 동의 줄임**을 쓴다
(`성남시 분당구 서현1동` → `분당 서현1` · `수정구 신흥2동` → `수정 신흥2`). 앱 `normalizeRegion` 이
이 줄임을 전제로 짜여 있으므로 **실물 02·11·13 의 표기에서 규칙을 뽑는다 — 지어내지 않는다.**

### 4-3. 문제지

- **돈의 크기가 다르다** — 인성 문제지는 3만 원대, 픽커 실물은 2천~1만7천 P. 인성 문제지를 픽커로 틀면
  `picker_alarm_min_fare`(기본 1만) 축이 엉뚱하게 시험된다 → **픽커 전용 문제지**를 만든다 (`presets.ts`, 주소는 `mockLocationData.json` 에서)
- 첫 문제지 후보 — 앱 알람 축 셋을 하나씩: ① 요금 하한 경계(9,900 / 10,000) ② 픽업거리 반경 안·밖(`pickupBand` 재사용)
  ③ 도착 동이 도착목표와 **줄임 표기로만** 만나는 콜(`정자3` ↔ `정자동`) ④ 예약·내일 콜 ⑤ **오더카드에 최고가 콜**(앱이 안 누르는가)
- 🔴 **개인정보가 든 실물 11~32 의 주소·동호수를 문제지에 옮기지 않는다** (레포에 안 넣기로 한 자료다)

### 4-4. 시간에 따라 값이 오른다 (실물 09→10)

선택 옵션 `?rise=1` — 리스트에 오래 남은 콜의 `promotion` 을 올린다. 기본 꺼짐(채점이 흐려진다).

## 6. 단계

각 단계는 **앱으로 한 번 돌려 로그를 확인**하고 다음으로 간다. 앞 단계가 실패하면 다음으로 안 간다.

| 단계 | 무엇을 만드나 | 앱 쪽에서 확인할 것 (완료 조건) |
|---|---|---|
| **0** | §1 의 A/B/C 결정 · 스캐너 담당이 반영 | 시뮬 픽커 화면에서 앱 라디오가 **픽커로 남는다** · 부팅 배너가 `픽커` |
| **1** | 홈 + 리스트 + 카드 (랜덤 콜) | ① `uiautomator dump` 로 시뮬 리스트를 떠서 **실물 덤프와 대조** — 요금 X·줄 간격·머리줄 Y ② 서버 `intel` 에 `targetApp=kakaopicker` 로 쌓이고 출발·도착·요금·픽업km 가 맞다 ③ 🔴 **이 덤프를 앱 단위검사(`KakaoPickerParserTest`)의 문제지로 넣으면 통과하는가** |

## 7. 검사와 게이트

- `onedal-sim` 은 **커밋 게이트 밖**이다 — 그래도 `cd onedal-sim && pnpm typecheck` 는 매번 돌린다
- 앱(`onedal-app/app/`)을 고치는 단계(0단계 · 1단계의 문제지 추가)는 **전체 게이트** + `:app:testDebugUnitTest`
- 🔴 **시뮬 덤프는 실물 덤프를 대신하지 않는다.** 앱 검사의 문제지로 넣을 때 파일 이름에 `sim_` 을 붙여 갈라 둔다 —
  시뮬 덤프만 통과하는 파서는 실물에서 틀린다
- 인성·24시 시뮬이 그대로인가: 0단계 뒤 `cd onedal-web && pnpm e2e:app` 한 바퀴
