## 1. 왜 만드나

픽커는 **수락하면 되돌릴 수 없다** (앱 안에 취소 버튼 없음 · 전화로만 취소 · 하루 5번).
그래서 원달앱이 픽커에서 제대로 도는지 실물로 시험하면 한 번 한 번이 비싸다.

| 원달앱이 픽커에서 하는 일 | 지금 시험하는 법 | 시뮬레이터가 생기면 |
|---|---|---|
| 리스트의 콜 읽기 (`KakaoPickerParser.groupListNodes`·`parse`) | 실물 폰 · 실물 화면 구조 추출로 만든 단위검사 | 원하는 카드를 책상에서 띄운다 |
| 알람 → 상세 진입 → 서버에 미리보기 콜 전송 (`sendPickerPreview`) | 실물에서 콜이 오기를 기다린다 | 문제지로 바로 |
| 기사님이 「수락하기」를 누르면 **잡은 콜로 올린다** (`reportPickerAccepted`) | **하루 5번 중 하나를 쓴다** | 몇 번이든 |
| 수락 뒤 운행 단계 알아보기 (`KakaoPickerKeywords.stageOf`) | 실제 배송을 한 건 끝까지 | 버튼으로 단계를 넘긴다 |
| 🔴 **오더카드의 요금을 누르지 않는가** (`isListCardAnchor` · 09-13 새벽 라이브에서 원달앱이 눌러 두 건이 배차됨) | 다시 만들어 볼 방법이 없다 | 오더카드를 일부러 띄운다 |

🔴 **시뮬레이터는 원달앱을 시험하는 도구다 — 픽커를 똑같이 베끼는 것이 목적이 아니다.**
그래서 그리는 기준은 «실물과 같은 모양»이 아니라 **«원달앱이 읽는 글자와 그 위치가 실물과 같은가»** 다.

## 3. 🔴 공통 코드에 배차망별 코드가 섞여 있다 — 먼저 떼어낸다

### 3-1. 왜 먼저인가

예전엔 픽커 값을 입히는 `picker.ts` 를 **공통 코드 안에** 두려 했다 (기사님 지적 2026-09-14 · 이번 개정에서 폐기).
그 파일이 필요해진 이유는 **공통 코드의 콜 생성기가 이미 인성 모양의 콜을 만들기 때문**이다.
화물24시를 붙일 때도 같은 방식으로 들어갔다 — 그때 이름 `format.ts` 에 24시 표기 함수, `types.ts` 에 «화물24시 전용 필드» 칸.
픽커를 그대로 얹으면 **같은 방식을 세 번째로 되풀이**하고, 넷째 배차망 때 또 한다.

### 3-2. 지금 섞인 것 — 실제로 어느 화면이 쓰나 (코드 검색으로 확인)

| 종류 | 무엇 | 쓰는 화면 | 갈 곳 |
|---|---|---|---|
| ① 정말 공통 | 주소 고르기(현위치 반경 · 가까운 곳 편향) · 좌표 · 직선거리 · 상차·하차 시각 · 문제지 순서 · `toForcedPair` · `mockLocationData` | 모든 배차망 | **공통 코드에 남는다** |
| ② 인성 모양 값이 공통 생성기에 | 요금 공식(`10,000 + 1,500×km`, 최소 요금 아래로 안 내림) · `paymentType` · `billingType` · `companyName` · `callCategory` · `isShared` · `isExpress` · `itemDescription` · `vehicleType` | 인성 화면 전부 · **화물24시 화면도 결제·계산서·회사·물품·차종을 빌려 쓴다** | 배차망 폴더마다 **자기 입히기 함수**가 채운다 |
| ③ 배차망별 표기 함수가 공통 파일에 | `formatInsungVehicle` · `formatRegionName` · `formatRegionFullName` | 인성 화면만 | `insung/insungCall.ts`(신설) |
| | `formatHwamul24Vehicle` · `formatHwamul24Region` | 화물24시 화면만 | `hwamul24/hwamul24Call.ts`(신설) |
| | `getNextPickupDetail` · `getNextDropoffDetail` (연락처 생성) | 인성 화면만 | `insung/insungContacts.ts`(신설) |
| | `CallItem` 의 «화물24시 전용 필드» 칸 (`tonnage`·`loadingType` …) | 화물24시 화면만 | `hwamul24/hwamul24Call.ts`(신설) 의 타입 |
| ④ 문제지 | 요금이 원 단위 · 정답(`expect`)이 **인성 콜 필터 기준** · 한 문제에 주소(공통)와 요금·차종·정답(배차망별)이 붙어 있다 | 인성 기준인데 24시도 그대로 씀 | **이번엔 안 가른다** (§3-4) |
| ⑤ 안 쓰이는 것 | `AutoDispatchFilter` · `RegionIntel` — 내보내기만 있고 읽는 화면이 없다 (지도 게임에서 가져올 때 딸려 온 것으로 보인다) | 없음 | **지우지 않는다** — 목록에만 올리고 기사님 확인 뒤 판단 |

### 3-3. 나누는 선 — «배차망을 아는가»

- **공통 코드**는 배차망 이름을 import 도 언급도 하지 않는다 — 검사로 잠근다 (§10 0단계)
- **배차망 폴더**는 서로를 import 하지 않는다. 화물24시가 인성 값을 빌려 쓰던 자리는 **화물24시 입히기 함수가 스스로 채운다**
- **`nets.ts`** 만 배차망 전부를 안다: `net` → 입히기 함수 · 화면 · 콜 타입
- **`nets.ts`(신설) 는 인터페이스 모양으로 만든다** — 서버의 `IAppPlugin`(배차망이 답해야 할 질문 목록) + `PluginFactory`(고르는 곳 하나)와 같은 짜임이다 (§3-6).
  배차망 하나가 채울 칸을 `SimNet` 인터페이스로 신설해 정해 두면, 넷째 배차망 때 **빠뜨린 칸을 타입 검사가 잡는다**:
  ```ts
  interface SimNet {                                // 신설 예정
    key: 'insung' | 'hwamul24' | 'kakaopicker';     // 서버·원달앱과 같은 값 (§3-5)
    label: string;                                  // 설정 화면에 보일 이름
    toCall(base: BaseCall, opts: CallOptions): SimCall;   // 콜에 값 입히기
    ListScreen: ComponentType<ListProps>;
    DetailScreen: ComponentType<DetailProps>;
    presets?: PresetProblem[];                      // 그 배차망 전용 문제지 (픽커)
  }
  ```
- 🔴 **모르는 배차망이면 멈춘다** — 지금 `DispatchPage` 는 `?net=` 이 `hwamul24` 가 아니면 **전부 인성**으로 본다.
  서버도 모르는 값이면 조용히 인성으로 떨어진다(`PluginFactory`·`screenLabelsOf`). 시뮬레이터에서는 문제지 이름을 못 찾을 때처럼
  **콜을 안 띄우고** «배차망 «abc» 가 없습니다 · 쓸 수 있는 이름: insung · hwamul24 · kakaopicker» 화면을 띄운다 —
  인성인 줄 모르고 30분 시험하면 그 30분이 헛것이다. `?net=` 이 **아예 없을 때**도 같다
- 콜 타입: 공통은 `BaseCall`, 배차망은 `InsungCall = BaseCall & {…}` 처럼 **덧붙인다**. `SimulationProvider` 의 리스트는 `nets.ts`(신설) 의 묶음 타입을 쓴다

### 3-4. 이번에 안 하는 것

- **문제지 가르기** — 한 문제 안에 공통 값과 인성 값이 붙어 있고 코드가 가장 길다. 인성·24시 문제지는 **그대로** 두고, 픽커 문제지만 `kakaopicker/pickerPresets.ts`(신설) 로 새로 만든다. 설정 화면은 배차망이 픽커일 때 픽커 문제지 목록을 보여 준다
- **⑤ 안 쓰이는 타입 지우기** — 확인 없이 지우지 않는다
- **인성·24시 상세의 뒤로 가기 문제**(§7-3) — 이번엔 픽커 분기에만

### 3-5. 배차망 이름을 서버·원달앱과 맞춘다 — `inseong` → `insung` (기사님 확정 2026-09-14)

서버·`shared`·원달앱은 `insung` 인데 시뮬레이터만 `inseong` 이다.
시뮬레이터는 `shared` 를 일부러 안 가져다 쓰므로(README «onedal-web 과 완전히 별개다») **코드로 묶지는 않고 값만 맞춘다.**

| 바꾸는 것 | 지금 | 뒤 |
|---|---|---|
| `SetupPage` 의 `NetKey`·`NETS` | `'inseong'` | `'insung'` |
| `DispatchPage` 의 `?net=` 해석 | `inseong` | `insung` (+ 모르는 값이면 멈춤 · §3-3) |

## 7. 🔴 픽커를 붙이기 전에 풀어야 할 문제 셋

### 7-1. 원달앱은 시뮬레이터 화면을 늘 «인성»으로 읽는다 → 화면 글자로 망을 가르게 바꾼다 (기사님 확정 2026-09-14)

지금 스캔앱은 폰 시스템이 화면마다 붙여 주는 **앱 이름**으로 망을 가른다 (`TargetApp.codeOfPackage`).
실제 픽커 앱은 이름이 달라 되지만, 시뮬레이터는 인성·24시·픽커 화면을 **한 앱**으로 띄우므로 늘 «인성»이 되고 관제앱 배지도 «인성»으로 보인다.
👉 **화물24시 시뮬레이터도 같은 문제를 겪고 있을 것이다** (코드를 읽어서 한 추정 — 1단계에서 폰으로 먼저 확인).

✅ **정한 방향** — 스캔앱이 **화면에 적힌 글자만으로** «이건 인성 리스트 · 이건 픽커 상세»를 가른다.
실제 픽커는 «나 픽커입니다»라고 알려 주지 않으니, 실제 앱과 시뮬레이터가 **같은 방법**으로 갈려야 한다 (기사님).

- 스캔앱 설정 화면의 망 선택 칸은 지운다 · 앱 이름으로 가르는 방식도 지운다
- 시뮬레이터에서 망은 **시뮬레이터 첫 화면**에서 고른다 — 스캔앱은 그 화면 글자로 따라온다
- 설계·테스트는 [원달앱 계획서](원달앱_시뮬레이터_낱말사전_정리.md) ③

🔴 **그러려면 시뮬레이터 화면이 스캔앱이 찾는 글자를 실제로 보여야 한다.** 코드 검색으로 확인한 결과 (2026-09-14):

| 망 | 스캔앱이 찾는 글자 (묶음 안 글자가 전부 있어야 함) | 시뮬레이터 화면에 있나 |
|---|---|---|
| 인성 리스트 | `신규` + `빠른설정` | ✅ |
| 인성 상세 | `적요상세` + `요금` | ✅ |
| 화물24시 리스트 | `화물정보` + `자동새로고침` | ✅ 고침 (2026-09-14) — 한 글자가 빠진 `자동새로침` 오타였다 |
| 화물24시 상세 | `화물상세정보` + `운송료` | 🔴 `화물상세정보` 가 없고 `운송료` 는 셋째 탭(결제정보)에만 있다 — 시뮬레이터 상세가 **배차한 뒤 화면**을 흉내 내고 있다 (확인 대기) |
| 픽커 리스트 · 상세 · 홈 · 수락 뒤 | `리스트 설정` · `넘기기`+`수락하기` · `시작하기` · 단계 글자 | 아직 화면이 없다 — §8 이 이 글자 그대로 만든다 |

→ 화물24시 시뮬레이터는 **지금도 스캔앱에게 리스트·상세로 안 읽히고 있을 수 있다.**
✅ **실물 캡처로 대조했다 (2026-09-14) — 스캔앱 글자가 맞고 시뮬레이터가 틀렸다.** 실물 리스트(`ex_images/화물24시/17_화물정보_리스트.png` · `36_화물정보_전체.png`)는 제목 줄에 `화물정보` 와 스위치 `자동새로고침 ON` 이 있고, 실물 상세(`18_화물상세정보_배차신청.png`)는 제목이 `화물상세정보` 이고 `운송료` 칸이 있다. → **1단계에서 시뮬레이터 화면에 넣는다.**

### 7-3. 원달앱의 «30초 뒤 뒤로 가기»가 시뮬레이터를 설정 화면으로 보낸다

```kotlin
// 원달앱 HijackService — 알람으로 상세에 들어간 뒤 30초 무응답
performGlobalAction(GLOBAL_ACTION_BACK)

// 시뮬레이터 앱 MainActivity
if (webView.canGoBack()) webView.goBack() else super.onBackPressed()
```

시뮬레이터의 상세는 **React 상태**(`selectedCall`)라 방문 기록에 안 남는다. 그래서 뒤로 가기를 누르면
상세가 닫히는 게 아니라 **`/dispatch` → `/`(설정 화면)로 나가 버린다** (코드를 읽어서 한 판단 — 2단계에서 확인).

→ **픽커 상세를 열 때 방문 기록에 한 칸 남긴다** (`?detail=<콜 id>` 를 `navigate` 로 붙이고, 뒤로 가기로 빠지면 닫힌다).

## 9. 픽커 데이터

### 9-1. `PickerCall` 타입 (`kakaopicker/pickerCall.ts` 에 신설)

```ts
export type PickerCall = BaseCall & {
  net: 'kakaopicker';
  itemSize: '초소형' | '소형' | '중형' | '대형';
  pickerTags: string[];         // 단거리 · 급송 · 반나절 · 승 · 착불 …
  prepMinutes: number | null;   // 준비 N분 — null 이면 「준비 완료」
  reservedAt?: string;          // 예약 시각 · 「내일」
  deliveryFee: number;          // 배송비
  promotion: number;            // 프로모션 — fare = deliveryFee + promotion
  orderNo: string;
};
```

마감 시각은 칸을 새로 안 만든다 — `pickupTime`·`deliveryTime` 을 `HH:MM까지 …` 로 그린다. 건물명도 `pickupDetails[0].customerName` 을 쓴다.

### 9-3. 픽커 문제지 (`kakaopicker/pickerPresets.ts` 에 신설)

- 🔴 **요금 크기가 다르다** — 인성 문제지(원 단위 · 수만~수십만)를 픽커 화면으로 띄우지 않는다. 주소는 공통 `findMockEntry` 로 찾는다
- 문제마다 `expect` 는 **원달앱 픽커 알람이 울려야 하나(PASS) / 안 울려야 하나(BLOCK)** 로 적는다

🔴 **정답을 문제지에 싣지 않는다** (기사님 2026-09-14: *"서버는 수시로 바뀔 수 있어 그리고 콜은 내 맘대로 나오는 것이 아냐 …
서버는 서버대로 문제는 문제대로 했을 때 정답이 계속 바뀌고 그 정답이 맞는가를 확인하면 어때?"*).

처음엔 알람 판정 세 축을 하나씩 시험하는 다섯 문제(«픽커기본» · 성남시 · 10,000 → 이천시 · 3,000 으로 한 번 고침)를 짰다.
그런데 원달앱이 보는 **상차 반경 · 도착 키워드는 서버가 매번 계산한 값**이라 콜을 잡거나 위치가 움직이면 바뀐다
(2026-09-14 실측: 합짐 중 반경 4.55km · 도착 키워드가 경로 띠 39개 — 신둔면·창전동이 빠졌다). 문제지에 박은 정답은 곧 틀린다.

그래서:
| 무엇 | 어떻게 |
|---|---|
| 지점 · 순서 | **인성 «칠지점»(이천 방향 — 집에서 이천까지 일곱 지점) 그대로** — 기사님이 계속 쓰는 문제 (`kakaopicker/pickerPresets.ts` 가 `presets.ts` 에서 가져온다 · 두 벌로 안 적는다) |
| 요금 | 원 ÷ 5 · 10P 단위 (5만 원 → 10,000P · 5천 원 → 1,000P) |
| 정답 · 차종 · 요구 조건 | 싣지 않는다 |
| 채점 | `node onedal-sim/scripts/pickerAlarmGrade.mjs` — 원달앱 로그의 `🧾 [알람 필터]`(필터가 바뀔 때만) · `🔔 [알람 판정] … · 축 요금✅ 상차✅ 도착✅` 을 읽어, **판정 순간의 필터로** 정답을 다시 계산하고 앱과 맞춰 본다 |
| 어긋나면 | 채점기 축 ≠ 앱 축 → **원달앱 판정**을 고친다 · 둘은 같은데 기사님이 원한 결과가 아니다 → **서버 필터**(계산 방식·값)를 기사님이 정한다 |

🔴 채점기의 판정 계산은 원달앱 `KakaoPickerParser.decideAxes` · `RegionMatch.hit` 을 **일부러 옮겨 적은 두 벌**이다 — 앱 코드를 부르면 앱이 틀려도 채점이 같이 틀린다.

- 🔴 **개인정보가 든 실물 11~32 의 주소·동호수를 문제지에 옮기지 않는다**

### 9-4. 시간이 지나면 값이 오른다 (실물 09→10)

옵션 `?rise=1` — 리스트에 오래 남은 콜의 `promotion` 을 올린다. 기본 꺼짐 (켜 두면 문제지 결과를 판단하기 어려워진다).

### 0단계 — 공통 코드에서 인성·24시를 떼어낸다 (§3)

**원칙:** 인성·화물24시 시뮬레이터 화면이 **한 글자도 안 바뀐다.** 기사님 폰 테스트가 지금 인성 시뮬레이터로 돈다.
`onedal-sim` 에는 검사가 하나도 없으므로 **«같은가»를 볼 수단부터** 만든다.

**조각마다 테스트** (기사님 요청 2026-09-14: *"중간 중간 테스트도 진행하는 것이 좋을 것 같아. 테스트 방법도 같이 만들고 공유해"* · 같은 날 *"웹에서만 확인하면 안 되는 건가"* 로 ③ 을 좁혔다)

🔴 **앱을 빌드하지 않는다.** 폰의 시뮬레이터 앱은 개발 PC 의 `pnpm dev` 화면을 띄우는 껍데기라 시뮬레이터 코드를 고치면 폰에 바로 실린다.
원달앱(스캔앱) 빌드는 **원달앱 코드를 고쳤을 때만** 한다.

| 층 | 언제 | 방법 | 통과 기준 | 시간 |
|---|---|---|---|---|
| **① 책상 자동** | **조각마다 반드시** | 아래 «① 명령» | 검사 전부 초록 · 🔴 **`Snapshots … written` 줄이 없다** (새로 썼다면 옮기다 무언가 바뀐 것) · 빌드 성공 | 1분 |
| **② 브라우저 눈** | **조각마다** | `cd onedal-sim && pnpm dev` → `http://localhost:5173` → 인성콜 · 화물24시 를 각각 «시작» | 콜이 뜬다 · 콜을 누르면 상세가 열린다 · 브라우저 개발자 도구 콘솔에 빨간 오류가 없다 | 1분 |
| **③ 폰 끝까지** | **아래 넷일 때만** | 폰의 시뮬레이터 앱(🏠 로컬)에서 문제지를 시작 → 아래 «③ 명령» | 원달앱이 `화면: LIST` 로 읽는다 · 로컬 서버 `intel` 에 새 줄이 생긴다 | 2분 |

③ 을 돌리는 때 — **웹 검사로는 알 수 없는 것**이 걸릴 때다:

### 5단계 — 오더카드 · 첫 계약 팝업

**만들 것:** `PickerOrderCard`(`?orderCard=1`) · 첫 계약 필수정보 팝업(`?firstContract=1`)

🔴 **오더카드의 수락 버튼은 누르면 시뮬레이터가 스스로 기록한다** — 원달앱 로그만 믿지 않는다:
화면 전체를 빨갛게 덮고 `🚨 오더카드 수락이 눌렸다 HH:MM:SS` 를 띄우고, 브라우저 콘솔에도 남긴다.

| 종류 | 방법 | 기대 |
|---|---|---|
| 원달앱 단위검사 | `PickerTapSafetyTest` (이미 있다) | 통과 |
| 🔴 폰 · 오래 | 픽커 문제 6 · `?orderCard=1&loop=1` · 원달앱 알람 모드로 **20분** 둔다 | 시뮬레이터 빨간 화면 **한 번도 없음** · 원달앱이 리스트 카드 상세에는 들어간다(알람이 살아 있다는 증거) |
| 위치 검사 | `pickerDumpCheck.mjs`(신설) 를 오더카드 켠 화면에 | 오더카드 요금이 「리스트 설정」 줄 **위**로 나온다 |
| 첫 계약 팝업 | `?firstContract=1` 로 상세 → 「수락하기」 | 팝업이 먼저 뜬다 · 원달앱이 팝업 뒤 「수락하기」를 **안 누른다** |

**통과 기준:** 빨간 화면 0. 한 번이라도 뜨면 **이 계획보다 앞선 발견**이다 — 기사님께 바로 알리고, 원달앱 쪽 수리는 이번 작업이 맡는다.

### 11-2. `pickerDumpCheck.mjs` — 화면 위치 검사 (신설)

`log/카카오픽커/probe.sh` 와 같은 방식으로 폰 화면 구조를 추출해, **원달앱 파서가 기대는 위치**를 검사한다.

```
node onedal-sim/scripts/pickerDumpCheck.mjs                 # 연결된 폰의 지금 화면 — 신설 도구
node onedal-sim/scripts/pickerDumpCheck.mjs <추출파일.xml>   # 저장된 파일 (실물 추출로 검사기 자체를 먼저 검증) — 신설 도구
node onedal-sim/scripts/pickerDumpCheck.mjs --kotlin        # 카드 글자 목록을 Kotlin listOf(...) 로 찍는다 — 신설 도구
```

| 검사 | 실패하면 |
|---|---|
| 요금 글자(쉼표 숫자)의 가운데가 가로 600px 이상 | 원달앱이 요금을 못 찾는다 |
| 「리스트 설정」 글자가 있다 · 리스트 요금은 전부 그 아래 · 오더카드 요금은 그 위 | 오더카드를 리스트 카드로 본다 |
| 요금이 아닌 글자마다 가장 가까운 요금이 60px 안 (지역·거리·태그가 어느 카드에도 안 붙으면 실패) | 카드가 반 토막 난다 |
| 한 글자 덩어리에 요금과 km 가 함께 있지 않다 | 웹뷰가 글자를 뭉쳤다 |
| 리스트 화면에 `수락하기` 가 없다 | 원달앱이 리스트를 상세로 본다 |

마지막에 **실물 추출 파일과 나란히** 줄 간격·카드 간격·「리스트 설정」 줄에서 첫 요금까지 거리를 찍는다 — 판정은 위 검사가 하고, 이 숫자는 눈으로 본다.
종료 코드: 검사 하나라도 실패하면 1.

🔴 **검사기부터 검사한다** — 실물 `log/카카오픽커/화면덤프/09_리스트_퀵7건.xml` 로 초록불, 일부러 요금을 왼쪽에 그린 시뮬레이터로 빨간불을 **먼저** 본다.

### 11-3. `pickerLoop.mjs` — 원달앱 로그를 따라가며 단계 판정 (신설)

`onedal-web/scripts/appLoop.mjs`(`pnpm e2e:app`)의 방식을 픽커용으로 옮긴다 — 원달앱 로그에서 문구를 **순서대로** 기다리고, 어디서 끊겼는지 말한다.

```
node onedal-sim/scripts/pickerLoop.mjs --stage 3 --preset picker   # 신설 도구
node onedal-sim/scripts/pickerLoop.mjs --stage 4                   # 신설 도구
```

- 읽는 곳: `adb logcat` (태그 `1DAL_PICKER` · `1DAL_ALARM`) — 원달앱 로그는 D 등급이라 필터를 I 이상으로 걸지 않는다
- 기다릴 문구·실패 문구: §10 각 단계의 표
- `--preset` 이면 `🔔 [알람 판정]` 줄의 요금으로 문제를 찾아 `expect` 와 대조해 표로 찍는다
- 전제 확인: 기기 연결 · 원달앱 실행 중 · 접근성 켜짐 · 시뮬레이터 :5173 응답 · 서버 :4000 응답

⚠️ **`pnpm e2e:app` 을 그대로 쓰지 않는다** — 그 스크립트는 옛 시뮬레이터 위치(`~/reps/map/map`)와 크롬을 전제로 하고,
검증 도구 표에 «미검수»로 적혀 있다. 픽커는 시뮬레이터 앱(WebView)으로 연다.
