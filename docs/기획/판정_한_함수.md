## 1. 바꿀 구조 — 여섯 축, 하나의 함수

### 값 카테고리는 일곱, 채점 축은 여섯

조사에서 나온 카테고리는 일곱인데 **「시간」은 축이 아니다** — 「돈」의 분모이고 「약속」의 재료다.
시간을 따로 채점하면 같은 사실을 두 번 세게 된다 (지금 버퍼↔약속이 그렇다).

```
① 돈    ← ② 시간(분모)
③ 약속  ← ② 시간(재료)
④ 공간   ⑤ 성질   ⑥ 지리   ⑦ 근거
```

### 축 여섯 — 전부 0~100 × 가중치

| # | 축 | 답하는 질문 | 100점 | 0점 |
|---|---|---|---|---|
| 1 | **돈** | 이 시간에 얼마를 버나 | 목표 시급의 100%↑ | 0원/h |
| 2 | **약속** | 이미 한 약속이 지켜지나 | 버퍼 30분↑ | 버퍼 음수(=깨짐) |
| 3 | **공간** | 실을 자리가 있나 | 여유 100% | 만재 |
| 4 | **성질** | 같이 실어도 되나 | 충돌 없음 | 같이 못 싣는 조합 |
| 5 | **지리** | 경로 위에 있나 | 순방향·길목 | 역주행·경로 밖 |
| 6 | **근거** | 판단할 재료가 있나 | 다 안다 | 다 모른다 |

🔴 **문지기(gates)를 없앤다.** 지금 「약속 보존」·「같이 못 실음」이 축 밖에서 색을 덮는데,
그 둘은 위 표의 **축 2·4** 그 자체다. 같은 사실을 두 번 세는 구조를 지운다.

**대신 «바닥»을 둔다** — 축 점수가 0이면 색을 `사고`로 덮는다. 지금 문지기가 하던 일을
축 안에서 한다. 가중치 0이면 축이 없으니 덮지도 않는다 (기사님 확정: *"가중치를 0으로 하면 그냥 통과"*).

### 함수 하나

```
judge(재료, 기준) → { color, score, axes[6], facts[] }
```

- **`OrderEvaluator` 는 재료만 모은다** — 카카오·적재·타임라인·필터. 채점은 안 한다
- **모든 조건이 이 함수를 지난다** — 지금 `reasons.push` 로 새던 것(차종·최저가·경유 이탈)도 축으로
- **색은 값으로 나간다** — 문자열에 심지 않는다. `judgment` 객체가 이미 화면까지 간다
- **순수 함수** — `shared/` 에 둔다. 세 앱이 같은 답을 내야 하고, 폰·DB 없이 검사된다

## 2. ⑤-4 넷 — 코드 전에 확정할 것

지우고 새로 만든다.

### ② 값 — 기본값과 근거

| 값 | 기본 | 근거 |
|---|---|---|
| 가중치 여섯 | **전부 1** | 기사님: *"지금은 모두 같은 가중치"* — 실측이 쌓이기 전엔 동등하게 둔다 |
| 바닥 여섯 | 약속 0 · 성질 0 · 나머지 **없음** | 지금 문지기가 덮던 둘만 바닥을 둔다. 나머지는 낮아도 «기사님이 판단»(규칙 ①) |
| `target_hourly_krw` | 30,000 | 그대로 (노하우 4콜 역산 · 문제지 캘리브레이션) |
| `color_honey_min` / `normal_min` | 70 / 40 | 그대로 |
| 옮겨 온 값 여섯 | 지금 코드 값 그대로 | 값을 바꾸는 것이 아니라 **고칠 수 있게** 하는 것이 목적 |

🔴 **값을 바꾸지 않는다.** 이번 작업은 구조를 바꾸는 것이고, 값이 함께 움직이면
«구조 때문인지 값 때문인지» 못 가린다.

### ③ 시점 — 언제 읽고 언제 쓰나

| | 언제 |
|---|---|
| **읽기** | 로그인 때 DB → 세션 (지금과 같다) · 판정 기준 탭에서 저장하면 세션 갱신 |
| **채점** | 콜을 집은 뒤 심사 **1회**. 그 결과를 `order_judgments` 에 저장 (지금과 같다) |
| **재채점** | 하지 않는다 — 심사는 한 번이고 불변이다. 경로가 바뀌어도 옛 판정은 그대로 남는다 |

⚠️ 지금과 같은 시점이다. **이번 작업에서 시점은 안 바꾼다.**

### ④ 화면 — 어디에 어떻게 보이나

**판정 카드** (`PinnedRouteCard`)
```
🔵 꿀 · 73점
  돈    92점 (×1)   5.0만 ÷ 88분 = 3.4만/h
  약속  100점 (×1)  최소 +54분
  공간  20점 (×1)   여유 20%
  성질  100점 (×1)  충돌 없음
  지리  100점 (×1)  경로 위 · 순방향
  근거  60점 (×1)   정차 미확인 · 배송주행 추정
```
- **축마다 «사실»을 함께** 적는다 (`raw`) — 지금 규칙 그대로
- 가중치 0인 축은 **회색으로** 보인다 (숫자는 계속 보인다 — 기존 약속)
- 바닥에 걸리면 그 줄이 🔴 로 뜨고 색이 `사고`

**판정 기준 탭** (`JudgmentSettingsTab`)
- 축 여섯이 **한 줄씩** — 가중치 · 바닥 · 지금 값
- 옮겨 온 값 여섯은 «세부» 로 접어 둔다 (평소엔 안 건드림)

## 3. 이행 순서 — 한 단계씩 검증하며

각 단계가 **끝날 때마다 게이트가 초록**이어야 한다. 중간에 멈춰도 제품이 돈다.

| 단계 | 무엇 | 어떻게 확인 |
|---|---|---|
| **1** | 죽은 값 아홉을 지운다 | `pnpm audit:dead` · jest |
| **2** | `judge()` 를 새로 만든다 (축 여섯 · 바닥). **아직 아무도 안 부른다** | 새 검사 파일 하나 |
| **3** | `reasons` 중 판정에 드는 것을 축으로 옮긴다 (차종·최저가·경유 이탈 → 지리·공간·돈) | 옮길 때마다 검사 추가 |
| **4** | `OrderEvaluator` 가 `scoreDryRun` 대신 `judge()` 를 부른다 | `pnpm scenario` · `pnpm drive` |
| **5** | 색을 **값으로** 내려보낸다. 화면이 문자열 파싱을 그만둔다 | 관제웹에서 눈으로 |
| **6** | 못 고치던 값 여섯을 DB 로 올린다 | 판정 기준 탭에서 바꿔 보고 색이 움직이나 |
| **7** | 옛 `scoreDryRun`·`gates` 철거 | jest · audit:dead |

🔴 **2단계에서 옛것을 지우지 않는다.** 2026-08-21 에 `dryRun` 을 **병행**으로 시작한 것과 같은 방식이다 —
새 채점기를 켜 두고 옛것과 답을 비교한 뒤에 갈아탄다.

### 각 단계의 «되돌리는 법»

| 단계 | 되돌리기 |
|---|---|
| 1~3 | git revert (아무도 안 부르는 코드) |
| 4 | `judge()` 호출을 `scoreDryRun()` 으로 되돌린다 (한 줄) |
| 5 | 화면이 값과 문자열 **둘 다** 읽게 두었다가 값이 확실해지면 문자열 제거 |
| 6~7 | 옛 칸을 남겨 둔 채로 진행 — 마지막에 한 번에 지운다 |

## 4. 이 작업이 답하지 **않는** 것

| | 왜 |

## 5. 확인이 필요한 것 — 기사님 결정

1. **바닥을 둘만 둘까, 여섯 다 둘까**
   지금은 「약속·성질」만 색을 덮는다. 「공간 0점(만재)」도 사고로 볼 것인가?
2. **「근거」 축을 넣을까**
   모르는 값이 많으면 점수를 깎는다. 지금은 반대로 **후해진다.**
   ⚠️ 규칙 ⑤-2(*"모르면 일반값으로 계산하고 미확인으로 표시"*)와 충돌할 수 있다 —
   일반값으로 계산해 놓고 «모른다»고 깎으면 두 번 손해다
3. **「지리」 축의 점수를 어떻게 낼까**
   순방향/역주행은 앱이 `progressKm` 으로 판정한다. 서버가 같은 판정을 하려면
   그 값이 서버에도 있어야 한다 (지금은 앱에만)
