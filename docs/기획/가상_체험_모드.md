# 가상 체험 모드 (`SIMULATION` / 체험) 기획서

> **2026-09-18 기사님 확정.**
> 기사님: *"알람, 자동, 직접에 '체험'을 만들어서 가짜로 잡아서 운행해보는 시뮬레이션을 만들고 싶어. 실제 수락은 절대 누르지 않고 뒤로가기가 되고, 관제탑에서는 [체험 운행 중] 딱지가 붙어서 진짜 콜 데이터로 합짐이 어떻게 걸리는지 바로 볼 수 있게. 색은 햇병아리 노랑으로 해줘."*

## 1. 기획 배경 및 핵심 목적

1. **실서버 오작동 및 패널티 불안감 0% (완전 무결한 안전성)**
   - 실제 배차망(카카오 픽커, 인성)의 `[수락하기]` 버튼을 물리적으로 누르는 행위를 100% 차단합니다.
   - 기사님이 안심하고 24시간 실시간 데이터를 켜둔 채 시스템과 필터를 튜닝할 수 있습니다.

2. **실시간 실제 콜 기반의 합짐(GATHERING) 체험**
   - 배차망 화면에 실시간으로 스캔되는 진짜 콜을 바탕으로, 관제탑에서 [킵]을 누르면 서버 내부적으로만 "내 차에 첫짐이 실렸다"고 승격합니다.
   - 관제탑은 즉시 `첫짐(STANDBY) → 합짐(GATHERING)` 국면으로 진입하며, 지도에 실제 경로가 그려지고 이후 스캔되는 콜들 중 경로상 꿀 합짐이 자동으로 추천됩니다.

3. **신규 기사 온보딩 & 영업 무기**
   - 처음 시스템을 접하는 기사님들에게 "일단 [체험] 모드로 켜두고 운행해 보세요. 진짜 콜은 절대 안 잡히고 어떤 합짐이 걸리는지만 보여줍니다"라고 안내하여 진입 장벽을 완전히 허뭅니다.

## 2. 4종 기기 모드 체계 및 색상 배색

| 모드 키 | 화면 명칭 | 테마 색상 | 폰 물리 터치 | 관제탑 동작 |
|---|:---:|:---:|:---:|---|
| `AUTO` | **자동** | **파랑 (Blue)** | ✅ 실서버 수락 클릭 | 자동 배차 및 실운행 |
| `ALARM` | **알람** | **초록 (Green)** | ✗ (터치 안 함) | 소리 알림만 제공, 기사 직접 수락 |
| `MANUAL` | **직접** | **차분한 회색 (Gray)** 🔄 | ✗ (터치 안 함) | 자동 필터 꺼짐, 수동 운행 모드 |
| `SIMULATION` | **체험** 🐥 | **햇병아리 노랑 (Amber/Yellow)** | ✗ (뒤로가기 수행) | 가상 내 콜 등록 + 실시간 합짐 시뮬레이션 |

> **직접 모드 색상 리뉴얼**: 햇병아리 노랑을 `체험` 모드가 선명하게 가져가고, `직접` 모드는 기능이 꺼진 상태를 뜻하는 차분한 무채색 회색(`bg-surface-alt text-text-muted`)으로 정돈합니다.

## 3. 전체 라이프사이클 동작 흐름

```
① 폰이 리스트를 스캔하다가 조건에 맞는 콜 발견 → 상세 화면 진입 (/detail 전송)
        ↓
② 모드가 [체험]이어도 관제탑에는 [자동]과 동일하게 결재 카드 ([킵] / [캔슬]) 노출
        ↓
③ 기사님이 관제탑 결재 카드에서 [킵] 클릭
        ↓
④ 서버가 폰에게 `SIMULATED_KEEP` 판결 전달
   - 폰: [수락하기]를 절대 누르지 않고, 안전하게 [뒤로가기(Back)]를 실행하여 리스트 화면으로 복귀!
   - 서버: 해당 콜을 `isSimulated: true` 상태의 내 콜(`myOrders`)로 승격
        ↓
⑤ 관제탑 화면에 [체험 운행 중] 딱지가 붙은 내 콜 카드가 생성됨
        ↓
⑥ 관제탑 국면이 '합짐(GATHERING)'으로 전환되어 지도가 경로를 그리고,
   리스트로 복귀한 폰이 계속 스캔하는 콜들 중 최적 합짐 콜을 자동으로 필터링 및 매칭!
        ↓
⑦ 기사님이 원할 때 카드 우측의 [체험 종료] 버튼을 눌러 언제든 패널티 없이 가상 짐을 비움
```

## 5. 아키텍처 특이점 및 잠재 결함 방어 규약 (Architecture Invariants & Pitfalls)

가상 체험 모드는 **"메모리 상에서는 완벽히 내 콜로 인식되어 합짐 동선을 그려야 하지만, 실물 배차망과 디스크 장부(SQLite)에는 일체 흔적을 남기지 않아야 하는"** 특수한 성격을 가집니다. 일반적인 상용 웹 설계 관점과 달라 주의해야 할 4대 아키텍처 규약입니다.

### ① 세션 계층 분리 엄수 (`UserSession` vs `DeviceSession`)
- **특이 구조**: 본 시스템은 기사 세션(`UserSessionStore`)과 기기 세션(`routes/devices.ts`의 `activeDevices`)이 별도 저장소로 분리되어 있습니다.
- **방어 규약**: 기기의 모드를 확인할 때 `session.devices`와 같이 객체 트리로 접근하면 즉시 `undefined.get()` 크래시가 발생합니다. 반드시 표준 인터페이스인 `getDeviceMode(deviceId, userId)`를 호출해야 합니다.

### ② 취소 및 수락의 단일 진실 공급원(SSOT) 내재화 (`cancelCount.ts`)
- **특이 구조**: 콜의 취소 경로는 결재([CANCEL]), 화면 이탈(뒤로가기), 30초 타임아웃(`forceCancelEvaluatingOrder`), 비상벨(`emergency`) 등 5개 경로로 다중화되어 있습니다.
- **방어 규약**: 호출부마다 개별적으로 `if (!isSimulated)` 분기를 치는 땜방식 처리는 누수를 유발합니다. 반드시 코어 엔진인 `cancelCount.ts`의 `countCancel` 및 `countKeep` 내부에서 `order.isSimulated`를 직접 검사하여, 어떤 경로로 취소/수락이 들어오더라도 기사님의 10회 취소 패널티 카운트가 100% 안전하게 보호되도록 해야 합니다.

### ③ SQLite 미저장 가상 콜에 대한 실물 마일스톤 격리
- **특이 구조**: 가상 콜은 실제 운행 장부를 오염시키지 않기 위해 SQLite `orders` 테이블에 `INSERT`되지 않습니다.
- **방어 규약**: 관제탑 [Keep] 후 실물 배송 6단계 마일스톤(`birthFirstStep`)을 호출하면 DB 미존재 예외가 발생하므로, `!isSimulated` 조건을 통해 실물 콜에 대해서만 마일스톤을 출생시키고 후속 타임라인 동기화가 중단되지 않도록 보호해야 합니다.

### ④ 프론트엔드 정규식 소스 검증 맹점 방어
- **특이 구조**: 프로젝트 내 700여 개 웹 테스트 중 상당수는 코드가 특정 정규식 패턴을 포함하는지 확인하는 정적 검사(`codeOnly`)입니다.
- **방어 규약**: `filterAlarm is not defined`처럼 하위 컴포넌트 Props 전달이 누락되어 런타임에 화면이 죽는 참사를 방지하기 위해, 핵심 조종석 컴포넌트는 정규식 테스트 외에 실제 컴포넌트 트리를 마운트하는 스모크 테스트(`render()`)를 병행해야 합니다.
