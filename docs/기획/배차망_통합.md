```
① 픽커는 되돌릴 수 없다      「수락하기」 = 계약 성립. 버튼 취소 없음, 전화만, 하루 5번
        ↓ 그러므로
   «잡고 나서 판정»을 못 쓴다   ← 인성 설계의 심장이 여기서 안 돈다
        ↓ 그런데 다행히
② 상세 화면에 다 있다        배송 km · 「17:04까지 픽업」「17:18까지 배송」· 물품 규격 · 수익
        ↓ 그리고
③ 이미 거기까지 가고 있다     3단계 알람이 상세로 이동시킨다 (scheduleAlarmDetailBack)
        ↓ 따라서
   픽커는 «잡기 전에 판정» 이 가능하다 — 그리고 그것만 가능하다
```

**이것이 이 기획의 축이다.** 인성과 픽커는 시퀀스 상수가 다른 게 아니라
**판정이 계약보다 앞이냐 뒤냐가 반대**다.

| | 인성 | 픽커 |
|---|---|---|
| 되돌리기 | 앱에서 **30초 안전취소** (위약금 0) | 🔴 **없다** — 전화만 |
| 횟수 | 10회 | 🔴 **하루 5회** |
| 그래서 판정은 | **잡은 뒤** 30초 안에 (서버가 CANCEL 을 보낼 수 있다) | **잡기 전에** (보낼 곳이 없다) |
| 앱이 누르는 것 | 확정 버튼 (자동 가능) | 알람일 때 **상세로 들어가는 것까지**. 🔴 **「수락하기」만은 안 누른다** |

🔴 **그래서 «인성 수순을 픽커로 복사»가 답이 아니다.** 방향이 반대라 복사하면
가장 비싼 사고(되돌릴 수 없는 계약)가 난다.

## 3. 가르는 기준 — 이 두 줄로 판단한다

기사님 말씀을 규칙으로 바꾸면:

- **공통** = 세 배차망에 **같은 질문**이 있고 **답하는 방식도 같은** 것
- **전용** = 그 배차망에만 있거나, **질문은 같은데 답이 다른** 것

🔴 **함정은 둘째 줄이다.** 이름이 같아서 공통으로 착각하기 쉽다 —
«취소»는 세 배차망에 다 있지만 **인성의 취소와 픽커의 취소는 다른 것**이다.
이 레포가 반복해 당한 «한 값이 여러 사실을 답한다»(규칙 ⑤-4 ⑤)와 같은 함정이다.

## 4. 그래서 층은 이렇게 갈린다

```
[앱별 층]  이 배차망을 어떻게 읽고 어떻게 움직이나
           키워드 · 파서 · 시퀀스 · 되돌리기 성질 · 필터 축
                    ↓ 라디오(타겟앱 선택) 하나가 이 묶음을 통째로 갈아끼운다
[공통 층]  회선 규격 — 콜 DTO · confirm/detail/scrap (targetApp 만 실린다)
[서버 층]  판정 · 장부 · 관제 — 배차망 무관, targetApp 열로 구분
```

### 항목별 판정

| 무엇 | 어디 | 왜 |
|---|---|---|
| 화면 낱말 · 파싱 | **앱별** | 이미 갈라짐 |
| 화면 상태 이름(LIST/DETAIL/…) | **공통** | 세 판에 같은 질문 — 다만 **어느 화면이 그 상태인가**는 앱별(키워드) |
| **잡는 수순** | **앱별** | 인성 상세→팝업3장→확정 / 픽커 수락 후에야 주소 |
| 🔴 **되돌리는 법** | **앱별 — 새 축** | §1. 인성 30초 / 픽커 없음. **지금 코드에 이 축이 없다** |
| 필터 축 | **앱별** | 차종(인성) vs 물품 크기(픽커) |
| 요금 하한 | 개념은 공통, **값은 앱별** | `min_fare` ↔ `picker_alarm_min_fare` — 이미 갈라 둠 |
| 알람 울릴지 판정 | **앱별** | 축이 다르니 |
| 알람 **울리는 수단** | **공통** | 소리·진동·테두리 — 배차망 무관 |
| 콜 DTO · 회선 | **공통** | 이미 |
| 판정 색 · 장부 · 관제 · GPS · 경로 · 정거장 | **공통** | 배차망 무관 |
| 표본(intel) 소비 | 공통 코드, **targetApp 로 걸러 쓴다** | 요금 체계가 다른 판을 섞으면 인성 판정이 오염된다 |

## 5. 시퀀스 플러그인 — 무엇을 담는 그릇인가

시퀀스 = **«화면 → 할 일 → 다음 화면»의 순서표 + 그 배차망의 성질**.

```
순서표   [ 화면상태, 할 일(클릭/수집/전송), 다음 ] 의 목록
성질     되돌릴 수 있는가 · 되돌릴 창(초) · 하루 취소 한도 · 판정이 계약보다 앞인가
```

### 두 수순을 한 틀에 담아 본다 (종이 검증)

| 단계 | 인성 | 픽커 (미래) |
|---|---|---|
| 1 | 리스트에서 대상 클릭 | 리스트에서 대상 클릭 |
| 2 | 상세: 2차 필터 → confirm 전송 → (주의 동이면 팝업 3단계) → **확정 클릭** | 상세: **읽는다** (배송km·마감시각·물품) → confirm 전송 → 🔴 **여기서 멈춘다** |
| 3 | 확정 화면: 팝업 3장 열어 **수집** | — (2단계에서 이미 다 읽었다) |
| 4 | detail 전송 → 리스트 복귀 | 판정 받아 **알람** → 기사님이 누르거나 30초 뒤 복귀 |
| 5 | — | (기사님이 눌렀다면) 수락 후 화면에서 전체 주소 **수집** |
| 성질 | 되돌리기 30초 · 판정이 계약 **뒤** | 되돌리기 없음 · 판정이 계약 **앞** |

→ **같은 틀에 담긴다.** «할 일»에 «클릭 안 함»이 있으면 되고, 성질이 그걸 강제한다.

⚠️ **5단계는 아직 미확인이다** — 기사님이 실제 콜을 수행하고 캡처해 주시기로 했다
(2026-09-03 예정). 그때까지는 [참고_2023 자료](../../ex_images/카카오픽커/README.md)로
**구조만** 세우고 낱말은 비워 둔다. 기사님 확정: *"켑처화면으로 이후를 예상하고
만들어야 한다. 내가 캡쳐해오면 그 단어만 바꿔치기 하면 되니까."* —
이 레포는 화면 낱말을 서버가 배포하므로(`keywords_*.json`) 구조는 안 흔들린다.

## 6. 🔴 중복을 만들지 않기 위한 금지 사항

기사님 걱정(*"인성시스템과 중복되면 안 된다"*)에 대한 답이다.

1. **«픽커용 화면 상태 기계»를 새로 만들지 않는다** — 상태 이름은 공통, 어느 화면이
   그 상태인지만 키워드로 가른다
2. **«픽커용 콜 DTO»를 만들지 않는다** — 회선은 하나, `targetApp` 만 실린다
3. **«픽커용 판정 엔진»을 만들지 않는다** — 판정 색은 배차망 무관. 다른 것은 **입력**뿐
4. **«픽커용 알람 수단»을 만들지 않는다** — `AlarmSignaler` 하나
5. 🔴 **인성 수순을 복사해 고치지 않는다** — §1 대로 방향이 반대다. 복사하면
   되돌릴 수 없는 계약이 자동으로 성립할 수 있다

## 7. ⑤-4 다섯 — 여기가 차야 코드를 시작한다

| | 상태 | 내용 |
|---|---|---|
| ① 스키마 | ⬜ | 시퀀스·성질을 **어디에 두나** — 앱 코드 상수 vs 서버 배포(`keywords_*.json` 처럼). 배포형이면 배차망을 앱 재설치 없이 붙일 수 있다 |
| ② 값 | 🔶 | 되돌리기 성질은 실측됨(인성 30초/10회 · 픽커 없음/5회). **픽커 수락 후 단계는 미확인** (09-03 캡처 대기) |
| ③ 시점 | ⬜ | 시퀀스를 **언제 갈아끼우나** — 라디오를 바꾼 순간? 화면 패키지가 바뀐 순간(`codeOfPackage`)? 둘이 어긋나면 누가 이기나 |
| ④ 화면 | ⬜ | 기사님이 «지금 어느 배차망의 어느 수순을 타고 있나»를 어디서 보나 |
| ⑤ 읽는 곳 | ⬜ | 시퀀스를 읽는 곳이 몇이나 되나 — 앱 상태 기계 · 잡기 차단 검사 · 관제웹 표시. **셋이 다른 질문을 묻고 있지 않은지** 그 자리에서 확인 |

## 8. 단계 (제안)

1. **⑤-4 다섯 채우기** — 특히 ①(어디에 두나)과 ③(언제 갈아끼우나). 기사님 확정 필요
2. **«되돌릴 수 있는가» 축 신설** — `supportsCatching` 옆에. 지금은 «잡을 수 있나»만 있고
   **«잡은 뒤 되돌릴 수 있나»가 없다.** 픽커로 잡기를 시작하는 날 이게 없으면 사고가 난다
3. **상세 화면에서 배송km·마감시각 읽기** (픽커) — 새로 갈 곳이 없다. 알람이 이미
   그 화면에 간다. **읽기만 더한다.**
4. **표시를 따라 떼어내기** — 🚧 5곳을 인성 시퀀스 플러그인으로. 그날의 ⑤-4 를 따로 쓴다
5. 픽커 잡기 수순 — **기사님이 실물 캡처를 주신 뒤에**

### ⏸️ 보류 — «AUTO 도 픽커 상세로 들어가게 하기» (기사님 확정 2026-09-02)

한때 «지금 바로 할 수 있다»고 적었던 것이다. **하지 않기로 했다.**

> 기사님: *"일단 이 코드를 수정하지 말자. 내일 나갈 때 자동을 그냥 딤드 시켜버리면
> 오토가 눌릴 일 없을 거니까. **코드를 단순하게 하자.** 그리고 일단 알람 작동에 초점을 두자."*

**왜 접었나** — 열면 AUTO 가 오더카드의 요금을 눌러 **되돌릴 수 없는 계약**이 성립할 수 있고
(전화 취소 하루 5번), 그 위험이 «자동↔알람 60초 지연»·«필터가 제대로 닿았나»와 겹친다.
자동을 못 고르게 막으면 코드를 안 늘리고도 같은 안전을 얻는다.

**검토하며 알아낸 것은 남긴다** (다시 열 때 되풀이하지 않도록):

| 처음 걱정 | 실제 |
|---|---|
| `isAutoActive` 를 켜면 콜 잡기가 잠긴다 | 🟢 **아니다.** 리스트로 돌아오면 `resetSessionState()` 가 자동으로 푼다(`HijackService:370`) |
| 서버에 «AUTO 로 잡았다»가 보고된다 | 🟢 **아니다.** 픽커는 상세 처리 첫 줄에서 되돌아가 `/confirm` 을 아예 안 보낸다 |
| 30초 안전취소 타이머가 돈다 | 🟢 **아니다.** `startSafeCancelTimer()` 는 그보다 뒤(1146행)에 있어 도달하지 못한다 |

🔴 **그래서 «픽커는 잡는 게 아니라 읽으러 간다»는 표현은 틀렸다** (기사님 지적).
픽커도 목적은 좋은 콜을 잡는 것이고, 상세에 들어왔으면 결정해야 하는 것도,
그 결정에 시한이 있는 것도 인성과 같다 — **다른 것은 누르는 손가락이 기사님이라는 점뿐이다.**
그래서 여는 날에도 **인성과 다른 코드를 만들 필요가 없다.** 열 자리는 두 곳뿐이다:
`HijackService:602` 의 `supportsCatching` 조건과, 읽고 난 뒤 뒤로 가기.
