구현이 끝나면 이 줄을 지우고 구현 문서로 바꾼다.

## 0. 왜 필요한가 — 지금은 고리가 끊겨 있다

상차 통화에서 **화물 보호**(결박·그물망·호루·탑박스)를 고른다. 그런데 **그 선택이 옳았는지
확인되는 데가 없다.** 결박을 안 하고 갔더니 짐이 무너졌어도 아무 데도 안 남는다.

```
지금:   상차에서 보호를 고른다  →  (끊김)
제안:   상차에서 보호를 고른다  →  하차 도착에서 짐 상태를 남긴다  →  다음에 그 화주·그 짐에 반영
```

같은 고리가 상차지에도 있다. *"이 곳은 늘 30분 기다린다"* 를 아무도 안 세고 있어서,
매번 추정값으로 약속을 잡는다.

## 1. 설계 원칙 — 기사님은 1~2초에 누른다

🔴 **기본은 한 번 누르면 끝이다.** 지금 `📍 도착` 을 누르는 동작이 그대로 유지된다.
문제가 있을 때만 사유를 고른다. 사유를 고르게 만들면 **아무도 안 누르게 된다.**

- 정상이면 **버튼 한 번** — 지금과 완전히 같다
- 문제면 **버튼 한 번 + 칩 한 번** — 두 번
- 사유는 **복수 선택**한다 (대기 + 진입 곤란이 함께 나기도 한다)
- 자유 입력은 만들지 않는다 — 통계를 낼 수 없고, 통화 중에 타자를 칠 수 없다
  (메모는 이미 신고 폼에 있다. 거기 쓴다)
  · **예외: `기타`** — 목록이 아직 가설이라(§3-4), 목록 밖의 일이 어디에도 안 남으면
    목록을 고칠 근거가 사라진다. `기타` 를 고를 때만 메모 한 줄을 받는다

## 2. ① 스키마 — 어디에 사는가

### 2-1. 사유는 마일스톤에 붙는다

도착 사유는 **그 도착의 성질**이다. 별도 테이블을 만들지 않고 `order_milestones` 에 한 칸 늘린다.

```sql
ALTER TABLE order_milestones ADD COLUMN reasons TEXT;   -- JSON 배열, 정상이면 NULL
```

`tags`·`protections`·`afterworks` 가 이미 JSON 문자열로 사는 것과 같은 방식이다
(`stop_cargo_reports`). 새 규약을 만들지 않는다.

> ⚠️ `UNIQUE(orderId, milestone)` 이라 도착을 다시 찍으면 덮어쓴다 — 지금과 같다.
> 되돌리기(`undo-milestone`)도 그대로 작동한다.

### 2-2. 왜 `stop_cargo_reports` 가 아닌가

신고(`DECLARED`)·실측(`ACTUAL`)은 **짐이 무엇인가**를 다룬다. 도착 사유는 **도착이 어땠는가**다.
섞으면 "실측 신고를 안 했는데 사유만 있는" 행이 생기고, `cargoMismatchRatio` 같은 기존 계산이
빈 실측을 실측으로 오해한다.

### 2-3. 누적은 `places` 로 (2단계)

장소별 통계는 이미 있는 그릇을 쓴다 — `places.blacklistMemo` 에 `appendPlaceMemo` 로 붙는다
(2026-08-14 에 만들어 둔 자리다). 사유가 쌓이면 **다음에 그 장소 콜을 잡을 때 미리 보여준다.**

## 3. ② 값 — 무엇을 고를 수 있나, 근거는

### 3-1. **단계마다 관심사가 다르다** (기사님 확정 2026-08-19)

기사님: *"상차지 도착에서는 단위·수량·방법·보호·성질 이것들이 모두 없어야 하는 거 아닌가?
상차지 도착에 관한 것만 있으면 될 것 같은데. 이동 중에 문제(진입곤란·교통지연·사고)가
없었는지, 상차지에 문제(주소 다름·점심시간) 뭐 그런 것들이 있을 거라 생각했어."*

> 🗂️ **갈래로 묶는다** (기사님 2026-08-19): *"모든 종류의 트러블이 하나에 모여 있어서
> 찾기 너무 어렵고 추가하기도 좀 그렇다. 도로문제 / 상차지문제 / 기타 이런 식으로."*
> 한 줄에 쏟으면 찾는 데 시간이 걸리고 **늘릴 자리도 없다** — 목록이 가설이라 자랄 것을
> 전제로 짠다. 갈래 이름은 같은 너비로 세워 **시트마다 높이가 비슷하게** 한다.

| 단계 | 짐 폼 | 사유 (갈래) |
|---|---|---|
| **상차지 도착** | ❌ | **도로 문제** 교통 지연·사고·진입 곤란<br>**상차지 문제** 주소 다름·점심시간·문 잠김 |
| **상차 완료** | ✅ 단위·수량·방법·보호·성질 | **상차 문제** 화주 미준비·물건 없음·상차 중 파손 |
| **하차지 도착** | ❌ | **도로 문제** 교통 지연·사고·진입 곤란<br>**하차지 문제** 주소 다름·수령인 부재<br>**짐 상태** 짐 무너짐·결박 풀림·파손 발견 |
| **하차 완료** | ✅ 하차 방법·후작업 | **하차 문제** 검수 지연·인수 거부 |

(모든 단계의 **마지막 갈래가 `기타`** — 목록이 가설이므로 그것을 고칠 재료가 필요하다)

🔴 **짐 폼을 도착 단계에서 뺀 것은 정리 문제가 아니다.** 도착 시점에 수량을 적으면
그건 **추측인데 `ACTUAL`(실측)로 저장**된다 — 문을 열기도 전에 "실측"이 생기고,
그 값으로 `cargoMismatchRatio`(신고 vs 실측)가 계산되어 **가짜 불일치 경고**가 뜬다.
실측이 가능한 시점은 **실어 본 뒤**다.

🔴 **`짐 무너짐`·`결박 풀림`·`파손 발견` 은 하차지 *도착*에 있다** — 문을 열면 바로 보이고,
그때가 화주에게 알릴 시점이다. 하차 *완료* 는 이미 내린 뒤라 늦다.

⚠️ **`수량 다름` 은 사유가 아니다** (기사님 확정: *"3 실측폼"*). 실측 폼에 실제 수량을
적으면 `cargoMismatchRatio` 가 차이를 **스스로 센다** — 사유로 또 적으면 같은 사실이
두 곳에 살고 갈라진다 (규칙 ③).

### 3-4. 근거 — **아직 없다. 그래서 이 목록은 잠정이다** (기사님 2026-08-19)

기사님: *"이건 나도 아직 나가 본 적이 없고 유튜브에서 본 것이 전부야. 일단 이 정도로 시작해 보자."*

🔴 **이것을 숨기지 않는다.** 지금 목록은 실측이 아니라 **가설**이다. 이 레포에서 근거 없는 값이
색을 정했다가 사고가 난 적이 있다 (첫짐 40/90분 — 버그 대장 #3). 같은 실수를 반복하지 않으려면,
값이 가설이라는 것을 **코드와 화면 어디서도 감추지 않아야** 한다.

다만 도착 사유는 그 사고와 성격이 다르다 —
**이 값은 아무것도 판정하지 않는다.** 색을 정하지 않고, 콜을 거르지 않고, 약속을 바꾸지 않는다.
그냥 기사님이 겪은 일을 적어 두는 칸이다. 그래서 **가설로 시작해도 안전하다.**

> 🔴 **이 목록은 실측이 쌓이면 갈아엎는다.** 그것이 이 기능의 설계다:
> 한 달쯤 뒤 *"한 번도 안 쓴 사유"* 와 *"기타로 적힌 것"* 을 세어
> 목록을 기사님의 실제 운행에 맞춘다. 처음부터 맞출 방법이 없다.
>
> 그래서 **`기타` 를 반드시 둔다** — 목록에 없는 일이 생겼을 때 그것이 어디에도 안 남으면
> 목록을 고칠 근거 자체가 사라진다. `기타` 를 고르면 그때만 메모를 받는다.

⚠️ 그러므로 이 절은 **"값이 확정됐다"가 아니라 "가설로 시작하기로 확정했다"** 이다.
잠정 목록으로 코드를 시작하되, 첫 화면에 *"이 목록은 쓰면서 고칩니다"* 를 적는다.

## 4. ③ 시점 — 언제 읽고 언제 쓰나

| 시점 | 무엇 |
|---|---|
| **쓰기** | `📍 도착` 을 누를 때 한 번. 사유를 안 고르면 `NULL`(= 정상) |
| **고치기** | 도착 기록을 되돌리고(`undo-milestone`) 다시 찍으면 덮인다 — 지금과 같다 |
| **읽기 ①** | 그 콜의 카드 — 도착 배지 옆에 사유가 붙는다 |
| **읽기 ②** | **다음에 같은 장소 콜을 잡을 때** — 심사 화면에 *"이 곳: 화주 미준비 3회"* |
| **읽기 ③** | 운행일지 — 하루 끝에 사유별 집계 |

🔴 **읽기 ②가 이 기능의 값어치다.** 쓰기만 하고 안 읽으면 죽은 데이터다
(`appLocation` 이 그렇게 죽었다 — `pnpm audit:dead` 가 잡았다).
그래서 **읽는 쪽을 같이 만든다.**

## 5. ④ 화면 — 어디에 어떻게 보이나

### 5-1. 누를 때

```
[3단계] 상차지 도착

   📍 도착                    ← 이것만 누르면 끝 (지금과 같다)

   ┌ 문제 있었나요? (없으면 그냥 도착) ──────────┐
   │  화주 미준비   물건 없음   진입 곤란        │
   │  교통 지연     사고        기타             │
   └──────────────────────────────────────────┘
        ↑ `기타` 를 고르면 그때만 메모 한 줄을 받는다 —
          목록에 없는 일을 남길 데가 있어야 목록을 고칠 수 있다
```

- 칩은 **도착 버튼 아래**에 늘 펼쳐 둔다 — 접어 두면 아무도 안 연다
- 아무것도 안 고르고 `📍 도착` 을 누르면 **정상 도착**
- 칩을 고르면 도착 버튼이 `📍 도착 (문제 2건)` 으로 바뀐다

### 5-2. 남았을 때

```
상차지 도착  📍 10:37  ⚠️ 화주 미준비 · 진입 곤란
```

도착 배지 옆에 붙는다. 되돌아보기로 언제든 확인된다.

### 5-3. 다음에 그 장소를 만났을 때 ← **이게 핵심**

콜 심사 화면(결재 전)에 한 줄:

```
📍 이 곳 기록: 화주 미준비 3회 · 평균 대기 25분 (5회 방문)
```

기사님이 **잡을지 말지** 판단하는 재료가 된다. 색을 바꾸지는 않는다 —
판정은 요율·경로가 하는 일이고, 이건 참고다 (규칙 ①: 결정은 기사님이).

## 6. 함께 나오는 것 — 새 입력 0

사유와 별개로, **이미 저장되는 데이터**로 지금 만들 수 있는 것이 둘 있다.
사유 목록이 확정되기를 기다릴 필요가 없다.

### 6-1. 장소별 대기 시간

```
대기 = PICKED_UP(상차 완료) − ARRIVED_PICKUP(도착)
```

두 마일스톤이 이미 저장된다. 장소별로 누적하면 *"홈플러스 광주점 평균 대기 25분"* 이 나오고,
**다음에 그 장소 콜의 약속을 잡을 때 25분을 미리 넣을 수 있다.**
지금은 매번 추정 여유 30분을 쓰고 있다.

### 6-2. 카카오 예측 오차

`order_milestones.predictedAt` 에 도착 예상이 이미 함께 저장된다 (실측과 짝).

```
오차 = occurredAt − predictedAt
```

누적하면 *"이 시간대 이 구간은 카카오보다 15분 더 걸린다"* 가 나온다.
약속의 정확도가 통째로 올라간다.

⚠️ 둘 다 **읽는 코드가 없어서** 지금은 쌓이기만 하고 있다.
