# 도착 감지 재설계 — 정거장별 자동 마일스톤 + 도착전 통화 (⑤-4 계획)

> 기사님 발의 (2026-08-17): *"모든 포인트에 가까워지면 이벤트를 발생할 수 있고
> 거기에 따라 마일스톤에 이벤트를 호출할 수 있을 듯싶은데."*
> todo 의 **도착 감지 중복 발화(1초 4연발)** 수정과 한 덩어리다 — 같은 코드가 대상이다.

## 0. 지금 상태 (실측)

```
geoService.processDriverMovement [2] 도착 감지:
  · 마지막 하차지 1곳만 봄 (getLastDropoffCoord — 경로의 끝점)
  · 500m 이내면 매 GPS 틱마다 발화 → 4연발 + 매번 filter 재계산   ← 멈춤 조건이 없다
  · 마일스톤 기록 없음 · 소켓 알림 없음 (주석: "발송하도록 … 활용" — 미완)
  · auto-arrived: 관제웹이 듣는데 서버가 안 쏨 — 이 기능의 유령(죽은 문)
스키마는 이미 준비됨:
  · order_milestones(orderId, milestone, source) UNIQUE(orderId, milestone)
  · ARRIVED_PICKUP·ARRIVED_DROPOFF 가 콜마다 따로 기록 가능 · source 로 GPS/수동 구분
  · GPS 좌표에는 출처(real/simulated)가 실려 온다 (gpsBridge)
```

## 1. 어떻게 개발하나 — 3단계, 단계마다 게이트

### P1 — 감시 대상을 "다음 정거장 하나"로 + 멈춤 조건 (중복 발화 todo 흡수)

- 정거장 목록은 `planMergedStops` 의 순서(상차지들→하차지들) + 각 콜의 마일스톤으로
  **"아직 도착 안 찍힌 첫 정거장"** 을 구한다 — 그게 유일한 감시 대상
- 세션에 정거장별 발화 플래그(`orderId:stopType`) — **한 번 찍으면 멈춘다**
- GPS 점프로 판정된 틱은 도착 판단을 건너뛴다 (기존 점프 가드 뒤에 위치)
- 기존 `driverAction: UNLOADING` 자동 전환은 하차지 도착 1회에만 (4연발 filter 재계산 해소)

### P2 — 도착을 마일스톤으로 자동 기록 + 화면

- 조건 충족 시 해당 콜의 `ARRIVED_PICKUP`/`ARRIVED_DROPOFF` 를 **`source: 'GPS'`** 로 기록
  → 기존 `milestone-log` 발신 (진행 바 전진) + **`auto-arrived` 부활** (죽은 문 살림):
  관제웹이 해당 정거장 시트를 하이라이트
- 🔴 **`PICKED_UP`·`DELIVERED` 는 절대 자동 기록하지 않는다** — 상차·하차는 물리 행위,
  GPS 는 모른다. 자동은 `ARRIVED_*` 둘뿐
- 수동 [도착] 버튼은 그대로 — 자동은 보조다. 틀리면 되돌리기(undo)로 뒤집는다
- 통화 없이 도착한 경우(뒤 증거가 앞을 함축) 시트에 "통화 전" 배지를 강조

### P3 — 근접 예고 (도착전 통화 — 용어집 §10 의 코드 없는 유일한 업무 단계)

- 다음 정거장 3km 진입 시 1회, 새 이벤트 `next-stop-approaching` → 관제웹 알림
  + 그 정거장 전화번호 바로걸기 버튼 (*"도착지 상하차 준비시킴"*)

## 2. 어떤 값을 쓰나 (전부 이름 붙인 상수 — `geoService` 의 `GPS_ARRIVAL` 블록 한 곳)

| 값 | 제안 | 근거 | 비고 |
|---|---:|---|---|
| 도착 반경 | **500m** | 기존값 유지 — 주차 위치·GPS 오차 감안. 바꿀 실측 근거 없음 | |
| 정지 판정 속도 | **< 5 km/h** | 서행·주차 중. 통과 차량(30km/h+)과 구분 | 실 GPS 만 |
| 정지 유지 | **30초** | 즉발이면 통과·급정거에 오발. ⚠️ 신호 대기(60~120초)는 못 거른다 — 사이드이펙트 ① | 실 GPS 만 |
| 시뮬 출처 | 근접만으로 판정 | 시뮬은 15배속이라 "정지"가 없다 — 정지 조건 걸면 L4 검증 불가 | `source: simulated` |
| 근접 예고 거리 | **3km** | 시내 평균 ~35km/h 기준 약 5분 — 용어집 "도착 5분전 통화" | 정거장당 1회 |

값이 코드 상수인 이유: 판정 기준(색)이 아니라 **감지 파라미터**라 도로에서 다이얼 돌릴 성격이
아니다. 실측(L4)에서 오발이 보이면 그때 숫자를 고친다 — 근거 없이 미리 다이얼을 만들지 않는다.

## 3. 사이드이펙트 — 예상되는 것과 방어

| # | 위험 | 방어 |
|---|---|---|
| ① | **신호 대기 오발** — 정거장 500m 안 신호등에서 30초+ 정차 → 도착 오판 | 완전히는 못 막는다. `source: GPS` 표시 + undo 로 뒤집기 + 자동은 `ARRIVED_*` 만이라 **상태 피해가 없다** (상차·하차는 수동). L4 실측으로 빈도 확인 후 값 조정 |
| ② | **순서 이탈 방문** — 기사님이 경로 순서를 무시하고 합짐1을 먼저 감 | "다음 정거장만 감시"라 자동은 놓친다 — **수동 버튼이 항상 있다** (자동은 보조). 수동으로 찍으면 감시 대상이 다음으로 전진 |
| ③ | 시뮬 15배속 — 정지 조건 미충족 | 출처별 조건 분리 (§2) |
| ④ | GPS 점프 (시뮬 종료 70km 점프 실측 있음) | 점프 가드 뒤에서만 판단 — 점프 틱은 스킵 |
| ⑤ | 서버 재시작 → 발화 플래그 유실 → 알림 1회 재발 | 마일스톤은 `UNIQUE(orderId, milestone)` 라 기록은 안 겹침 — 알림 1회 중복은 무해로 수용 |
| ⑥ | 통화 단계 건너뜀 표시 — 자동 도착이 찍히면 6단계가 통화를 지나감 | 사실이 그러하므로 규칙("뒤 증거가 앞을 함축")대로 — 시트에 "통화 전" 배지 강조으로 보완 |
| ⑦ | `auto-arrived` 부활로 관제웹 동작 변화 | 기존 청취자(Dashboard:85)가 이미 있다 — 내용물만 규격 맞춰 보냄. audit:socket 이 검증 |
| ⑧ | 하차지끼리 가까운 합짐 (500m 내 두 정거장) | 감시가 "다음 하나"뿐이라 동시 오발 없음 — 순서대로 하나씩 찍힘 |

## 4. 검증 — L1~L4

| 층 | 무엇을 | 어떻게 |
|---|---|---|
| **L1 규칙** | · 감시는 다음 정거장 하나뿐이다<br>· 한 정거장당 발화 1회 (플래그)<br>· **GPS 가 기록하는 마일스톤은 `ARRIVED_*` 둘뿐** (`PICKED_UP`·`DELIVERED` 금지)<br>· 점프 틱은 도착 판단을 안 탄다 | `tests/rules/` 신규 — 변이 테스트로 확인 |
| **L2 값** | 감지 순수함수 — (거리, 속도, 유지시간, 출처) → 도착 여부 표 기반 | jest 단위 테스트 |
| **L3 시나리오** | `pnpm scenario` 에 GPS 재생 확장: 정거장 **통과**(고속) 미발화 · **정차** 발화 · 순서대로 전진 · 근접 예고 1회 | 실제 서버 재생 |
| **L4 실물** | 기사님 모의주행 — 합짐 2건(6정거장): 정거장마다 🏁 **1회씩**(4연발 0) · 통과 오발 0 · 근접 예고 각 1회 · 시트 하이라이트 | 서버 로그 전수 검산 (이번처럼) |

## 5. 하지 않는 것 (선 긋기)

- 상차완료·하차완료 자동 기록 — 절대 안 함 (물리 행위)
- ETA 기반 정밀 "5분 전" — 거리 기준(3km)으로 단순하게 시작. ETA 는 실측 후 필요하면
- 값 다이얼 화면 — 감지 파라미터를 설정 탭에 노출하지 않음 (실측 근거 생기면 재론)
