# 콜 시한과 합짐 예산 — 한 번 이동에 3콜을 싣는 계산

> 🔴 **이 문서는 계획이다. 코드에 아직 없다.** (2026-08-19 기사님 확정)
> 구현 진행은 [todo.md](../todo.md) 에서 관리한다. 여기 적힌 것을 "지금 동작"으로 읽지 말 것.

## 1. 시한 — 업계 퀵 룰

기사님이 교육 영상에서 확인하신 계산이다.

> *"내비상으로 1시간 10분 즉 110분 거리였다. 교육받은 대로라면 50%를 더해 165분 안에
> 갖다 주면 되는 것이다. 거기에 픽업 시간 20분을 더하면 185분이다.
> 즉 3시간 5분 안에 가져다 주면 된다."*

```
콜 시한 = 배송 주행 × 1.5 + 픽업 20분        (기산점: 콜을 받은 시각)
```

**멀수록 여유가 커진다.** 지금 코드는 거리와 무관하게 고정 30분을 주는데,
파주 가는 콜이나 관내 콜이나 같은 여유를 준다 — 그건 현실과 다르다.
200분 길에서 정체·휴게소·화장실이 30분으로 끝날 리 없다.

| 배송 주행 | 시한(픽업 제외) | 여유 |
|---|---|---|
| 20분 (관내) | 30분 | 10분 |
| 60분 | 90분 | 30분 |
| 110분 | 165분 | 55분 |
| 200분 | 300분 | 100분 |

### 🔴 수식은 **하나**로 간다

기사님: *"두 가지로 가면 수식이 복잡해진다. 위 퀵 룰로 계산하는 것이 좋을 것 같다."*

`max(30분, 주행×50%)` 같은 이중 수식을 제안했으나 **기각됐다.** 순수 50%로 간다.

⚠️ **대신 짧은 콜은 지금보다 빡빡해진다** (20분 콜: 여유 30분 → 10분).
관내·복귀 국면에서 이게 문제가 되는지는 실측으로 확인한다 —
그 국면은 원래 합짐 대상이 아니라 영향이 없을 수도 있다. **미확인 항목이다.**

### 픽업 시간은 **20분(상차) / 10분(하차)**

기사님: *"픽업 20분은 일반적인 값이라 하니 픽업 20분은 되돌리지 말고
20분(상차)/10분(하차)로 하자."*

- **모를 때 쓰는 일반값만 바꾼다** (`DWELL_UNKNOWN_PICKUP_MINUTES` 15 → **20**).
  하차는 10분 그대로
- 🔴 **짐을 아는 콜은 계속 계산한다** — 지게차 4분 · 수작업 27분 · 결박 +4분.
  20분 고정으로 되돌리면 지게차 콜에서 12분을 헛되이 버린다.
  우리 계산이 업계 관행보다 **이미 정확하다**

### 이 룰의 약점 — 접근 주행이 안 들어간다

기사님: *"단점은 상차지까지 가는 시간을 콜에 포함해 주지 않는다는 거다."*

시한은 **배송 주행(상차지→하차지)**만 본다. 현위치에서 상차지까지 가는 시간은
전부 내 부담이다. 그래서 **멀리 있는 상차지일수록 같은 콜이라도 손해**다.
→ 콜을 고를 때의 판단 재료이지, 시한을 늘릴 근거가 아니다.

## 2. 버퍼 — 시한에서 실제 소요를 뺀 것

```
버퍼 = 콜 시한 − (접근 주행 + 배송 주행 + 상차 정차)
```

이건 **예산**이다. 여기 서서 합짐을 기다리는 데 쓰거나, 우회에 쓴다.
가만히 있어도 1분에 1분씩 줄어든다.

> ⚠️ 이름은 아직 확정 전이다. 용어집의 `상차버퍼`·`경유버퍼`와 **다른 것**이라
> 구분되는 이름이 필요하다 (`시한 버퍼`? `납기 버퍼`?). — [용어집](용어집.md) 확정 대상

## 3. 합짐 판단 — 예산에서 비용을 뺀다

기사님의 계산을 그대로 옮긴다 (숫자 검산 완료).

> *"각각 콜의 화주 입장에서는 합짐을 하든 한 콜씩 하든 관심사가 아니다.
> 그냥 그 시간에 가져다 주면 되는 거다."*

🔴 **이 한 문장이 설계의 뿌리다.** 화주는 내 경로를 모른다. 그러니 **콜마다 시한이
독립적으로** 돌고, 합짐은 그 예산을 쓰는 행위다.

### 예시

**① 18:10 — 1번 콜을 잡는다** (경안동 → 금촌동 · 주행 120분 · 상차 8분)

```
시한  = 120 × 1.5 + 20                      = 200분   (21:30 까지)
실제  = 접근 28 + 주행 120 + 상차 8          = 156분
▶ 버퍼 44분
```

**② 18:20 — 10분 기다렸다. 버퍼는 34분으로 줄었다**

2번 콜이 뜬다 (초월읍 → 탄현면 · 주행 140분 · 상차 20분)
```
2번 시한 = 140 × 1.5 + 20 = 230분           (18:20 기준 → 22:10)
```

**③ 합짐 비용 = 경로가 늘어난 만큼 + 정거장 두 곳**

```
추가 주행 = |2콜 합친 경로| − |1콜 단독 경로|   = 10분
비용      = 10 + 상차 8 + 하차 8              = 26분
▶ 남는 버퍼 34 − 26 = 8분
```

기사님: *"이 값은 첫짐 때 저장한 값이 있으니 그것과 추가로 받아온 합짐 값과
비교하면 얻을 수 있을 거고."* — 맞다. **단독 경로를 저장해 두는 것이 전제다.**

**④ 8분으로 오토바이짐 하나를 더 싣는다**

> *"이때 출발하면서 오토바이짐 하나 더 가는 길에 가져가면 상하차 시간이
> 오토바이는 많이 줄어들 거니까 얼추 딱 맞을 것 같은데? 그래서 한 번 이동할 때
> 3콜을 합짐해서 갈 수 있다."*

오토바이짐은 상하차가 짧아 비용이 작다. 남은 8분에 들어간다.
**한 번 이동에 3콜** — 이게 [하루 7콜 운행 모델]의 실행 방법이다.

## 4. 🔴 예산은 **모든 활성 콜**이 동시에 만족해야 한다

위 예시는 1번 콜의 예산만 봤다. 실제로는 합짐을 붙이는 순간
**2번 콜의 하차도 2번의 시한 안**에 들어가야 한다.

```
합짐 가능  ⟺  모든 활성 콜 c 에 대해   도착 예상(c 하차) ≤ 접수(c) + 시한(c)
```

한 콜이라도 넘기면 그 합짐은 못 붙인다. 화면에는 **어느 콜이 막았는지**를 적는다 —
"안 된다"만 말하면 기사님이 판단할 수 없다 (규칙 ①).

## 5. 지금 코드와 무엇이 다른가

| | 지금 | 이 문서 |
|---|---|---|
| 여유 | 고정 30분 (`arrivalMarginMinutes`) | 배송 주행 × 50% |
| 기준 | 정거장마다 약속을 잡는다 | 콜마다 **시한 예산**이 돈다 |
| 합짐 판단 | 우회 비용으로 순위를 매긴다 | 예산에서 비용을 빼서 **되는지 안 되는지**를 본다 |
| 단독 경로 | 저장하지 않는다 | **저장한다** (추가 주행을 절대값 차이로 구하려면 필요) |

⚠️ **약속과 시한은 다른 값이다. 섞지 않는다.**
- **약속** — 화주와 통화로 합의한 도착 시각. 한 번 정하면 안 바뀐다 (규칙 ①)
- **시한** — 늦어도 되는 한계. 예산 계산에 쓰는 내부 값

| | 상태 |

| ② 값·근거 | ✅ 50% · 픽업 20/10분 — 업계 교육 영상 |
| ③ 시점 | ❌ 시한은 **콜을 받는 순간** 고정인가, 경로가 바뀌면 다시 세나 |
| ④ 화면 | ❌ 버퍼를 어디에 어떤 이름으로 · 합짐이 막혔을 때 어느 콜 때문인지 |

**③이 특히 중요하다.** 시한을 재계산하면 합짐을 붙일 때마다 예산이 늘어나
무한정 실을 수 있게 된다 — **시한은 콜을 받은 순간 고정**이어야 할 것으로 보이나,
기사님 확인이 필요하다.
