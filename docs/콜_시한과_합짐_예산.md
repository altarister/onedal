# 콜 시한과 합짐 예산 — 한 번 이동에 3콜을 싣는 계산

> 🔴 **이 문서는 계획이다. 코드에 아직 없다.** (2026-08-19 기사님 확정)
> 구현 진행은 [todo.md](../todo.md) 에서 관리한다. 여기 적힌 것을 "지금 동작"으로 읽지 말 것.

## 1. 시한 — 업계 퀵 룰

기사님이 교육 영상에서 확인하신 계산이다.

> *"내비상으로 1시간 10분 즉 110분 거리였다. 교육받은 대로라면 50%를 더해 165분 안에
> 갖다 주면 되는 것이다. 거기에 픽업 시간 20분을 더하면 185분이다.
> 즉 3시간 5분 안에 가져다 주면 된다."*

```
콜 시한 = 배송 주행 × 1.5 + 픽업 20분        (기산점: 콜을 받은 시각)
```

**멀수록 여유가 커진다.** 지금 코드는 거리와 무관하게 고정 30분을 주는데,
파주 가는 콜이나 관내 콜이나 같은 여유를 준다 — 그건 현실과 다르다.
200분 길에서 정체·휴게소·화장실이 30분으로 끝날 리 없다.

| 배송 주행 | 시한(픽업 제외) | 여유 |
|---|---|---|
| 20분 (관내) | 30분 | 10분 |
| 60분 | 90분 | 30분 |
| 110분 | 165분 | 55분 |
| 200분 | 300분 | 100분 |

### 🔴 수식은 **하나**로 간다

기사님: *"두 가지로 가면 수식이 복잡해진다. 위 퀵 룰로 계산하는 것이 좋을 것 같다."*

`max(30분, 주행×50%)` 같은 이중 수식을 제안했으나 **기각됐다.** 순수 50%로 간다.

⚠️ **대신 짧은 콜은 지금보다 빡빡해진다** (20분 콜: 여유 30분 → 10분).
관내·복귀 국면에서 이게 문제가 되는지는 실측으로 확인한다 —
그 국면은 원래 합짐 대상이 아니라 영향이 없을 수도 있다. **미확인 항목이다.**

### 픽업 시간은 **20분(상차) / 10분(하차)**

기사님: *"픽업 20분은 일반적인 값이라 하니 픽업 20분은 되돌리지 말고
20분(상차)/10분(하차)로 하자."*

- **모를 때 쓰는 일반값만 바꾼다** (`DWELL_UNKNOWN_PICKUP_MINUTES` 15 → **20**).
  하차는 10분 그대로
- 🔴 **짐을 아는 콜은 계속 계산한다** — 지게차 4분 · 수작업 27분 · 결박 +4분.
  20분 고정으로 되돌리면 지게차 콜에서 12분을 헛되이 버린다.
  우리 계산이 업계 관행보다 **이미 정확하다**

### 이 룰의 약점 — 접근 주행이 안 들어간다

기사님: *"단점은 상차지까지 가는 시간을 콜에 포함해 주지 않는다는 거다."*

시한은 **배송 주행(상차지→하차지)**만 본다. 현위치에서 상차지까지 가는 시간은
전부 내 부담이다. 그래서 **멀리 있는 상차지일수록 같은 콜이라도 손해**다.
→ 콜을 고를 때의 판단 재료이지, 시한을 늘릴 근거가 아니다.

## 2. 시한은 **임시**다 — 통화로만 늘어난다 (기사님 확정 2026-08-19)

기사님: *"시한은 콜 받는 순간 **임시로** 정해진다. 내가 전화 통화를 통해서 늘릴 수 있다."*

| 언제 | 시한 |
|---|---|
| 콜을 받는 순간 | `주행 × 1.5 + 픽업 20분` — **임시**. 업계 관행으로 채운 값 |
| 통화한 뒤 | 화주가 말한 시각이 **이긴다.** 늘어날 수도 줄어들 수도 있다 |
| 경로가 바뀌었을 때 | 🔴 **다시 세지 않는다** |

🔴 **자동으로 늘어나는 길은 없다.** 합짐을 붙일 때마다 시한을 다시 계산하면
예산이 계속 늘어나 **무한정 실을 수 있게 된다.** 늘리려면 통화라는 실제 행위가 있어야 한다
(규칙 ① — 콜의 주인은 기사님이고, 시간은 통화에서 확보된다).

⚠️ 그래서 화면은 **임시인지 통화로 정한 것인지**를 구분해 보여야 한다.
약속에 `~` 를 붙이는 것과 같은 이치다.

## 3. 버퍼 — 시한에서 실제 소요를 뺀 것

```
버퍼 = 콜 시한 − (접근 주행 + 배송 주행 + 상차 정차)
```

이건 **예산**이다. 여기 서서 합짐을 기다리는 데 쓰거나, 우회에 쓴다.
가만히 있어도 1분에 1분씩 줄어든다.

### 🔴 첫짐을 잡는 순간 **그날 노선의 예산이 정해진다**

기사님: *"첫 콜을 잡으면 그날 노선의 합짐의 여유가 도출될 수 있다."*

첫짐을 KEEP 하면 버퍼가 나온다. 그게 **그 노선에서 합짐에 쓸 수 있는 전부**다.
44분이면 넉넉하고, 12분이면 사실상 첫짐 단독 운행이다.
→ **KEEP 직후 화면에 즉시 보여야 한다.** 합짐을 기다릴지 바로 출발할지가 그 숫자로 갈린다.

> ⚠️ 이름은 아직 확정 전이다. 용어집의 `상차버퍼`·`경유버퍼`와 **다른 것**이라
> 구분되는 이름이 필요하다 (`시한 버퍼`? `납기 버퍼`?). — [용어집](용어집.md) 확정 대상

## 4. 합짐 판단 — 예산에서 비용을 뺀다

> *"각각 콜의 화주 입장에서는 합짐을 하든 한 콜씩 하든 관심사가 아니다.
> 그냥 그 시간에 가져다 주면 되는 거다."*

🔴 **이 한 문장이 설계의 뿌리다.** 화주는 내 경로를 모른다. 그러니 **콜마다 시한이
독립적으로** 돌고, 합짐은 그 예산을 쓰는 행위다.

### 4-1. 🔴 비용은 **그 콜의 하차 전에 생기는 것만** 센다

기사님 정정(2026-08-19): *"아까 예시는 하차지가 첫콜 경로 밖에 있으므로
하차 시간 8분을 뺄 수 있다."*

합짐 순서가 이렇게 될 때 —

```
현위치 → 경안동(1상차) → 초월읍(2상차) → 금촌동(1하차) → 탄현면(2하차)
                          └─ 여기까지가 1번 콜의 지연 ─┘   └ 1번과 무관 ┘
```

**2번 콜의 하차(탄현면)는 1번 하차 뒤에 있다.** 1번 짐은 이미 내렸으므로
1번 콜의 도착 시각에 아무 영향이 없다. 그러니 1번 예산에서 빼면 안 된다.

```
콜 c 의 합짐 비용 = (c 의 하차 전에 새로 생기는 주행) + (c 의 하차 전에 끼는 정거장 정차)
```

⚠️ 순서가 바뀌면 값도 바뀐다 — 2번 하차가 금촌동보다 **앞**에 오면 그때는 8분을 뺀다.
**경로 순서를 모르면 비용을 셀 수 없다.**

### 4-2. 시나리오 A — 지게차 (붙는다)

**① 18:10 — 1번 콜을 잡는다** (경안동 → 금촌동 · 배송 주행 120분 · 상차 8분)

```
시한  = 120 × 1.5 + 20                      = 200분   (21:30 까지)
실제  = 접근 28 + 주행 120 + 상차 8          = 156분
▶ 버퍼 44분   ← 이것이 그날 이 노선의 합짐 예산이다
```

**② 18:20 — 10분 기다렸다. 버퍼는 34분으로 줄었다**

2번 콜이 뜬다 (초월읍 → 탄현면 · 배송 주행 140분 · 상차 8분)
```
2번 시한 = 140 × 1.5 + 20 = 230분           (18:20 기준 → 22:10)
```

**③ 합짐 비용 — 1번 하차 전에 생기는 것만**

```
추가 주행 = |2콜 합친 경로| − |1콜 단독 경로|   = 10분
비용      = 10 + 2번 상차 8                    = 18분
             (2번 하차 8분은 1번 하차 뒤 → 안 센다)
▶ 남는 버퍼 34 − 18 = 16분
```

기사님: *"이 값은 첫짐 때 저장한 값이 있으니 그것과 추가로 받아온 합짐 값과
비교하면 얻을 수 있을 거고."* — 맞다. **단독 경로를 저장해 두는 것이 전제다.**

**④ 남은 16분으로 오토바이짐 하나를 더 싣는다**

> *"이때 출발하면서 오토바이짐 하나 더 가는 길에 가져가면 상하차 시간이
> 오토바이는 많이 줄어들 거니까 얼추 딱 맞을 것 같은데? 그래서 한 번 이동할 때
> 3콜을 합짐해서 갈 수 있다."*

오토바이짐은 상하차가 짧아 비용이 작다. **한 번 이동에 3콜** —
이게 [하루 7콜 운행 모델]의 실행 방법이다.

### 4-3. 시나리오 B — 수작업 (못 붙인다. 잡았으면 뺀다)

기사님: *"예시에서는 10분을 기다릴 수 있었고, 만약 **상하차가 20분씩** 걸린다면
잡은 콜을 뺐어야 한다."*

같은 두 콜인데 **상차가 수작업이라 20분씩** 걸리는 경우다.

```
1번  시한 200 − 실제(28 + 120 + 20) 168      ▶ 버퍼 32분   ← 시작부터 12분 적다
18:20 (10분 경과)                            ▶ 버퍼 22분
합짐 비용 = 추가 주행 10 + 2번 상차 20        = 30분
▶ 22 − 30 = −8분   🔴 못 붙인다
```

**이미 KEEP 했다면 방출한다.** 억지로 끌고 가면 두 화주 모두에게 늦는다.

> 🔴 **상차 방법이 예산을 지배한다.** 지게차 4분과 수작업 27분은 23분 차이인데,
> 그게 정거장마다 붙는다. 위 두 시나리오는 **주행도 거리도 똑같고 상차 방법만 다른데**
> 하나는 3콜을 싣고 하나는 1콜도 못 붙인다.
> → 그래서 통화에서 상차 방법을 확인하는 것이 이 시스템에서 가장 값진 1분이다.

### 4-4. 🔴 예산은 **모든 활성 콜**이 동시에 만족해야 한다

위 계산은 1번 콜의 예산만 봤다. 실제로는 합짐을 붙이는 순간
**2번 콜의 하차도 2번의 시한 안**에 들어가야 한다.

```
합짐 가능  ⟺  모든 활성 콜 c 에 대해   도착 예상(c 하차) ≤ 접수(c) + 시한(c)
```

한 콜이라도 넘기면 그 합짐은 못 붙인다. 화면에는 **어느 콜이 막았는지**를 적는다 —
"안 된다"만 말하면 기사님이 판단할 수 없다 (규칙 ①).

## 5. 이 계산이 무엇을 위한 것인가 — **시급** (기사님 2026-08-19)

> *"오전에 4시간 일하고 점심 1시간 하고 복귀 4시간 일하면 총 하루 9시간 정도 일할 수
> 있겠다. 2콜에 이동해야 한다면 파주 갔다가 안산 갔다가 복귀콜을 잡아야겠다.
> 그럼 **시급을 산출 가능**하겠다. 이렇게 하려면 **첫짐 잡는 것이 중요**하겠고
> **합짐 잡는 것이 아주 중요**하겠다."*

🔴 **분모가 생겼다.** 하루 9시간이라는 고정된 그릇이 있으면, 그 안에 무엇을 담느냐로
좋고 나쁨을 잴 수 있다. 지금 판정은 콜 하나를 놓고 *"이 콜이 돈이 되나"* 를 묻는데,
시급은 *"이 시간에 얼마를 버나"* 를 묻는다. **후자가 기사님이 실제로 최적화하는 것이다.**

### 하루의 모양 — **6콜 · 3콜씩 왕복** (기사님 확정)

기사님: *"판교 갈 때 2콜, 안산 갈 때 2콜, 복귀할 때 2콜 이렇게 6콜을 해야 한다는
이야기야. **가장 좋은 것은 3콜씩 왕복**하는 것이 가장 좋다. 그래야 운행거리도 짧아지고
효율이 좋아진다."*

| | 시간 | |
|---|---|---|
| 왕복 ① — 광주 → 판교 | 3시간 | 첫짐 + 합짐 2 |
| 점심 | 1시간 | |
| 왕복 ② — 판교 → 광주(복귀) | 4시간 | 복귀 첫짐 + 합짐 2 |
| | **9시간 · 6콜 · 이동 2회** | |

🔴 **콜 수가 같아도 이동 횟수가 적을수록 좋다.**

```
3회 이동 (2+2+2)  판교 ▸ 안산 ▸ 광주   — 구간마다 빈 주행이 생긴다
2회 이동 (3+3)    판교 ▸ 광주          — 왕복이라 빈 주행이 없다   ✅
```

같은 6콜인데 **운행거리가 다르다.** 시급의 분모는 시간이지만, 거리는 기름값으로
순이익을 깎는다. → 판정은 *"몇 콜이냐"* 가 아니라 **"몇 번 움직여 몇 콜이냐"** 를 봐야 한다.

### 🔴 대기 시간을 **확보**하는 것이 전략이다

기사님: *"이동하면서 콜을 잡는 것이 아닌 **대기 시간을 최대한 확보**해야
먼거리 합짐을 잡는 데 유리하다."*

이동 중에 잡는 합짐은 **이미 경로가 정해진 뒤**라 고를 수 있는 것이 좁다 —
지나가는 길 옆에 뜬 콜만 된다. 반면 출발 전에 서서 기다리면 **아직 경로가 안 굳어서**
먼거리·장거리 합짐까지 후보에 들어온다. 3콜 왕복이 되려면 이쪽이어야 한다.

→ §3 의 버퍼는 그래서 **아껴 쓰는 예산**이다. 일찍 출발해 버리면 그 예산은
   길 위에서 소진되고, 남은 선택지는 경로 주변으로 좁아진다.
   **화면은 "지금 출발"이 아니라 "언제까지 기다릴 수 있다"를 크게 말해야 한다**
   (지금 카운트다운이 하는 일이 맞다).

### 왜 합짐이 "아주 중요"한가 — 분모가 거의 안 늘어난다

같은 3시간짜리 노선에 몇 콜을 실었느냐로 시급이 갈린다.

| | 매출 | 시급 |
|---|---|---|
| 1콜 (단독) | 10만원 | **3.3만원** |
| 2콜 (합짐 1) | 17만원 | **5.7만원** |
| 3콜 (합짐 2) | 22만원 | **7.3만원** |

합짐 운임은 첫짐보다 작다 — 우회분만 받는 셈이다. 그런데 **시간이 거의 안 늘어난다**
(§4-2에서 비용 18분). 분자만 커지고 분모는 그대로니 시급이 뛴다.
§3의 버퍼는 결국 **시급을 올릴 수 있는 여지**를 분 단위로 잰 것이다.

### 왜 첫짐이 "중요"한가 — 그날 노선과 예산을 둘 다 정한다

첫짐을 잡는 순간 **그날 그 노선의 방향**이 정해지고(파주행), **합짐 예산**도 정해진다(§3).
잘못 고르면 3시간을 1콜로 보내게 된다 — 되돌릴 방법이 없다.

### 복귀는 비용인가 매출인가

안산까지 갔으면 돌아와야 한다. 그 2시간은 **아무것도 안 해도 흘러간다.**

```
복귀 빈 차   매출 44만 / 9시간 = 시급 4.9만원   ← 2시간이 순수 비용
복귀콜 12만  매출 56만 / 9시간 = 시급 6.2만원   ← 같은 9시간, 27% 상승
```

→ **복귀콜은 운임이 낮아도 시급에는 크게 기여한다.** 어차피 지나갈 길이라 분모가 안 늘기 때문이다.
지금 판정이 복귀콜을 요율로만 재면 이 사실을 놓친다.

### 🔴 그래서 합짐 판정의 최종 기준은 시급일 수 있다

```
붙인다  ⟺  (매출 + 합짐 운임) / (소요 + 합짐 비용)  >  매출 / 소요
```

§4 의 예산은 **"물리적으로 가능한가"** 를 묻고, 이 식은 **"붙이는 게 이득인가"** 를 묻는다.
둘 다 필요하다 — 가능해도 시급이 떨어지는 합짐이 있다(운임은 작은데 우회는 큰 콜).

> ⚠️ 이건 아직 **방향**이다. 규칙 ⑤-4 의 넷을 따로 채워야 코드로 간다.
> 숫자(3시간·10만원·22만원)도 그림을 그리기 위한 가정이지 실측이 아니다.
> 🔴 **실측이 쌓이면 이 표를 실제 값으로 바꾼다** — 그때까지 판정 근거로 쓰지 않는다.

## 6. 목표 매출에서 콜당 하한가를 역산한다 (기사님 2026-08-19)

기사님: *"하루 매출 25~30(만원)을 목표로 하고 있기 때문에 거기에 따른
**콜당 하한가를 정할 수 있을 것 같다.**"*

지금 `minFare`(첫짐 절대하한가)는 기사님이 **감으로 넣는 값**이다
(`OrderEvaluator.ts:310` — `STANDBY` 국면에서만 본다). 목표 매출이 있으면 **역산**할 수 있다.

```
콜당 평균 하한 = 하루 목표 ÷ 6콜
```

| 하루 목표 | 콜당 평균 | 노선당(3콜) |
|---|---|---|
| 25만원 | **41,700원** | 12.5만원 |
| 30만원 | **50,000원** | 15만원 |

### 🔴 하한가는 **하나가 아니다** — 첫짐과 합짐은 다른 값이다

평균만으로 자르면 안 된다. 첫짐이 노선을 정하고 합짐은 우회분만 받으므로,
같은 4만원짜리라도 **첫짐이면 부족하고 합짐이면 충분**하다.

배분을 `5 : 3 : 2` 로 잡으면 (노선 15만원 기준)

```
첫짐  7.5만원   ← 이 값이 그날 노선을 정한다. 낮으면 하루가 낮아진다
합짐  4.5만원
합짐  3.0만원   ← 합짐 하한. 우회 비용만 넘으면 이득이다 (§5)
```

| 하루 목표 | 첫짐 하한 | 합짐 하한 |
|---|---|---|
| 25만원 | 62,500원 | 25,000원 |
| 30만원 | **75,000원** | **30,000원** |

⚠️ **배분(5:3:2)은 아직 가정이다.** 실측이 쌓이면 실제 비율로 바꾼다.
그전까지는 이 표를 판정에 쓰지 않는다.

### 지금 코드와의 차이

| | 지금 | 이 문서 |
|---|---|---|
| 하한가 | `minFare` **하나** — 첫짐에만, 감으로 | 첫짐·합짐 **둘**, 목표 매출에서 역산 |
| 합짐 하한 | **없다** (합짐은 하한가를 안 본다) | 우회 비용 기준 하한 |
| 근거 | 없음 | 하루 목표 ÷ 6콜 ÷ 배분 |

🔴 **합짐에 하한가가 없는 것은 지금은 옳다** — 규칙 ⑤-1(*"돈은 앱이 이미 걸렀다"*).
여기에 하한을 새로 두려면 **그것이 시급을 올리는지**부터 확인해야 한다.
운임이 낮아도 우회가 거의 없으면 붙이는 게 이득이다 (§5 복귀콜과 같은 논리).

## 7. 콜할인율 — 기다리면서 **눈높이를 낮춘다** (기사님 2026-08-19)

기사님: *"이것 때문에 km당 단가를 필터에 넣은 이유이긴 하다. 처음에는 **시세로**
합짐을 잡다가 **5분 지나면 10%씩 줄여나가서** 단가 좋은 합짐을 잡으려는 거다."*

🔴 **버퍼를 쓰는 방법이 이것이다.** §5 에서 *"대기 시간을 확보해야 한다"* 고 했는데,
그 대기 시간에 **무엇을 하느냐**의 답이다 — 처음엔 좋은 콜만 기다리고,
시간이 갈수록 눈을 낮춰 **결국 빈손으로 출발하지 않는다.**

### 🔴 7-0. **첫짐에는 시간 하강이 없다** (기사님 확정 2026-08-19)

기사님: *"**첫짐은 오래 기다리더라도 비싼 것을 잡을 거고 자동으로 할인율이 높아지지
않을 거야.** 그 선택은 내가 설정에서 바꿀 거야."*

| | 할인율 | 왜 |
|---|---|---|
| **첫짐** (`first`) | **고정** — 기사님이 설정에서 직접 | 지금 코드 그대로 |
| **합짐** (`merge`) | **시간 하강** — 시세에서 시작해 5분마다 | 새로 만든다 |

⚠️ **이 비대칭은 결정이다. "첫짐에도 넣어야 하는 것 아닌가"로 고치지 말 것.**
근거는 **못 잡았을 때 잃는 것이 다르다**는 데 있다:

```
첫짐을 못 잡으면  →  아무것도 안 잃는다. 기다리면 또 온다
                     대신 잘못 잡으면 그날 노선과 예산이 통째로 정해진다 (§5)

합짐을 못 잡으면  →  버퍼가 그냥 사라진다. 출발하면 그 시간은 영영 없다
                     그래서 눈을 낮춰서라도 잡는 것이 이득이다
```

버퍼는 **첫짐을 잡은 뒤에만 존재한다**(§3). 그러니 "시간이 지나면 손해"라는 압박도
합짐에만 있다. 첫짐 앞에서는 시계가 안 돈다.

### 지금 코드는 이렇게 안 되어 있다

`discountPct` 는 **국면별 고정값**이다 (`shared/src/phases.ts:168`).

```
first 10%  ·  merge 10%  ·  drive 10%  ·  local 20%  ·  home 10%
         ↑ 이건 그대로 둔다        ↑ 여기에 시간 하강을 넣는다
```

국면에 들어갈 때 한 번 정해지고 **시간이 지나도 안 움직인다.**
로그의 `🧭 [국면 설정] first → merge · … · 할인 10%` 가 그 1회 적용이다.
기사님이 말씀하신 *"시세로 시작해서 5분마다"* 는 **시작점도 속도도 아직 없다.**

⚠️ `merge` 의 시작점도 지금은 10% 다. *"처음에는 **시세로**"* 라면 **0% 에서 시작**해야 한다 —
시작점을 바꿀지, 아니면 설정값을 시작점으로 삼고 거기서 내려갈지 정해야 한다.

❓ **`drive`·`local`·`home` 은 어떻게 하나** — 미정.
운행 중(`drive`)에도 합짐을 잡지만, §5 에서 *"이동하면서 잡는 것보다 대기가 유리"* 라 하셨다.
길 위에서는 버퍼가 이미 주행에 쓰이고 있어 **기다림의 성격이 다르다.**

### 🔴 바닥이 없으면 자원봉사가 된다

5분마다 10%p 를 그대로 적용하면 —

| 경과 | 할인 | 시세 대비 | 1t (5,000원/km 기준) |
|---|---|---|---|
| 0분 | 0% | 100% | 5,000원/km |
| 10분 | 20% | 80% | 4,000원/km |
| 20분 | 40% | 60% | 3,000원/km |
| 30분 | 60% | 40% | 2,000원/km |
| 40분 | 80% | **20%** | **1,000원/km** |

버퍼 44분을 다 쓰면 시세의 20% 짜리 콜을 잡게 된다. **그건 콜이 아니라 자원봉사다.**
→ **바닥이 반드시 있어야 한다.** 두 가지로 막을 수 있다:

1. **최대 할인율** — 예: 30% 까지만 (15분이면 바닥)
2. **합짐 하한가** — §6 의 3만원. 할인해도 이 아래로는 안 내려간다

⚠️ 둘 다 두면 먼저 걸리는 쪽이 이긴다. **어느 쪽을 원천으로 할지 정해야 한다** —
같은 바닥을 두 곳에서 정하면 갈라진다 (규칙 ③).

### 멈추는 조건도 필요하다

```
버퍼가 다하면  →  더 못 기다린다. 출발한다 (할인도 멈춘다)
합짐이 붙으면  →  경로가 바뀌었다. 할인율을 되돌리나, 이어가나?
```

두 번째가 특히 애매하다. 합짐 하나를 붙이고 나면 **남은 버퍼로 또 기다릴 수 있는데**,
그때 할인율을 0%로 되돌리면 좋은 콜을 다시 기다리게 되고,
이어가면 이미 낮아진 눈으로 두 번째 합짐을 잡는다.
**§5 의 "3콜 왕복" 목표를 생각하면 되돌리는 쪽이 맞아 보이나, 기사님 확인이 필요하다.**

### 이 값은 **앱까지 내려가야 한다**

콜할인율은 차종별 하한 단가표(`ratePerKm`)를 만들고, 그 표로 **앱이 콜을 거른다**
(`filterManager.ts:58` — *"차종별 하한 단가표는 콜할인율에서만 파생된다"*).
그러니 5분마다 값이 바뀌면 **그때마다 앱에 새 필터가 내려가야 한다.**

→ 피기백 구조가 이미 있어 경로는 문제없다. 다만 **5분마다 필터가 바뀌는 것을
앱이 견디는지** 확인해야 한다 (지금은 국면이 바뀔 때만 내려간다).

| | 지금 | 이 문서 |
