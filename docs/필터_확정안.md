## ① 스키마

### ①-A. 국면 옵션 — blob 해체, 표 패턴으로

지금: `user_filters.phase_settings` **TEXT JSON 한 칸** (스키마·라벨·근거 없음).
확정: **`user_filter_phases` 테이블 신설** — 행 = (사용자, 국면), 칸 = 옵션.

```sql
CREATE TABLE user_filter_phases (
    user_id  TEXT NOT NULL,
    phase    TEXT NOT NULL CHECK(phase IN ('first','merge','drive','local','home')),
    -- ↓ 칸 목록은 shared 의 FILTER_FIELDS 표가 유일한 원천 (JUDGMENT_FIELDS 와 같은 문법)
    destination_city   TEXT,
    pickup_radius_km   REAL,      -- 이식 단계에선 현행 그대로 (축 개편은 구현 4에서)
    pickup_reach_min   INTEGER,   -- 🆕 시간 축: 도달 한계 덮어쓰기(분). NULL = 자동(상차 시계) — 구현 4에서 표에 추가
    detour_allow_km    REAL,
    dropoff_radius_km  REAL,
    discount_pct       INTEGER,
    PRIMARY KEY (user_id, phase)
);
```

⚠️ 이식(구현 2)은 **현행 5칸을 그대로** 옮긴다 — 구조를 바꾸는 일과 축(km→분)을 바꾸는
일을 같이 하지 않는다. `pickup_reach_min` 은 구현 4에서 표에 한 줄 얹는다.

- `FILTER_FIELDS` 표(shared 신설): 칸 하나 = DB 컬럼 + 폼 라벨 + 단위 + 범위 + **근거(why)**
  + **국면별 노출 모드**(기존 `PHASE_FIELDS` 의 input/override/auto/hidden 을 표에 통합)
- ~~`pickup_radius_km`(입력)~~ → `pickup_reach_min`(덮어쓰기) — **반경은 이제 입력이 아니라
  파생값이다**: 서버가 "앞 일 포함, 도달 한계 안에 닿는 거리"를 계산해 km 로 피기백
- 기존 phase_settings 의 **값은 그대로 이식**한다 — 구조를 바꾸는 일과 값을 바꾸는 일을
  같이 하지 않는다 (판정 전환 때와 같은 원칙)

### ①-B. 성과 기록 — 신설 (정의서 4장)

```sql
CREATE TABLE filter_day_results (
    user_id   TEXT NOT NULL,

    settings  TEXT NOT NULL,          -- 그날 국면 설정 스냅샷 (JSON — 기록용이라 blob 허용)
```

"이 설정이 얼마를 벌었나"의 재료 — 콜할인율을 감이 아니라 성과로 정하게 하는 기반.

**🔴 앱 호환 — `minFare` 는 칸이 죽어도 규격에선 못 죽는다** (앱 grep 실측):

- 인성 파서: 단가식(`ratePerKm`)이 주 판정, **`minFare` 는 구서버 폴백** — 키가 사라지면
  폴백까지 사라져 fail-open 위험
- 화물24 파서: **`minFare`/`maxFare` 가 아직 주 판정** — 단가식 미적용
- 방안 (순서가 생명):
  ① 서버는 피기백 `minFare` 를 계속 채우되 **파생값으로 강등** (당분간 = 현행 값)
  ② 앱 릴리스: 화물24 파서에 단가식 적용 (인성과 같은 모양)
  ③ 그 뒤에야 `minFare` 를 보수 폴백값으로 고정 — **DTO 필드 자체는 남긴다**
- DB 칸 삭제(3단계)와 앱 트랙은 **독립** — 서버가 파생해서 내려보내므로 앱 업데이트를 기다릴 필요 없음

삭제 공통 원칙: 화면 → 코드 참조 → DB 칸 순서로 걷어내고, DROP 은 **손으로, 의도적으로**
(부팅 경로 금지). 실서버 `data.db` 는 배포 때 같은 손 순서.

### 실서버 data.db — 배포 때 손 순서

> 🔴 **대체됨 (2026-08-22 기사님 확정)** — 실서버도 테스트 용도라 이식 없이
> **백업 → 삭제 → 새로 시작**으로 결정. 아래 이식 SQL 은 "8월 중간 상태에서
> 배포할 때" 용이었고 이제 안 쓴다. 현행 배포 절차는 [todo.md](../todo.md) 🚀 절.

🔴 새 코드에는 blob→행 이식 코드가 **없다** (병행 단계에서 local 은 이식 완료 후 지웠다).
data.db 는 배포 시점에 아직 blob 만 있으므로 **이식 SQL 을 손으로 돌려야** 기사님 라이브
설정이 산다. 순서가 생명:

```
1. 배포 (새 코드 부팅 — user_filter_phases 테이블이 생긴다. 이 사이 로그인하면
   표 기본값이 시드되지만, 2번의 INSERT OR REPLACE 가 blob 값으로 덮으므로 안전)
2. 이식:
   INSERT OR REPLACE INTO user_filter_phases
       (user_id, phase, destination_city, pickup_radius_km, detour_allow_km, dropoff_radius_km, discount_pct)
   SELECT f.user_id, j.key,
          COALESCE(json_extract(j.value, '$.destinationCity'), ''),
          json_extract(j.value, '$.pickupRadiusKm'),
          json_extract(j.value, '$.detourAllowKm'),
          json_extract(j.value, '$.dropoffRadiusKm'),
          json_extract(j.value, '$.discountPct')
   FROM user_filters f, json_each(f.phase_settings) j
   WHERE f.phase_settings IS NOT NULL AND f.phase_settings != '';
3. 값 확인 (SELECT * FROM user_filter_phases) 후 서버 재시작 — 세션이 행을 읽는다
4. DROP 8칸 (phase_settings · destination_city · destination_radius_km ·
   pickup_radius_km · detour_radius_km · call_discount_pct · max_discount_percent · load_state)
5. 전수조사(2026-08-21) 죽은 칸 10개도 같은 손으로 DROP — local 은 완료:
   user_filters.is_shared_mode · user_filters.driver_action · user_settings.car_type ·
   orders.payerName · orders.payerPhone · orders.settlementMemo · orders.createdAt ·
   orderStops.stopOrder · orderStops.requestedTime · places.mileage
   (지운 이유와 "기능 만들 때 다시 판다"는 db.ts 의 🪦 주석에 있다)
```

## ② 값 — 기본값과 근거

| 값 | 초안 | 근거 |
|---|---|---|
| 국면 옵션 전체 | **현 phase_settings 값 그대로 이식** | 구조와 값을 같이 바꾸지 않는다 |

| 도달 시간→km 근사 계수 | ❓ **잠정 1.5분/km (직선거리 기준)** — dryRun 로그로만 검증 | 앱 1차 필터는 오프라인이라 근사 필수. **실측 캘리브레이션 절차**: 서버가 실제 콜의 (직선거리, 카카오 분)을 `reach_samples` 장부에 모아 역산 (`pnpm reach` — 로그는 3일 순환이라 장부로 옮김, 2026-08-21). ⚠️ 첫날 표본 8건이 이미 **단일 계수가 틀린 모델**임을 보였다 — 3.8km 는 5.0분/km, 31.4km 는 1.2분/km. 후보는 1차식 `소요 ≈ 기본분 + 분/km × 직선km` (첫 적합 10.4분 + 0.89분/km, 산포 ±3.8분). **확정은 표본 20건+ 뒤 기사님이** |

## ④ 화면 — 어디에 어떤 이름으로

- **🔍 필터 모달**: 상차 반경 칸 → `도달 30분 안 (반경 12km 자동)` + 덮어쓰기 입력.
  헤더에 **취소 카운터** `인성 3/10 · 24시 1/10` 상시 (정의서 2장 — 소진 속도가 조임 신호)
- **요율/필터 탭**: 노선 기본 4칸·절대가 2칸·평면 콜할인율 제거 → 남는 것: 차종별 단가표 ·
  수수료율 · 블랙리스트 (금액 축의 원천만)
- **요약줄 → 모니터**: 지금 앱에 내려가 있는 필터 전체(파생 포함 — 도달 반경·키워드 수·
  단가표·국면)를 펼쳐 보는 시트 (정의서 6장 "무엇이 실제로 돌고 있는가")
- **성과**: 위치 후보 — 운행일지(logbook)에 "설정과 성과" 절 (관제앱은 업무 단위 원칙과 정합)

## 구현 순서

1. **판정 기준 시간 4칸 화면 반영 수리** (빨간불 먼저 — 탭 값≠기본값일 때 화면 파생이 따라오는지)
2. `FILTER_FIELDS` 표 + `user_filter_phases` 신설 + 값 이식 + blob·폴백 제거 (기존 DB 부팅 스모크)
3. 화면 삭제(요율 탭 6칸) + DB 손 DROP (삭제 리스트 1~7)
4. 시간 축 — 도달 한계 파생 + 피기백 + 모달 개편 (계수는 dryRun 로그로 캘리브레이션)
5. 취소 카운터 표시
6. 성과 기록 테이블 + 자정 집계
7. 모니터 시트
- (별도 앱 트랙) 화물24 단가식 → `minFare` 폴백 강등

합격 기준: 문제지 4콜이 **필터를 통과**하고(16-4 전반부 — gosuExam 에 필터 통과 검사 추가),
