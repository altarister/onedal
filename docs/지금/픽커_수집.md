🔴 **이 일의 본질은 «플랫폼 앱 통합»이다** (기사님 확정 2026-08-30).
*"우리는 플랫폼 앱들을 통합해야 하는 거라 — 그 부분에 포커스 되어야 해."*
픽커는 세 번째 배차망이자, **배차망을 하나 더 붙일 때 무엇이 얼마나 드는가**를 재는
첫 실측이다. 여기서 아픈 곳(흩어진 매핑·앱별 특수 분기)이 통합 구조의 숙제 목록이 된다.

## 1. 왜 이 판인가

- **사업자가 필요 없다** — 인성 임계 경로를 우회해 지금 바로 실배차망을 본다
- **잡지 않으므로** 취소·페널티·법적 부담이 없다 — 감지·표시·기록만 한다
- 리스트를 스캔하는 것만으로 **실콜 표본**(요금·거리·지역·시간대)이 쌓인다 —
  판정 기준의 근거를 사업자 전에 모은다

## 2. 스크랩 정보 대조 — 인성과 무엇이 다른가 (덤프 실측)

픽커(`com.kakaomobility.flexer`)는 **네이티브 앱**이다. TextView 노드가 낱개로
깨끗하게 잡힌다 — 인성(웹뷰 압축 텍스트)보다 파싱이 쉽다.

| 항목 | 인성 리스트 | 픽커 리스트 | 비고 |
|---|---|---|---|
| 요금 | ✅ (카드 닻) | ✅ `14,168` | 픽커도 요금 노드가 카드 닻 후보 |
| 상차지 | 동 이름 텍스트 | ✅ 구+동 두 노드 (`중원`·`상대원2`) | 픽커가 더 구조적 |
| 하차지 | 동 이름 텍스트 | ✅ 구+동 두 노드 | 〃 |
| 픽업 거리 | ✅ | ✅ `15.2km` | |
| **배송 거리** | ✅ (거리 2개) | 🔴 **리스트에 없음** | 단가식(요금≥배송거리×단가)을 리스트에서 못 돌린다 |
| 차종 | ✅ (오·다·라·1t…) | 🔴 없음 — 대신 **물품 크기** (`초소형`·`소형`) | 축 자체가 다르다 |
| 긴급/예약 | 급송(형태) | ✅ 태그: `급송`·`예약 17:00`·`단거리`·`준비 32분` | 픽커의 «준비 N분»은 인성에 없는 정보 |
| 적요 | 상세 팝업 | 상세에 **구조화**: `세 변의 합 70cm ∙ 2kg 이하` | 픽커가 낫다 |
| 수익 분해 | 없음 | ✅ 상세: 배송비 7,000P + 프로모션 1,200P | |
| 상세 주소 | 팝업 3장 | ✅ 상세 화면에 픽업지 전문 | 하차지 전문은 덤프에 없음 — **스크롤 아래 추정, 실물 확인 필요** |
| 노출 반경 | 인성 설정 | 픽커 설정 `20km`(덤프 최대값) · 정렬(추천/높은가격) | **수집이니 최대로 연다** |

🔴 **결정적 차이 둘**: ① 배송거리가 리스트에 없어 요금 판단축이 다르고
② 차종 대신 물품 크기라 **인성 필터를 그대로 재사용할 수 없다** — 픽커 전용 축이 필요.

### 🔴 ①은 절반만 맞았다 — **상세 화면에는 다 있다** (2026-09-02 실물 정정)

기사님 캡처([ex_images/카카오픽커/실물_2026](../../ex_images/카카오픽커/README.md) 05~10)로 드러났다.
**리스트에 없을 뿐, 상세 화면에는 배송거리도 마감시각도 늘 있다.**

```
리스트     요금 · 픽업km · 구+동(줄임말) · 태그
  ↓ 누르면
상세       ＋ 배송 km · 건물명 · 「17:04까지 픽업」「17:18까지 배송」
           ＋ 물품 규격(세 변의 합·kg) · 최종수익 분해(배송비＋프로모션)
```

⚠️ **이건 «오더카드»가 아니다.** 오더카드는 리스트 맨 위에 뜨는 **제안 띠**이고 **이벤트다**
(기사님 확정 2026-09-02: *"오더카드는 이벤트다. 우리는 그것만 노리는 것이 아니다.
일단은 무시한다"*). 위 표의 상세는 **리스트 항목을 누르면 언제나 나오는 화면**으로,
**인성의 상세 화면과 같은 자리**다 — 「넘기기」는 *다른 기사에게 기회를 넘기고 리스트로 복귀*다.

🟢 **그리고 우리는 이미 그 화면에 가고 있다.** 3단계 알람이 잡기 수순 없는 배차망에서
**그 콜의 상세까지 이동**시킨다(`scheduleAlarmDetailBack` · 30초 무응답 시 자동 복귀).
즉 **새로 갈 곳을 만들 필요가 없고, 거기서 읽기만 더하면 된다.**

→ 열리는 것: **배송거리 기반 단가식**(인성과 같은 축) · **마감시각**(인성에서는 추정으로
만드는 값을 픽커는 그냥 준다) · 물품 규격.

### 🔴 값이 시간에 따라 오른다 (2026-09-02 실물)

같은 콜의 배송비는 **8,393P 로 고정**인데 프로모션이 붙어 4분 만에 최종수익이
**9,693 → 11,393P** 가 됐다(실물 09·10). **인성도 안 팔리면 값을 올려 다시 올린다**(기사님) —
픽커만의 성질이 아니다.

→ **요금 하한으로 한 번 거르고 잊으면 «곧 하한을 넘을 콜»을 놓친다.** 3단계 알람 하한
(`picker_alarm_min_fare`)의 설계에 직접 걸리는 축이다 — 아직 정하지 않았다.

## 3. 앱을 따로 만드나 — **아니오, 셋째 플러그인이다** (통합 구조의 첫 실측)

이미 있는 구조가 정확히 이 확장을 위해 설계돼 있다:

- **타겟 스크래핑 앱 선택이 이미 있다** — `SettingsScreen`(설정 화면)에서 고르고
  `MainViewModel` 이 `targetApp` 프리퍼런스에 쓴다 → 선택지에 **«픽커» 추가**.
  그래야 픽커의 작동 방식과 문자 체계를 인성·24시와 **구분해서** 다룬다 (기사님 지적)
- 파서는 플러그인이다 (`plugins/insung`·`plugins/hwamul24`) → `plugins/kakaopicker` 신설
- 화면 판별 키워드는 서버가 배포한다 (`server/config/keywords_*.json`) → `keywords_picker.json`
- 알람 수단(`AlarmSignaler` — 소리·진동·`TYPE_ACCESSIBILITY_OVERLAY` 테두리)은 그대로 재사용
- 폰 판이 «인성 시뮬 대신 픽커»라 접근성 서비스 하나로 충분하다 (동시 감시 아님)

🔴 **통합 관점에서 먼저 고칠 것 하나** — 이름→코드 매핑(`"인성콜"→insung / "24시"→hwamul24`)이
**네 곳에 흩어져 있다** (`HijackService:163` · `TelemetryManager:176` · `ApiClient:400` ·
`MainViewModel:68`). 지금은 두 값이라 안 갈라졌지만, 셋째를 네 곳에 각각 더하는 순간
⑤-4 ⑤(«누가 이 값을 읽는가»)를 어기는 그 모양이 된다 — **픽커를 붙이기 전에 매핑을
한 곳으로 모은다.** 배차망을 앞으로 계속 붙일 거라면(통합이 본질) 이게 첫 공사다.
✅ 완료 (2026-08-30 · `TargetApp.kt` + shared `TARGET_APPS`).

### §3-확장 — **시퀀스도 플러그인이다** (기사님 확정 2026-08-30)

> 🔴 **이 절은 스케치다. 확장판은 [기획/배차망_통합.md](../기획/배차망_통합.md) 에 있다**
> (2026-09-02 신설). «공통 / 그 배차망만의 것» 가르기는 **거기가 원천**이다 —
> 여기에 또 적으면 두 벌이 된다 (규칙 ③). 특히 그 문서 §1 은 오늘 드러난 축을 담는다:
> **픽커는 되돌릴 수 없어서 «잡기 전 판정» 만 가능하다** — 인성과 방향이 반대다.

기사님: *"인성은 상세 → 3개 팝업 → 확정 수순인데, 카카오퀵은 상세 보고 확정하면
그때 주소가 나오는 식이야. 우리 시퀀스대로 작동하려 하면 에러가 날 거란 말이지.
앱에서 라디오로 선택하면 **예약된 시퀀스를 타게** 한다면 3개의 플랫폼을 통합할 듯해."*

플러그인 경계가 지금은 **«읽기»까지**다 (키워드 + 파서). **«움직이기»(잡는 수순)는
공용 코드**(HijackService 화면 상태 기계 + DetailCollectMachine)에 인성 모양으로 박혀 있다:

```
인성   : 리스트 클릭 → 상세(2차 필터·confirm) → 팝업 3장 수집 → 확정 클릭 → detail 전송
픽커   : 리스트 → 상세(토스트) → 수락 → 🔴 그제야 주소 공개 → (인성식 팝업 수집 = 에러)
화물24시: 자기 수순
```

**목표 구조**: 라디오(타겟앱 선택) 하나가 **키워드·파서·시퀀스 세 벌을 함께** 갈아끼운다.
플러그인 = 읽는 법 + 움직이는 법.

기사님: *"앱에서 서버로 보내는 값은 대략 비슷할 건데, **앱의 트래킹은 앱마다 완전
다를 수 있다**."* — 층이 정확히 그렇게 갈린다:

```
[앱별 층]  화면 트래킹 — 키워드 · 파서 · 시퀀스        ← 라디오가 세 벌을 함께 교체
[공통 층]  회선 규격 — 콜 DTO · confirm/detail/scrap    ← 하나 (targetApp 만 실림)
[서버 층]  판정 · 장부 · 관제                            ← 배차망 무관 (targetApp 열로 구분)
```

회선과 서버는 이미 배차망 축이 깔려 있으니(§6-전), **앞으로 배차망을 붙이는 비용은
앱별 층 세 벌**뿐이다 — 그게 통합 구조의 값어치다.

**단계적으로 간다 — 중간길** (기사님 확정 2026-08-30: *"리스크를 지금 구간 표시로 줄이고,
대공사는 표본이 쌓이는 동안"*):
1. ✅ **잡기 차단 검사 + 인성 전용 구간 표시 (2026-08-30 완료)**: `TargetApp.supportsCatching`(능력 표) 신설,
   인성 잡기 수순의 입구 **6곳**(리스트 자동클릭 · 확정 전/후 화면 · 팝업 3종)에
   잡기 차단 검사 설치 — 픽커는 **인성 잡기 수순을 타지 않는다** (알람일 때 상세로 들어가는 것은 별개다). 🚧 주석이 곧 그 구간 표시이고,
   `networkAxis.test.ts` 가 그 검사 6개를 소스로 잠근다. «그때 가서 못 떼어낸다» 시나리오가
   사라졌다 — 떼는 날의 일은 실뭉치 풀기가 아니라 **표시를 따라 떼어내기**다
2. **잡기 시작하는 날**: 금을 따라 인성 수순을 «인성 시퀀스 플러그인»으로 떼고,
   픽커 수순을 둘째로. 그날의 ⑤-4 를 따로 쓴다

**종이 검증 — 두 수순이 한 틀에 담기는가** (구간 표시 때 확인 · 2026-08-30):
시퀀스 = «화면 → 할 일(클릭/수집/전송) → 다음 화면»의 순서표 + 단계 속성(타이머 등).

| 단계 | 인성 | 픽커 (잡기, 미래) |
|---|---|---|
| 1 | 리스트에서 대상 클릭 | 리스트에서 대상 클릭 |
| 2 | 상세: 2차 필터 → confirm 전송 → (주의 동이면 3단계 팝업) → **확정 클릭** | 상세(토스트): confirm 전송 → **수락 클릭** |
| 3 | 확정 화면: 팝업 3장 열어 **수집** | 🔴 **수락 후에야** 주소 화면 → 거기서 **수집** |
| 4 | detail 전송 → 리스트 복귀 | detail 전송 → 리스트 복귀 |
| 속성 | 안전취소 30초 타이머 (위약금 없이 되돌릴 수 있다) | 🔴 **되돌릴 창이 없다** — 아래 |

→ **같은 틀(순서표+속성)에 둘 다 담긴다.** 수집이 확정 앞이냐 뒤냐의 순서 차이일 뿐,
인터페이스가 못 담는 모양은 없다 — 종이 검증 통과.

🔴 **속성 칸은 2026-09-02 에 정정됐다 — «타이머 상수만 다름»이 아니었다.**
원래 *"취소 10분 창(전화 불필요)"* 이라 적혀 있었는데 **영상 자막에서 뽑은 틀린 값**이었다.
기사님 실사용:

| | 되돌리는 법 | 횟수 |
|---|---|---|
| 인성 | 앱에서 **30초 안전취소** (위약금 없음) | 10회 |
| **픽커** | 🔴 **버튼 취소 없음 · 전화만** | 🔴 **하루 5번** |

**「수락하기」를 누르는 순간 계약이 성립한다.** 그래서 두 판의 차이는 상수가 아니라
**«되돌릴 수 있는가»라는 성질**이다. `supportsCatching` 잡기 차단 검사가 막고 있는 것이
바로 이것이고, 픽커에서 계약 행위는 **기사님 손가락뿐**이어야 한다
([노하우 §2](../자료/노하우/카카오픽커/노하우_추출.md)).

## 4. 저장 — **같은 서버, 같은 표, 열로 가른다**

- `intel` 표에 **`targetApp` 열이 이미 있다** (`db.ts` · ensureColumns 로 소급 적용됨)
  → 픽커 수집은 `targetApp='kakaopicker'` 로 들어가고, 인성 표본과 **처음부터 갈라진다**
- 🔴 판정·요율의 표본으로 쓸 때는 **반드시 targetApp 으로 걸러 쓴다** — 요금 체계가
  다른 판을 섞으면 인성 판정이 오염된다 (규칙 ⑤-4 ⑤ «누가 이 값을 읽는가»)
- 잡지 않으므로 `orders`·심사·판정·피기백 명령은 **타지 않는다** — 수집(intel)만

|---|---|---|
| ① 스키마 | 🔶 반확정 | intel 재사용 + `targetApp` ✅. **추가 필드가 결정 전**: 물품 크기·태그(급송/예약/준비N분)·픽업거리를 어디 싣나 — intel 열 추가 vs 안 싣고 버리나 |
| ② 값 | 🔶 반확정 | 수집 조건 = **전부** (기사님 확정). **알람 울림 조건은 미정** — 전부 울리면 «알림 피로» 노하우 그대로 당한다. 후보: 요금 하한 하나만 두고 시작 |
| ③ 시점 | ⬜ | 스캔 주기(인성과 같은 5초?) · 수집 중복 제거 기준(지문: 출발+도착+요금?) |
| ④ 화면 | ⬜ | 관제웹에 픽커 수집이 어떻게 보이나 — 수집 카운트만? 별도 표시? |
| ⑤ 읽는 곳 | ✅ | intel 소비자는 targetApp 필터 필수. 판정·필터·피기백은 이 데이터를 읽지 않는다 |

## 6-전. «어느 배차망» 축 전수조사 (기사님 지시 2026-08-30 — 표면만 고치지 말 것)

> 기사님: *"관제앱 폰 영역에서 각 폰이 어떤 어플을 보고 있는지 확인돼야 한다.
> 그것과 파생되는 것 모두를 찾은 후 어떻게 정리할지 — 나중에 일지 등에 6하원칙으로
> 필터링·표시해야 하니까."*

### 이미 흐르는 곳 — 원천은 하나다

앱이 **모든 요청**(scrap·confirm·detail)에 `targetApp` 을 싣는다. 그래서:
- `intel.targetApp` ✅ (수집 원장) · `orders.targetApp` ✅ (콜 원장 — KEEP 시 기록,
  `orders.ts:124` *"어느 배차망에서 온 콜인가 — 원장에 남긴다"*) · 파서 선택 ✅

**→ 새 원장 열은 필요 없다.** 6하원칙의 «어디서(배차망)»는 이미 저장되고 있다.
나중에 일지·통계에서 `targetApp` 으로 필터링하면 된다.

### 끊긴 자리 — 파생이 안 된 곳

| 자리 | 상태 | 6하원칙 |
|---|---|---|
| **기기 세션** (`touchDeviceSession`·`DeviceSession`) | ❌ targetApp 없음 — scrap 이 갖고 오는데 버린다 | 누가·**어디서** |
| **관제웹 폰 영역** | ❌ 그래서 «이 폰이 뭘 보나»를 못 그린다 (기사님 지적의 표면) | 〃 |
| 관제웹 콜 카드·완료 목록·**일지** | ❌ 원장엔 있는데 표시가 없다 | 어디서 |
| **값 표준** | 🔴 한글라벨→코드 매핑 앱 4곳(§3) + 서버 `\|\| 'insung'` 폴백 3곳 흩어짐 | — |
| **«어떻게»** | 🔴 원장 `type` 에 `AUTO_CLICK`/`MANUAL_CLICK` 뿐 — **알람 듣고 잡음과 손수 잡음이 구분 안 남는다** (#75 보호 때문에 알람도 MANUAL 로 합쳐짐) | **어떻게** |

### 안 넣는 곳 — 파생 가능 (규칙 ③: 원장에서 join)

`order_judgments`·`gps_tracks`·`orderStops`(orderId→orders) · `places`(장소는 배차망
중립 — 주선사 소속은 orders 의 dispatcherName+targetApp 에서 파생) ·
`reach_samples`(도달은 지리 문제 — 배차망 무관)

### 나중에 필요한 곳 — 픽커를 «잡기» 시작하는 날

`user_filters`/`user_filter_phases`(배차망별 필터 축이 다르다 — 물품크기) · `call_options`

### 정리안 (⑤-4 다섯)

## 6. 단계

1. **0단계 (기사님)** — 픽커 계정 심사 통과 확인 (8/28 «심사 중») · 픽커 설정에서
   노출 반경 최대·정렬 확인
2. **1단계 (통합 공사)** — 타겟앱 이름→코드 매핑을 한 곳으로 (네 곳 → 하나 · §3)
3. ✅ **2단계 — 수집 가동 (2026-08-30 20:48 첫 실배차망 표본)**: «픽커» 선택지 ·
   `KakaoPickerKeywords`/`KakaoPickerParser`(요금 닻 ±60px 띠 묶기) · intel 배선.
   첫 수집에서 실물이 가르쳐 준 것 셋을 바로 수리 — 태그 «반나절·승·내일·서포트모드»
   (지역 오인), 하단 메뉴 낱말 노이즈, 헤더 반경. 검사 9건이 실물 카드를 문제지로 잠근다.
   ⚠️ 알려진 가장자리: 화면 끝에 걸린 카드는 동 이름이 잘려 시 단위만 남는다 (원문은 rawText 보존)
4. ✅ **3단계 — 알람 가동 (2026-08-30)**: 판정 축은 셋 — ① 요금 ≥ 픽커 알람 하한
   ② 픽업거리 ≤ 상차 반경(국면 값 재사용 · 모르면 막지 않는다) ③ 도착 구·동 ↔ 국면
   도착목표(`destinationKeywords`·`keywordTraps` 재사용 — 비면 제한 없음 · 못 읽은 카드는
   막지 않는다). ③은 첫 설계에서 빠졌었다 — 대조표에 도착 동이 있다고 적고도 «배송거리
   없음 → 판정 불가» 결론만 들고 왔다. 기사님이 잡았다 (원자료를 다시 읽을 것).
   예약·내일 콜(표본 22%)도 울린다 — 미리 확보할 가치(기사님 확정). 준비 시간 상한·물품
   크기 축은 보류(소형이 95%라 변별력 없음 — 316건 실측). 하한의 ⑤-4:
   ①스키마 `user_settings.picker_alarm_min_fare` ②기본 1만 원(첫 표본 분포 2.5천~1.6만 —
   1만 이상만 울리면 드문 울림) ③관제웹 저장 → 피기백 → 앱 프리퍼런스 ④관제웹 일반
   설정 입력 + 폰 소리·진동·테두리(AlarmSignaler 재사용) ⑤픽커 파서만 읽는다.
   🔴 인성 min_fare 를 재사용하지 않았다 — 한 값 두 역할 금지. 알람이 «울렸다»는 사실은
   DB에 안 남는다(로그만) — 콜 내용은 intel 에 이미 있다. 기기 모드 «알람»에서만 울린다.
   **동시 통과 여러 건이면 요금 최고 하나만** 울리고 가리키며(`pickBestIndex`), 잡기 수순
   없는 배차망은 그 콜의 **상세까지 이동**한다 (기사님 확정 0830: *"선택만 내가 하면
   되니까"* — 30초 무응답 시 자동 복귀 `scheduleAlarmDetailBack`). **수락 클릭은 없다** —
   상세의 잡기 수순은 잡기 차단 검사가 건너뛰므로 계약 행위는 기사님 손가락뿐이다
5. **4단계** — 쌓인 표본으로 픽커 판의 리포트 (시간대·지역·요금 분포)

**오더카드 (2026-08-30 21:52 실물 발견 · 아직 전용 파싱 없음)** — 리스트 **맨 위 한 자리**에
뜨는 **제안 띠**다. 플랫폼이 밀어 준다. 콜이 없으면 그 자리에 «퀵 오더카드 대기 중…»이
떠 있다. 초록 «수락» 버튼 + 상차 km 와 하차 km 둘 다 보인다.

🔴 **상세 화면과 다른 것이다** — 상세는 리스트 항목을 눌러 들어가는 화면이고,
버튼이 「넘기기 / 수락하기」다. 둘을 섞지 말 것.

⚠️ **«하차 km 는 여기서만 얻는 재료»라고 적었던 것은 틀렸다** (2026-09-02 실물 정정) —
**상세 화면에도 늘 있다**(§2 참조). 오더카드가 유일한 출처가 아니다.

🔴 **오더카드는 이벤트다 — 일단 무시한다** (기사님 확정 2026-09-02:
*"우리는 그것만 노리는 것이 아니다"*). 지금은 리스트 파서가 띠로 주워 요금·지역은
대체로 맞게 읽고, «수락» 글자는 노이즈로 걸러 둔 상태다(#85 덤).

🔴 **다만 손대면 안 되는 이유는 남는다** — 오더카드는 **요금 숫자가 「수락」 버튼 안에**
있어서, 요금 노드를 탭하면 그게 **곧 계약**이다. 그래서 자동 진입은 반드시
`KakaoPickerParser.clickSafe`(«수락» 글자가 보이면 손대지 않는다)를 지나야 한다.
전용 파싱(오더카드 구분 저장)은 표본 리포트(4단계)와 함께 판단한다.
