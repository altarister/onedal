*"우리는 플랫폼 앱들을 통합해야 하는 거라 — 그 부분에 포커스 되어야 해."*
픽커는 세 번째 배차망이자, **배차망을 하나 더 붙일 때 무엇이 얼마나 드는가**를 재는
첫 실측이다. 여기서 아픈 곳(흩어진 매핑·앱별 특수 분기)이 통합 구조의 숙제 목록이 된다.

## 1. 왜 이 판인가

- **사업자가 필요 없다** — 인성 임계 경로를 우회해 지금 바로 실배차망을 본다
- **잡지 않으므로** 취소·페널티·법적 부담이 없다 — 감지·표시·기록만 한다
- 리스트를 스캔하는 것만으로 **실콜 표본**(요금·거리·지역·시간대)이 쌓인다 —
  판정 기준의 근거를 사업자 전에 모은다

## 2. 스크랩 정보 대조 — 인성과 무엇이 다른가 (덤프 실측)

픽커(`com.kakaomobility.flexer`)는 **네이티브 앱**이다. TextView 노드가 낱개로
깨끗하게 잡힌다 — 인성(웹뷰 압축 텍스트)보다 파싱이 쉽다.

| 항목 | 인성 리스트 | 픽커 리스트 | 비고 |
|---|---|---|---|
| 요금 | ✅ (카드 닻) | ✅ `14,168` | 픽커도 요금 노드가 카드 닻 후보 |
| 상차지 | 동 이름 텍스트 | ✅ 구+동 두 노드 (`중원`·`상대원2`) | 픽커가 더 구조적 |
| 하차지 | 동 이름 텍스트 | ✅ 구+동 두 노드 | 〃 |
| 픽업 거리 | ✅ | ✅ `15.2km` | |
| **배송 거리** | ✅ (거리 2개) | 🔴 **리스트에 없음** | 단가식(요금≥배송거리×단가)을 리스트에서 못 돌린다 |
| 차종 | ✅ (오·다·라·1t…) | 🔴 없음 — 대신 **물품 크기** (`초소형`·`소형`) | 축 자체가 다르다 |
| 긴급/예약 | 급송(형태) | ✅ 태그: `급송`·`예약 17:00`·`단거리`·`준비 32분` | 픽커의 «준비 N분»은 인성에 없는 정보 |
| 적요 | 상세 팝업 | 상세에 **구조화**: `세 변의 합 70cm ∙ 2kg 이하` | 픽커가 낫다 |
| 수익 분해 | 없음 | ✅ 상세: 배송비 7,000P + 프로모션 1,200P | |
| 상세 주소 | 팝업 3장 | ✅ 상세 화면에 픽업지 전문 | 하차지 전문은 덤프에 없음 — **스크롤 아래 추정, 실물 확인 필요** |
| 노출 반경 | 인성 설정 | 픽커 설정 `20km`(덤프 최대값) · 정렬(추천/높은가격) | **수집이니 최대로 연다** |

🔴 **결정적 차이 둘**: ① 배송거리가 리스트에 없어 요금 판단축이 다르고
② 차종 대신 물품 크기라 **인성 필터를 그대로 재사용할 수 없다** — 픽커 전용 축이 필요.

## 3. 앱을 따로 만드나 — **아니오, 셋째 플러그인이다** (통합 구조의 첫 실측)

이미 있는 구조가 정확히 이 확장을 위해 설계돼 있다:

- **타겟 스크래핑 앱 선택이 이미 있다** — `SettingsScreen`(설정 화면)에서 고르고
  `MainViewModel` 이 `targetApp` 프리퍼런스에 쓴다 → 선택지에 **«픽커» 추가**.
  그래야 픽커의 작동 방식과 문자 체계를 인성·24시와 **구분해서** 다룬다 (기사님 지적)
- 파서는 플러그인이다 (`plugins/insung`·`plugins/hwamul24`) → `plugins/kakaopicker` 신설
- 화면 판별 키워드는 서버가 배포한다 (`server/config/keywords_*.json`) → `keywords_picker.json`
- 알람 수단(`AlarmSignaler` — 소리·진동·`TYPE_ACCESSIBILITY_OVERLAY` 테두리)은 그대로 재사용
- 폰 판이 «인성 시뮬 대신 픽커»라 접근성 서비스 하나로 충분하다 (동시 감시 아님)

🔴 **통합 관점에서 먼저 고칠 것 하나** — 이름→코드 매핑(`"인성콜"→insung / "24시"→hwamul24`)이
**네 곳에 흩어져 있다** (`HijackService:163` · `TelemetryManager:176` · `ApiClient:400` ·
`MainViewModel:68`). 지금은 두 값이라 안 갈라졌지만, 셋째를 네 곳에 각각 더하는 순간
⑤-4 ⑤(«누가 이 값을 읽는가»)를 어기는 그 모양이 된다 — **픽커를 붙이기 전에 매핑을
한 곳으로 모은다.** 배차망을 앞으로 계속 붙일 거라면(통합이 본질) 이게 첫 공사다.

## 4. 저장 — **같은 서버, 같은 표, 열로 가른다**

- `intel` 표에 **`targetApp` 열이 이미 있다** (`db.ts` · ensureColumns 로 소급 적용됨)
  → 픽커 수집은 `targetApp='kakaopicker'` 로 들어가고, 인성 표본과 **처음부터 갈라진다**
- 🔴 판정·요율의 표본으로 쓸 때는 **반드시 targetApp 으로 걸러 쓴다** — 요금 체계가
  다른 판을 섞으면 인성 판정이 오염된다 (규칙 ⑤-4 ⑤ «누가 이 값을 읽는가»)
- 잡지 않으므로 `orders`·심사·판정·피기백 명령은 **타지 않는다** — 수집(intel)만

## 5. ⑤-4 다섯 확정 — 무엇이 비었나 ⚠️ 여기가 차 있어야 코드 시작

| | 상태 | 내용 |
|---|---|---|
| ① 스키마 | 🔶 반확정 | intel 재사용 + `targetApp` ✅. **추가 필드가 결정 전**: 물품 크기·태그(급송/예약/준비N분)·픽업거리를 어디 싣나 — intel 열 추가 vs 안 싣고 버리나 |
| ② 값 | 🔶 반확정 | 수집 조건 = **전부** (기사님 확정). **알람 울림 조건은 미정** — 전부 울리면 «알림 피로» 노하우 그대로 당한다. 후보: 요금 하한 하나만 두고 시작 |
| ③ 시점 | ⬜ | 스캔 주기(인성과 같은 5초?) · 수집 중복 제거 기준(지문: 출발+도착+요금?) |
| ④ 화면 | ⬜ | 관제웹에 픽커 수집이 어떻게 보이나 — 수집 카운트만? 별도 표시? |
| ⑤ 읽는 곳 | ✅ | intel 소비자는 targetApp 필터 필수. 판정·필터·피기백은 이 데이터를 읽지 않는다 |

## 6-전. «어느 배차망» 축 전수조사 (기사님 지시 2026-08-30 — 표면만 고치지 말 것)

> 기사님: *"관제앱 폰 영역에서 각 폰이 어떤 어플을 보고 있는지 확인돼야 한다.
> 그것과 파생되는 것 모두를 찾은 후 어떻게 정리할지 — 나중에 일지 등에 6하원칙으로
> 필터링·표시해야 하니까."*

### 이미 흐르는 곳 — 원천은 하나다

앱이 **모든 요청**(scrap·confirm·detail)에 `targetApp` 을 싣는다. 그래서:
- `intel.targetApp` ✅ (수집 원장) · `orders.targetApp` ✅ (콜 원장 — KEEP 시 기록,
  `orders.ts:124` *"어느 배차망에서 온 콜인가 — 원장에 남긴다"*) · 파서 선택 ✅

**→ 새 원장 열은 필요 없다.** 6하원칙의 «어디서(배차망)»는 이미 저장되고 있다.
나중에 일지·통계에서 `targetApp` 으로 필터링하면 된다.

### 끊긴 자리 — 파생이 안 된 곳

| 자리 | 상태 | 6하원칙 |
|---|---|---|
| **기기 세션** (`touchDeviceSession`·`DeviceSession`) | ❌ targetApp 없음 — scrap 이 갖고 오는데 버린다 | 누가·**어디서** |
| **관제웹 폰 영역** | ❌ 그래서 «이 폰이 뭘 보나»를 못 그린다 (기사님 지적의 표면) | 〃 |
| 관제웹 콜 카드·완료 목록·**일지** | ❌ 원장엔 있는데 표시가 없다 | 어디서 |
| **값 표준** | 🔴 한글라벨→코드 매핑 앱 4곳(§3) + 서버 `\|\| 'insung'` 폴백 3곳 흩어짐 | — |
| **«어떻게»** | 🔴 원장 `type` 에 `AUTO_CLICK`/`MANUAL_CLICK` 뿐 — **알람 듣고 잡음과 손수 잡음이 구분 안 남는다** (#75 보호 때문에 알람도 MANUAL 로 합쳐짐) | **어떻게** |

### 안 넣는 곳 — 파생 가능 (규칙 ③: 원장에서 join)

`order_judgments`·`gps_tracks`·`orderStops`(orderId→orders) · `places`(장소는 배차망
중립 — 주선사 소속은 orders 의 dispatcherName+targetApp 에서 파생) ·
`reach_samples`(도달은 지리 문제 — 배차망 무관)

### 나중에 필요한 곳 — 픽커를 «잡기» 시작하는 날

`user_filters`/`user_filter_phases`(배차망별 필터 축이 다르다 — 물품크기) · `call_options`

### 정리안 (⑤-4 다섯)

| | 정리 |
|---|---|
| ① 스키마 | DB 열 추가 **0개** (원장 완비). ⓐ `DeviceSession.targetApp`(메모리 — 실시간 상태는 저장 아님) ⓑ **결정 필요**: orders 에 «어떻게» 열(잡은 방식: 자동/알람/직접) |
| ② 값 | `shared` 에 배차망 상수+라벨 한 벌 신설 — 앱 매핑 4곳·서버 폴백 3곳이 **이것 하나**를 읽게 (§3 1단계 공사의 실체) |
| ③ 시점 | 기기 targetApp 은 scrap 마다 갱신(메모리) · 원장은 confirm/KEEP 때(이미 동작 중) |
| ④ 화면 | 폰 영역 기기줄 배지 + 콜 카드·일지 배차망 배지. **라벨·색은 기사님 확정 필요** |
| ⑤ 읽는 곳 | 파서 선택(앱) · 표본 필터(intel 소비자) · 일지/통계(orders) · 화면 배지 — 넷이 **다른 질문**을 같은 값에 묻는다. 값은 shared 한 벌 |

1. **«어떻게»를 원장에 남길까** — 지금은 자동/직접 둘뿐이고 알람은 직접에 합쳐진다

2. **배차망 배지의 라벨·색** — 인성/24시/픽커를 화면에 뭐라고, 무슨 색으로
