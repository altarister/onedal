# 기기 모드 — 앱이 콜을 어떻게 대할 것인가

> **모드를 둘에서 셋으로 늘린다** (기사님 지시 2026-08-30).
>
> 기사님: *"대기 라는 걸 하나 만들고 지금의 노멀과 같은 동작을 하면 될 것 같고,
> 메뉴얼은 진짜 메뉴얼처럼 필터를 통과한 콜이 리스트 맨 위에 나타나면 알람을 주는 기능이야.
> 그러면 내가 직접 크롤링앱의 인성리스트 첫 번째 것을 클릭하는 거지."*
>
> 🔴 이 문서는 규칙 ⑤-4 의 **넷(스키마·값·시점·화면)** 을 확정하는 자리다.
> 비어 있는 칸이 하나라도 있으면 **코드를 시작하지 않는다.**
>
> 말의 원천은 [용어집](용어집.md) §9 「콜 필터 켬/끔」 — **그 등재어가 이 문서로 바뀐다.**

## 이 문서의 상태

✅ **⑤-4 의 넷이 다 찼다** (기사님 2026-08-30). 스키마·값·시점·화면 전부 §0 과 §6 에 있다.

**두 단계로 나눠 만든다** (규칙 ⑥ — 한 번에 두 단계를 건너뛰지 않는다):

| | 무엇 | 상태 |
|---|---|---|
| **1단계** | 모드 셋 + DB 칸 + 관제웹 버튼·알람 | ✅ **2026-08-30** |
| **2단계** | 앱의 소리·진동 + 인성 화면 위 테두리 | ⬜ |

1단계만으로도 **관제웹에서 알람이 울린다.** 2단계는 스캐너 폰을 더하는 일이다.

### ✅ 1단계에서 실제로 한 것 (2026-08-30)

🟢 **앱을 한 줄도 안 고쳤다.** 필터 성적표(`FilterTally.passed`)가 이미 서버로 오고,
앱은 이미 본 콜을 지문으로 건너뛰므로 그 숫자가 **새로 본 통과 콜**만 센다.

🔴 **캐다가 진짜 문제를 하나 찾았다 — 아래 §2-1.** 설계대로만 짰으면
**알람이 한 번도 안 울렸을 것이다.**

검사 `server/tests/rules/deviceMode.test.ts` **17건**. 게이트 전부 통과 —
`tsc`(서버·관제웹) · `jest` 1167건 · `test:web` 71건 · `scenario` 53건 ·
`audit:socket`·`audit:dead`·`audit:docs` · **칸 없던 옛 DB 사본으로 부팅 스모크**
(`🔧 [스키마] user_devices.mode 컬럼 추가` · 기존 행 `mode = NULL`).

## 0. 기사님이 정하신 것 (2026-08-30)

| 물음 | 답 |
|---|---|
| 알람 보고 **내가 누른 콜**을 서버가 심사하나 | **아니다 — 지금 직접콜 그대로.** 색도 안전취소도 없다 |
| 알람은 어디서 울리나 | **둘 다** — 스캐너 폰과 관제웹 |
| 통과한 콜이 리스트 맨 위가 아니면 | **화면에서 그 콜을 표시한다** (세지 않고 보이는 대로 누른다) |

🔴 **첫 답이 가장 크다.** 규칙 ① *"직접콜(MANUAL)은 심사하지 않는다"* 를 **안 건드린다**는 뜻이다.
알람은 «필터가 통과시켰다»는 신호 그 자체이고, 기사님은 그걸 믿고 누른다.
그래서 이 일은 **판정에 한 줄도 닿지 않는다** — 규칙 ①·⑤-3 이 그대로 산다.

## 1. 모드 셋

| 화면 이름 | 키 | 필터 | 앱이 누르나 | 알람 | 콜의 출신 |
|---|---|---|---|---|---|
| **자동** | `AUTO` | 돈다 | ✅ 앱이 누른다 | — | 필터콜 (심사 O) |
| **알람** | `ALARM` (신설) | 돈다 | ❌ | ✅ | **직접콜** (심사 X) |
| **직접** (구 «대기» · 08-30 개명) | `MANUAL` | 돈다 (기록용) | ❌ | ❌ | 직접콜 (심사 X) |

🟢 **필터는 이미 세 모드 모두에서 돌고 있다.**
[HijackService.kt:479](../../onedal-app/app/src/main/java/com/onedal/app/HijackService.kt#L479) 가
`// 🌟 [항시 인터셉터] … MANUAL/AUTO 무관하게 항시 실행` 이라 적고 `shouldClick` 을 부른다.
**알람이 쓸 판정 결과가 그 자리에 이미 있다** — 필터를 새로 돌리지 않는다.

### 🔴 「대기」에 새 키를 만들지 않는 이유

「직접」(구 «대기»)의 동작은 **지금 `MANUAL` 과 완전히 같다** (보고만 하고 안 누른다).
키를 그대로 두면 서버·앱의 기존 `MANUAL` 분기가 **한 줄도 안 바뀐다.**
반대로 「알람」에 `MANUAL` 을 주고 「직접」에 새 키를 주면 **분기 전부를 다시 읽어야 한다** —
바꿔서 얻는 것이 없다. 바뀌는 것은 **화면에 적히는 이름**뿐이다.

⚠️ **`STANDBY` 는 쓰지 않는다.** `dispatchPhase` 가 이미 `STANDBY`(첫짐 탐색)를 쓴다.
같은 낱말에 두 뜻을 주면 로그를 읽을 때 어느 쪽인지 모른다.

## 2. ① 스키마 — 어디에 사는가

| 무엇 | 예전 (값 둘) | 지금 |
|---|---|---|
| 타입 | `"AUTO" \| "MANUAL"` | `DEVICE_MODES` = 자동·알람·직접 (`shared/src/index.ts`) |
| 기사님의 선택 | 메모리 맵 (서버가 뜨면 사라짐) | **DB `user_devices.mode`** (`NULL` = 아직 안 골랐다) |
| 지금 상태 | `activeDevices` (메모리) | 그대로 — 통신 상태에 따라 흔들리는 값이라 여기 맞다 |
| 앱이 쥔 곳 | `TelemetryManager.currentMode` | 그대로 |

🟢 **마이그레이션도 CHECK 제약도 없다.** `user_devices` 는 다섯 칸뿐이었고 모드를 담은 적이 없다.
칸은 `ensureColumns` 로 붙고, 옛 DB 사본 부팅으로 실증했다.

### 🔴 왜 메모리로 두면 안 됐나 — 역파생이 깨진다

`resolveDefaultMode` 는 기사님이 고른 값이 없으면 **필터 상태에서 모드를 되파생**한다:

```
activeFilter.isActive ? "AUTO" : "MANUAL"
```

값이 둘일 때는 이게 성립했다. 셋이 되면 `isActive = false` 에서
**「대기」인지 「알람」인지 못 되살린다.** 그리고 예전의 메모리 맵은 **서버가 다시 뜨면
사라졌다** — 즉 **알람 모드가 말없이 대기로 떨어졌을 것**이다.

⚠️ 화면은 아무 이상이 없다. 필터 성적표도 계속 오른다. 다만 **알람만 안 울린다** —
이 레포가 여러 번 당한 「화면이 조용히 거짓말한다」의 모양 그대로다.

→ **DB 칸으로 정했다** (`user_devices.mode`, `NULL` 허용 · §6-①).
   `NULL` 이라야 «아직 안 골랐다»가 표현되고, 그때만 위 역파생이 돈다 (규칙 ④).

## 2-1. 🔴 설계에 없던 진짜 문제 — `isActive` 가 **세 말**을 하고 있었다

1단계를 짜다 나왔다. **설계대로만 만들었으면 알람이 한 번도 안 울렸을 것이다.**

앱의 `decide()` 는 맨 앞에서 이렇게 끊는다 (`InsungParser` · `Hwamul24Parser` 둘 다):

```kotlin
if (!filter.isActive) { return false }     // ← 조건 0
```

그런데 `isActive` 는 **AUTO 기기가 있을 때만** 켜졌다. 즉 알람 모드에서는
필터가 **아예 안 돌아** 통과 콜이 영영 0건이다. 「항시 인터셉터」가 `shouldClick` 을
모든 모드에서 부르는 것은 맞지만, **그 함수가 스스로 첫 줄에서 돌아선다.**

🔴 **뿌리는 한 값이 여러 사실을 답하고 있던 것이다** (규칙 ③).
값이 둘이던 시절엔 그것들이 같은 말이라 아무도 눈치채지 못했다.

> ⚠️ **처음엔 «두 말»이라 적었다가 코드리뷰에서 셋인 걸 알았다.** 축을 쪼개다 만 것이다 —
> 쪼갤 때는 **읽는 자리를 전수로** 세어야 한다.

| 물음 | 예전 | 지금 |
|---|---|---|
| ① 기사님이 필터를 켰는가 | `isActive` | `session.filterEnabledByMode` (자동·알람이면 켬) |
| ② 앱이 누르는가 | `isActive` | 앱의 `currentMode == "AUTO"` (자동만) |
| ③ 지금 콜을 물어도 되는가 | `isActive` | 선점 잠금 — 불변식이 푼다 (**①을 넘지 못한다**) |
| ④ 필터를 믿을 수 있는가 | `isActive` | `scrap.ts` 넷 — 부트스트랩·만석·미접속·고장 |

`activeFilter.isActive` 는 이제 **넷의 AND 결과**다. 예전에는 넷이 서로 **덮어썼다.**

🔴 **③이 ①을 덮고 있었다.** 「대기」로 바꿔도 불변식(*"선점 중인 콜 0건이면 다시 켠다"*)이
곧바로 되켜서 **«대기 = 필터 꺼짐» 이 거짓**이었다. 그 거짓을 용어집에 적을 뻔했다.
지금은 불변식이 `filterEnabledByMode !== false` 일 때만 켠다.
(`undefined` 는 «켬» — 모드를 한 번도 안 고른 사용자는 예전 그대로 돈다)

⚠️ **④는 그대로 겹쳐 둔다** (규칙 ②). 그 넷은 **알람도 울리면 안 되는 경우**라 맞다.

→ 용어집 §9 의 「콜 필터 켬/끔」을 이 뜻으로 고쳤다.

## 2-2. 🔴 모드 이름이 «콜의 출신»으로 새어 나갔다 (코드리뷰 2026-08-30)

**«앱 무변경»이 성과가 아니라 «앱을 안 본 것»이었다.**

```kotlin
HijackService   type = "${mode}_CLICK"      →  "ALARM_CLICK"
SessionManager  currentOrderId = "$mode-…"  →  "ALARM-1234…"
```
```ts
devices.ts   if (stuckOrder && (isPreviewStuck || !stuckOrder.type?.startsWith("MANUAL")))
                 forceCancelEvaluatingOrder(...)      // ← "ALARM_CLICK" 은 안 걸러진다
```

알람 듣고 직접 누른 뒤 리스트로 돌아오면 **서버가 그 콜을 버린다** — 규칙 ① 위반.

🔴 **모드가 셋이라 커졌을 뿐 원래 틀려 있었다.** `type` 을 정하는 판단이 **두 벌**이었다:
`handleDetailScreen` 은 「누가 눌렀나」(`isAutoActive`)를 봤고, `buildOrderFromScreen` 은
**스위치**를 봤다. 그래서 자동 스위치인 채 손으로 확정하면 `"AUTO_CLICK"` 이 찍혀
같은 사고가 났다.

→ 출신은 `SessionManager.clickOrigin` **한 곳**에서만 파생한다 (규칙 ③).
   모드 값이 몇 개로 늘든 출신은 늘 `AUTO`·`MANUAL` 둘이다.
   검사 `ClickOriginTest`(앱 5건) + `deviceMode.test.ts` 의 대조 3건.

## 3. ② 값 — 기본값과 근거

| 값 | 기본 | 근거 |
|---|---|---|
| 새 기기의 모드 | 지금 그대로 (`isActive ? AUTO : MANUAL`) | 알람은 **기사님이 명시적으로 고를 때만** 켜진다 |
| 앱의 오프라인 폴백 | `MANUAL` (`SharedModels.kt:248` 그대로) | 서버가 죽으면 **아무것도 안 잡는 것**이 안전하다 ([앱 CLAUDE.md](../../onedal-app/CLAUDE.md) 「필터 기본값은 안전한 방향으로」) |
| 관제웹 알람음 | `playBeep()` 두 번 + 강한 진동 | §6-② |
| 앱 알람음·진동 | 짧은 소리 두 번 + 강한 진동 (2단계) | 앱에는 **아무 수단도 없다** — 신설이다 |
| 알람이 그치는 때 | 콜이 리스트에서 사라지거나 **10초** — 먼저 오는 것 | §6-③ |

🔴 **콜 필터는 자동·알람 둘 다 켠다** (`hasFilteringDevice`). 대기만 끈다.
왜 그래야 하는지는 §2-1 에 있다 — 안 그러면 알람에서 필터가 통째로 죽는다.

## 4. ③ 시점 — 언제 읽고 언제 쓰는가

| 언제 | 무슨 일 |
|---|---|
| 관제웹에서 모드를 누를 때 | `POST /api/devices/:id/mode` → **DB 에 기록**(내 폰일 때만) + 세션·메모리 갱신 |
| 앱이 텔레메트리를 보낼 때 | 응답 꼬리(피기백)에 모드가 실려 온다 → `TelemetryManager.currentMode` |
| 리스트를 훑을 때 | `shouldClick` 이 `isTarget` 을 낸다 (**모드와 무관, 지금도 그렇다**) |
| `isTarget && 모드 == ALARM` | 🔔 **알람 + 화면 표시** |
| 그 콜이 리스트에서 사라지거나 10초 | 🔇 알람·표시가 그친다 (§6-③) |
| 서버가 다시 뜰 때 | **모드가 살아남는다** — DB 에서 읽는다 (§6-①) |

### 알람이 콜당 한 번만 울리는 것은 이미 보장된다

[HijackService.kt:472](../../onedal-app/app/src/main/java/com/onedal/app/HijackService.kt#L472) 의
`processedOrderHashes`(지문 = 상차+하차+요금)가 이미 본 콜을 건너뛴다.
**새 장치를 만들지 않는다** — 그 자리에 알람을 얹으면 콜당 1회가 저절로 나온다.

⚠️ 다만 지문은 **차종만 바뀐 콜을 같은 콜로 본다** (2026-08-25 기록). 알람도 같은 한계를 물려받는다.

⬜ **언제 그치나** — §6-③.

## 5. ④ 화면 — 어디에 어떤 이름으로 보이나

### 관제웹 — 버튼 둘이 셋이 된다

[DeviceControlPanel.tsx](../../onedal-web/client-app/src/components/dashboard/DeviceControlPanel.tsx)
의 모드 버튼에 「알람」을 더한다.

🔴 **판정 색과 겨루지 않는다** (규칙 ⑤-3 · [시각_표시 §4](시각_표시.md)).
🔵🟢🟡🔴 는 판정의 것이고 지도는 상차=초록·하차=빨강을 쓴다.
모드 버튼은 **글자와 켜짐/꺼짐**으로 말한다.

### 관제웹 알람 — 만들 것이 거의 없다

[soundManager.ts](../../onedal-web/client-app/src/lib/soundManager.ts) 에 이미 있다:

| 함수 | 소리 | 진동 |
|---|---|---|
| `playCallRinging()` | 무한 반복 | 강함 |
| `playBeep()` | 짧게 한 번 | 약함 |
| `playEmergencyAlarm()` | 사이렌 | 강함 |

볼륨은 기사님이 이미 조절할 수 있다(`setVolume` · localStorage). **소켓 이벤트 하나면 된다.**

### 앱 — 소리·진동·표시가 전부 신설이다

🔴 **앱에는 알람 수단이 하나도 없다** (2026-08-30 실측):
`Ringtone`·`Vibrator`·`MediaPlayer`·`NotificationCompat` 을 쓰는 자리가 **0곳**이고,
`AndroidManifest` 에 `VIBRATE`·`POST_NOTIFICATIONS` 권한도 **없다** — 둘 다 앞으로 넣을 것이다.

🟢 **다만 화면 표시는 권한이 필요 없다.** 앱이 이미 접근성 서비스라
접근성 오버레이 창(`TYPE_ACCESSIBILITY_OVERLAY`)을 **신설**해 인성 화면 위에 그릴 수 있다.
그래서 「다른 앱 위에 표시」(`SYSTEM_ALERT_WINDOW`)는 기사님이 켤 일이 **없다**.
(`minSdk 26` · `targetSdk 35` — 이 창 종류는 API 22 부터다)

**무엇을 그리나** — 통과한 콜 줄에 **테두리** (§6-④). 글자를 안 가리고 터치를 안 먹는다.

## 6. ✅ 기사님이 정하신 넷 (2026-08-30)

**① 모드는 DB 로 내린다** — `user_devices.mode` 칸 하나.

메모리에만 두면 **서버가 다시 뜰 때 알람이 말없이 대기로 떨어진다**(§2). 화면은 멀쩡하고
알람만 안 울리는 종류라, 이 레포가 여러 번 당한 「조용한 실패」 그대로다.
🔴 **원천은 DB 하나다** (규칙 ③) — 옛 메모리 맵은 없앴다. 그리고 `user_id` 로 걸러
**남의 폰 모드를 못 바꾸게** 한다 (코드리뷰 2026-08-30 — 메모리일 땐 재시작에 사라지던
구멍이 DB 로 내리며 영구화될 뻔했다).

**② 알람은 짧게 두 번 + 강한 진동**

소리는 짧게 끝내되 **진동을 세게** 준다. 근거: 운전 중에는 네비 소리·음악이 깔려 있어
짧은 소리 하나는 묻힌다. 반대로 무한 반복은 이미 남에게 간 콜에도 계속 울린다.

| 어디 | 무엇 |
|---|---|
| 관제웹 | `playBeep()` **두 번** + `Haptics.notification`(강함) |
| 스캐너 폰 | 짧은 소리 두 번 + 강한 진동 (2단계) |

**③ 알람과 표시는 «먼저 오는 것»으로 그친다**

```
그 콜이 리스트에서 사라짐   ← 내가 잡았거나 남이 가져갔거나
10초 경과
```
둘 중 먼저 오는 쪽. 오래 남지도, 헛되지도 않는다.

> ⬜ **절반만 구현됐다** (2026-08-30). 10초 타이머는 있다(`FILTER_ALARM_HOLD_MS`).
> «리스트에서 사라짐»으로 그치는 길은 **아직 안 이었다** — 다음 성적표의 통과 수가
> 0 이 되는 것을 신호로 쓰면 되는데, 그 배선이 없다. 2단계와 함께 잇는다.

**④ 통과한 콜 줄에 테두리를 그린다** (2단계)

```
1  성남 → 분당       4만
╭──────────────────────╮
│ 2  곤지암 → 관고동  8만 │   ← 여기를 누른다
╰──────────────────────╯
3  이천 → 여주       6만
```

🔴 **두 가지를 반드시 지킨다** — 인성앱 글자를 **하나도 가리지 않고**, **터치를 먹지 않는다**
(그 줄을 눌러야 하므로 창에 `FLAG_NOT_TOUCHABLE` 을 준다). 테두리를 고른 이유가 그것이다.

⚠️ 그래서 「몇 번째」를 세지 않아도 된다 — **보이는 대로 누른다**(기사님 답 ③).

## 7. 규모 — 무엇이 크고 무엇이 작은가

| 일 | 크기 | 왜 |
|---|---|---|
| 모드 값 하나 늘리기 | **작음** | 타입 1줄 · 서버 검증 1줄 · 앱 무변경(AUTO 게이트가 이미 막는다) |
| 관제웹 버튼·알람 | **작음** | `soundManager` 가 이미 있다 · 소켓 이벤트 하나 |
| 모드를 DB로 (§6-①) | **작음** | 칸 하나 · 마이그레이션 없음 |
| 앱 소리·진동 | **중간** | 통째로 신설 · `VIBRATE` 권한 · 앱 재설치 필요 |
| 앱 화면 표시 | **중간** | 오버레이 창 신설 (권한은 불필요) |

| 출신을 파생하는 자리가 하나 | 판단이 두 벌이면 또 갈라진다 (규칙 ③) |
| **남의 폰 모드를 못 바꾼다** (`user_id`) | DB 로 내리며 영구화될 뻔했다 |
| 앱은 `currentMode == "AUTO"` 문 안에서만 누른다 | 알람·대기가 콜을 잡으면 약속이 깨진다 |

| 서버가 ALARM 에서만, 성적표가 온 보고에서만 쏜다 | 하트비트마다 옛 숫자로 울지 않게 |
