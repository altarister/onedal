# 🚀 1DAL 로컬 개발 및 무중단 배포 가이드 (Zero-Downtime Pipeline)

이 문서는 실서버(AWS EC2) 데이터 오염을 방지하고, 내 PC와 스마트폰만으로 1DAL의 전체 시스템(웹 ↔ 백엔드 ↔ 안드로이드 앱)을 개발 및 테스트한 후, 원클릭으로 안전하게 배포하는 라이프사이클을 안내합니다.

---

## 0. 🔄 판을 새로 여는 순서 (2026-09-02 실측으로 신설)

**이 절만 따라 하면 판이 선다.** 아래 순서는 실제로 한 번 겪고 적은 것이다 —
겪은 함정을 각 단계에 붙여 뒀다.

### ① 먼저 다 죽인다 — **포트로 죽인다**

```bash
cd onedal-web
kill -TERM $(pgrep -f "trap 'kill 0'")                      # pnpm dev 묶음
for p in 4000 3000 3001 4012 4014; do lsof -ti :$p | xargs kill -9; done
for p in 4000 3000 3001 4012 4014; do echo -n "$p: "; lsof -ti :$p; echo; done   # 전부 비었나
```

- 🔴 **`pkill -f "PORT=4012"` 는 안 잡힌다** — 환경변수는 명령줄에 안 보인다. 반드시 포트로.
- 🔴 **4012·4014 를 같이 본다.** `pnpm scenario`(4012)·`pnpm drive`(4014)가 남긴 **고아 서버**가
  부모 없이 며칠씩 산다. 실측: 21시간 살아 있는 4012 서버를 발견했다.

### ② 서버가 아닌 것도 죽었는지 본다

```bash
ps -eo pid,command | grep -E "rehearsal|reps/onedal" | grep -v grep
```

🔴 **`scripts/rehearsal.mjs` 는 서버가 아니라 포트 그물에 안 걸린다.** 살아 있으면
실폰과 **같은 기기 ID 로 동시에 신호**를 보내고, 서버가 이렇게 경고한다:

```
🛰️⚠️ [이중 발신] 앱폰-… 가 두 곳에서 동시에 신호 중 — 127.0.0.1 ↔ 172.30.x.x
```

이 상태면 **화면 이탈 감지가 심사 중인 콜을 강제 취소**한다. 리허설과 실폰 중 하나만 켠다.

### ③ 띄운다 — 필요한 것만

```bash
cd onedal-web && pnpm dev              # 서버 4000 + 관제웹 3000 + 운행일지 3001
# 또는 따로:  pnpm run dev:server / dev:client / dev:logbook
cd onedal-sim && pnpm dev              # 배차망 시뮬레이터 5173 (`--host` 라 폰에서 보인다)
```

- ⚠️ **관제웹(3000)은 `127.0.0.1` 에만 바인딩된다 — 폰에서 안 보인다.** 시뮬(5173)만 보인다.
- ⚠️ 백그라운드로 띄운 `pnpm dev` 는 **그 터미널 세션이 끝나면 셋 다 함께 죽는다.**

### ④ **`bootedAt` 으로 새 세대인지 확인한다** — 이게 이 절의 핵심이다

```bash
curl -s localhost:4000/api/health | python3 -m json.tool
```

🔴 **무인증 응답에는 `bootedAt` 과 uptime 뿐이다.** git 커밋은
`GET /api/health/detail`(로그인 필요)에 있다 — 2026-08-09 에 정찰 정보 노출을 줄이며 옮겼다.

«도는 코드 = 내 코드» 인지는 이렇게 본다:
```bash
git status --porcelain          # 비어야 한다 (작업트리 == HEAD)
find onedal-web/server/src onedal-web/shared/src -name "*.ts" -newermt "<bootedAt(KST)>"
# 위가 비면 = 부팅 뒤 고친 소스가 없다 = 도는 것이 내 코드다
```

### ⑤ PC IP 가 바뀌었으면 — **저장된 곳이 셋이다**

`ipconfig getifaddr en0` 로 지금 IP 를 확인한 뒤:

| 어디 | 무엇 | 어떻게 |
|---|---|---|
| **스캐너 앱** | 폰 SharedPreferences `localPcIp` | 앱 설정 화면에서 입력 |
| **시뮬 앱** (`com.onedal.simulator`) | 폰 SharedPreferences `OnedalSimPrefs` | 앱에서 **볼륨 업** → 주소 목록 → `개발용 PC IP` |
| **관제앱** | [`client-app/src/lib/serverTarget.ts`](../../onedal-web/client-app/src/lib/serverTarget.ts) `TARGETS.local` | 코드 수정 후 재빌드 |

- 🔴 **폰에 저장된 값이 소스 기본값을 이긴다.** `adb install -r` 은 SharedPreferences 를
  지우지 않으므로, **소스만 고치고 재설치해도 옛 IP 그대로**다. 폰에서 바꿔야 한다.
- 🟢 **`onedal-sim` 자체에는 IP 가 없다** — `window.location.hostname` 에서 파생한다
  (`SimulationContext.tsx`). 시뮬을 연 주소가 곧 서버 주소다. 고칠 것이 없다.

폰에 실제로 뭐가 저장돼 있는지는 이렇게 본다:
```bash
adb shell run-as com.onedal.simulator cat shared_prefs/OnedalSimPrefs.xml
```

### ⑥ 앱을 새로 깔아야 하면

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"

# 스캐너
cd onedal-app && ./gradlew :app:testDebugUnitTest assembleDebug \
  && adb install -r app/build/outputs/apk/debug/app-debug.apk

# 관제앱 (Capacitor — dist 를 싣는다. 웹 빌드 → sync → gradle 순서를 지킨다)
cd onedal-web/client-app && pnpm run build && npx cap sync android \
  && (cd android && ./gradlew assembleDebug) \
  && adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

- ⚠️ **버전 이름으로는 새 빌드인지 못 가린다** (스캐너 `2.6.1-meter` · 관제앱 `1.0` 고정).
  `adb shell dumpsys package <패키지> | grep lastUpdateTime` 으로 본다.
- 접근성 서비스는 재설치 후에도 대개 살아남지만, 확인은 해 둔다:
  `adb shell settings get secure enabled_accessibility_services`

### ⑦ 폰에서 시뮬을 열 때 — **크롬으로**

기본 브라우저가 삼성 인터넷이면 **앱이 화면 글자를 2개(URL·탭 수)밖에 못 읽는다.**
웹 콘텐츠를 접근성 트리에 안 올리기 때문인데, 겉보기엔 «앱이 고장난 것»처럼 보인다.
시뮬 앱(`com.onedal.simulator`)은 자체 웹뷰라 이 문제가 없다.

### ⑧ 도는지 확인 — 로그 두 곳

```bash
tail -f onedal-web/server/logs/server-$(date +%F).log     # 서버 (3일 보관)
adb logcat -d | grep -i onedal                            # 앱
```

⚠️ 앱 로그는 `D`(Debug)·`V`(Verbose) 라 **필터를 `I` 이상으로 걸면 통째로 안 보인다.**

## 1. 🖥️ 로컬 개발 환경 실행 (웹 + 백엔드)

로컬에서 프론트엔드와 백엔드를 동시에 띄우고, 코드 수정 시 즉각적으로 브라우저에 반영(Hot-reload)되도록 설정합니다.

1. **터미널 실행 및 서버 기동**
   ```bash
   cd onedal-web
   pnpm dev
   ```
2. **접속 주소**
   - 관제탑 대시보드: `http://localhost:3000`
   - 로컬 백엔드 API: `http://localhost:4000`
3. **핵심 원리 (Vite Proxy)**
   - 로컬 관제탑(3000)에서 발생한 모든 `/api` 및 `/socket.io` 요청은 Vite에 의해 자동으로 내 PC의 백엔드(4000)로 중계됩니다.
   - ⚠️ `client-app/.env` 파일에 `VITE_API_URL=https://1dal.altari.com/api` 와 같이 실서버 URL이 적혀 있으면 프록시가 깨지므로 **반드시 비워두어야 합니다.**
4. **로컬 DB 자동 분리**
   - 로컬 개발 시에는 실서버 DB가 아닌 `onedal-web/server/local.db` 파일이 생성되어 사용됩니다. 기사님들의 실제 데이터를 실수로 덮어쓸 위험이 0%입니다.

## 2. 📱 모바일 앱(Android) 로컬 연결 및 검증

안드로이드 폰(또는 에뮬레이터)을 들고 밖에 나가지 않아도, 방 안에서 배차와 지오코딩 로직을 100% 테스트할 수 있습니다.

### 사전 조건
- PC와 폰이 **동일한 Wi-Fi** 네트워크에 연결되어 있어야 합니다.
- (Mac 기준) `ifconfig | grep "inet "` 커맨드로 현재 PC의 내부 IP(예: `172.30.1.89`)를 확인합니다.

### 연결 방법
1. 앱 실행 후 우측 상단의 **[설정 탭]** 진입
2. **`📡 실서버로 발송 중`** 스위치를 **OFF** (왼쪽)로 변경
   - 라벨이 `🏠 개발용 로컬망 전송`으로 바뀝니다.
3. 아래 나타난 **`개발용 PC IP`** 입력칸에 방금 확인한 PC의 내부 IP를 입력합니다 (기본값: 172.30.1.89).
   - *참고: 안드로이드 에뮬레이터(AVD) 사용 시에는 `10.0.2.2:4000` 을 입력하면 호스트 PC로 연결됩니다.*

### 가상 콜(Mock Order) 테스트
1. 설정 화면 하단의 **[테스트 가상 콜 화면 열기]** 버튼 클릭
2. 브라우저에서 인성콜 시뮬레이터가 열리면, 가짜 콜을 발생시킵니다.
3. PC 터미널(백엔드) 로그를 확인하여 필터 통과 여부 및 카카오 지오코딩 연산 결과를 확인합니다.
4. PC 브라우저(`localhost:3000`) 관제탑 화면에 해당 콜이 즉시 뜨는지 확인합니다.

## 3. 🚢 원클릭 무중단 배포 (Zero-Downtime Deploy)

개발과 테스트가 끝나면 아래의 두 가지 방법 중 하나로 실서버에 코드를 올립니다.
두 방법 모두 PM2의 `reload` 기능을 사용하여, **서버가 꺼졌다 켜지는 시간(다운타임) 없이 기사님 앱의 연결을 부드럽게 유지**합니다.

### A. 깃허브 자동 배포 (권장)
단순히 코드를 커밋하고 Push하면 GitHub Actions 로봇이 알아서 배포합니다.
```bash
git add .
git commit -m "feat: 새로운 기능 추가"
git push origin main
```

### B. 수동 원클릭 배포 (긴급 시)
GitHub 결제 제한(Billing Lock)이 걸렸거나 빠른 강제 반영이 필요할 때 사용합니다.
```bash
./deploy-auto.sh
```
- 내부에 EC2 IP(`44.222.73.86`)와 PEM 키 경로가 미리 지정되어 있어, 비밀번호나 IP를 칠 필요 없이 엔터 한 번에 AWS 접속부터 빌드, 무중단 리로드까지 모두 끝납니다.

## 💡 시니어 개발자 Tip

1. **로그인 에러 시**: 로컬 DB(`local.db`)는 빈 깡통이므로 로그인이 안 될 수 있습니다. 이럴 때는 실서버의 `local.db`를 다운받아 덮어씌우거나, DBeaver 등의 툴로 테스트 계정 하나를 `users` 테이블에 인서트해두면 편합니다.
2. **Vite 프록시 갱신**: 프론트엔드의 환경변수(`.env`)를 수정했다면, 반드시 실행 중인 `pnpm dev`를 끄고(Ctrl+C) 다시 켜야 반영됩니다.
3. **PM2 Reload 주의사항**: `ecosystem.config.cjs` 등 PM2의 설정 파일 자체를 바꾼 경우에는 `reload`가 먹히지 않을 수 있습니다. 이때만 예외적으로 `./deploy.sh` (구버전)을 사용하여 `pm2 delete all` 후 강제로 다시 시작하세요.
