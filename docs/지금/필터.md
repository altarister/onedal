# 필터 — 콜을 집기 전에 거르는 것

> **필터는 «무념(無念)의 하루»를 만드는 자동 문지기다.**
> 기사님이 매 콜을 읽고 판단하지 않아도 좋은 콜만 올라오고 나쁜 콜은 걸러지는 상태 — 그게 완성형이다.
>
> 🔴 **필터는 «집기 전», 판정은 «집은 뒤»다.** 둘은 완전히 격리되어 각각 따로 작동한다.
> 판정은 [판정 문서](판정.md)에 있다. 말의 원천은 [용어집](용어집.md).

---

## 1. 무엇을 위해 있나

> *"돈 많이 벌려면 **높은 단가의 최적의 경로 콜을 많이 수행**해야 한다."*

이 한 문장을 풀면 필터가 지켜야 할 다섯이 나온다.

| | 조건 |
|---|---|
| ① | **단가 중간 이상** — 싼 콜을 안 올린다 |
| ② | **짐 많은 지역을 향해** — 첫짐은 방향 선택이다 |
| ③ | **길 위의 짐을 최대 합짐** — 가는 길에 가까운 짐을 최대한 |
| ④ | **약속을 지키는 한도 안에서** — 상차 시계와 배달 마감 |
| ⑤ | **내 차 공간 안에서** — 라면박스 100칸 |

**느슨하게 올리고 정밀하게 구분한다** (규칙 ⑤). 앱은 애매하면 올리고, 서버가 판정에서 가른다.
확실히 불가능한 것만 거른다.

## 2. 두 그릇 — 서로 남남이다

```
baseFilter    DB · 평소 설정          saveBaseFilter()      DB 만 건드린다
activeFilter  메모리 · 오늘의 콜 필터  updateActiveFilter()  메모리만 건드린다
```

로그인할 때 `base → active` 로 **1회 복사**되고, 그 뒤로는 격리된다.
설정을 바꿔도 진행 중인 콜 잡기가 안 흔들리는 이유가 이것이다.

🔴 **저장은 둘이다** — `💾 서버 저장`(DB) · `↩︎ 되돌리기`(서버 값으로). **안 누르고 닫으면 오늘만**이다
(메모리 · 자정에 되돌아감). 판정 기준에는 그 구분이 없다 — 바꾸면 바로 계속 적용된다.

🔴 **파생값은 `filterManager` 한 곳에서만 만든다.** 호출부는 **입력만** 넘긴다
(`destinationCity` · `destinationRadiusKm`). 키워드를 직접 채워 넘기면
`recalculateDerivedFields` 가 자기 계산을 건너뛰어 **다른 파생값이 안 채워진다.**

## 3. 값은 한 벌 — 옵션의 원천

콜 필터는 **사용자당 한 벌**이다. 행 = 사용자 (`user_filters`).

```sql
user_filters (
    user_id,
    destination_city,            -- 목적지
    pickup_radius_km,            -- 현위반경 (km)
    detour_radius_km,            -- 라인반경 (km)
    destination_radius_km,       -- 목적반경 (km)
    call_discount_pct,           -- 콜할인율 (%)
    src_angle_deg, dst_angle_deg, quad_radius_km,   -- 마름모 셋 (§3)
    radius_auto, radius_base_km, -- 반경 자동 맞춤 (§10-1)
    accepted_vehicle_types,      -- 받을 짐 (§5)
    route_mode,                  -- 노선(1) / 동선(0)
    excluded_regions, excluded_keywords
)
```

### 📐 마름모의 모양 — 사용자당 한 벌

그물의 모양은 *"어디로 가는가"* 가 정하지 *"콜을 몇 개 쥐었는가"* 가 정하지 않는다.

```
src_angle_deg    출발각 (°)       기본 110
dst_angle_deg    목적각 (°)       기본 110
quad_radius_km   마름모 반경 (km)  기본 25
```

🔴 **값을 상황별로 여러 벌 두지 않는다** — 지금 안 쓰는 칸은 **흐리게** 보인다(라인반경은 노선일 때만 진하다).
여러 행에 두면 화면이 말하는 값과 DB 값이 갈린다 (규칙 ③ · 버그 대장 #106).

### 📏 라인반경 — **「우회 허용」이 아니다**

```
라인반경   길 중심선에서 **한쪽으로** 몇 km 까지 콜을 받나   ← 이 칸이 하는 일
우회 허용   카카오가 재는 **총거리 증가분** (100km → 105km)   ← 다른 값이다
```

🔴 **라인반경을 «우회 허용»·«총거리 증가분»으로 부르거나 설명하지 않는다** — 값은 **길 양옆 폭**으로 쓰인다
(`netKeywordsOf` 의 `lineRadiusKm` · turf 버퍼 반경). 둘 다 km 라 한 이름으로 부르면 조용히 섞인다 (규칙 ⑤-4 ④).
칸 이름은 DB `detour_radius_km` · 평면 `detourRadiusKm`.

### 값은 한 벌이다 — 국면마다 다르지 않다

`FILTER_FIELDS` 가 유일한 원천이다 — **컬럼·라벨·범위·기본값이 전부 그 표에서 나온다.**
이름은 **평면(앱 피기백)과 같다** — 그래서 옮길 다리가 필요 없다.

| 칸 | DB 컬럼 | 기본값 | 언제 쓰이나 |
|---|---|---|---|
| 목적지 | `destination_city` | (빈칸) | 늘 — 합짐·복귀에서는 서버가 경로·집 주소로 채운다 |
| 현위반경 | `pickup_radius_km` | 10km | 늘 (내 위치 마름모) |
| 라인반경 | `detour_radius_km` | 6km | **🛣️ 노선이고 경로가 있을 때만** — 아니면 흐리게 |
| 목적반경 | `destination_radius_km` | 15km | 늘 (목적지 마름모) |
| 콜할인율 | `call_discount_pct` | 10% | 늘 (차종별 단가 하한) |

자리는 **`user_filters` 한 행**이다 (마름모 셋·제외 지역과 같은 행).

🔴 **상황별 기본값을 규칙으로 되살리지 않는다** — 기본값은 편의이지 규칙이 아니다. 진짜 규칙은 판정(서버)이 지킨다.
- 운행 중 우회를 막으려고 반경을 0 으로 좁히지 않는다 — 기사님: *"영역 안에 들어가면 잡는 로직에서 버리는 것이 맞다."* (규칙 ⑤ — 앱은 느슨하게, 서버가 정밀하게)
- 관내만 할인을 바꾸는 것은 기사님이 콜할인율을 열어 바꾼다 — 손잡이는 늘 거기 있다

⚠️ **«지금 무엇을 하나»는 남는다** — `resolvePhaseKey`·`PHASE_LABEL` 이 **문구**를 고른다
(무엇을 찾는 중인가 · 요약줄의 «N 읍면동»). 한 벌이 된 것은 **값**이지 상황이 아니다.

### 국면의 닻

```
첫짐   작업 시작 지역/방향        신림에 있어도 가산 콜을 잡는다
합짐   지금 경로
복귀   최종 하차지 기점            현위치가 아니다
공통   상차 시계
```

### 🚫 제외 지역 — 사용자당 한 벌

*"거긴 안 간다"* 는 그 지역이지 그 국면의 사정이 아니다. 마름모와 같은 이유로
사용자당 한 행(`user_filters.excluded_regions`, JSON 배열)에 산다.

```
S|<도>              도 통째      예: S|서울
R|<시·군·구>         시군구 통째   예: R|강화군
D|<시·군·구>|<동>    동 하나      예: D|파주시|금촌동
```

🔴 **키에 «서울 전체» 같은 화면 글자를 담지 않는다.** 화면이 부르는 이름과 판정이 맞춰 볼
이름은 다르다 — 도를 제외하면 **그 도의 시·군·구 이름으로 펴서** 다룬다(`sggList`).

**어디서 걸러지나** — `destinationKeywords`(앱의 2단계 필터가 읽는 동 목록)를 **만들 때**
뺀다. 그래서 앱은 제외를 몰라도 되고, 지금 앱을 안 고쳐도 동작한다.

> ⚠️ **빼는 자리는 `pruneExcludedRegions()` 하나다** (`shared/src/callNet.ts` · 규칙 ③).
> 서버의 파생 두 자리(도시 둘레 · 경로 주변)와 실험실 아웃풋이 **같은 함수**를 부른다.
> 판별 규칙(`isRegionExcluded`)을 각자 또 쓰면 «화면은 뺐는데 판정은 안 뺀다»가 된다.
>
> 🔴 **앱에는 아직 `excludedRegions` 키를 안 내린다.** 서버가 목록에서 이미 뺐으니
> 지금은 필요 없다. 앱의 2단계 필터를 «지역 이름으로도» 강화하는 것은 별도 일이다.

## 4. 세 축 — 금액 · 시간 · 짐

필터는 **금액·시간·짐** 셋을 본다.

### 금액

```
통과 = 요금 ≥ 배송거리 × 단가(차종) × (1 − 콜할인율)
```

- 하한 입력이 없다. **단가표(DB) × 콜할인율에서 파생**된다
- 단가의 원천은 DB(`user_filters.vehicle_rates`). 코드 상수는 폴백이다
- **콜할인율은 자동으로 안 내려간다** — 콜의 주인은 기사님이다
- `100%` = 금액 무관(순증 매출). 합짐·관내·복귀합짐이 그 자리다

### 시간

상차 시계 안에 닿을 수 있는가. **지금은 `pickup_radius_km`(km) 로 잰다.**
분(分) 축으로 바꾸는 일은 §11 에 있다.

도달 시간을 반경으로 바꾸는 함수는 있고, **판정의 딱지에만 쓴다** — 거르는 데는 안 쓴다.

```
reachRadiusKm(분) = 분 ÷ 계수        계수 잠정 1.5분/km
```

🔴 **계수가 근거 없는 값이라 콜을 떨어뜨리지 않는다.** 실측 표본(`reach_samples`)이
쌓이면 역산해 확정하고, 그때 이 상수는 판정 기준처럼 DB 칸으로 올라간다.
역산 보고서는 `pnpm reach`.

### 짐

적재 여유(라면박스) 안에 들어가는가.

```
1t 100박스 · 1t짐 80 · 라보 40 · 다마스 30 · 승용차 5
```

## 5. 앱이 실제로 거르는 여섯 축

앱은 콜을 **집기 전에** 여섯을 다 본다. **전부 AND 이고 중간에 멈추지 않는다** —
어느 축에서 몇 개가 떨어졌는지를 세야 *"이 축을 풀면 몇 개가 들어오나"* 를 읽을 수 있다.

| 축 | 무엇 |
|---|---|
| `vehicle` | 차종이 맞는가 |
| `region` | 도착지가 목표 안인가 |
| `fare` | 요금 ≥ 배송거리 × 단가 |
| `pickup` | 상차지 동이 **상차 목록**(`pickupKeywords`)에 있나 — 상차 목록이 안 오면(옛 서버) 옛 판정: 상차지가 반경 안인가 |
| `blacklist` | 제외 단어가 있는가 |
| `routeOrder` | 경로 순서 — 역주행이 아닌가. **상차 목록이 오면 안 쓴다** (인성 · 화물24시 파서 — 옛 칸은 «옛 칸 걷는 날»에 걷는다) |

🔴 **한 콜은 «첫 번째로 걸린 축»에만 센다.** 다 세면 합이 본 수를 넘어 뜻을 잃는다.
그릇(`FilterTally`)은 **호출자가 만들어 넘긴다** — 파서 안에 두면 갱신 시점이 호출 순서에 달린다.

### 🚚 `vehicle` 축 — 「고른 것」과 「막힌 것」은 다른 칸이다

기사님: *"내 차가 1톤이지만 라보 다마스 짐만 받겠다 … 합짐을 위해 필요."*

#### 왜 나누나

`allowedVehicleTypes` 한 칸이 **두 사실을 답하면 안 된다** (규칙 ⑤-4 ⑤):

| 묻는 것 | 누가 정하나 | 언제 바뀌나 |
|---|---|---|
| «나는 어떤 짐을 **받겠다**고 했나» | **기사님** | 필터에서 고칠 때만 |
| «지금 짐 때문에 어떤 것이 **막혔나**» | **서버** | 콜을 잡고 내릴 때마다 |

🔴 **한 칸에 겹쳐 두지 않는다** — 짐 한 번에 기사님이 고른 것이 지워지거나 용량 제한이 조용히 풀린다 (경위: 버그 대장 «필터 규칙 경위»).

#### 규칙 ⑤-4 의 다섯

| | 무엇 |
|---|---|
| **① 스키마** | `user_filters.accepted_vehicle_types`(TEXT · JSON 배열). **`allowedVehicleTypes` 는 DB 에 없다** — 파생이다 |
| **② 값** | 기본 **`[]` = 제한 없음**. 근거: 새 칸이 생겨도 **아무것도 안 바뀌는 것**이 기본이어야 한다. 기사님이 켜실 때만 좁아진다 |
| **③ 시점** | 필터 화면에서 고르면 그 자리에서 메모리로(💾 를 눌러야 DB). 읽는 것은 `recalculateDerivedFields` 가 **매번** — 짐이 바뀔 때마다 교집합을 다시 낸다 |
| **④ 화면** | 반경 아래 `🚚 받을 짐` 칸. **고른 것이 보이고, 용량으로 막힌 것은 흐리게+취소선.** 「왜 이 콜이 안 올라오나」가 화면에서 읽힌다 (규칙 ⑤-2 — 감추지 않고 표시한다) |
| **⑤ 읽는 곳** | 서버 `recalculateDerivedFields` **한 곳**이 교집합을 만든다. **앱은 `allowedVehicleTypes` 하나만 본다 — 앱 규격을 안 바꾼다**(`APP_FILTER_KEYS` 그대로) |

#### 계산

```
allowedVehicleTypes = (고른 것이 비었으면 «내 차로 가능한 전부», 아니면 고른 것)
                      ∩ 지금 적재로 «아직 실을 수 있는 것»
```

🔴 **교집합이 비면 그것이 「만재」다** — 빈 배열이 만재의 뜻이다(`capacityFullHold`).
   지어내서 채우지 않는다 (규칙 ④).
🔴 **`allowedVehicleTypes` 를 화면에서 서버로 보내지 않는다.** 보내면 서버가
   `if (!changes.allowedVehicleTypes)` 에 걸려 **제 계산을 통째로 건너뛴다.**
   화면이 보내는 것은 **`acceptedVehicleTypes` 뿐**이다.

### 🧭 `routeOrder` 축 — **구 단위 상차지는 막는다**

> ⚠️ **이건 버그가 아니라 결정이다.** 「왜 합짐이 안 붙나」로 다시 파기 전에 여기를 읽는다.

합짐 국면에서 경유 목록(`orderKm`)의 키는 **읍·면·동**이다. 그런데 배차망은 상차지를
**구·시 단위**로도 적는다(`분당구`·`중원구`·`광주시`). 글자가 안 맞으므로
`RouteOrderFilter` 가 **「경로 밖」으로 차단**한다 — 실제로는 경로 위여도 막힌다.

🔴 **비대칭이 하나 있고, 그것도 결정이다.** `region` 축은 구 별칭(`customCityFilters`)을
받아 「분당구」를 통과시키는데 `routeOrder` 축은 안 받는다. 둘이 답하는 질문이 다르기
때문이다 (규칙 ⑤-4 ⑤):

| | 묻는 것 | 구 단위로 답할 수 있나 |
|---|---|---|
| `region` | «하차지가 **내 그물 안인가**» | ✅ 구 전체가 그물 안이면 답이 하나다 |
| `routeOrder` | «상차지가 **경로의 몇 km 지점인가**» | ❌ 분당구 안에 6.8km 지점도 24.8km 지점도 있다 |

기사님 확정 — **«구 단위 상차지는 어디서 태울지 모르니 안 잡는 것이 안전하다»** ·
*"**인성이나 24시도 그렇게 작동하니까**"* — 배차망이 상차지를 구·시 단위로 적는 것은
파서의 한계가 아니라 **배차망 화면이 원래 그렇다.** 그러니 이 차단은 «못 읽어서»가
아니라 **«정말로 모르니까»** 다. 잡았다 취소하면 배차망 취소 횟수를 쓴다.

⚠️ **대가를 알고 고른 것이다** — 도시 안에서의 합짐은 사실상 안 붙는다.
🔬 그래서 **합짐을 시험하려면 문제지가 상차지를 읍·면·동으로 주어야 한다** — 시뮬 문제지는 기사님이 고치신다.
`tests/rules/routeOrderCityWide.test.ts` 가 이 결정을 잠근다.

### 🕸️ `region` 축의 목록은 **그물이 만든다**

앱이 보는 `destinationKeywords` 는 **«이 콜의 하차지가 내 그물 안인가»** 하나를 답한다
(`InsungParser.kt` 의 `anyHit(pureDropoffText, …)`). 만드는 자리는 서버이고,
**계산은 `shared/callNet.ts` 하나다** — 관제웹 지도가 그리는 그 계산이다.

```
첫짐   netForGoal(목적지, { line: null, anchor: 내 위치 })   → 내 위치 원 ∪ 목적지 원 ∪ 마름모
합짐   netForGoal(목적지, { line: 지금 경로, lastDrop })     → 라인 띠 ∪ 목적지 원 ∪ 마름모
```

**목록을 만드는 모든 때가 그물 한 곳을 지난다** (`filterManager.rebuildNetFilter` · 버그 대장 #121).
- 라인은 **KEEP 순간 얼린 경로**(`filterLineOf`) — 하차·취소·재탐색으로 안 바뀐다. 첫 콜만 쥔 동안은 경로 방침을 바꾸면 따라간다
- 앱 순서표(`orderKm`)와 지나온 곳 빼기(`progressKm`)도 **같은 그물**의 라인 진행도에서 나온다. 빼기는 얼린 라인 위 GPS 진행도(`progressAlongKm`)
- 옛 계산(`recalculateDetourFilter`)은 설정의 미리보기 API 둘에만 남았다 — 관제웹이 안 부른다

🔴 **서버가 제 계산을 따로 두지 않는다** — 기사님 «실험실 것으로 통일». 서버와 지도가 다르게 계산하면
«화면은 든다는데 판정은 탈락»이 난다 (규칙 ⑤-3).

> ⚠️ **알고 고른 것** — 실험실은 동을 **중심점 하나**로 보고 서버 turf 는 **폴리곤 모양**으로 본다.
> 그래서 면적이 넓은 읍·면은 가장자리가 걸쳐도 중심이 밖이면 **빠질 수 있다.** 차이는 `pnpm net:compare` 로 잰다.
>
> 🔴 **내 위치를 모르면 옛 방식(도시 둘레)으로 간다.** 첫짐 그물은 내 위치가 꼭짓점이라
> 없으면 못 그리는데, **빈 목록은 «제한 없음»이 아니라 고장**이다 (규칙 ④).
> 지어내지도 비우지도 않고 «잴 수 있는 방법»으로 물러선다.

### 🧩 필터 영역 — 영역 열한 개를 살아 있는 목적지마다 합친다 (기사님 확정 · 🟡 코드와 다른 곳은 아래 표)

**필터 영역 = 상차 영역 ∪ 하차 영역**이고, 둘은 아래 두 절에 따로 적는다.
«목적지»는 기사님이 정한 곳이다 — **파주든 집이든 목적지다.** 복귀를 켜면 목적지가 둘(목적지 · 집)이 되어 영역이 늘어난다.
기호: `∪` 합집합 · `∩` 교집합

**영역 열한 개**

| 기호 | 이름 | 모양 | 손잡이 |
|---|---|---|---|
| A | 현위치 영역 | 내 위치 둘레 원 | 현위반경 |
| D | 목적지 영역 | 목적지 둘레 원 | 목적반경 |
| H | 목적지(집) 영역 | 집 둘레 원 | 목적반경 |
| L | 라인 영역 | 목적지 쪽으로 잡은 콜 경로 양옆 띠 — «경로의 라인반경 영역». ✂️ 운행 뒤에는 **현위치부터 앞으로만** · 시작 끝은 평평하게 | 라인반경 |
| LH | 집 라인 영역 | 집으로 가는 콜 경로 양옆 띠 — 운행 뒤에는 L 과 같이 현위치부터 · 시작은 평평하게 | 라인반경 |
| A∩L | 교집합 영역 | 현위치 영역 안에 든 라인 영역 | — |
| A∩LH | 교집합 영역 | 현위치 영역 안에 든 집 라인 영역 | — |
| Q(A→D) | 마름모 | 현위치와 목적지를 대각선으로 잇는 마름모 | 출발각 · 목적각 · 마름모반경 |
| Q(E→D) | 마름모 | 경로의 종착지와 목적지를 대각선으로 잇는 마름모 | 〃 |
| Q(A→H) | 마름모 | 현위치와 집을 대각선으로 잇는 마름모 | 〃 |
| Q(EH→H) | 마름모 | 집 가는 경로의 종착지와 집을 대각선으로 잇는 마름모 | 〃 |

**목적지 하나의 영역 — 그 목적지의 상태 셋**

| 그 목적지의 상태 | 영역 |
|---|---|
| 콜 없음 | A ∪ Q(현위치→목적지) ∪ 목적지 영역 |
| 콜을 잡아 경로가 생김 (운행 시작 전) | A ∪ 라인 ∪ Q(경로 종착지→목적지) ∪ 목적지 영역 |
| 운행 시작 뒤 | (A ∩ 라인) ∪ 라인 ∪ Q(경로 종착지→목적지) ∪ 목적지 영역 |

«(A ∩ 라인) ∪ 라인»은 셈으로는 라인과 같다 — 앞의 것은 **상차 자리**, 뒤의 것은 **하차 자리**라 따로 적는다.
목적지가 집이어도 **똑같은 모양**이다.

**살아 있는 목적지**

| 목적지 | 살아 있는 동안 |
|---|---|
| 목적지 | 복귀 끔 · 복귀 켬이지만 집 가는 콜(복귀콜)을 아직 못 잡음 · 목적지 콜이 남아 있음 |
| 집 | 복귀 켬 |

까닭 — 기사님: *"복귀를 눌렀다면 집 가는 콜을 잡기를 희망하는 거다. 아직 못 잡았으면 가만히 있으면 효율이 떨어지니 관내 가까운 거 하자.
집 방향 콜을 잡았다면 더 이상 관내콜은 필터에서 거르고, 집 방향으로 잡은 콜부터 여러 개 합짐하여 복귀한다."*

**관내** — 국면 · 단계 · 타겟이 아니다. 기사님: *"그쪽에 도착했으니 다른 곳을 정하지 않았으면 그곳에서 일 있으면 하자."*
관내는 아래 **«목적지 가까이 옴»** 으로 저절로 갈린다 — 따로 재는 규칙을 두지 않는다. **관내콜**은 그때 목적지 영역 안에서 싣고 내리는 콜을 부르는 이름일 뿐이다.

**🎯 목적지 가까이 옴 — 목적지마다 따로 본다**

**Q(현위치→목적지) 마름모가 현위치 영역 ∪ 그 목적지 영역 안에 통째로 들어가면** 그 목적지는 «가까이 옴»이다.

| 그 목적지 | 상차 | 하차 |
|---|---|---|
| 🎯 가까이 옴 | 현위치 영역 전체 | **그 목적지 영역 전체** — 상차 목록 동을 빼지 않는다 |
| 멀다 | 아래 «상차 영역» 표 | 아래 «하차 영역» — 상차 목록 동을 뺀다 |

- 현위반경 · 목적반경을 따로 두면 «가까이 옴»이 되는 거리와 관내 넓이를 따로 고른다 (기사님 *"수동으로 둘의 크기를 다르게 설정할 수 있어"*)
- 판단에 쓰는 마름모는 목적지 상태와 상관없이 늘 **현위치 → 목적지**다 — «종착지 → 목적지»로 보면 종착지만 목적지 근처여도 차는 먼데 «가까이 옴»이 된다
- 복귀를 켜면 목적지마다 따로 갈린다 — 파주에 와서 복귀를 켜면 파주는 «가까이 옴»(파주 영역 전체), 집은 «멀다»(빼기 규칙)
- 계산은 마름모 테두리 점(`callNet.quadOutline`)이 전부 두 원 중 하나 안에 드는가 — shared `filterArea.isNearGoal` · `withNearness` 한 곳을 서버 상차 · 하차 목록(`goalZonesNow`)과 지도(`StageView`)가 부른다

**필터 영역 = 살아 있는 목적지마다 영역을 만들어 합친 것.** (`[운행 뒤]` = (A∩L) ∪ L ∪ Q(E→D) ∪ D) — 가까이 온 목적지는 A ∪ 그 목적지 영역이다:

| 경우 | 필터 영역 |
|---|---|
| 콜 없음 | A ∪ Q(A→D) ∪ D |
| 콜을 잡아 경로가 생김 | A ∪ L ∪ Q(E→D) ∪ D |
| 운행 시작 뒤 | (A∩L) ∪ L ∪ Q(E→D) ∪ D |
| 운행 뒤 · 목적지 콜 남음 · 복귀 켬 | [운행 뒤] ∪ A ∪ Q(A→H) ∪ H |
| 위 + 집 가는 콜 잡음 | [운행 뒤] ∪ (A∩LH) ∪ LH ∪ Q(EH→H) ∪ H |
| 목적지 콜 끝 · 복귀 켬 · 집 가는 콜 잡음 | (A∩LH) ∪ LH ∪ Q(EH→H) ∪ H |
| 🎯 목적지에 가까이 옴 | A ∪ D |

- 🔴 **필터는 방향을 따지지 않는다** — 기사님: *"필터가 그렇게 디테일할 수 없다. 빠른 판단을 위해 그냥 올리고,
  판정에서 나쁜 점수를 받으면 기사는 선택하지 않는다"*. 진행 방향 뒤는 운행을 시작하면 현위치 영역이 «A ∩ 라인»으로 줄고, 하차에서 상차 목록 동을 빼는 것으로 빠진다
- **첫 콜을 확정하고 합짐이 생기기 전까지는 카카오 경로를 바꿀 수 있다** (기사님). 라인 영역은 그 경로를 따른다. 그 뒤 라인은 KEEP 순간 얼린 경로다
- **운행 시작은 주행이 감지되면 켜진다** (관제웹 `StageView` · 목업 «주행» 버튼과 같은 뜻) — 운전 중에는 버튼을 누를 수 없다
- 🔷 **동선을 고르면 라인이 없다** — 목적지는 «콜 없음» 모양으로 본다 (아래 «노선 ↔ 동선»)
- 스캔앱은 **지역명 목록만** 본다 — 서버가 영역을 목록으로 만들어 내려준다. 지도도 **같은 영역**을 그린다 — 교집합도 보여야 한다 (기사님 지적)

| 무엇 | 지금 코드 | 새 정의 |

### 🟢 상차 영역 — 원달앱이 상차지를 거르는 영역 (✅ 코드 — 서버 목록 · 지도 레이어)

**필터 영역 중 현위치 영역이 들어간 항만 상차 자리다.** 기사님: *"아무리 빨리 가도 마름모 영역까지 상차를 20분 안에 할 수 없잖아"*.
그 영역에 걸친 읍·면·동이 **상차 목록**(`pickupKeywords`)이다. 🔴 원달앱은 **상차지 동이 이 목록에 없으면 콜을 잡지 않는다** (`PickupListFilter.check`).

| 그 목적지 | 상차 영역 |
|---|---|
| 🎯 가까이 옴 | A (상태와 상관없이) |
| 멀고 콜 없음 | A |
| 멀고 경로 생김 (운행 시작 전) | A |
| 멀고 운행 시작 뒤 | A ∩ 라인 |

합치면 **살아 있는 목적지가 전부 «멀고 운행 뒤»일 때만 A ∩ 라인**, 나머지는 A 전체다.

✂️ **A ∩ 라인의 라인은 현위치부터 앞으로만 · 시작 끝은 평평하게 자른다** — 뒤가 남으면 역방향을 줄이려던 뜻과 멀어진다.
지나온 길(출발 → 앞 정거장 → 현위치)과 차 뒤 반원은 상차 영역이 아니다. 먼 끝 둘레 · 꺾인 자리는 둥근 그대로. 라인 끝을 지나 앞이 없으면 «라인 없음» — A 전체.
코드: `callNet.lineFromPoint` · `distToLineFlatStartKm` — 서버 상차 목록(`pickupListFor`) · 지도 «상차» 띠 · 운행 뒤 «하차» 띠가 같은 모양이다. 로그 `📋 [상차 목록] … 내 위치 ∩ 라인(현위치부터)`.
⚠️ 서버 **하차** 목록의 지나온 곳은 도형이 아니라 동의 진행도로 뺀다(아래 «지나온 라인») — 지도 하차 띠는 도형으로 평평하게 자른다. 경계에 걸친 동에서 조금 다를 수 있다.

| 경우 | 상차 영역 |
|---|---|
| 콜 없음 | A |
| 콜을 잡아 경로가 생김 | A |
| 운행 시작 뒤 | A∩L |
| 운행 뒤 · 목적지 콜 남음 · 복귀 켬 | A (집 쪽이 «콜 없음») |
| 위 + 집 가는 콜 잡음 | (A∩L) ∪ (A∩LH) |
| 목적지 콜 끝 · 복귀 켬 · 집 가는 콜 잡음 | A∩LH |
| 🎯 목적지에 가까이 옴 | A |

- 상차 영역은 **현위치 영역 밖으로 나가지 않는다.** 경로 위라도 원 밖이면 가까워질 때 올라온다
- 뒤쪽은 «경로 몇 km 지났나»가 아니라 **«현위치 영역 밖»** 으로 빠진다 — 원 안이면 지나온 길도 남는다 (까닭은 아래 «상차 목록 · 하차 목록»)
- 🔴 좌표를 모르는 도형(목적지 · 집을 모름)이 든 항은 비운다 — 지어내지 않는다 (규칙 ④)

### 🔵 하차 영역 — 원달앱이 하차지를 거르는 영역 (✅ 코드 — 서버 목록 · 지도 레이어 · 🟡 남은 차이는 위 표)

**목적지마다 따로 만들어 합친다.** 가까이 온 목적지는 **그 목적지 영역 전체**, 먼 목적지는 그 목적지의 하차 조각에 걸친 동에서 **상차 목록 동을 뺀다.**
합친 것이 **하차 목록**(`destinationKeywords`)이다.

```
하차 목록 = ∪ 가까이 온 목적지 [ 그 목적지 영역에 걸친 동 ]
          ∪ 먼 목적지      [ 그 목적지의 하차 조각에 걸친 동 − 상차 목록 동 ]
```

까닭 — 기사님: *"하차는 상차 영역을 빼야 해 — 상차한 지역에 하차하지 않을 꺼 같아. 역방향도 많이 걸릴꺼 같고"*.

- 🔴 **동 목록으로 뺀다 (도형으로 안 뺀다)** — 원달앱은 상차지 동이 상차 목록에 있어야 콜을 잡는다. 그래서 하차 목록에서 상차 목록 동을 빼면
  **«싣는 동에 내리는 콜»이 정확히 막힌다.** 도형으로 빼면 경계에 걸친 큰 읍·면이 두 목록에 다 남아 샌다
- 🔴 **시 · 군 · 구와 짝지어 뺀다** — 이름만 보면 먼 도시의 같은 이름 동(중앙동 · 신촌동)까지 빠진다. 원달앱 하차는 «시 + 동»(`customCityFilters`)으로 보니 먼 쪽 동은 다른 곳이다
  (서버는 상차 목록을 시 · 군 · 구로 묶어 `activeFilter.pickupGroups` 에 싣는다 — 관제웹 지도 «동 점»도 이것을 읽는다 — 원달앱에는 `pickupKeywords` 이름만 간다 · 버그 대장 #148)
- 운행 뒤에는 그 목적지 라인이 없어도(종착지 좌표를 모름 · 🔷 동선) **현위치 원을 다시 넣지 않는다** — 운행 뒤 하차 영역에 현위치 영역은 없다 (`dropoffPartsOf`)
- ⚠️ 알고 고른 것: 경계에 걸친 큰 읍·면 안에서 싣고 **같은 읍·면 반대쪽 끝**에 내리는 콜도 막힌다 — «상차한 지역에 하차하지 않는다»와 같은 뜻이다
- 가까이 온 목적지는 빼지 않는다 — 안 그러면 목적지 영역이 현위치 영역과 겹쳐 **관내콜이 전부 막힌다**

| 먼 목적지의 상태 | 하차 조각 (여기에 걸친 동 − 상차 목록 동) |
|---|---|
| 콜 없음 | A ∪ Q(현위치→목적지) ∪ 목적지 영역 |
| 경로 생김 (운행 시작 전) | A ∪ 라인 ∪ Q(종착지→목적지) ∪ 목적지 영역 |
| 운행 시작 뒤 | 라인 ∪ Q(종착지→목적지) ∪ 목적지 영역 |

A 조각은 상차 목록(= A 에 걸친 동)과 겹쳐 빼면 남지 않는다 — 운행 뒤 상차가 A ∩ 라인일 때만 A 쪽 동이 조각에 없다.

| 경우 | 하차 목록 |
|---|---|
| 콜 없음 (목적지 멂) | [Q(A→D) ∪ D] − 상차 목록 |
| 콜을 잡아 경로가 생김 | [L ∪ Q(E→D) ∪ D] − 상차 목록 |
| 운행 시작 뒤 | [L ∪ Q(E→D) ∪ D] − 상차 목록 (상차 = A∩L) |
| 운행 뒤 · 목적지 콜 남음 · 복귀 켬 | [L ∪ Q(E→D) ∪ D ∪ Q(A→H) ∪ H] − 상차 목록 |
| 위 + 집 가는 콜 잡음 | [L ∪ Q(E→D) ∪ D ∪ LH ∪ Q(EH→H) ∪ H] − 상차 목록 |
| 목적지 콜 끝 · 복귀 켬 · 집 가는 콜 잡음 | [LH ∪ Q(EH→H) ∪ H] − 상차 목록 |
| 🎯 목적지에 가까이 옴 · 복귀 끔 (관내) | [D] 전체 |
| 🎯 목적지에 가까이 옴 · 복귀 켬 · 복귀콜 없음 | [D] 전체 ∪ ([Q(A→H) ∪ H] − 상차 목록) |

- 🔴 **라인 영역에 동을 넣는 기준은 «동 경계가 띠에 걸치면»이다** (기사님 결정). 목업은 상차지 **좌표**로 재지만 스캔앱은 **지역명**만 본다 —
  동 중심점으로만 넣으면 넓은 읍·면의 길 위 콜을 놓친다. 서버 `netKeywordsOf` 가 그물 목록에 띠에 걸친 동을 더한다
- 지나온 라인(동의 진행도가 내 진행도보다 뒤)은 목록에서 뺀다 — 목적지 · 마름모 · 현위치 영역으로 든 동은 «아직 안 간 곳»이라 안 뺀다 (`callNet.lineZoneOf` 의 `onlyByLine`)

### 📋 상차 목록 · 하차 목록 — 앱이 거르는 두 목록 (✅ 1단계 서버 · ✅ 2단계 원달앱 · 🟡 3단계 옛 칸 걷기 아직)

> 이 절은 서버와 원달앱이 **같은 글을 보고 고치는** 규격이다 (규칙 ⑤-4).
> ✅ **1단계 서버** — `pickupKeywords` 를 옛 칸과 함께 보낸다 (`shared/src/pickupList.ts` · `filterManager.rebuildPickupList` · `geoService.getRegionsTouchingCircle`). ✅ **2단계 원달앱** — 인성·화물24시 파서가 `pickupKeywords` 가 오면 그것으로 거르고 상차 반경·`RouteOrderFilter` 를 안 쓴다 (`PickupListFilter.check` · 인성 상세는 `PickupListFilter.insungDetailPickupText`). 칸이 안 오면 옛 칸으로 — 3단계에 함께 지운다. 🟡 **픽커 알람 판정은 아직 상차 반경**이다 (콜을 잡지 않는 배차망이라 2단계에서 뺐다).
> 기사님 확정: ① 하차 목록 = 위 «하차 영역» · ③ 구 단위 상차지는 막는다 · ② **0.5km 움직일 때마다** 다시 만든다 · ④ 상차 목록 = 위 «상차 영역».

**왜** — 동을 경로 위 **한 지점**으로만 기억하면 되돌아가는 경로에서 다시 지날 동을 «지나왔다»며 빼고, 원달앱 경로 순서 필터(경로 밖·역주행)가 앞길 위 좋은 콜을 막는다 (버그 대장 #134).
기사님 원칙: **«지나온 곳은 빼고, 앞으로 지날 곳은 잡는다.»** 뒤쪽은 «경로 몇 km»가 아니라 **«지금 내 위치 둘레»** 로 뺀다.

**원달앱이 보는 것** — 상차지 글자가 **상차 목록**의 동에 걸리나 · 하차지 글자가 **하차 목록**의 동에 걸리나 · 차종 · 요금 · 제외어. 그 밖에는 없다.

**걷는 것** — 원달앱: 상차 반경 숫자 비교(«현위치 → 상차지 N km» ↔ `pickupRadiusKm`) · `RouteOrderFilter.kt`(경로 밖·역주행 · `routeOrderCityWide`) · 순서표 `orderKm` 받기 ·
서버: `buildAppOrderKm` · 지나온 구간의 동별 km 비교. 시뮬레이터 화면의 거리 글자는 **그대로 둔다** — 실제 인성도 보여 준다(원달앱이 안 읽을 뿐).

**상차 영역 · 하차 영역** — 위 «상차 영역» · «하차 영역» 두 절이 원천이다. 그 영역에 **걸친** 읍·면·동이 각 목록이다 (기사님 *"영역에 지역이 걸치고 있으면 들어가는거야"*).
✅ **코드 (하차 목록)** — `filterManager.netOfGoals` 가 목적지마다 조각(`dropoffPartsOf` · 종착지 `lastDropOf` · 라인 `lineUntil`)을 만들고 `mergeDropoffGroups` 로 합친다 — 먼 목적지는 상차 목록 동을 뺀다. 가까이 온 목적지는 원에 걸친 동(`geoService.regionsTouchingCircleGrouped`) · 먼 목적지도 원 · 마름모 가장자리에 걸친 동(`geoService.regionsTouchingNetGrouped` — 판정은 그물과 같은 `callNet.netAreaTesterOf`). 상차 목록을 먼저 만들고(`rebuildNetFilter`), 0.5km 마다 상차 목록 · 가까이 옴이 바뀌면 하차 목록도 다시 만든다(`maybeRebuildPickupList`). 남은 차이는 위 «지금 코드와 다른 곳».

**코드 (상차 목록)** — 목적지 상태는 shared `goalZonesOf`, 모양은 `pickupShapeOf`, 계산은 `geoService.pickupListFor` 한 곳 — 관제웹 «상차» 레이어가 같은 두 함수로 그린다.
걸침은 둘로 잡는다(`geoService.regionsTouchingArea`): 영역 안 **0.3km 격자 점**이 동 안에 있거나, 동 테두리 **꼭짓점**이 영역 안에 있으면 넣는다.
둘 다 놓치는 것은 동 테두리의 한 변이 꼭짓점 없이 영역 가장자리를 0.3km 보다 얇게 스치는 경우뿐이다. 라인 판정은 `callNet.distToLineKm`.

**하차 목록** — 위 «하차 영역» 에 걸친 동이다. 칸도 지금 것(`destinationKeywords` · `customCityFilters` · `keywordTraps`)을 쓴다 — 이름을 안 바꿔 앱·서버 변경을 줄인다.

**구 단위 상차지** (기사님 ③) — 상차지가 «분당구»처럼 동 없이 오면 상차 목록 어느 동에도 안 걸려 **막힌다.** 따로 규칙이 필요 없다 (`routeOrderCityWide` 는 함께 걷는다).
🔴 그러려면 **`pickupKeywords` 에는 읍·면·동 이름만 싣는다** — 시·구 이름은 안 싣는다. 픽커 카드는 «분당 서현1»처럼 구 토큰이 있어
하차지에 쓰는 토큰 대조(`dongTokenMatch`)가 «분당구»와 맞출 수 있다 — 목록에 구가 섞이면 구 단위 상차지가 새어 나간다 (`KakaoPickerParser.kt`).

**원달앱이 상차지를 대조하는 법**:

| 배차망 · 단계 | 상차지 글자 | 대조 |
|---|---|---|
| 인성 리스트(1차) | `order.pickup` | 하차지와 같은 `RegionMatch.anyHit(글자, pickupKeywords, keywordTraps)` |
| 인성 상세(2차) | 상세 글에서 **«출발지 ~ 도착지» 사이**를 자른다 (하차지는 «도착지» 뒤) | 동 대조만 — 🔴 시 이름 추정 분기(`customCityFilters`)는 **하차 도시 전용이라 상차지엔 없다** |
| 화물24시 | `pickupInfo.cleanRegion` | ⬜ 표기에 동이 실리는지 실물 캡처로 확인 |
| 픽커 | «출발 시 + 출발 동» — 동·구를 뗀 줄임(«분당 서현1») | 하차지와 같게 `anyHit` **또는** `dongTokenMatch` |

**오탐 막는 낱말** (`keywordTraps` — «남동»⊂«인천 남동구» 같은 것) — 상차 목록 ∪ 하차 목록으로 한 벌 만든다(`filterManager.refreshKeywordTraps` → `trapsForKeywords`).
**상차 목록 ∪ 하차 목록으로 한 벌**을 만든다 — 막는 낱말이 늘 뿐이라 통과를 넓히지 않고, 칸이 하나로 남는다 (규칙 ③).

#### 규칙 ⑤-4 의 다섯 — 상차 목록

| | 무엇 |
|---|---|
| **① 스키마** | **저장하지 않는다** — 필터 영역에서 파생(규칙 ③) · 서버 메모리 `activeFilter`. 앱 새 칸 **`pickupKeywords: string[]`** (`APP_FILTER_KEYS` ↔ 원달앱 `FilterConfig` 짝 — `appFilterKeys` 검사) |
| **② 값** | 기본값 없음. 🔴 **빈 목록은 «제한 없음»이 아니라 «고장 → 잡지 않음»** (규칙 ④) — 서버 `callFilterBlocker` 에 «상차 목록이 비었다»를 더하고, 원달앱은 빈 `destinationKeywords` 를 `false` 로 두는 자리와 같은 모양으로 막는다. 읍·면·동 이름만 싣는다 |
| **③ 시점** | **만드는 때**: 하차 목록을 다시 만들 때마다(`rebuildNetFilter` — 콜 확정 · 출발 · 복귀 켬/끔 · 콜 끝이 여기로 모인다) + 내 위치가 **0.5km**(`PICKUP_LIST_MOVE_KM` · 기사님 확정) 넘게 움직일 때(관제웹 GPS 받을 때마다 `maybeRebuildPickupList` — 콜이 없어도 돈다). **보내는 때**: 피기백 v2 버전 게이트 그대로 — 바뀔 때만(`scrap.ts` `filterVersionOf`) |
| **④ 화면** | 🟡 규격 확정 뒤 [화면규칙](../기획/화면규칙.md) 에 — 관제웹 지도에 상차 목록 동 표시 · 필터 요약줄 «상차 N곳 · 하차 M곳» |
| **⑤ 읽는 곳** | 원달앱 파서 셋(인성 · 화물24시 · 픽커) — «이 상차지에서 실어도 되나» · 서버 `callFilterBlocker` — «잡아도 되는 필터인가» · 관제웹 지도 — «어디서 싣는 콜을 받나» |

**막힘 축 이름** — 원달앱이 올리는 판정(`intel.verdict`) `pickup`(상차 거리) · `routeOrder`(경로 순서) 대신 **`pickupList`** 하나. 관제웹 현황판 `VERDICT_AXIS_LABEL` · 시나리오 `blockBy` 가 함께 바뀐다.

**올리는 순서** — 앱 설치 전후 어느 때도 필터가 비지 않게:
1. **서버**: `pickupKeywords` 를 **더해** 보낸다. 옛 칸(`pickupRadiusKm` · `orderKm`)도 그대로 — 옛 앱은 새 칸을 모르니 지금처럼 돈다
2. **원달앱**: `pickupKeywords` 가 오면 그것으로 거르고 옛 판정(상차 반경 · `RouteOrderFilter`)을 안 쓴다. 안 오면(옛 서버) 옛 칸으로. 설치한다
3. **옛 칸 걷기**: 서버 옛 칸 + 🔴 **원달앱의 «안 오면 옛 칸으로» 길을 함께 지운다** — 남기면 판정 길이 두 벌이다(규칙 ③). 걷는 날은 [todo.md](../../todo.md) 에 걸어 둔다

**⚠️ 알고 둔 것**:
- **폰은 새 콜을 직전 필터로 먼저 판정한다** — 피기백이라 «판정 → 전송 → 새 필터» 순서다. 실운행(시속 60km)에서 틀린 거리는 대개 0.5km 안팎이라 **따로 안 고친다.**
  그 틈에 막힌 콜은 원달앱이 **필터 버전이 바뀌면 막았던 콜만 다시 판정**해 거둔다 (`CallMemory.onFilterVersion` · 버그 대장 #135 — 이것이 없으면 한 번 막힌 콜이 가까워져도 영영 안 올라온다)
- **긴 터널에서 GPS 가 5분 넘게 멈추면** 서버 기점이 «낡은 좌표 → 집 주소»로 물러서(`geoService.originOf` ②) 그동안 상차 목록이 집 둘레로 틀어진다.
  몇 분치이고 터널을 나오면 다음 좌표로 곧 돌아온다 — 위 «다시 판정»으로 그 사이 막힌 콜도 풀린다. **따로 안 고친다.**
- 모의 주행이 빈 차로 서 있는 동안 서버가 모의 좌표를 안 믿는 것(`originOf` ③)은 **시험에서만** 난다 — 실 GPS 는 빈 차여도 그 자리를 쓴다. 제품 규칙은 그대로 둔다

### 🏠 복귀 대기 — 목적지가 둘이다

| 상태 | 살아 있는 목적지 | 뜻 |
|---|---|---|
| 복귀 끔 | 목적지 | 평소 |
| 복귀 켬 · 복귀콜 없음 | **목적지 ∪ 집** | 복귀콜을 잡기 전까지 관내콜을 진행한다 |
| 복귀 켬 · 복귀콜 잡음 · 목적지 콜 남음 | **목적지 ∪ 집** | 목적지 콜을 다 내릴 때까지 목적지 쪽 영역도 남는다 (`filterArea.goalZonesOf`) |
| 복귀 켬 · 복귀콜 잡음 · 목적지 콜 끝 | 집 | 목적지 콜은 뜨면 안 된다 |

원천은 위 «필터 영역» 의 «살아 있는 목적지» 표다.

- 규칙은 `callNet.activeGoals` 한 곳이다. 서버 `filterManager.goalCitiesOf` 가 정하고 필터의 `goalCities` 로 내려준다
- **필터 목록은 목적지마다 그물을 만들어 합친다** (`filterManager.netOfGoals`) — 앱은 합친 지역명 목록 한 벌만 본다.
  어느 그물에서든 진행도 없이 든 동은 «아직 안 간 곳»이라 지나온 곳 빼기에 안 먹힌다.
- **복귀콜을 잡았나 = 콜의 판** — 확정하는 순간 서버가 «통과한 목적지»를 콜에 적는다(`filterManager.goalOfCall` · 콜의 `goalCity`).
  복귀 대기(목적지 둘)면 **하차지가 목적지 원(관내로 재는 그 원 · `destRingKm`) 안이면 목적지(관내콜)** · 그 밖이면서 집 그물 안이면 집(복귀콜) — 원을 먼저 본다 (기사님 확정 · 버그 대장 #139). ⚠️ 목적지 원이 집 쪽으로 걸치면 그 안의 집 방향 하차지도 관내콜로 적힌다.
  복귀 대기면 하차지가 **목적지 원 안이면 목적지**, 아니면 집 그물 안이면 집, 둘 다 아니면 목적지다 (`filterManager.goalOfCall`)
  · 🔴 **복귀를 켠 뒤에 잡은 콜만 센다** (버그 대장 #131) — 하차를 마친 콜도 세고, 취소·방출한 콜은 안 센다.
    «이번 운행»(`deckOfCycle` — 진행 중인 콜이 0건이면 빈 목록)으로 세지 않는다 — 콜 0건 틈에 «안 잡음»이 된다
  · 판은 `orders.goalCity` 에도 적는다 — 서버가 다시 켜져도 되살린다. 칸이 빈 옛 콜만 하차지의 시로 대신한다

#### 🧭 복귀 켬 — 규칙 ⑤-4 의 다섯 (버그 대장 #130 · #131)

기사님: *"방향 전환은 기사님이 정한다 — 활성 콜 수에서 파생될 수 없다"*.
짐의 수명(콜 0건이면 끝)과 **방향의 수명**(복귀를 켜서 복귀콜을 집 가까이 내릴 때까지)은 다른 값이다.

| | 무엇 |
|---|---|

### 🛣️ 노선 ↔ 🔷 동선 — 그물의 모양을 기사님이 고른다

```
🛣️ 노선   지금 경로 양옆 «라인반경» ∪ 마지막 하차지 → 목적지 마름모
🔷 동선   내 위치 → 목적지 마름모 하나 (현위치 둘레 원이 돌아온다)
```

기본은 **노선**이다 (기사님 확정).

🔴 **버튼이 바꾸는 것과 화면이 읽는 것이 다르다.**

```
버튼      → routeMode              기사님이 «고른 것»
화면·판정 → lineOn = routeMode && 경로가 실제로 있나
```

🔴 **단추만 보고 그리지 않는다** — «노선 단추»가 아니라 «라인이 실제로 있는가»로 가른다.
단추로 그리면 라인이 없을 때 화면에서 마름모가 사라지는데 판정은 그 마름모로 해, 화면이 조용히 거짓말한다 (규칙 ⑤-4 ④).

🔴 **직선으로 지어내지 않는다** (규칙 ④). 카카오 경로가 아직 안 왔으면 마름모로 본다 —
그 사이 화면은 *"⏳ 경로를 기다립니다"* 라고 **말해야 한다.** 직선을 라인으로 쓰면
산·강을 가로지르는 엉뚱한 동네가 그물에 들어온다.

⚠️ **기억하지 않는다.** 레이어 토글(🧅)은 «보기»라 `localStorage` 에 남기지만, 이것은
**판정을 바꾸는 값**이라 새로고침하면 기본(노선)으로 돌아간다 — 어제 상태가 오늘
되살아나지 않는다 (규칙 ③).

### 📦 앱에 내려가는 것은 **표가 정한다**

앱은 필터 JSON 에서 **`APP_FILTER_KEYS` 에 적힌 키**만 읽는다. 서버는 그 키만 싣는다 —
`shared/src/index.ts` 의 `APP_FILTER_KEYS` 가 유일한 원천이고(목록은 거기서 본다), `scrap.ts` 는 그 표로 **고른다**.

> 🔴 **골라 싣는다, 떼어내지 않는다.** 떼는 키를 손으로 나열하면 **새 칸이 생길 때마다 그 목록에 넣어야 하고,
> 안 넣으면 조용히 앱으로 간다.** 골라 싣는 쪽은 **기본이 «안 간다»** 라 안전하다.
>
> ⚠️ **`orderKm`·`pickerAlarmMinFare` 는 평면 필터에 없다** — 조립할 때 얹는다
> (경로 순서 맵 · 픽커 알람 하한). 그래서 표는 «앱이 읽는 키»이지
> «`AutoDispatchFilter` 의 부분집합»이 아니다.
>
> 🔴 **표 ↔ 앱(Kotlin)이 어긋나면 검사가 잡는다** — `server/tests/rules/appFilterKeys.test.ts`
> 가 Kotlin 소스에서 실제로 읽는 키를 긁어 표와 견준다. 앱이 읽는데 서버가 안 보내면
> **조용한 고장**이고(빈 값으로 거른다), 서버가 보내는데 앱이 안 읽으면 **낭비**다
> (하트비트마다 재전송된다).

## 6. 취소 예산 — 한 판 10회

취소는 **리셋 없는 예산**이다. 페널티는 피할 수 없는 영업 비용이고, 관리할 것은 **빈도**다.

- **한 판 = 10회** (`CANCEL_BUDGET_PER_ROUND`), 배차망별로 따로 센다
- 다 쓰면 **토스트로 알리고 새 판**을 연다
- 🔴 **총량은 사라지지 않는다** — 판수가 남는다. `3/10 · 2판째` = 지금까지 13회
- 리셋 시각만 저장한다 (`cancel_budget_resets`). 카운트는 `orders` 에서 센다 (규칙 ③)

**소진 속도가 «필터를 조여라»의 신호다.** 그래서 화면에 상시 뜬다.

⚠️ 카운터에 들어가는 것은 **안전취소뿐**이다. 취소 세 갈래는 [용어집 §2-1](용어집.md).

## 7. 성과 기록 — 이 설정이 얼마를 벌었나

영업일이 넘어갈 때(자정) 어제치를 **1회** 집계한다.

```sql
filter_day_results (
    user_id, day,
    settings,     -- 그날 국면 설정 스냅샷
    revenue,      -- 그냥 매출 (관제앱은 업무 단위 — 정산 아님)
    calls,        -- 완료 콜 수
    cancels,      -- 취소 소진 (망별)
    colors        -- 판정 색 분포
)
```

콜할인율을 감이 아니라 **성과로** 정하기 위한 재료다. 화면은 운행일지(logbook)에 있다 —
관제앱은 1~2초 결재 화면이라 여기에 안 둔다.

## 10-1. 반경 자동 맞춤 — 목적지가 가까우면 손잡이가 죽는다

기사님: *"목적지와의 거리에 따라 반경이 자동으로 바뀌어 주면 좋겠다. 그래서 자동, 수동으로."*
목적지가 가까우면 손잡이를 움직여도 그물이 거의 안 바뀐다 (실측 표는 버그 대장 «필터 규칙 경위»).

- **가까우면 목적반경 하나가 전부를 정한다**
- **마름모반경은 가까운 곳에서 완전히 죽는다**

**왜** — 마름모반경은 「얼마나 멀리」가 아니라 **축에서 좌우로 몇 km 까지**다
(`distToLineKm ≤ r` · `callNet.makeInQuad`). 마름모의 폭은 **각도와 거리**가 먼저 정하므로,
거리가 짧으면 각도로 이미 좁아져 반경이 그 바깥에 있어 안 걸린다.
현위반경 + 목적반경보다 목적지가 가까우면 원 둘이 서로를 덮는다.

### 규칙 ⑤-4 의 다섯

| | 무엇 |
|---|---|
| **① 스키마** | `user_filters.radius_auto`(0/1) · `radius_base_km`(REAL). **반경 넷은 저장하지 않는다** — 파생이다 (규칙 ③)<br>**«잰 거리» 하나를 메모리에 들고 있는다**: `activeFilter.radiusDistanceKm`. DB 에는 안 쓴다 (기사님 *"변수로 메모리에 두면 될 것 같은데"*) — 서버가 다시 켜지면 비어서 그때 위치로 한 번 다시 잰다. 영업일 전환(`resetToBaseFilter`)이 비운다 (어제 거리가 오늘 살아나지 않게 · 규칙 ③) |
| **② 값** | 기준 거리 **40km**. 근거: 지금 값(10·15·25·6)으로 거리만 바꿔 재니 **35km 부터 마름모가 일하기 시작**하고 **40km 에서 폭이 크게 뛴다**. 곧 지금 값은 40km 안팎에 맞춰진 값이라, 거기서 **배율 1.0** 이 되어 «아무것도 안 바뀌는 지점»이 기사님이 손으로 맞춘 그 자리가 된다 |
| **③ 시점** | **하루에 한 번 잰다. 달리는 동안 다시 재지 않는다** — 기사님: *"자동 반경은 그날 첫짐일 때 적용되는 거다. 위치가 바뀐다고 바뀌어서는 안 된다"* (버그 대장 #117)<br>· **재는 때**: 들고 있는 거리가 **비어 있을 때만** «내 위치 → 목적지»로 잰다 (`heldRadiusDistanceKm`). 그날 처음 그물을 만들 때가 곧 출발 전이다 · 🔴 상차 목록 · 하차 목록 **둘 다 반경을 쓰기 전에** 잰다(`filterManager.holdRadiusDistance` 한 곳 · #149)<br>· **비우는 때**(= 다음에 다시 잰다): ⓐ 기사님이 **[↻ 다시 구하기]** 를 누를 때(`radiusDistanceKm: null`) · ⓑ 영업일 전환 · ⓒ 기사님이 **목적지를 실제로 바꿀 때** (`updateActiveFilter` — 같은 값을 다시 보내면 안 비운다) · ⓓ 서버 재시작 · 🔴 **목적지가 바뀌어도 저절로 다시 재지 않는다** — 복귀로 목적지가 집이 될 때도 그대로 둔다. 필요하면 [↻ 다시 구하기]<br>· DB 에는 모드·기준·잰 거리만 쓴다. 수동으로 넘기면 **그때 계산값이 손잡이에 남아** 거기서부터 손으로 민다<br>🔴 **그물을 만들 때마다 «마지막 하차지 → 목적지»로 다시 재지 않는다** — 목적지 근처에서 반경이 사라져 관내콜과 가는 길 좋은 콜을 놓친다 (#117) |
| **④ 화면** | 반경 격자 위 `[40km 기준 반경 | 수동]` 토글 하나. 자동일 때도 **숫자는 그대로 보이고 흐리게만** 둔다 (기사님 *"모두 꺼내 두고"*)<br>**기준거리는 ⚙️ 설정 → 필터에서 고친다.** 반경 셋(현위·목적·라인)은 «오늘 조이는 값»이고 기준거리는 «한 번 정하면 두는 값»이라 **층이 다르다** — 한 그리드에 섞지 않는다.<br>🔴 **필터 화면은 «말하기만» 한다** — 고치는 자리는 설정 하나이고, **«오늘만»이 없다**(곧 평소값)<br>토글 아래 한 줄에 **무엇으로 정했나**를 적고(`출발 때 18km 로 정함 · ×0.45`), 오른쪽에 **[↻ 다시 구하기]** 를 둔다 — 자동일 때만 보인다. 🔴 다시 구하기는 **모드가 아니라 한 번 누르는 동작**이라 토글 안에 넣지 않는다 (셋째 칸으로 넣으면 «재설정 모드»에 들어가 있는 것처럼 읽힌다) |
| **⑤ 읽는 곳** | 서버 `filterManager.netKeywordsOf` 의 `params` · 관제웹 `StageView`(«상차» · «하차» 레이어 · `effectiveRadii`). **둘이 같은 함수를 부른다** — `shared` 에 한 곳(규칙 ③). 앱에는 **계산된 반경**이 내려간다(앱은 모드를 모른다)<br>서버가 싣는 `radiusDistanceKm` 은 **저장된 거리**다 — 읽는 쪽(`effectiveRadii` · 지도 · 앱)은 그 값을 그대로 쓴다 |

### 계산

```
배율 = min(1, 목적지까지 거리 ÷ 기준 거리)

현위반경   = 10 × 배율        목적반경   = 15 × 배율
마름모반경 = 25 × 배율        라인반경   =  6 × 배율
```

🔴 **각도 둘(출발각·목적각)은 자동이 손대지 않는다** — 거리와 무관한 「방향 허용폭」이다.

🔴 **상한(`min(1, …)`)을 둔다** — 순수 비례면 먼 목적지에서 그물이 **더 넓어진다.**
멀리 갈 때는 넷이 다 일하고 있어 고칠 이유가 없다. **가까울 때만 줄인다.**

⚠️ **목적지가 아주 가까우면 자동으로도 마름모가 안 산다.** 어떤 값을 넣어도
원 둘이 다 덮는다 — 그 거리에서는 마름모라는 개념이 성립하지 않는다.
**감추지 않고 「이 거리에서는 안 쓰임」으로 흐리게** 적는다 (규칙 ⑤-2 · 규칙 ④).
