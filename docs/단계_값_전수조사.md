# 6단계 화면이 쓰는 값 — 전수 조사

> 📌 **구조 변경의 1단계** (기사님 계획 2026-08-20). 스키마를 정하기 **전에**
> _"화면이 지금 무엇을 쓰고, 그게 어디서 오고, 어디에 저장되는가"_ 를 다 뽑는다.
> 이걸 안 하고 스키마를 먼저 정하면 나중에 _"이 값이 빠졌네"_ 가 된다.
>
> **출처 표기**: `상수` 코드에 박힘 · `DB` 테이블에서 · `카카오` 경로 연산 ·
> `파생` 다른 값에서 계산 · `입력` 기사님이 화면에서 고름

---

## 0. 여섯 단계 (`shared/src/callSteps.ts`)

| #   | id               | 라벨        | 정거장  | 건너뛸 수 있나       |
| --- | ---------------- | ----------- | ------- | -------------------- |
| 1   | `CALL_PICKUP`    | 상차지 통화 | pickup  | ⭕                   |
| 2   | `CALL_DROPOFF`   | 하차지 통화 | dropoff | ⭕                   |
| 3   | `ARRIVE_PICKUP`  | 상차지 도착 | pickup  | ❌(스킵 버튼은 있다) |
| 4   | `LOADED`         | 상차 완료   | pickup  | ❌                   |
| 5   | `ARRIVE_DROPOFF` | 하차지 도착 | dropoff | ❌                   |
| 6   | `DELIVERED`      | 하차 완료   | dropoff | ❌                   |

**단계는 저장하지 않는다** — `deriveCallStep` 이 `stop_cargo_reports` 와
`order_milestones` **행의 존재**로 매번 파생한다.

## 1. 화면에 보이는 값 — 어디서 오나

### 1-1. 짐 (상차지 통화 · 상차 완료)

| 값             | 화면                                         | 출처                                  | 어디에     |
| -------------- | -------------------------------------------- | ------------------------------------- | ---------- |
| 단위           | `파레트 · 라면박스 · 마대 · 서류봉투 · 기타` | `상수` `cargoUnits.ts`                | ❌ DB 없음 |
| 단위→박스 환산 | 파레트 40 · 마대 1 · 서류봉투 0.2            | `상수` `CARGO_UNIT_POINTS`            | ❌         |
| 수량           | `1 · 2 · 3` 버튼                             | `파생` 차종 정원에서                  | ❌         |
| 차종 정원      | 1t = 라면박스 100개                          | `상수` `VEHICLE_CAPACITY`             | ❌         |
| 차종 기본 짐   | 1t → **파레트 2개**                          | `상수` `defaultCargoByVehicle`        | ❌         |
| 상차 방법      | `지게차 4분 · 수작업 27분`                   | `상수` `DWELL_BASE`·`DWELL_PER_POINT` | ❌         |
| 화물 보호      | `결박 4분 · 그물망 1 · 호루 3 · 탑박스 1`    | `상수` `PROTECTION_MINUTES`           | ❌         |
| 후작업(하차)   | `정리 1분 · 검수 60분`                       | `상수` `AFTERWORK_MINUTES`            | ❌         |
| 화물 성질      | `일반화물 · 농산물 · …`                      | `상수` `cargoTags`                    | ❌         |
| 짐 모를 때     | 상차 15분 · 하차 10분                        | `DB` `user_judgment`                  | ⭕         |

🔴 **열 중 아홉이 코드 상수다.** 기사님이 화면에서 못 바꾼다 (용어집 §5 에 이미 경고).

### 1-2. 시간 (모든 단계)

| 값                 | 화면                        | 출처                                 | 어디에                      |
| ------------------ | --------------------------- | ------------------------------------ | --------------------------- |
| 접근 주행          | `주행 13분`                 | `카카오` → `routeStops.driveMinutes` | ⭕ `orders`                 |
| 구간 주행          | `주행 95분`(⚠️ 지금은 누적) | `카카오`                             | ⭕ `orders`                 |
| 닻                 | 경로 계산 시각              | `카카오` 호출 시각                   | ⭕ `orders.routeComputedAt` |
| 도착 예상          | `10:25`                     | `파생` 닻 + 주행                     | ❌ **저장 안 됨**           |
| **도착 약속 여유** | `+ 30분`                    | `상수` `arrivalMarginMinutes`        | ❌ **DB 표에 빠져 있음**    |
| 도착 약속          | `10:55`                     | `파생` 도착 예상 + 여유              | ⚠️ 칸을 눌러야만 저장       |
| 상차 정차          | `상차 8분`                  | `파생` 방법 + 보호                   | ❌                          |
| 출발 시각          | `11:03`                     | `파생` 약속 + 정차                   | ❌                          |
| 휴게 여유          | `+ 30분`                    | `DB` `unknown_rest_margin_minutes`   | ⭕                          |
| 도착시간 칸        | `10:25 · 10:55 · …`         | `파생` 도착 예상 기준 30분 간격      | ❌                          |

🔴 **파생값이 하나도 저장되지 않는다.** 시트를 열 때마다 다시 계산하고,
그래서 **하차 시트가 상차 약속을 못 본다** (지금 고치려는 문제).

### 1-3. 사유 · 증거 (도착 · 완료 단계)

| 값        | 화면                                  | 출처                           | 어디에                               |
| --------- | ------------------------------------- | ------------------------------ | ------------------------------------ |
| 도착 사유 | `교통 지연 · 주소 다름 · …` 갈래별 칩 | `상수` `REASON_GROUPS_BY_STEP` | ❌                                   |
| 도착 시각 | 버튼 누른 시각                        | `입력`                         | ⭕ `order_milestones.occurredAt`     |
| 예측 시각 | (화면에 없음)                         | `파생`                         | ⭕ `predictedAt` ⚠️ **읽는 곳 없음** |
| 출처      | `직접 · 자동(GPS) · 건너뜀`           | `파생`                         | ⭕ `source`                          |
| 기타 메모 | 자유 입력                             | `입력`                         | ⭕ `memo`                            |

## 2. 저장되는 값 — `save-cargo-report` 가 보내는 것

```
unit · quantity · handling · tags · protections · afterworks · memo
promisedAt · promisedArrivalAt · promisedArrivalFromAt · onwardDeadlineAt
```

⚠️ **조건부로 빠지는 것들**

|                     | 언제 안 보내나                                           |
| ------------------- | -------------------------------------------------------- |
| `promisedArrivalAt` | 🔴 **칸을 직접 안 누르면** (`deadlineTouched === false`) |
| `unit` · `quantity` | 하차 시트에서는 아예 안 보낸다                           |
| `onwardDeadlineAt`  | 상차 + `DECLARED` 일 때만                                |
| `protections`       | 상차만 · `afterworks` 하차만                             |

⚠️ **화면에 있는데 안 보내는 것** — `도착 예상` · `출발 시각` · `상차 정차` ·
`도착시간 칸`. 전부 파생값이라 저장 자리가 없다.

## 3. 🔴 검사 — 기사님이 주신 시나리오

> **1톤 콜 → 상차지 통화에서 파레트 선택된 채 [통화 스킵] → 상차 완료에서 라면박스로 변경 후 저장**

### 지금 구조에서 남는 것

```
① KEEP              (행 없음)          화면엔 파레트 2개 · 지게차 · 결박이 눌려 있다
② 통화 [스킵]        pickup · SKIPPED   unit=∅ quantity=∅ handling=∅ memo='통화 없이 진행'
③ 상차 완료 [라면박스] pickup · ACTUAL    unit='라면박스'
                     milestones (PICKED_UP)
```

### 네 값 중 **둘이 사라진다**

| 무엇                            | 남나 |                                            |
| ------------------------------- | ---- | ------------------------------------------ |
| ① **계획**: 파레트 2개          | ❌   | 화면에 눌려 있었는데 **어디에도 없다**     |
| ② **스킵 사실**                 | ⭕   | `SKIPPED` 행 (빈 행)                       |
| ③ **실측**: 라면박스            | ⭕   | `ACTUAL` 행                                |
| ④ **오차**: 파레트 2 → 라면박스 | ❌   | ①이 없으니 `cargoMismatchRatio` 가 못 돈다 |

🔴 **가장 값진 기록(예측이 얼마나 틀렸나)이 사라진다.**
그리고 스킵 행은 값이 하나도 없는 **빈 행**이다 — 지금 구조가 이미 만들고 있다.

### 왜 이렇게 되나

`stop_cargo_reports` 가 `stopType × kind` 로 **행을 가르기** 때문이다.
한 정거장의 이야기가 최대 세 행(`SKIPPED`·`DECLARED`·`ACTUAL`)으로 흩어지고,
**어느 것이 진실인지 읽는 쪽이 매번 판단**해야 한다.

## 4. 이 조사에서 나온 것 — 스키마가 풀어야 할 문제 다섯

|     | 문제                                   | 지금                       |
| --- | -------------------------------------- | -------------------------- |
| 1   | **계획을 저장할 자리가 없다**          | KEEP 해도 행이 안 생긴다   |
| 2   | **파생값이 매번 다시 계산된다**        | 하차가 상차 약속을 못 본다 |
| 3   | **한 정거장이 세 행으로 흩어진다**     | `kind` 가 행을 가른다      |
| 4   | **기본값 아홉이 코드 상수다**          | 기사님이 못 바꾼다         |
| 5   | **`arrivalMarginMin` 이 DB 표에 없다** | 30분 고정                  |

🔴 **1·2·3 은 한 뿌리다** — _"콜을 잡는 순간 정해지는 값을 담을 그릇이 없다."_

---

## 5. 그래서 새 스키마의 **합격 기준**

새 구조를 그렸으면 **§3 시나리오를 넣어 네 값이 다 남는지** 본다.

```
계획 파레트 2개  ·  스킵 사실  ·  실측 라면박스  ·  오차(파레트 2 → 라면박스)
```

넷이 다 남고 **한 정거장이 한 행**이면 통과다.

### 함께 확인할 것

- 통화를 **안 하고** 도착·완료만 해도 계획값이 남는가
- 통화를 **두 번** 해도(다시 걸어 시각을 바꿈) 마지막 값이 남는가
- 콜이 **취소·방출**돼도 계획이 남는가 (그래야 손실을 잴 수 있다 — 용어집 §2-1)
- 서버를 **재시작**해도 합짐 판정이 첫짐 계획을 읽는가
  (지금은 메모리에만 있어 이것 때문에 사고가 났다 — 버그 대장 #21)

### 순서

1, 콜 옵션이 모두 들어가있는 디폴트 값을 정의하는 테이블을 만들 스키마를 만든다. (타입스크립트로도 만든다) 2. 콜 옵션 테이블을 생성한다. 3. 6 단계의 화면을 분석해 옵션의 디폴트 값이 모두 메칭 되는지 확인한다. 4. 각 페이지 별로 테이블을 만든다. 5. 관제웹에 임시 버튼을 킵 버튼옆에 만들고 클릭하면 서버통신으로 6개의 테이블에 임시 값을 넣고 소켓통신으로 관제웹에 전달한다. 6. 데이터를 전달 받으면 그걸 화면에 뿌린다.
