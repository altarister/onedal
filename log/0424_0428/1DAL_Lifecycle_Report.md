이 문서는 04/24~04/28 기간 및 05/08 AWS EC2 환경에서 발생한 로그 데이터를 기반으로 작성된 1DAL 배차 알고리즘 라이프사이클 분석 및 오류 진단 리포트입니다.

## 📌 주요 에러 및 문제점 요약

1. **브라우저 권한(Geolocation & Audio) 거부 문제**
   - **현상**: `User denied Geolocation`, `NotAllowedError: play() failed because the user didn't interact with the document first.`
   - **원인**: 사용자가 권한 알림을 무시하거나, 문서와 상호작용하기 전에 스크립트가 오디오/진동을 발생시키려 하여 브라우저 정책에 의해 차단됨.
   - **해결 방안**: 앱 최초 구동 시 강제로 사용자가 상호작용(예: '시작하기' 버튼 클릭)하도록 UX 플로우를 변경하여 권한 및 오디오 정책을 충족시켜야 함.

2. **통신 지연 및 데스밸리(Death Valley) 문제**
   - **현상**: 서버 응답이 늦어지거나 모바일 네트워크 불안정으로 인해 30초 데스밸리 타이머가 종료되며 `AUTO_CANCEL` 이 트리거됨.
   - **해결 방안**: 
     - 네트워크 실패에 대비해 재시도 로직을 구현.
     - 통신 실패 시 단순히 타임아웃 처리하지 않고 `[ROADMAP $ts] [📱앱] ❌ 서버 통신 실패 (이유: Timeout)` 과 같이 명확한 실패 원인을 로깅.
     - 데스밸리 30초 타이머의 보수적 접근이 필요하며, 서버에서 응답이 지연될 경우를 대비해 스캐너폰 2개 이상의 동시 접속 및 상호 상태 체크 구조를 확립해야 함 (다중 폰 환경).

3. **다중 스캐너 폰 동기화 구조**
   - 현재 구조에서 스캐너 폰이 2개 이상일 때 동일 콜을 동시에 잡지 않도록 서버 측의 Lock 검증(`order-evaluating` 소켓 푸시)과 필터 비활성 전파가 원활하게 이루어져야 함.

## 🚀 추가 개선 계획안 (Implementation Plan 요약)

*   **스캐너 폰이 2대 이상인 경우 (Multi-Scanner Environment)**
    *   **문제**: A폰이 확정 버튼을 눌러 데스밸리에 들어간 사이, B폰도 동일한 리스트를 스캔하다가 오작동 또는 락을 무시하고 중복 스크래핑을 할 우려가 있음.
    *   **구조적 해결책**: 서버가 A폰으로부터 1차 선점 요청(`/orders/confirm`)을 받은 즉시, 모든 스캐너 폰에 `filter-updated` 소켓 이벤트를 전송하여 `isActive: false` (배차 중지 모드)로 전환시켜야 함. 
    *   판결이 KEEP으로 완료되거나, AUTO_CANCEL 된 이후에만 다시 `isActive: true` 상태로 일괄 복귀시키는 세션 잠금(Session Lock) 메커니즘 필수.

*   **통신 실패 보완 구조**
    *   통신(HTTP / Socket) 과정에서 응답이 시간 안에 온다는 담보가 불가능함(모바일 네트워크 터널 진입 등).
    *   타임아웃(Timeout) 발생 시 1회성 종료가 아닌, 지수 백오프(Exponential Backoff)를 통한 3회 재시도 구현.
    *   모든 재시도 실패 시 1DAL 리포트 형식(`[ROADMAP $ts] [📱앱] ❌ [API 실패] /orders/detail - 사유: Timeout`)으로 에러 로그 명시 후 강제 취소 안전망(Safeguard) 전개.
