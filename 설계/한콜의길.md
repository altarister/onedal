# 한 콜의 길

콜 한 건이 화면에서 완료까지 지나는 곧은 길이다. 화면을 보고 코드를 찾을 때 쓴다. 곧은 길에서 벗어나는 경우는 아래 «곁길»에 있다.

**확인 칸:** `로그` 는 `pnpm scenario` 의 서버 로그에서 그 차례를 본 줄이고, `코드` 는 코드만 읽은 줄이다. 시나리오는 콜을 서버에 직접 넣으므로 폰 화면 줄은 로그에 없다.

| 차례 | 기사님이 보는 곳 | 하는 일 | 파일 · 함수 | 채워지는 칸 | 확인 |
|---|---|---|---|---|---|
| 1 | 새 콜 목록 | 줄을 읽어 콜로 만든다 | `HijackService.handleListScreen` → `ListRowScan.scanRow` → 배차망 파서(`scrapParser`) | `pickup` · `dropoff` · `fare` · `vehicleType` · `pickupDistance` · 예약 칸 | 코드 |
| 2 | 새 콜 목록 | 요금 · 상차지 · 하차지 · 상차지거리를 다 읽었나 본다. 모자라면 다음 스캔으로 미룬다 | `OrderRequirement.listComplete` | | 코드 |
| 3 | 새 콜 목록 | 필터를 걸어 판정을 싣는다. 인성은 자기 함수, 화물24시 · 플렉스는 공통 함수, 픽커는 자기 함수를 쓴다 | `scrapParser.withVerdict` → `InsungParser.judge` / `ListJudge.judge` / `verdictAxisOf` | `verdict` | 코드 |
| 4 | 새 콜 목록 | 목록 줄을 서버에 보고한다 | `ApiClient.sendScrapTelemetry` → `POST /api/scrap` (`routes/scrap.ts`) | intel 표 | 코드 |
| 5 | 새 콜 목록 | 통과 콜 중 요금이 가장 높은 하나를 누른다. 누를지는 모드가 정한다 | `handleListScreen` → `AlarmSignaler.pickBestIndex`, 누를지는 `ModeActs.tapsList` · `ListTapPick.gate` | | 코드 |
| 6 | 새 콜 화면 | 값을 채운다. 인성은 팝업 3장(적요 → 출발지 → 도착지), 픽커는 사진 | `PreConfirmSequence.handlePreConfirmScreen` → `executePreConfirmSpecial`, `fillDetail`, 사진은 `handlePreConfirmSnapshot` | 상세 주소 · 원문 | 코드 |
| 7 | 새 콜 화면 | 요금과 전체 주소를 본다. 모자라면 버린다 (손으로 연 상세는 보고를 미룬다) | `OrderRequirement.missingDetail`, `dropUnfilledCall` | | 코드 |
| 8 | 새 콜 화면 | 원달앱이 누른 그 콜인지 본다 | `dropIfNotTappedCall`, `TappedCall` | | 코드 |
| 9 | 새 콜 화면 | 채운 값이 필터를 지나는지 다시 본다. 원달앱이 연 콜만 거른다 | `passesFilterAfterFill` | | 코드 |
| 10 | 관제웹 판정 칸에 콜이 뜸 | 선점을 보고한다 | `sendConfirmOnce` → `POST /api/orders/confirm` (`routes/orders.ts`) → `rememberOrder` → 소켓 `order-evaluating` | 상태 `ORDER_PRE_SECURED` | 로그 |
| 11 | 관제웹 판정 칸 | 상세를 보고한다. 서버가 원문에서 상세 칸을 뽑는다 | `sendDetail` → `POST /api/orders/detail` (`routes/detail.ts`) → `evolveOrder`, `detailRecordOf` (`shared/src/network/pageRead.ts`), `rememberOrder` → 소켓 `order-detail-received` | 연락처 · 적요 · 수수료 등, 상태 `ORDER_SECURED_EVALUATING` | 로그 |
| 12 | 관제웹 판정 칸 | 판정한다. 주소 → 좌표 → 경로 → 점수 · 색. 다른 진행 콜과 같이 가는 길도 센다 | `evaluateNewOrder` → `OrderEvaluator` (`geocodeStage`, `soloStage`, `mergedStage`, `finishStage`) → 소켓 `order-evaluated` | 좌표 · 경로 · `judgment`, 상태 `ORDER_AWAITING_DECISION` | 로그 |
| 13 | 관제웹 결재 단추 | KEEP 또는 취소. 판결을 폰으로 보낸다 | 소켓 `decision` (`socket/socketHandlers.ts`) 또는 `POST /api/orders/decision` → `handleDecision` → 소켓 `order-confirmed` / `order-canceled` | 상태 `ORDER_CONFIRMED` 또는 `SAFE_CANCEL` | 로그 |
| 14 | 배차망 앱 | 확정 단추를 누른다. 자동 모드만 원달앱이 누르고, 나머지는 기사님이 누른다 | `clickFirstMatchingButton`, 누를지는 `ModeActs.contracts` · `contractedByApp` | | 코드 |
| 15 | 내 콜 화면 | 확정 뒤 화면을 읽는다. 지금은 인성만 한다 | `InsungSequence.handleConfirmedScreen` | | 코드 |
| 16 | 관제웹 콜 스텝 | KEEP 하면 첫 단계 행이 생긴다 | `birthStepsOnKeep` → `stepSeeder.birthFirstStep` | 단계 행, DB `orders` (`OrderRepository.upsertOrder`) | 로그 |
| 17 | 관제웹 콜 스텝 | 상차지 통화, 하차지 통화 때 적는 짐(단위 · 수량)을 기록한다 | `saveCargoReport` → `stepSeeder.bridgeCargoReport` | 짐 신고 | 로그 |
| 18 | 관제웹 콜 스텝 | 상차지 도착, 상차 완료, 하차지 도착을 기록하고 다음 단계 행을 만든다 | `milestones.reportMilestone` → `stepSeeder.bridgeMilestone` | 도착 시각, 상태 `ORDER_PICKED_UP` | 로그 |
| 19 | 관제웹 콜 스텝 | 하차 완료. 남은 경로를 보고 필터를 다시 계산한다 | `milestones.reportMilestone` | `completedAt`, 상태 `ORDER_DELIVERED` | 로그 |

## 차례에 따라 달라지는 것

- **자동 모드:** 차례가 10 → 14 → 11 → 12 → 13 이다. 원달앱이 확정(14)을 누른 뒤 상세를 보고하고, 안전취소 시계가 그때 시작한다
- **알람 · 직접 모드:** 10 → 11 → 12 → 13 → 14 다. 기사님이 확정을 누른다
- **값을 읽는 차례:** 1~9 는 모드와 상관없이 같다. 자세한 표는 [배차망_모드표.md](../배차망_모드표.md) 「상세에서 서버로 보내는 차례」에 있다
- **직접 콜:** 11 상세 보고 때 바로 KEEP 하고, 12 판정은 그 뒤에 표시용으로 돈다
- **배차망:** 화물24시는 팝업이 없고, 픽커는 사진으로 읽는다. 플렉스는 상세 글에서 읽는다. 15는 인성만 한다

## 곁길

| 경우 | 어디서 갈라지나 | 하는 일 | 파일 · 함수 | 확인 |
|---|---|---|---|---|
| 안전취소 시간 초과 · 화면 이탈 | 13 에서 결재가 안 올 때 | 판정 중인 콜을 강제로 정리한다 | `forceCancelEvaluatingOrder` | 로그 (강제 정리) |
| 취소 · 놓기 | 13 에서, 또는 운행 중 | 콜을 끝난 상태로 바꾼다 | `handleDecision`, 운행 중에는 소켓 `cancel-at-stop` | 13 의 취소만 로그, 운행 중은 코드 |
| 예약 콜 | 13 KEEP 때 오늘 콜이 아니면 | 진행 콜이 아니라 예약 보관으로 간다 | `handleDecision` → `reservedOrders` | 코드 |
| 재시작 복구 | 서버가 켜질 때 | DB 에서 진행 콜을 되살린다 | `state/sessionRestore.ts` | 로그 (복구) |
| 정산 | 19 뒤 | 상태 `ORDER_COMPLETED` 는 지금 아무도 안 쓴다 | `call/callStatus.ts` | 코드 |

## 로그에서 본 차례

시나리오는 콜 하나로 19줄을 다 지나지 않는다. 10~13 과 16 은 장부 검사용 직접 콜이고, 17~19 는 씨앗으로 넣은 콜이다. 한 콜로 끝까지 지나는 로그는 `pnpm drive` 로 얻을 수 있으나 아직 안 해 봤다.

| 로그 낱말 | 차례 |
|---|---|
| `[1차 선점 수신]`, `order-evaluating` | 10 |
| `2차 오더 상세`, `order-detail-received` | 11 |
| `[판정]`, `[요율 판정]`, `order-evaluated` | 12 |
| `[결재]`, `[REST Decision 수신]`, `order-confirmed` | 13 |
| `[출생] … 상차지 통화 — KEEP` | 16 |
| `[상차지 통화 신고]`, `[하차지 통화 신고]` | 17 |
| `[마일스톤] 상차지 도착 · 상차 완료 · 하차지 도착` | 18 |
| `[하차 완료]`, `[경로 유지]`, `[적재 회복]` | 19 |

**로그로 못 본 것:** 1~9, 14, 15 는 폰 화면이라 시나리오에 없고, `/api/scrap` 도 이 시나리오는 부르지 않는다. 인성 · 화물24시는 실물 앱으로 돌려 본 적이 없다.
