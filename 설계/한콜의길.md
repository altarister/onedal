# 한 콜의 길

콜 한 건이 화면에서 완료까지 지나는 길이다. 화면을 보고 코드를 찾을 때 쓴다.

**확인 칸:** `로그` 는 `pnpm scenario` 의 서버 로그에서 그 차례를 본 줄이고, `코드` 는 코드만 읽은 줄이다. 시나리오는 콜을 서버에 직접 넣으므로 폰 화면 줄은 로그에 없다.

| 차례 | 기사님이 보는 곳 | 하는 일 | 파일 · 함수 | 채워지는 칸 | 확인 |
|---|---|---|---|---|---|
| 1 | 새 콜 목록 | 줄을 읽어 콜로 만든다 | `HijackService.scanScreenBody` → 플러그인 파서 → `ListRowScan.scanRow` | `pickup` · `dropoff` · `fare` · `vehicleType` · `pickupDistance` · 예약 칸 | 코드 |
| 2 | 새 콜 목록 | 다 읽었나 본다. 모자라면 다음 스캔으로 미룬다 | `OrderRequirement.listComplete` | | 코드 |
| 3 | 새 콜 목록 | 필터를 건다 | `ListJudge.judge` | `verdict` | 코드 |
| 4 | 새 콜 목록 | 목록 줄을 서버에 보고한다 | `ApiClient.sendScrapTelemetry` → `POST /api/scrap` (`routes/scrap.ts`) | intel 표 | 코드 |
| 5 | 새 콜 목록 | 통과 콜 중 요금이 가장 높은 하나를 누른다. 누르는지는 모드가 정한다 | `HijackService.scanScreenBody`, `ModeActs.tapsList` | | 코드 |
| 6 | 새 콜 화면 | 값을 채운다. 인성은 팝업 3장(적요 → 출발지 → 도착지), 픽커는 사진 | `PreConfirmSequence.handlePreConfirmScreen` → `executePreConfirmSpecial`, `fillDetail`, 사진은 `handlePreConfirmSnapshot` | 상세 주소 · 원문 | 코드 |
| 7 | 새 콜 화면 | 요금과 전체 주소를 본다. 모자라면 버린다 (손으로 연 상세는 보고를 미룬다) | `OrderRequirement.missingDetail`, `dropUnfilledCall` | | 코드 |
| 8 | 새 콜 화면 | 누른 그 콜인지, 채운 값이 필터를 지나는지 본다 | `dropIfNotTappedCall`, `TappedCall` | | 코드 |
| 9 | 새 콜 화면 → 관제웹 판정 칸 | 선점을 보고한다 | `sendConfirmOnce` → `POST /api/orders/confirm` (`routes/orders.ts`) → `rememberOrder` → 소켓 `order-evaluating` | 상태 `ORDER_PRE_SECURED` | 로그 |
| 10 | 관제웹 판정 칸 | 상세를 보고한다. 서버가 원문에서 상세 칸을 뽑는다 | `sendDetail` → `POST /api/orders/detail` (`routes/detail.ts`) → `evolveOrder`, `detailRecordOf`, `rememberOrder` → 소켓 `order-detail-received` | 연락처 · 적요 · 수수료 등, 상태 `ORDER_SECURED_EVALUATING` | 로그 |
| 11 | 관제웹 판정 칸 | 판정한다. 주소 → 좌표 → 경로 → 점수 · 색 | `evaluateNewOrder` → `OrderEvaluator.evaluate` (`geocodeStage`, `soloStage`, `mergedStage`, `finishStage`) → 소켓 `order-evaluated` | 좌표 · 경로 · `judgment`, 상태 `ORDER_AWAITING_DECISION` | 로그 |
| 12 | 관제웹 결재 단추 | KEEP 또는 취소. 판결을 폰으로 보낸다 | 소켓 `decision` (`socketHandlers.ts`) 또는 `POST /api/orders/decision` → `handleDecision` | 상태 `ORDER_CONFIRMED` 또는 `SAFE_CANCEL` | 로그 |
| 13 | 배차망 앱 | 확정 단추를 누른다. 자동 모드만 원달앱이 누르고, 나머지는 기사님이 누른다 | `PreConfirmSequence`, `ModeActs.contracts` | | 코드 |
| 14 | 내 콜 화면 | 확정 뒤 화면을 읽는다. 지금은 인성만 한다 | `InsungSequence.handleConfirmedScreen` | | 코드 |
| 15 | 관제웹 콜 스텝 | KEEP 하면 첫 단계 행이 생긴다 | `birthStepsOnKeep` → `stepSeeder.birthFirstStep` | 단계 행, DB `orders` (`OrderRepository.upsertOrder`) | 로그 |
| 16 | 관제웹 콜 스텝 | 상차지 통화, 하차지 통화를 기록한다 | `stepSeeder.bridgeCargoReport` | 짐 신고 | 로그 |
| 17 | 관제웹 콜 스텝 | 상차지 도착, 상차 완료, 하차지 도착을 기록한다 | `milestones.reportMilestone` → `stepSeeder.bridgeMilestone` | 도착 시각, 상태 `ORDER_PICKED_UP` | 로그 |
| 18 | 관제웹 콜 스텝 | 하차 완료. 경로와 필터를 다시 계산한다 | `milestones.reportMilestone` | `completedAt`, 상태 `ORDER_DELIVERED` | 로그 |

## 차례에 따라 달라지는 것

- **모드:** 값을 읽는 차례는 모드와 상관없이 같다. 모드가 바꾸는 것은 원달앱이 누르느냐(5, 13)와 상세 보고 때(10)다. 자세한 표는 [배차망_모드표.md](../배차망_모드표.md) 「상세에서 서버로 보내는 차례」에 있다
- **직접 콜:** 11 다음에 결재를 기다리지 않고 바로 KEEP 한다
- **배차망:** 화물24시는 팝업이 없고, 픽커는 사진으로 읽는다. 플렉스는 상세 글에서 읽는다. 14는 인성만 한다

## 로그에서 본 차례

`pnpm scenario` 의 콜 한 건을 서버 로그에서 뽑았다 (직접 콜 → KEEP, 다른 콜로 취소, 기존 두 콜로 운행 단계).

| 로그 낱말 | 차례 |
|---|---|
| `[1차 선점 수신]`, `order-evaluating` | 9 |
| `2차 오더 상세`, `order-detail-received` | 10 |
| `[판정]`, `[요율 판정]`, `order-evaluated` | 11 |
| `[결재]`, `[REST Decision 수신]`, `order-confirmed` | 12 |
| `[출생] … 상차지 통화 — KEEP` | 15 |
| `[출생] … 하차지 통화`, `상차지 도착` | 16 |
| `[마일스톤] 상차지 도착 · 상차 완료 · 하차지 도착` | 17 |
| `[하차 완료]`, `[적재 회복]` | 18 |

**로그로 못 본 것:** 1~8, 13, 14 는 폰 화면이라 시나리오에 없고, `/api/scrap` 도 이 시나리오는 부르지 않는다. 인성 · 화물24시는 실물 앱으로 돌려 본 적이 없다.
