# 기본 콜로 옮기는 계획 (초안 — 기사님 확인 전)

기사님 말씀: «최종 목표는 OfficeOrder 가 사라지고 지금 기준으로 만든 값을 사용 하는것이다.»

**목표:** 끝 모습은 [onedal-89_08](../onedal-web/shared/src/call/sandbox/onedal-89_08.ts) 이고, 칸마다 배차망별 화면과 글자는 [칸 표](../onedal-web/shared/src/call/sandbox/onedal-89_08.fields.ts)에 있다. 콜은 기사의 질문으로 나뉜 `BaseCall` 이고, 배차망은 그 칸을 채우며, 판정과 화면은 `CallFacts` 의 답만 읽는다. 끝나면 `OfficeOrder` 와 `DetailedOfficeOrder` 이름은 없다.

**끝이 아닌 것:** 손에 오는 돈으로 판정하기, 짐 «못 잼», 필수 켜기, 하차 약속을 판정에 쓰기, 인성 착불 콜의 받을 돈 고치기, 화물24시 «수» 금액을 요금에서 뺄지 정하기, 왕복 · 경유 콜의 목록 필터 고치기. 운행이 바뀌는 일이라 이 계획에 넣지 않고 건마다 따로 승인을 받는다.

## 이 수정이 기사님 하루에 무엇을 하나

| | 좋은 콜 | 노이즈 | 기사님 손 |
|---|---|---|---|
| 이 계획 전부 | 변화 없음 | 변화 없음 | 변화 없음 |

이 계획만으로는 콜이 더 잡히거나 덜 잡히지 않는다. 얻는 것은 두 가지다. 다음 배차망을 붙일 때 표와 파서에 일이 모이고, 나중에 운행을 바꿀 때 고칠 자리가 판정 함수 하나가 된다.

그래서 **어느 묶음에서 멈춰도 운행은 그대로**여야 한다. 이 조건이 깨지면 그 묶음을 되돌린다.

**지금도 이렇게 돌고, 이 계획은 그대로 둔다.** 고치면 운행이 바뀌어 따로 승인을 받는다.

- 인성 경유 콜 «풍납동>논현동»: 목록 필터는 마지막 하차지 «논현동»만 본다. 하차 목록에 풍납동만 있으면 놓치고(좋은 콜 감소), 논현동만 있으면 첫 하차가 목록 밖인데 올라온다(노이즈 증가). 상세 단계 대조는 상세 글 전체를 보지만, 경유 콜 상세 이미지가 없어 거기서 걸리는지 모른다
- 인성 왕복 콜 «왕복/낼7시/송파»: 하차를 «송파»로 읽는다. 하차 목록이 동 이름뿐이면 막힌다(좋은 콜 감소). 통과하면 돌아오는 구간(낼 7시 송파 → 출발지)은 판정 · 거리 · 시한에 없이 잡힌다(노이즈 증가)

## 지금은 이렇게 돈다

- 원달앱은 목록 글자에서 앞글자를 뗀 동 이름으로 필터를 돌리고, 상세 주소로 `pickup` · `dropoff` 를 덮은 뒤 서버에 보낸다. 콜 행에는 목록 동 이름이 없다. 목록 줄은 intel 표로 서버에 오지만, 원달앱이 목록을 읽을 때마다 번호를 새로 만들어 콜과 잇지 못한다
- 서버는 상세 원문에서 칸을 뽑아(`detailRecordOf`) 콜에 덮는다. `evolveOrder` 는 얕은 병합이다
- 판정의 제외어 검사와 상세 칸 채우기가 `rawText` 를 읽는다
- 같은 콜 찾기는 덮인 전체 주소 · 요금 · 전화를 글자로 비교한다(`routes/detail.ts`). 이 자리를 지키는 검사가 없다
- 저장은 `OrderRepository` 의 평평한 칸, 복원은 `sessionRestore` 다

## 묶음

순서: 지키는 검사 → 옮기는 도구 → 작은 묶음부터. 크고 위험한 «어디서 어디로»는 도구가 검증된 뒤에 한다.

### A. 지키는 검사 — 코드 동작 없음

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |
|---|---|---|
| A1 | 같은 콜 찾기 검사를 쓴다. «동과 요금이 같고 전체 주소가 다른 두 콜은 다른 콜» · «끝난 콜에는 안 붙는다» 사례를 넣는다 | 지금 코드에서 통과하고, 비교를 일부러 깨면 빨간불이다 |
| A2 | 고정 입력 비교 기준을 만든다. 네 배차망 사례를 넣어 나온 콜 값을 저장한다. 플렉스는 xml 실물을 쓴다 | 카카오 없이 돌고, 다시 돌려도 같다 |

### B. 타입과 도구 — 아무도 안 부른다

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |

| B1-1 | 칸 표를 `call-fields.table.ts` 에 갈아 끼우고, 그 파일을 읽는 보기 페이지 표(콜 칸 × 네 배차망)를 함께 고친다. 채운 예 · 대조표는 검사 파일로 옮긴다 | 보기 페이지가 열리고 `audit:dead` 가 통과한다 |

## 지금 DB 값 대조

이 계획은 값을 바꾸지 않는다. C2 의 새 칸은 비어 있어도 부팅되는지 기존 DB 사본으로 확인한다.

## 실물로 확인 못 하는 것

사업자가 없어 인성 · 화물24시 앱을 설치할 수 없고, 그 두 배차망의 DB 콜은 전부 시뮬레이터가 만든 가짜다. 인성플렉스는 목록 · 상세의 실물 사진과 xml 이 있으나 앱으로 콜을 잡아 본 적이 없고, 내 콜 화면은 안내 영상뿐이다. 앱으로 돌려 볼 수 있는 것은 픽커뿐이며, 그것도 콜 확정 전까지다. 왕복 · 경유 콜의 상세 이미지가 없어, 적요에 어떻게 풀리는지는 기사님 말씀을 근거로 적었다.

## 안 하는 것

- 운행이 바뀌는 판정 · 필수 수정
- 목록 앞글자(«왕복/» · «A>B» · «폰)» · «2분동승»)를 칸으로 푸는 규칙. 퀵사마다 달라 상세 · 적요에서 읽는다 (칸 표의 «안 풂»)
- 픽커 도보배송 · 한차배송 · 대리 칸. 기사님은 퀵 배송만 켠다. 원달앱의 퀵 · 도보 판단 코드는 그대로 둔다
- 정의 표의 페이지 모양을 페이지 없는 배차망에 맞추는 일. 그런 배차망이 올 때 한다
- 다른 표의 스크롤 · 모양 수정
