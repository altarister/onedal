# 기본 콜 계획 (초안 — 기사님 확인 전)

기사님 말씀: «지금 원달만의 한 콜당 배송데이터가 있고 그 값이 체워지면 한콜로 인정하고 그 콜의 값을 어떤 배차망이라도 채워 넣을수 만 있으면 된다.» · «큰 일을 잘게 나누고 단계를 정하고 테스트와 리뷰를 적절히 받아가면서 진행해야 할꺼 같아.»

**목표:** 원달만의 기본 콜을 정하고, 배차망은 뽑은 값을 그 칸에 연결만 한다. 새 배차망이 와도 키를 늘리지 않는다.

## 이 수정이 기사님 하루에 무엇을 하나

| 묶음 | 좋은 콜 | 노이즈 | 기사님 손 |
|---|---|---|---|
| A~E | 변화 없음 | 변화 없음 | 변화 없음 |
| F 판정 · 필수 바꾸기 | 더 정확히 고른다. 배차망이 달라도 같은 돈과 짐으로 비교한다. 통과하는 콜 수는 수수료율에 따라 줄 수 있다 | 준다. 지어낸 짐 값으로 판정하지 않는다 | 는다. «못 잼» 콜은 기사님이 보셔야 한다 |

A~E 는 새 배차망 비용과 다음 수정의 위험을 줄이는 일이다. 하루가 달라지는 것은 F 부터이고, F 는 항목마다 따로 승인을 받는다.

## 지금은 이렇게 돈다

- `OfficeOrder` 42칸은 목록 콜 23칸(원달앱이 보냄)과 상세 콜 15칸(서버가 채움), 배차망 · 보고 값 4칸이다
- `pickup` 은 목록에서는 지역 글자, 상세에서는 더 긴 주소로 덮인다. 같은 콜 찾기와 목록 필터가 이 글자를 쓴다
- 서버는 상세 원문에서 `DetailRecord`(`network/pageRead.ts`)를 뽑아 콜에 덮는다(`routes/detail.ts`). 이것이 기본 콜의 씨앗이다. 못 찾은 칸은 싣지 않아 앞 기억을 안 지운다
- 페이지마다 따로 오는 값을 한 콜에 모으는 일은 `evolveOrder`(`state/orderMemory.ts`)가 한다
- 콜 칸 표 `call/call-fields.table.ts` 는 41줄이고 `OfficeOrder` 와 조금 다르다 (표에 없는 칸 5, 표에만 있는 칸 4)
- 정의 표 `networkPages.<배차망>.ts` 에는 화면 → 화면 칸 이름이 있고, 화면 칸 → 콜 칸 연결은 `pageRead.ts` 와 파서에 흩어져 있다
- 판정은 요금에서 기름값 · 톨비만 빼고 수수료는 안 뺀다(`judge/criteria.ts`). 적재를 셀 때 짐 신고가 없으면 콜 차종이나 내 차 한 대 분량으로 짐작한다(`core/helpers.ts`)

## 고른 방법

| 순위 | 방법 | 쓰는 쪽 정리 | 읽는 코드 변경 | 되돌리기 |
|---|---|---|---|---|
| 1 | 기본 콜 + 치환 (기사님 안) | 된다 | 처음엔 없음 | 쉽다 |
| 2 | 읽기 함수 `stopOf` 만 | 안 된다, 값을 계속 덮어쓴다 | 적다 | 쉽다 |
| 3 | `pickup` 칸 타입을 바로 바꿈 | 된다 | 한 번에 수십 개 파일 | 어렵다 |

## 진행 규칙

**한 번에 한 걸음, 커밋 하나.** 묶음 안에 걸음이 있고, 걸음마다 다음을 지킨다.

| 언제 | 무엇을 |
|---|---|
| 코드를 쓰기 전 | 그 걸음의 파일과 줄을 기사님께 올린다 |
| 커밋 전 | 게이트(서버 · 관제웹 타입 검사 · 운영센터 · 운행일지 빌드 · 서버 jest · `test:web` · `audit:dead` · `lint:gate` · 기존 DB 사본 부팅) |
| 커밋 뒤 | onedal-89 세션이 커밋을 줄 단위로 대조한다. 지적이 있으면 다음 걸음 전에 처리한다 |
| 묶음이 끝날 때 | onedal-1e 세션이 큰 그림을 리뷰한다. 기사님께 결과를 올리고 다음 묶음을 여쭙는다 |
| 콜 흐름을 건드린 걸음 뒤 | `pnpm scenario`. `pnpm drive` 는 B4 뒤 한 번, D 의 걸음마다, E 의 배차망마다. 둘은 실제 카카오를 불러 값이 흔들리니 값 비교가 아니라 «깨지지 않는다» 확인이다 |
| 원달앱이 바뀔 때 | gradle 검사 + 시뮬레이터 폰 시험. 서버를 먼저 올린다 |

**바로 멈추고 여쭙는 경우**

- 치환 전후 콜 값이 달라진다
- 운행 동작, 관제웹 화면, 새 설정값, 새 저장 칸이 걸린다
- 칸이나 파일을 지워야 한다
- 한 걸음이 `as any` 를 더 만들거나 실행 갈래를 늘려야 한다
- 걸음이 커져 커밋 하나로 설명이 안 된다
- 계획서와 다른 길이 낫다고 판단된다

push 는 이 계획에 넣지 않는다.

## 묶음과 걸음

### A. 기준 정하기 — 코드 동작 없음

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |
|---|---|---|
| A1 | 목록 글자를 `pickup.text` 칸에 둘지 정한다 (추천: 칸을 더함) | 기사님 답이 있다 |
| A2 | 콜 칸 표 `call-fields.table.ts` 를 지금 42칸에 맞춘다. 칸마다 뜻 · 출처 · 누가 채우나를 적는다. 문서를 따로 쓰지 않는다 | 표의 키가 `OfficeOrder` 칸과 같다. 모든 칸이 기본 콜 · 서버 값 · 보고 값 · 뺄 후보 중 하나다 |
| A3 | 치환 규칙을 칸마다 표에 적는다. «기본 콜은 저장하지 않고 `OfficeOrder` 로 저장한다»를 적는다 | 칸마다 `OfficeOrder` 의 어느 칸으로 가는지 있다. 값이 지금과 달라지는 칸이 표시되어 있다 |

### B. 기본 콜 타입과 치환 — 운행 그대로

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |
|---|---|---|
| B0 | 지금 동작을 지키는 검사를 먼저 쓴다. 같은 콜 찾기(`routes/detail.ts`)는 검사가 없다 | 지금 코드에서 통과한다 |
| B1 | shared 에 `BaseCall` 타입과 치환 함수를 더한다. 아직 아무도 안 부른다 | 타입 검사, 왕복 검사, «찾은 칸만 싣는다» 검사 통과 |
| B2 | 비교 기준을 만든다. 배차망 넷의 대표 콜과 원문을 넣어 나온 콜 값을 저장한다. 카카오 없이 고정 입력으로 돈다 | 같은 입력을 다시 넣으면 기준과 같다 |
| B3 | 상세 입구: `DetailRecord` 자리를 기본 콜로 대신한다 (`routes/detail.ts`) | 비교 기준 · 문제지 · `detailRecordFromTable` · `detailParsedNoUndefined` 그대로 |
| B4 | 선점 입구: `/confirm` 에서 기본 콜을 거치게 한다 (`routes/orders.ts`) | 비교 기준 그대로. `scenario` · `drive` 에서 기본 콜을 거친 콜이 판정 · 결재 · 운행을 지난다 |

**왕복 검사:** 받은 콜 → 기본 콜 → `OfficeOrder` 가 받은 콜과 같아야 한다. 값이 달라지면 멈춘다. 기본 콜에 없는 칸(`rawText`, 좌표 등)은 치환 때 함께 넣어 잃지 않는다.

**찾은 칸만 싣는다:** `evolveOrder` 는 키가 있으면 `undefined` 여도 앞 기억을 덮는다. 치환 함수가 못 찾은 칸을 실으면 `/confirm` 의 값이 `/detail` 에서 지워지므로 이 규칙을 검사로 묶는다.

**비교에서 빼는 값:** 카카오 시간 · 거리 · 경로, 계산 시각, 보고 시각처럼 돌릴 때마다 달라지는 값.

**B 에서 안 건드리는 자리:** `/scrap`(콜 객체를 안 만들고 intel 표에 넣는다), 재시작 복원(`sessionRestore`), 확정 복사(`dispatchEngine`). 콜이 들어오는 자리 중 상세와 선점 둘만 모으는 것이다.

### C. 배차망 표에 연결 — 운행 그대로

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |

| C1 | 정의 표 모양에 «콜 칸»과 «필수»를 더한다. 아직 아무도 안 읽는다. 한 화면 칸이 두 콜 칸을 채우는 쌍(`itemSize`, `tags`, `reservation`)을 담는 모양을 정한다 | 타입 검사 통과, 생성 파일 변화 없음 |
| C2 | 인성 표를 채운다 | 칸 이름 오타를 타입이 잡는다 |
| C3 | 인성 몫의 연결을 표에서 뽑는다 (`pageRead.ts`) | `detailRecordFromTable` · `detailParsedNoUndefined` · 비교 기준 그대로 |
| C4 | 픽커 · 플렉스 · 화물24시 표를 하나씩 채우고 연결을 옮긴다 (커밋 셋) | 위와 같음 |
| C5 | 보기 페이지: 콜 칸 × 네 배차망, 처음 얻는 페이지만 | 콜 칸이 적힌 정의 표 줄이 모두 나오고 수가 같다. 어느 배차망도 안 주는 칸이 색으로 보인다 |

### D. 읽는 코드 옮기기 — 운행 그대로

한 묶음씩 옮긴다. 콜 찾기 · 키 · 필터는 목록 글자를 계속 쓰게 한다.

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |

### E. 스캔앱 — 원달앱이 바뀜, 운행은 값이 같아야 그대로

서버를 먼저 올리고 원달앱을 나중에 올린다. 그 사이 폰에 옛 앱이 있어도 깨지지 않게 서버는 옛 앱의 값과 새 값을 모두 받는다.

| 걸음 | 할 일 | 무엇이 참이면 끝인가 |
|---|---|---|
| E1 | `gen:pages` 가 콜 칸 · 필수를 Kotlin 에 싣는다. 생성 파일과 짝 검사, gradle 을 함께 고치므로 시작할 때 커밋을 나눈다 | 짝 검사 통과, 생성 파일 차이가 새 칸뿐이다 |
| E2 | 플렉스 상세가 표로 칸을 채운다 (파서가 가장 작다) | 옛 파서와 값이 같다, 시뮬레이터 폰 시험 |
| E3 | 픽커 목록 | 옛 파서와 값이 같다, 실물로 콜 확정 전까지 확인 |
| E4 | 인성 · 화물24시 | 사업자가 생긴 뒤로 미룬다 |

### F. 판정 · 필수 바꾸기 — 🔴 운행이 바뀜, 항목마다 별도 승인

## 어디서 멈춰도 얻는 것

| 어디까지 | 얻는 것 |
|---|---|
| A | 콜 칸의 뜻과 출처가 한 표에 있다 |
| B | 상세와 선점 입구가 한 모양으로 모이고, 비교 기준이 이후 수정을 지킨다 |
| C | 네 배차망의 매칭을 화면에서 본다. 새 배차망은 표 한 장으로 시작한다 |
| D | 코드에서 `pickup` 같은 칸의 뜻이 하나가 된다 |
| E | 표로 스캔앱이 도는 것을 증명한다 |
| F | 판정이 공정해진다 |

## 지금 DB 값 대조

A~E 는 새 값이 없다. F1 · F2 시작 전에 지금 DB 의 콜 필터 최저 요금 · 판정 기준 · 시세표를 읽어 대조한다. 시험 기록의 콜 수와 분포는 실측 근거로 쓰지 않는다.

## 크기

어림이고 근거가 약하다. B 를 마치고 다시 어림한다.

| 묶음 | 커밋 | 세션 |
|---|---|---|
| A | 2 | 1 |
| B | 5 | 2 |
| C | 7~8 | 2 |
| D | 6 이상 | 3 이상 |
| E | 배차망마다 2~3 | 배차망마다 1 + 폰 시험 |

## 안 하는 것

- 전송 칸 이름 · DB 칸 변경. 새 저장 칸이 필요하면 근거를 들어 먼저 여쭙는다
- 세 콜 타입의 이름 없애기
- 시간 표: 기사님이 더 고민하신다
- 배차망별 설정 칸 일반화

## 실물로 확인 못 하는 것

사업자가 없어 인성 · 화물24시 앱을 설치할 수 없고, DB 콜은 전부 시뮬레이터가 만든 가짜다. 플렉스는 실물 캡처가 있으나 앱으로 콜을 잡아 본 적이 없다. 앱으로 돌려 볼 수 있는 것은 픽커뿐이다. 비교 기준이 같다는 것은 «옛 코드와 값이 같다»는 뜻이지 «실물에서 맞다»는 뜻이 아니다.
