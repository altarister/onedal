# shared 파악 계획 (초안 — 기사님 확인 전)

기사님 말씀: «orderShapes 한 파일안에도 지금 비슷 비슷한것이 엄청 들어가 있는데.. 내가 다 파악도 못하고 있고 어디서 무얼 어떻게 쓰고 있는지 지워도 되는건지 아닌지도 모르고 있어 이런 파일이 지금 shared 안에 엄청 많이 있잖아.»

**목표:** 다 외우는 것이 아니라, 무엇이 어디에 쓰이는지 기사님이 찾아볼 수 있는 상태를 만든다. 지우거나 합치는 일은 이 계획에 넣지 않는다. 그 판단을 할 수 있게 만드는 계획이다.

## 이 수정이 기사님 하루에 무엇을 하나

| | 는다 / 준다 |
|---|---|
| 좋은 콜 | 변화 없음 |
| 노이즈 | 변화 없음 |
| 기사님 손 | 변화 없음 |

운행과 화면은 그대로다. 달라지는 것은 코드를 고칠 때다. 어디에 번지는지 미리 보이고, 비슷한 칸을 또 만들지 않게 되고, 라이브에서 문제가 났을 때 볼 곳을 찾을 수 있다.

## 지금은 이렇게 돈다

- `/shared/` 보기 페이지는 파일마다 머리글 · 함수 · 타입 · 값을 보여 준다. 누가 쓰는지는 안 보여 준다
- `pnpm audit:dead` 는 새로 죽는 함수 · 값을 막는 검사다. 타입은 안 보고, 이름을 낱말로 센다. 아무도 안 쓰는 14개는 «남겨 둠» 까닭이 붙어 있다
- 내보낸 것 687개 중 441개는 서버 · 관제웹 · 운영센터가 쓰고, 47개는 다른 shared 파일만, 148개는 자기 파일만, 29개는 검사만 쓴다. 22개는 아무도 안 쓴다 (표 파일 2개를 빼면 20개). onedal-89 세션이 TypeScript 참조 찾기로 센 어림이다. 운행일지와 `ui` 를 넣지 않았으니 1단계에서 다시 세어 확정한다
- `orderShapes.ts` 는 `interface` 12개와 `type` 1개이고, 같은 칸 이름이 둘 이상의 `interface` 에 있는 것이 34개다

## 단계

순서는 3 → 1 → 2 → 4 다. 번호는 일의 이름이다. 콜의 길을 먼저 알아야 숫자 화면을 읽을 수 있고, 코드도 바뀌지 않는다.

### 3. «한 콜의 길» 한 장을 만든다 (먼저)

콜 한 건이 지나는 길을 화면 순서대로 적는다. 때마다 거치는 파일과 함수, 그때 채워지는 칸을 한 줄씩 쓴다.

```
새 콜 목록 → 새 콜 화면 → 판정 → 결재 → 확정 → 운행 → 완료
```

- **어떻게:** 코드를 읽어 쓰고, `pnpm scenario` 로 콜 한 건을 돌려 서버 로그와 대조한다. 이 스크립트는 자기 포트와 자기 DB 를 쓰며 떠 있는 개발 서버를 안 건드린다
- **한계:** 시나리오는 서버에 콜을 직접 넣으니 목록과 상세 화면, 인성 팝업, 픽커 사진은 로그에 없다. 그 줄은 «코드만 읽음»으로 표시한다. 시나리오가 `/scrap` · `/confirm` · `/detail` 을 모두 지나는지는 돌려 보고 적는다
- **위치:** `설계/한콜의길.md`
- **끝:** 로그의 때마다 문서 줄이 하나씩 대응하고 빠진 때가 없다. 로그로 못 본 줄은 모두 «코드만 읽음»으로 표시했다
- **되돌리기:** 문서를 되돌린다

### 1. 페이지에 «누가 쓰나»를 넣는다

파일 페이지의 함수 · 타입 · 값 표마다 칸을 더한다.

| 칸 | 내용 |
|---|---|
| 쓰는 곳 | 서버 · 관제웹 · 운영센터 · 운행일지 · ui · shared · 검사 파일 수. 펼치면 파일 이름이 나온다 |
| 원달앱과 주고받음 | `appOrderShape` 가 대조하는 칸과 JSON 모양 타입에 표시한다. `id`, `type` 같은 짧은 이름은 낱말로 세면 크게 틀리므로 낱말 수를 쓰지 않는다 |
| 같은 이름의 칸 | `interface` 의 칸마다 같은 이름의 칸이 있는 다른 타입 (shared 안) |

- **범위:** 내보낸 것 단위로만 센다. **`interface` 안의 칸마다 쓰는 곳을 세는 일은 이번에 안 한다.** `(x as any).itemSize` 처럼 실제로 읽히는 칸이 0으로 나와, 지워도 된다는 틀린 판단을 낳기 때문이다
- **어떻게:** TypeScript 언어 서비스의 참조 찾기로 센다. 전체 프로젝트를 한 번 읽어 메모리에 두고, 바뀐 파일만 다시 계산한다. 첫 계산에 약 8초가 걸리니 그동안 «계산 중»을 표시한다
- **«쓰는 곳 0 = 지워도 됨»이 아니라고 페이지에 적는다.** `as any` · 글자로 읽는 곳 · 원달앱 JSON 은 못 찾는다
- **고치는 파일:** `client-app/vite.config.ts`, `shared/src/preview/`. 개발 서버 전용이라 배포에 안 들어간다
- **끝 (넷 다 참):**
  1. 메뉴의 모든 페이지(지금 폴더 10 + 파일 79)가 오류 없이 열린다
  2. 알려진 반례 셋이 맞게 나온다. `TABLE`(글자로 읽음), `ScrapResponse`(앱 JSON)는 «0이지만 지우면 안 됨»으로 표시되고, `SimplifiedOfficeOrder` 는 쓰는 곳이 있다
  3. 참조 찾기와 낱말 세기가 갈리는 이름을 전부 목록으로 뽑아, 쓰는 곳이 0건 · 1건인 것부터 10개를 코드로 대조했다
  4. 운행일지와 `ui` 를 넣어 다시 센 합계를 위 «지금은 이렇게 돈다»에 고쳐 적었다
- **되돌리기:** 커밋을 되돌린다

### 2. 쓰임 목록 페이지를 만든다

`/shared/` 첫 화면에 내보낸 것을 쓰임별로 모아 보여 준다.

- 아무도 안 씀
- 검사에서만 씀
- 자기 파일에서만 씀 (내보낼 필요 없음)

- **끝:** 아무도 안 쓴다는 항목마다 `audit:dead` 의 «남겨 둠» 까닭이 있거나, 왜 통과하는지 한 줄이 붙어 있어 설명 없는 항목이 0개다. [shared_할일.md](shared_할일.md) 의 «안 쓰는 내보내기» 이름이 이 목록에 모두 있다. 파일을 지우거나 고치지 않는다
- **되돌리기:** 커밋을 되돌린다

### 4. orderShapes 를 함께 본다

1단계 화면으로 `orderShapes.ts` 의 타입을 하나씩 본다. 비슷한 타입을 나란히 놓고 칸의 차이를 보여 드리고, 타입마다 «누가 만들고 누가 읽나» 한 줄을 주석에 적는다.

- **끝:** `interface` 12개와 `type` 1개마다 그 한 줄이 있고, 기사님이 지우거나 합칠 후보를 정하셨다. 주석을 뺀 코드는 전과 같다
- **되돌리기:** 커밋을 되돌린다

여기까지 마치면 기본 콜로 돌아간다. 겹침을 푸는 일이 기본 콜이기 때문이다. 다른 파일은 기본 콜을 하면서 만나는 대로 본다.

## 쓰는 곳을 세는 방법 비교

| 순위 | 방법 | 타입 | 정확도 | 비용 |
|---|---|---|---|---|
| 1 | TypeScript 참조 찾기 (고른 방법) | 봄 | 내보낸 것 단위로 정확. `as any` 못 봄 | 약 8초, 한 번 계산 |
| 2 | 낱말 세기 | 봄 | 같은 이름의 다른 변수까지 셈 | 빠름 |
| 3 | `audit:dead` 결과 표시 | 안 봄 | 0건만 믿을 만함 | 빠름 |

1번과 2번으로 세어 본 합계는 비슷하다 (아무도 안 씀 20 / 19). 이 숫자는 운행일지와 `ui` 를 넣기 전의 어림이다.

## 안 하는 것

- 코드 · 타입 · 파일 지우기 (기사님이 말씀하실 때만)
- 값이 바뀌는 수정
- shared 밖(서버 · 원달앱) 정리. 다만 «누가 쓰나»는 서버와 관제웹도 함께 찾아 준다
- 기본 콜 작업. 멈춘 자리는 [할일.md](../할일.md) 에 있다

## 이 계획으로 안 풀리는 것

찾아볼 수 있게 되어도 라이브 위험이 직접 줄지는 않는다.

- **코드 쪽:** 검사 파일을 뺀 서버 · shared · 관제웹 소스의 `as any` 가 약 277곳 있다. 앱 ↔ 서버 JSON 은 짝 검사가 칸 이름만 대조하고 뜻과 타입은 안 본다
- **실물:** 사업자가 없어 인성 · 화물24시를 실물로 돌려 본 적이 없다. 이것이 더 큰 공백이다
- **모드:** 코드가 계약을 만드는 자리는 자동 모드뿐이다. 알람 · 직접 모드에서 코드를 잘못 알아도 사고는 콜을 놓치거나 노이즈가 느는 선이고, 자동 모드에서만 잘못된 계약이 된다
