# 콜 타입 공통화 계획

## 하려는 일

기사님 말씀: «이걸 공통으로 하나로 만드는거 하고 싶은데 할수 있을까? … 다른것보다 이것이 가장 중요한거 같아.»

콜 하나를 코드에 적는 모양을 하나로 모은다. 칸 하나를 더할 때 세 곳이 아니라 한 곳만 고치게 하고, 배차망에서 온 값과 서버가 계산한 값을 묶음으로 구분한다.

**결론: 할 수 있다.** 타입만 고치는 일이라 전송되는 값 · DB · 원달앱은 그대로다.

## 이 수정이 기사님 하루에 무엇을 하나

| | 는다 / 준다 |
|---|---|
| 좋은 콜 | 변화 없음 |
| 노이즈 | 변화 없음 |
| 기사님 손 | 변화 없음 |

오늘 운행에 달라지는 것은 없다. 달라지는 것은 다음 수정이다.

- 콜 칸 하나를 더하거나 고칠 때 타입 세 곳이 한 곳으로 준다
- 표의 칸과 콜 모양을 맞추는 일(콜 기준표)이 쉬워진다. 원콜 같은 새 배차망을 더할 때 볼 곳도 준다
- 타입이 실제보다 좁아 `as any` 로 덮던 길이 일부 닫힌다. 판정 결과(`judgment`)를 넣는 줄이 그 예다

이 일만으로 줄지 않는 것도 있다. 콜 칸 하나는 타입 말고도 원달앱 모델 · 서버 저장 · DB 칸 등에 따로 적혀 있다(`reservedAt` 은 검사를 빼고 12개 파일). 그 사본은 이번 범위가 아니다.

## 지금은 이렇게 돈다

`shared/src/call/orderShapes.ts`

| 타입 | 뜻 | 칸 수 | 쓰는 곳 |
|---|---|---|---|
| `OfficeOrder` | 배차망에서 온 콜 한 건 (목록 콜 + 상세 콜) | 48 | 아래 셋의 부모 |
| `PendingOrder` | 심사 중 콜 | 78 | 서버 |
| `MyOrder` | 내 콜 | 78 | 서버 |
| `SecuredOrder` | 관제웹이 받는 콜 | 82 | 관제웹 대부분 · 서버 일부 |

- **겹침:** 세 타입이 `OfficeOrder` 밖의 같은 칸 25개를 각자 적는다. 24개는 이름 · 필수 여부 · 타입이 글자까지 같고, 다른 것은 `status` 하나다(`MyOrder` 만 `MyOrderStatus`)
- **다시 적은 칸:** `deliveryDistance` 는 부모에도 있는데 `PendingOrder` · `MyOrder` 가 또 적는다. `vehicleType` 은 목록 콜과 상세 콜 양쪽에 있다
- **실제로는 이미 한 객체다:** 심사 중 콜을 내 콜로 바꿀 때 객체를 통째로 펼쳐 상태만 바꾼다(`dispatchEngine.ts:533-539`). 세 타입은 같은 객체에 붙은 다른 이름이다
- **그래서 덮는 줄이 있다:** `PendingOrder` 에 `judgment` 칸이 없어 `(securedOrder as any).judgment = dry` 로 넣는다(`OrderEvaluator.ts:410,509,550`). `sessionRestore.ts:353` 은 심사 중 콜 저장소의 값을 `as MyOrder[]` 로 바꾼다
- **좁은 상태 타입의 쓸모:** `MyOrderStatus` 를 쓰는 곳은 `MyOrder.status` 하나다. 이 좁힘에 기대는 코드가 없다
- **원달앱:** `PendingOrder` · `MyOrder` · `SecuredOrder` 는 Kotlin 에 없다. 다만 `DetailedOfficeOrder` 는 Kotlin 에도 같은 이름이 있고 내용이 다르다. 이번에 건드리지 않는다

## 고른 모양

```
OfficeOrder       배차망 · 원달앱에서 온 값 (지금 그대로)
ServerCallFields  서버가 계산 · 기록한 값 (한 번만 적는다 · 칸마다 주석 한 벌)
SecuredOrder      OfficeOrder + ServerCallFields = 콜 한 건의 몸통
PendingOrder · MyOrder   SecuredOrder 의 다른 이름 (쓰는 코드는 그대로)
```

심사 중인지 내 콜인지는 타입 이름이 아니라 `status` 칸이 말한다.

### 고른 까닭 — 세 안을 나란히

| | 가. 겹치는 칸만 묶기 | **나. 몸통 하나 + 이름 유지 (고름)** | 다. 이름까지 하나로 |
|---|---|---|---|
| 칸을 고칠 곳 | 묶음 하나, 타입별 칸은 따로 | **한 곳** | 한 곳 |
| `judgment` 를 덮는 `as any` | 남는다 | **없앨 수 있다** | 없앨 수 있다 |
| 고치는 코드 | `orderShapes.ts` 하나 | **`orderShapes.ts` + 덮는 줄 몇 개** | 서버 · 관제웹의 타입 이름 전부 |
| 기사님 «하나로» | 일부 | **모양은 하나** | 이름까지 하나 |
| 되돌리기 | 쉽다 | **쉽다** | 어렵다 |

순위: 나 > 가 > 다. 가는 칸 차이가 남아 덮는 줄이 그대로이고, 다는 얻는 것에 비해 고치는 파일이 많다. 이름을 지우는 일은 나를 마친 뒤 언제든 할 수 있다.

### 두 세션이 갈린 것과 제 결정

| 갈린 것 | onedal-1e | onedal-89 | 결정 |
|---|---|---|---|
| `MyOrder` 의 좁은 상태 | 남긴다 | 넓힌다 | **넓힌다.** 좁히면 `sessionRestore.ts:353` 의 변환이 남고, 좁힘에 기대는 코드가 없다. 합쳐 본 실험도 넓힌 쪽이다 |
| 안 쓰는 칸 5개 | 공통화 뒤 | 공통화 앞 | **뒤에 따로.** 공통화는 `OfficeOrder` 를 안 건드려 서로 독립이다. 기사님이 가장 중요하다고 하신 일을 먼저 한다 |

## 단계

커밋은 단계마다 하나다. 어느 단계든 그 커밋만 되돌릴 수 있다.

**1. 서버 값 묶기.** `ServerCallFields` 를 만들고 세 타입이 물려받는다. 다시 적은 `deliveryDistance` 와 겹친 `vehicleType` 을 지운다.
끝: 서버 · 관제웹 · 운영센터 · 운행일지 타입 검사가 통과하고, 코드 차이가 `orderShapes.ts` 하나다.

**2. 몸통 하나로.** `PendingOrder` · `MyOrder` 를 `SecuredOrder` 의 다른 이름으로 바꾼다. 쓰는 곳이 없어지는 `MyOrderStatus` 를 지운다. `OfficeOrder` 와 `ServerCallFields` 의 칸이 겹치면 타입 오류가 나게 한다.
끝: 타입 검사 · 서버 jest · 관제웹 vitest 가 통과하고, 검사 수가 그대로다.

**3. 덮는 줄 떼기.** 2단계로 필요 없어진 줄만 뗀다. `OrderEvaluator.ts` 의 `judgment` 줄과 `sessionRestore.ts:353` 이 대상이다. `dispatchEngine.ts:539` 의 `delete` 처럼 값을 바꾸는 줄은 그대로 둔다. `orderMemory.ts:24` 는 제네릭 병합이라 타입 오류가 나면 남긴다.
끝: 대상 줄의 변환이 사라지고, 게이트 전체가 통과한다.

**4. 주석 한 벌로.** 칸마다 흩어진 주석을 `ServerCallFields` 에 하나로 합친다. 코드와 다른 주석을 고친다(`MyOrder.isPreview` 는 «`false` 로 덮인다»고 적혀 있으나 코드는 지운다). 파일 머리글과 제목 옆 설명을 고친다.
끝: 표 페이지에서 `SecuredOrder` 의 칸마다 설명이 나오고, 주석을 뺀 코드가 3단계와 같다.

### 값이 안 바뀐다는 확인

- 각 단계 커밋 전에 onedal-89 세션이 디프를 줄 단위로 읽어 값을 만들거나 바꾸는 줄이 없는지 본다
- 게이트: 타입 검사 넷 · 서버 jest · `test:web` · `audit:dead` · `lint:gate` · 기존 DB 사본 부팅
- `SimplifiedOfficeOrder` 칸을 지우지 않으므로 `appOrderShape` 검사와 원달앱 JSON 은 그대로다. `vehicleType` 은 상세 콜 쪽 선언만 지운다

## 지금 DB 값 대조
