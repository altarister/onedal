# 콜 상태 전수 조사 (검수 반영)

조사 에이전트(읽기 전용)가 코드를 읽고 만든 결과다. 경로는 따로 적지 않으면 `onedal-web/` 기준이다. 두 에이전트가 코드를 읽어 대조했다(돌려 본 것은 아니다).

## 0. 검수 결과 — 본문보다 이 장이 앞선다

**맞음** — 2장 T1~T12 는 상태를 바꾸는 서버 코드를 빠짐없이 덮는다(두 검수 모두 서버 src 의 상태 쓰기 줄을 전부 뽑아 대조). 3장 정상 흐름 · 갈래 · 4장 DB/메모리 · 5장 성질 표(아래 빠짐 제외) · 6장 «한 화면에 여러 상태» 결론 · 8장 ③④⑤⑥⑧⑨⑪⑫⑬⑭⑯.

**고침**
- 6장 첫 줄 «서버도 `RUN_*` · `DETAIL_CONFIRMED` · `MY_ORDERS` 를 이름으로 읽지 않는다» → 틀림. 서버는 `DETAIL_CONFIRMED`(`DETAIL_SCREENS`)와 `MY_ORDERS`(`isListScreen` 의 listReturn)를 읽는다. 안 읽는 것은 `RUN_*` 뿐이다.
- 6장 표 첫 줄(DETAIL_PRE_CONFIRM) → 원달앱이 확정을 누르는 콜은 «선점 중»까지만 새 콜 화면에 있고 그 뒤는 내 콜 화면이다. 새 콜 화면에서 «심사 중 · 결재 기다림»이 되는 것은 **미리보기뿐**이다.
- 8장 ⑩ → 코드로는 맞지만 `SIM-` 으로 시작하는 id 를 만드는 곳이 없어 지금은 일어나지 않는다(죽은 분기).
- 8장 ⑮ → 반쪽. PICKED_UP 콜에 `cancelPressed=true` 가 와도 심사 캐시가 남아 있으면(KEEP · 받았음 어디서도 심사 캐시를 안 지운다) «심사 중 아님» 방어(`dispatchEngine.ts:105`)가 막아 아무 상태도 안 바뀐다 — 그런데 원달앱에 가는 응답 글은 «안전취소로 적음»(`emergency.ts:136`)이라 거짓이다. RELEASED_BY_OFFICE 가 되는 것은 캐시가 없을 때(재기동 뒤 등)다.

**빠짐**
- T2 «이전» 칸에 `AWAITING_DECISION` · `SECURED_EVALUATING` — 미리보기 → 손 확정으로 /detail 이 다시 오면 `detail.ts:91` 이 SECURED_EVALUATING 으로 덮는다(결재 기다림 → 심사 중, 뒤로 가는 전이). 같은 딱지 재시도는 안 바꾸고(:75-83) 이미 KEEP 된 콜은 `existingMatch`(:150-166)가 막는다.
- 3장 갈래: 종결 콜에 KEEP 이 오면 승격하지 않는다(`dispatchEngine.ts:494-497`) · 서버 재기동 때 메모리에만 있는 세 상태의 콜은 사라진다(복구 대상이 아님).
- 5장: `type` 값에 `INTEL_BULK` · `ALARM`(EVENT_TYPES `orderShapes.ts:4-10`) — 한 칸에 일곱 값, 타입은 다섯 · «상대가 취소했다고 함»(`counterpartCancelled` — 콜 칸이 아니라 단계 장부 칸 · `stepTables.ts:56-57,89-90`) — 상태가 아닌 사실로 `ORDER_RELEASED_BY_OFFICE` 와 따로 있다 · 취소 까닭 값(`countCancel` 의 `FORCE_CANCEL` · `TIMEOUT` · `APP_PRESSED` · `DECISION_CANCEL` — 장부에 안 남음) · 판정(`judgment` — 심사 1회 · 고정 스냅샷)을 성질로 둘지.
- 6장 반대 방향: **한 상태가 여러 화면에 걸린다** — «진행 중» 콜이어도 인성 · 화물24시 폰은 대부분 새 콜 목록에 있다.

**한 줄 답(1e)** — 서버가 **화면을 보고 상태를 바꾸는 문은 하나**(T7: 상세 이탈 → 미리보기 정리 · 목록 복귀 → 심사 콜 정리)다. 그 밖의 모든 전이는 결재 · 마일스톤 · 타이머 · 비상 보고가 만들고 화면은 안 본다(픽커 `RUN_*` 도 마일스톤을 안 만든다). 그래서 상태 ↔ 화면은 대응표가 아니라 «화면이 상태를 끝내는 문 하나 + 다대다»다.

**🔴 운행에 닿는 것 — 둘 다 코드로 사실 · 고치지 않음(지금은 리팩터링만 · 운행 동작이 바뀌어 기사님 합의 거리)**
- ① `/confirm` 의 `presecured_` 타이머(`orders.ts:280-281`)는 /detail 이 끄지 않는다. 원달앱이 계약한 인성 · 화물24시 콜은 /confirm 뒤 안전취소 시간이 되면 서버가 `handleDecision(SAFE_CANCEL)` 로 장부 · 취소 셈 · 폰 CANCEL 을 먼저 한다. /detail 의 «원달앱 보고 기다림»(`WAIT_APP_REPORT` · 안전취소+5초)은 늘 뒤라 닿지 않는다. 원달앱이 «취소를 못 눌렀다(배차망엔 계약이 남음)»고 보고해도 서버 장부는 이미 안전취소 — 배차망 실제와 장부가 어긋난다. 시험은 타이머가 «걸리는지»만 본다(`coreRulesBehavior.test.ts:123-139`) · 로컬 로그 19개에 관련 줄 0건이라 실주행에서 일어났는지는 모른다. 정상일 때는 원달앱 자기 타이머와 거의 같은 시각이라 결과가 같다. **그 전에 결재(KEEP)가 나면 이 타이머는 꺼진다**(`handleDecision` 첫 줄 `cancelOrderWaits`) — 걸리는 것은 안전취소 시간 안에 결재가 없었던 콜뿐이다. 원달앱이 «취소를 못 눌렀다»고 보고하면 서버는 «세지 않는다»고 답하지만(`emergency.ts:101-106` — 종결 검사 :118 보다 앞) 이미 센 것은 되돌리지 않는다.
- ② 인성 · 화물24시 미리보기에도 /detail 시한이 걸린다(`detail.ts` 가 `isPreview` 를 안 봄) — 안전취소+5초 뒤 서버가 결재석 카드를 지운다(장부 · 셈 없음). 두 설계 주석이 갈렸다: `timeoutActionOf` 주석은 «미리보기는 서버가 치운다», `orders.ts:264-271` 은 «미리보기에는 안전취소 타이머를 걸지 않는다». 그 뒤 손 확정하면 판정을 다시 계산한다(«판정은 미리보기 순간의 것» 원칙과 어긋남). 픽커 · 인성플렉스는 해당 없음.
  - 경위(git): /detail 시한(4월부터 있음)을 배차망별 DB 값 + 5초 정리로 바꾼 커밋 (`a894c5cd`) → **기사님 말씀** «타이머로 미리보기 켜고 끄기 기능은 빼 … 페이지를 이탈하면 끄는 걸로 예외 없이» (`220f03a8` — 그때 /confirm 타이머만 빼고 /detail 시한은 남음) → `timeoutActionOf` 주석 (`4242a232` — 커밋의 기사님 인용은 «원달앱이 확정한 콜은 원달앱이 끝까지 책임진다»이고 «미리보기는 서버가 치운다»는 그때 있던 동작을 적은 서술). 기사님이 분명히 말씀하신 쪽은 09-17 이다 — 여쭐 때: «09-17 말씀대로 /detail 시한에서 미리보기를 뺀다 / 09-17 말씀을 바꾼다».
- ⑦ 방출된 콜의 마일스톤을 되돌리면 방출 상태가 «진행 중»으로 되살아난다(`undoMilestone` 에 종결 검사 없음) · `handleDecision` 방출 갈래에도 종결 검사 없음.

**«진행 상태 / 콜의 성질» 분리에 모자란 재료(리뷰 이후 일)**
1. 끝난 까닭 — 거절 · 시한 · 화면 이탈 · 원달앱 누름 · KEEP 못 받음이 모두 SAFE_CANCEL 한 값. 까닭이 지금 어디에 남나(로그 · `countCancel` reason)를 적고, 장부에 남길지는 새 칸이라 기사님 거리.
2. 배차망 쪽 계약이 살아 있나 — ①의 «못 눌렀음»이 콜에 안 적힌다.
3. 확정 주체 — 결재석 KEEP 인지 직접 수락인지가 콜에 반쯤만 남는다.
4. 성질마다 불변 / 변함 / DB 저장 여부 — `matchType` · `isPreview` · `whoConfirmed` 는 DB 칸이 없어 재기동 뒤 «누가 잡았나»를 일부만 안다.
5. 폰 쪽 상태(원달앱 `contractedByApp` · `openedByApp` · `DecisionPlan` · 폰 작업 단계 `workStage`)가 서버 상태와 따로 돈다는 한 장.
6. 전이 허용 규칙이 흩어져 있다 — 마일스톤은 `canReportMilestone`, 심사 중은 `isEvaluating` · `isTerminal` 방어, 방출은 검사 없음.

## 8. 어긋남 · 이상한 점 (조사 에이전트가 찾은 것 — 검수 대상)

① `/confirm` 안전취소 타이머가 «원달앱 보고 기다림»을 앞지를 가능성 — `presecured_` 타이머(orders.ts:281)는 결재 · 정리 전까지 안 꺼진다(`armWait` 는 같은 키만 끔 · waits.ts:46). 원달앱 계약 콜은 /confirm 뒤 cancelSec 초에 SAFE_CANCEL(CANCEL 전송 · 장부 · 셈). /detail 의 `WAIT_APP_REPORT`(detail.ts:389-396)는 /detail 뒤 cancelSec+5초라 닿기 어렵다 — «원달앱이 계약한 콜은 서버 시계로 세지 않는다» 원칙과 충돌. (시험으로 덮인 곳 없음)
② 미리보기에도 /detail 안전취소 시한 — detail.ts:351-406 은 isPreview 를 안 본다. 인성 · 화물24시 미리보기는 FORCE_CANCEL 로 시간 정리 — orders.ts:264-271 «미리보기에는 안전취소 타이머를 걸지 않는다»와 반대.
③ `ORDER_RELEASED_BY_OFFICE` 의 뜻이 둘 — 주석 «사무실이 일방적으로 취소»(callStatus.ts:22) vs 비상 보고 옛 길 (c)(emergency.ts:125,166-177 · 머리 :17).
④ 패널티 주석끼리 모순 — callStatus.ts:6 «2단계부터 버리면 모두 패널티» vs :19-20 «안전취소에만» · CONFIRMED · PICKED_UP · DELIVERED 에 «(패널티 O)» · 방출(dispatchEngine.ts:782)과 emergency(:163)도 기기 `canceled` 셈을 올리는데 장부 셈(cancelCount.ts:120-125)은 SAFE_CANCEL 만.
⑤ SAFE_CANCEL 주석 «확정 후 30초 안에 내가 취소»가 실제와 다르다 — 확정 전 정리 · 서버 시한 · 화면 이탈 · 새 콜 진입 · 손 확정 실패 · 연습 끝까지 · 30초도 배차망별 DB 값.
⑥ detail.ts:176-181 기기 충돌 잠금은 웹에 SAFE_CANCEL 을 보내 카드를 지우지만 서버 상태는 그대로 · 기기 A 심사는 계속.
