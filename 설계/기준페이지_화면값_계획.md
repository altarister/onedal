# «화면 값 바꾸기» 단계 계획서 (초안 — 기사님 승인 전)

이름의 원천은 `기준페이지_이름표.md` 3장 · 8장이다. 이 문서는 «어떻게 올리나»를 적는다. 코드는 아직 안 고쳤다. 숫자는 2026-11-04 에 `grep` 과 로컬 DB(`onedal-web/server/local.db`)로 센 것이다.

한 줄 요약: 화면 이름 넷(`LIST` · `DETAIL_PRE_CONFIRM` · `DETAIL_CONFIRMED` · `MY_ORDERS`)을 기준 페이지 이름(`NEW_LIST` · `NEW_CALL` · `MY_CALL` · `MY_LIST`)으로 바꾸고, 원달앱 안에서만 쓰는 `LIST_COMPLETED` 를 없앤다. 기사님이 보시는 화면 글자는 안 바뀐다.

---

## 0. 이 단계가 하는 것 · 안 하는 것

| 하는 것 | 안 하는 것 |
|---|---|
| 정의 표의 «화면 종류»(`standard`)와 서버로 가는 «화면 값»을 같은 이름으로 바꾼다(이름표 1장 ②③ — 한 단계) | `RUN_*` · `HOME` · `TRANSITION` · `NETWORK_MENU` · `OTHER_APP` · `LAUNCHER` · `UNKNOWN` · `POPUP_*` 이름 |
| `LIST_COMPLETED` 를 없앤다(8장 ④가). 목록 복귀는 «내 콜 목록 + 그 화면 줄의 목록 복귀 표시(`listReturn`)»로 안다 | 콜 상태 이름(`ORDER_CONFIRMED` …) — 콜 상태 정의 계획서가 따로 정한다 |
| 서버가 옛 값을 새 값으로 받는 대응표 한 곳 | 관제웹 화면 글자 · 배지 색 |
| DB 에 쌓인 옛 값 옮기기(별도 커밋 · 새 원달앱이 모든 폰에 오른 뒤) | 사진 이름 바꾸기(이름표 10장) |

## 1. 지금은 이렇게 돈다 (②)

1. 원달앱이 화면 글자를 정의 표(배차망마다 생성된 코틀린 파일)에 대 본다. 표의 `standard` 가 `LIST` · `DETAIL_PRE_CONFIRM` · `DETAIL_CONFIRMED` · `MY_ORDERS` 중 하나면 `ScreenDetector.wireOf`(`ScreenDetector.kt:74`)가 **같은 글자의 화면 값**으로 바꾼다. 서버로 가는 값(`wire`)이다.
2. 원달앱 안에서는 값이 하나 더 있다(`ScreenRead.context`). 같은 화면이 «내 콜 목록 + 목록 복귀 표시»면 `LIST_COMPLETED`, 덧칸이 시키는 일이 있으면 `POPUP_*`(`ScreenDetector.kt:53`). 원달앱 안 코드(`HijackService.kt:1369-1371` 목록 복귀 · `KakaoPickerPlugin.kt:318`)는 이 안쪽 값을 본다.
3. 서버로는 `reportedScreen ?: currentScreenContext`(`TelemetryManager.kt:365`)가 가는데 `reportedScreen` 이 늘 `wire` 로 채워져(`HijackService.kt:2040`) **지금은 `wire` 만 간다**. 단 하나 예외가 있다: **비상 보고**(`HijackService.kt:2263` `sendEmergencyReport`)는 안쪽 값(`currentScreenContext`)을 그대로 실어 `LIST_COMPLETED` · `POPUP_*` 도 갈 수 있다. 서버는 비상 보고의 화면 값을 로그와 기록에만 쓴다(`emergency.ts:58,76`) — 판단에 안 쓴다.
4. 서버는 화면 값을 shared 의 세 함수로만 읽는다: `isListScreen`(목록 복귀) · `isDetailScreen`(상세) · `isBlipScreen`(스치는 화면). 서버 `src` 에서 이름을 직접 비교하는 곳은 **없다**(`deviceSessions.ts:331` 의 주석 한 줄뿐).
   - `LIST_SCREENS = ['LIST', 'LIST_COMPLETED']` (`screenKinds.ts:71`) · `MY_ORDERS` 는 `screenPage` 가 목록 복귀 페이지일 때만(`screenKinds.ts:87`).
   - `DETAIL_SCREENS = [DETAIL_PRE_CONFIRM, DETAIL_CONFIRMED, POPUP_*]` (`screenKinds.ts:99-102`).
5. 관제웹은 화면 값을 `screenLabels.ts` 이름표를 거쳐 한글로 그린다. 새 원달앱은 페이지 이름(`screenPage`)을 같이 보내 배지가 그 이름을 쓴다.
6. 다른 곳에서 화면 값을 직접 쓰는 곳: 관제웹 상황판 시험 버튼이 `screenContext: 'LIST'` 로 보고를 만든다(`StatusBoard.tsx:589`) · 폰 시험 문제지(`phone-e2e-test/*.json` 약 20곳).
7. **지금 쓰이지 않는 값**: `DETAIL_SCREENS` 의 `POPUP_*` 넷은 일반 보고로는 오지 않는다(`wire` 가 늘 `DETAIL_*`). 이번엔 안 지운다(0장) — 찾은 것으로만 적는다.

## 5. 올리는 순서 (서버 · 관제앱 · 원달앱)

**먼저 알아 둘 사실 셋**
- **관제앱은 이 레포 안에 있다.** `onedal-web/client-app/android`(Capacitor)가 관제웹 빌드(`dist`)를 앱 안에 **통째로 담는다**(`capacitor.config.ts` `webDir: 'dist'`, 서버 주소로 불러오는 설정 없음). 그래서 관제웹은 서버를 올리면 바뀌지만 **관제앱은 새 APK 를 깔기 전까지 옛 이름표를 쥔다.** 옛 관제앱이 서버가 보낸 새 화면 값(`NEW_LIST` …)을 만나면 이름표에 없어 **배지 색이 회색(모름 색)으로 떨어진다**(글자는 페이지 이름이라 그대로). 이것은 기사님 화면이 바뀌는 일이라 기사님이 «관제앱 APK 를 서버보다 먼저»(2가)로 정하셨다(13장).
- **서버 · 관제웹 · shared 는 한 번의 `main` push 로 함께 배포된다**(`.github/workflows/deploy.yml` — `onedal-web/**` 가 바뀐 push 한 번, `deploy.sh` 가 서버를 올리고 관제웹 `client-app` · 운영센터 `ops` 를 한 배포에서 빌드해 바꾼다). 그래서 «서버 먼저, 그다음 관제웹»은 **한 push 안에서 나눌 수 없다.** 나눌 수 있는 것은 커밋(검토 단위)뿐이고, 배포는 한 번이다. 둘 다 옛 값과 새 값을 함께 알도록 만들어 두면 한 번에 나가도 안전하다.
- **원달앱 · 관제앱 APK 는 손으로 깐다.** 서버가 새 값을 알아 두기 전에 새 원달앱을 깔면 안 된다.

**README 75줄과 나란히**

> README: «원달앱 · 관제앱과 서버가 같이 바뀌면 **폰 먼저 · 서버 나중** — 서버는 `main` 에 올라가면 실서버에 자동 배포되지만 두 앱은 손으로 깐다. 서버가 새 칸 · 새 길을 기대하면 옛 원달앱 · 관제앱은 그 칸을 모른 채 돈다 … → 새 버전을 폰에 깔고 본 뒤 서버를 올린다.»
>
> 이번 단계: **관제앱 먼저 → 서버(+관제웹) → 원달앱 나중.**

- **관제앱은 README 와 같은 순서다.** 새 관제앱은 옛 값 이름표도 새 값 이름표도 함께 담으므로, 옛 서버에 먼저 깔아도 그대로 돈다(폰 먼저).
- **원달앱만 README 와 반대다.** README 의 규칙은 «서버가 새 칸을 **기대할 때**» 옛 앱이 깨지는 경우를 막는다. 이번 서버는 새 값을 **기대하지 않고 옛 값도 새 값도 받는다**(6장). 깨지는 쪽이 거꾸로다 — **새 원달앱이 새 값을 보내는데 옛 서버가 그 값을 모른다**(목록 복귀를 못 알아봐 결재석의 콜이 남는다 — `screenKinds.ts` 가 경고하는 사고). 그래서 서버가 먼저다.
- README 의 «새 버전을 폰에 깔고 **본** 뒤 서버를 올린다»는 그대로 지킨다 — 새 원달앱은 **로컬 서버(새 코드)에 붙여** 먼저 본다(`test-local-before-push`). 실서버에 붙은 폰에 새 원달앱을 까는 것만 서버 push 뒤로 미룬다.
- **이 단계가 끝나면 README 75줄에 한 문장을 더하자고 제안한다**: «서버가 옛 값과 새 값을 함께 받는 변경은 서버 먼저 · 원달앱 나중.» (README 고침은 합의 뒤에)

| 차례 | 올리는 것 | 어떻게 | 까닭 |
|---|---|---|---|
| ① | **새 관제앱 APK**(이름표가 옛·새 값 둘 다) | 로컬에서 만들어 설치(기사님 손) | 새 관제앱은 옛 서버에서도 돈다 — 서버보다 **먼저** 깔 수 있고, 먼저 깔아야 ②에서 옛 관제앱이 회색 배지 · «알 수 없는 화면» 빨간 깜빡임을 안 그린다 |
| ② | shared + 서버 + 관제웹 이름표 | 커밋은 나누고 **배포는 push 한 번**(기사님이 말씀하실 때만 · 운행 중이 아닐 때). 서버는 옛·새 값 모두 받고, 관제웹 이름표도 둘 다 같은 한글 | 같은 push 로 같이 나가므로 둘 다 이미 양쪽을 안다 |

| ④ | 실서버에 붙은 스캔폰에 새 원달앱을 깐다 | 기사님 손 | ② 뒤에만 |
| ⑤ | (나중) 모든 폰이 새 버전이면 대응표를 지운다 · 이상 기록 `screen_name` 옮기기 | 이름표 7장 C 단계는 `screen_words` 를 뺀 것으로 줄어든다(12장) | |

정의 표 · 원달앱 생성 파일은 원달앱 커밋(③)에 들어간다 — 정의 표가 원천이고 생성 파일이 갈라지면 검사가 문다.

### 순위 검산 (④) — 순서 둘을 나란히

| | 가: 관제앱 → 서버+관제웹 → 원달앱 (위) | 나: 원달앱 먼저 |
|---|---|---|

## 6. 옛 원달앱을 받는 대응표 — 화면 값이 서버로 들어오는 길 전부

옛 값 → 새 값 대응은 아래 한 줄이다(shared `screenKinds.ts` 옆 한 곳 · 서버와 관제웹이 같이 쓴다).

| 옛 원달앱이 보내는 값 | 새 값으로 읽는다 |
|---|---|
| `LIST` | `NEW_LIST` |
| `DETAIL_PRE_CONFIRM` | `NEW_CALL` |

## 7. `LIST_COMPLETED` 를 없앨 때 — 목록 복귀 판단이 그 순간 어떻게 도는지

기준 장면: 인성 «완료» 탭(= 내 콜 목록 + 목록 복귀 표시)으로 기사님이 갔다. 서버는 그 폰의 콜 하나를 쥐고 있다.

**먼저 풀어야 하는 문제 — 안쪽 값 하나가 세 가지를 말하고 있었다.** 지금 완료 탭의 안쪽 값은 `LIST_COMPLETED` 하나다. 이 이름 하나가 ① «지금 목록 복귀다»(`HijackService.kt:1369-1371`, `KakaoPickerPlugin.kt:318`) ② «이전 화면이 목록 복귀였다»(같은 줄의 `previous`) ③ «목록 감시 묶음에 안 든다»(`ListWatch.kt:23` — `MY_ORDERS` 는 들고 `LIST_COMPLETED` 는 안 든다)를 한꺼번에 답한다. 없애면 이 셋을 **각자 자기 사실로** 읽어야 한다(CLAUDE.md 의 «뭉친 이름으로 가르지 않는다»).

| | 지금 | 바꾼 뒤 |
|---|---|---|
| **원달앱 — 화면 읽기** | `ScreenDetector.read` → 안쪽 `LIST_COMPLETED`, 보낼 값 `MY_ORDERS`, 페이지 `완료 탭` | 안쪽 `MY_LIST`, 보낼 값 `MY_LIST`, 페이지 `완료 탭`, 그리고 정의 표 줄의 **`listReturn`**(참)을 `ScreenRead.returnedToList` 로 함께 담는다 |
| **원달앱 — «지금 목록 복귀다»** | `detected == LIST \|\| detected == LIST_COMPLETED` | `ScreenRead.returnedToList` 하나로 가른다. 이 값은 **정의 표 줄의 `listReturn` 칸 그대로**다. 신규 콜 목록 줄도 표에서 `listReturn: true` 로 바꾼다(아래 «정한 것 ⓐ») — 그러면 «`NEW_LIST` 이거나 …» 같은 이름 분기가 앱에서 사라지고 사실 하나만 읽는다 |
| **원달앱 — «이전 화면이 목록 복귀였다»** (`HijackService.kt:1303 · 1371` `wasListScreen`) | `previous`(`ScreenContext` 한 개)가 `LIST` 이거나 `LIST_COMPLETED` | `previous` 값만으로는 **완료 탭(목록 복귀)과 픽커 «내 오더»(목록 복귀 아님)를 못 가른다.** 이전 화면의 **페이지 이름**을 `previous` 옆에 지역 변수로 함께 붙잡고(`val previousPage = telemetryManager.screenPage`), 이전 복귀를 «정의 표에서 그 페이지의 `listReturn`»으로 읽는다(아래 «정한 것 ⓑ» — 새 칸 없음) |
| **원달앱 — 목록 감시 묶음** (`ListWatch.kt:23` `OFF_LIST_WATCHED` = 메뉴 · 홈 · `MY_ORDERS` · 모름) | 완료 탭은 `LIST_COMPLETED` 라 **묶음에 안 든다**(감시 꺼짐). 픽커 «내 오더» 탭은 `MY_ORDERS` 라 든다(감시 켜짐) | `MY_LIST` 가 묶음에 들어 있으면 **완료 탭도 감시 켜짐으로 바뀐다(운행 동작이 바뀜).** 막으려면 묶음 판정에 `returnedToList` 를 같이 넘긴다: «`MY_LIST` 이고 `returnedToList` 가 거짓일 때만 감시». 부르는 곳은 둘 — `HijackService.kt:1171`(`armSpot`, **안쪽 값 `detected`**) · `:1201`(`listWatchdog`, **안쪽 값 `currentScreenContext`**) — 둘 다 안쪽 값을 넘기므로 둘 다 `returnedToList` 를 같이 넘기게 바꾼다 |
| **서버 — 목록 복귀 판단** | `isListScreen`: `LIST`·`LIST_COMPLETED` 이거나 `MY_ORDERS` + 정의 표 `listReturn` | `NEW_LIST` 이거나 `MY_LIST` + 정의 표 `listReturn`. 대응표가 살아 있는 동안은 `NEW_LIST` 이름 분기를 둔다(옛 원달앱은 페이지 이름을 안 보내 표로 못 읽는다). 대응표를 지울 때 이름 분기도 지우고 `screenPage` + 표의 `listReturn` 하나만 남긴다. `LIST_COMPLETED` 는 `LIST_SCREENS` 에서 빠지고 대응표(6장)만 안다 |
| **서버 — 놓음 판단** | `isLetGoScreen` = 목록 복귀 + `landsAfterAccept` 아님 | 그대로 |
| **기사님 손** | 완료 탭을 누르면 서버가 쥔 콜을 유예 뒤 치운다 · 완료 탭에서 목록 감시는 꺼져 있다 | **같다** — 위 셋(지금 복귀 · 이전 복귀 · 감시 묶음)이 모두 같아야 한다 |

**정한 것 (묻지 않고 정해 쓴다 — 저장 칸 · 설정값이 생기지 않는다)**
- **ⓐ «지금 목록 복귀다»는 정의 표의 `listReturn` 하나로 읽는다.** 네 배차망의 신규 목록 줄(인성 «신규 콜 목록» · 화물24시 «화물정보(실시간 목록)» · 픽커 «신규 리스트» · 인성플렉스 «목록(신규)»)을 `listReturn: true` 로 바꾼다. `listReturn` 이 참인 줄은 지금 `MY_ORDERS` 두 줄(인성 완료 탭 · 화물24시 배차내역 목록)뿐이라, 참이 되는 줄은 늘고 `ScreenDetector` 의 `LIST_COMPLETED` 갈래(`wire == MY_ORDERS && listReturn`)는 신규 목록에 닿지 않는다. 정의 표 줄이 바뀌므로 건수 표 3장에 더하고 정의 표 검사(`networkPages.test.ts` · `pagesDoc`)가 같은 커밋에서 초록이어야 한다. 딸려 바뀌는 곳 셋: ① `networkPages.test.ts:170-172` 가 «`listReturn` 은 둘뿐 · 전부 `MY_ORDERS`»를 박아 두므로 기대값이 여섯 줄로, 172줄은 «`MY_LIST` 또는 `NEW_LIST`»로 바뀐다 ② 주석 `PageSpec.kt:95`(«LIST 가 아닌 페이지를 목록 복귀로 치는 표시»)는 원달앱 커밋에서 ③ 주석 `networkPages.ts:230`(«인성 완료 탭 · 화물24시 배차내역 목록»)은 shared 커밋에서 고친다. `NetworkPagesPairTest.kt:91,107` 은 생성 파일을 다시 뽑으면 그대로 맞는다. **안전한 근거**: `listReturn` 을 읽는 코드는 둘뿐이고 둘 다 `MY_ORDERS` 일 때만 본다(`ScreenDetector.kt:53` · `screenKinds.ts:87`) — 신규 목록 줄을 참으로 바꿔도 지금 동작은 안 바뀐다.
- **ⓑ «이전 화면이 목록 복귀였다»는 새 칸 없이 읽는다.** `HijackService.kt:1303` 에서 `previous` 를 붙잡는 자리에 `previousPage` 도 같은 지역 변수로 붙잡는다(`updateScreenContext` 가 `:1337` 에서 돌면 `screenPage` 가 새 페이지로 바뀌므로 그 전에 붙잡아야 한다). `:1371` 의 `wasListScreen` 은 «그 페이지의 정의 표 `listReturn`»으로 읽는다. `onScreenChanged(previous …)`(`:1310`)는 그대로. `TelemetryManager` 에 불리언을 더하지 않는다.
- **ⓒ 감시 묶음**은 현재 페이지(`telemetryManager.screenPage`)의 `listReturn` 을 같이 넘긴다.

### 🔴 운행 동작이 바뀔 수 있는 지점 (기사님 몫)

| 번호 | 무엇이 | 왜 | 안 바뀌는 조건 |
|---|---|---|---|
| ① *(정해짐)* | 옛 원달앱의 `LIST_COMPLETED` 를 서버가 어떻게 읽나 | `NEW_LIST` 로 읽으면 목록 복귀 동작은 같고 관제웹 배지 글자도 페이지 이름이라 같지만 배지 색이 «신규 목록» 색이 된다. `MY_LIST` 로만 읽으면 `screenPage` 가 없는 옛 버전은 목록 복귀가 아니게 된다 → 결재석의 콜이 남는다 | **정함(기사님 1가): 줄을 안 둔다.** 스캔폰 앱(버전 80 · 오늘 설치)은 10-02 이후 버전이라 일반 보고로는 이 값이 안 온다(비상 보고는 판단에 안 쓰임) |

| ③ | `HijackService` 의 `LIST` 비교 약 20곳이 `NEW_LIST` 로 바뀐다 | 이름만 바뀌는 것이 맞다. 단 **`MY_ORDERS`/`LIST_COMPLETED` 를 보던 곳은 이름 바꾸기가 아니라 사실 읽기로 바뀐다**: 목록 복귀(1369-1371 · 318) · 이전 목록 복귀(1371) · 감시 묶음(`ListWatch.kt:23`, 호출 1171 · 1201). 이 다섯 곳이 «MY_ORDERS 를 보던 곳 + LIST_COMPLETED 를 보던 곳»이다 | 아래 동작 검사 |
| ④ | 완료 탭의 목록 감시가 **꺼진 채로** 남는다 | 지금 꺼져 있다. `MY_LIST` 가 묶음에 들어서 켜지면 완료 탭에서 목록 읽기가 돌아 불필요한 읽기(노이즈)가 생긴다 | `returnedToList` 를 넘겨 «꺼짐»을 지킨다 · 동작 검사 |

**끝 조건에 넣을 동작 검사(JVM · 원달앱)**
1. `ListWatch.watches`: 신규 목록 켜짐 · 완료 탭(`MY_LIST` + 정의 표 `listReturn` 참) **꺼짐** · 픽커 «내 오더»(`MY_LIST` + 정의 표 `listReturn` 거짓) **켜짐** · 홈 · 메뉴 · 모름 켜짐(배차망 안일 때만).

3. 픽커: `KakaoPickerPlugin.onScreenChanged` 의 «목록으로 돌아옴» — 완료 탭에서도 같은 알림이 선다.

## 9. 폰 시험 범위

검사(JVM · vitest · jest)가 못 잡는 것은 «실제 폰이 새 값을 보내고 서버가 목록 복귀를 알아보나»이다. 시험은 시뮬레이터 + 스캔폰(A24)에서만 한다.

| 시험 | 보는 것 | 끝 조건 |
|---|---|---|
| S30 꼴(인성 목록 · 상세 · 완료 탭) | 원달앱 로그 `📄 [페이지]` 줄과 서버로 간 화면 값이 **새 이름** | 새 이름으로 간다 · 관제웹 배지 글자는 이전과 같다 |
| S32 | 완료 탭 → 확정 뒤 상세 → 닫기 → 새 목록 | 목록 복귀 때 서버가 쥔 콜을 치우거나 유지하는 것이 이전과 같다 |
| 서버 로그 | 목록 이탈 유예(`listExit_*`)가 완료 탭에서 지금처럼 건다 | `🚀 [화면 이탈 감지]` 줄이 나온다 |

## 12. 콜 상태 정의 계획서와 부딪히는 곳

| 곳 | 부딪힘 | 제 생각 |
|---|---|---|
| 이름표 3장 «`DETAIL_CONFIRMED` → `MY_CALL`(콜 전체 보기)» | 콜 상태 «진행 중»(`ORDER_CONFIRMED`)은 «CONFIRMED» 라는 같은 글자를 쓴다 | 화면 값만 `MY_CALL` 이 되면 겹침이 풀린다. 콜 상태 이름은 이번 단계에서 안 건드린다 |
| 이름표 9장 «새 콜 목록에서 3초 뒤 치운다» | 3초는 서버 상수 `LIST_EXIT_GRACE_MS`. 화면 값 이름과 무관하나 문장이 `LIST` 로 적혀 있다 | 문서의 `LIST` 표기를 `NEW_LIST` 로 함께 고친다(문서 고침은 콜 상태 정의 쪽) |
| 이름표 3장 «`LIST_COMPLETED`·`POPUP_*` 는 지금 폰이 보내지 않는다» | 비상 보고는 안쪽 값을 실어 보낸다(1장 3번) | 문장을 «일반 보고로는 안 보낸다(비상 보고는 서버가 판단에 안 쓴다)»로 고칠 것 |
| 이름표 3장 «관제앱 코드는 이 레포에 없다» | 관제앱은 `onedal-web/client-app/android` 로 이 레포 안에 있고 관제웹 빌드를 담는다(5장) | 문장을 고칠 것. 관제앱 APK 를 새로 깔아야 한다는 일이 생긴다 |
| 이름표 7장 C 단계 «DB 옛 값 옮기기 — `screen_words.page` 1,410줄 · `telemetry_anomalies.screen_name`» | 기사님 3나: **`screen_words.page` 는 옮기지 않는다**, 이상 기록 `screen_name` 만 옮긴다. C 단계의 `screen_words` 합치기 규칙(처음 본 때는 이른 쪽 · 횟수 합 …)과 대응(`list → newList` 등)이 쓸모없어진다. 숫자도 낡았다(오늘 로컬 1,600줄) | C 단계 문장을 «`telemetry_anomalies.screen_name` 만 옮긴다»로 줄일 것 |
| 이름표 3장 «옛 버전이 남았으면 `LIST_COMPLETED` 는 `MY_LIST` + 목록 복귀 참으로 받아야 한다» | 기사님 1가: **받는 줄을 두지 않는다** | 그 문장을 «받지 않는다(스캔폰 앱이 새 버전이라 오지 않는다)»로 고칠 것 |
| 이름표 3장 «옛 값 → 새 값 대응표» 네 줄 | 대응표는 필요하다(옛 원달앱 `LIST` 등) — 단 `LIST_COMPLETED` 줄은 없다 | 대응표 네 줄 그대로 둘 것 |

찾은 것(계획 밖 · 기록만): 레포 루트 `deploy.sh` 는 `cd client && pnpm build` 라 지금 폴더(`client-app`)와 안 맞고 배포가 쓰지 않는다(배포는 `.github/workflows/deploy.yml` 이 `onedal-web/scripts/deploy.sh` 를 돌린다). 지우기는 기사님 몫.
