# 콜 상태 정의 계획서 (초안 — 기사님 승인 전)

기사님 말씀: «콜 상태의 진행 순서와 갈림을 정의한다» · «상태값을 **진행 상태**와 **콜의 성질**로 나눠 정의한다». 재료는 `콜상태_전수조사.md`(코드를 읽어 대조한 것이고, 돌려 본 것은 아니다)다.

한 줄 요약: 동작 코드와 이름은 그대로 두고 **말의 뜻만** 정한다. 정해지면 사진 이름의 상태 자리를 채울 수 있다.

---

## 1. 이 수정이 기사님 하루에 무엇을 하나

| | 영향 |
|---|---|
| 좋은 콜 | **그대로.** 동작 코드가 안 바뀐다(코드 주석만 고친다). |
| 노이즈 | **그대로.** 동작 코드가 안 바뀐다. |
| 기사님 손 | **그대로.** 화면 글자 · 단추가 안 바뀐다. |

이 일이 주는 것은 운행 동작이 아니라 다음 결정의 재료다. 사진 이름을 정할 수 있고, 운행에 닿는 문제 넷(5-2)을 «어느 약속을 어겼나»로 말할 수 있다.

---

## 2. 지금은 이렇게 돈다

- 서버는 콜 상태를 열 가지 이름 하나로 적는다. 그 안에 «어디까지 왔나»와 «누가 · 왜»가 섞여 있다.
  - «안전취소» 한 이름이 다섯을 다 뜻한다: 기사님이 결재석에서 거절 · 서버가 시간이 다 돼 취소 · 원달앱이 화면을 떠나 서버가 정리 · KEEP 을 원달앱이 못 받아 취소 · 원달앱이 배차망 취소를 누름. 어느 것인지는 서버 기록 파일에만 남는다. 체험 콜의 끝도 이 이름이다.
  - 방출(기사님) · 방출(사무실)은 이름 안에 «누가 놓았나»가 들어 있다.
- 서버 장부는 «누가 잡았나»를 네 칸으로 나눠 적는다: 콜 종류(`type`) · 누가 열었나(`openedBy`) · 그때 모드(`capturedMode`) · 누가 확정했나(`whoConfirmed`). 콜 종류는 체험 여부까지 함께 담고, 직접 잡은 콜을 두 표기(`MANUAL` · `MANUAL_CLICK`)로 적는다. 다섯째 칸(`capturedVia`)은 새 콜마다 비어 있다.
- 선점 중 · 심사 중 · 결재 기다림은 서버가 기억만 한다. 서버를 다시 켜면 사라진다.
- 상태를 바꿔도 되는지 묻는 검사가 흩어져 있다. 상차 · 하차 보고는 순서를 검사하고, 심사 중 콜은 끝난 콜인지 검사하지만, 방출과 되돌리기는 검사가 없다.

새 저장 칸 · 새 값을 만들지 않으므로 옮길 것은 없다. 정의가 값을 빠뜨리지 않았는지만 본다.

| 칸 | 로컬 값 | 정의에서 |

| 콜 상태 `orders.status` | `ORDER_CONFIRMED` 7 | 진행 중 |
| 콜 종류 `orders.type` | `MANUAL` 7 | 성질 «누가 확정했나» · «체험» |
| 그때 모드 `orders.capturedMode` | `ALARM` 5 · 빈 값 2 | 성질 «그때 모드» |
| 누가 열었나 `orders.openedBy` | `APP` 5 · 빈 값 2 | 성질 «누가 열었나» |

## 5. 정의안

### 5-1. 진행 상태 — 이 콜이 어디까지 왔나

말은 관제웹에 보이는 이름 그대로 쓴다.

| 진행 상태 | 뜻 | 묶음 | 저장 |
|---|---|---|---|
| 상태 없음 | 아직 1DAL 장부에 없다 | — | — |
| 선점 중 (`ORDER_PRE_SECURED`) | 원달앱이 자동 모드면 확정을 누르기 직전부터, 알람 · 직접 모드면 상세를 연 순간부터 | 심사 묶음 | 서버 기억만 |
| 심사 중 (`ORDER_SECURED_EVALUATING`) | 서버가 상세를 받아 판정한다 | 심사 묶음 | 서버 기억만 |
| 결재 기다림 (`ORDER_AWAITING_DECISION`) | 판정이 나 기사님 결재를 기다린다 | 심사 묶음 | 서버 기억만 |
| 진행 중 (`ORDER_CONFIRMED`) | 내 콜이 됐다 | 운행 묶음 | 장부 |
| 상차 완료 (`ORDER_PICKED_UP`) | 짐을 실었다 | 운행 묶음 | 장부 |
| 하차 완료 (`ORDER_DELIVERED`) | 짐을 내렸다 — 끝 | 끝 | 장부 |
| 안전취소 (`SAFE_CANCEL`) | 내 콜이 되기 전에 물러났다. KEEP 뒤 원달앱이 못 받아 취소한 것도 여기 — 끝 | 끝 · 놓음 | 장부(미리보기 · 체험은 서버 기억만) |
| 방출(기사님) (`ORDER_RELEASED_BY_ME`) | 내 콜을 기사님이 놓았다 — 끝. 콜의 방출 단추 · 예약 방출 · 짐 불일치 신고 · 현장 상차 취소 네 길로 온다 | 끝 · 놓음 | 장부 |
| 방출(사무실) (`ORDER_RELEASED_BY_OFFICE`) | 내 콜을 사무실 쪽 사정으로 놓았다 — 끝 | 끝 · 놓음 | 장부 |
| 완료 (`ORDER_COMPLETED`) | 정산까지 끝났다 — 끝. 새로 만드는 코드는 없고, 정산 화면이 생기면 거기서 만든다(기사님 결정) | 끝 | 장부(옛 줄만) |

### 5-2. 진행 순서와 갈림

```
상태 없음 → 선점 중 → 심사 중 → 결재 기다림 → 진행 중 → 상차 완료 → 하차 완료
                                              └─────── 상차 없이 ─────┘

선점 중 · 심사 중 · 결재 기다림 ↓ 안전취소
진행 중 ↓ 안전취소(KEEP 을 원달앱이 못 받음) · 방출 둘
상차 완료 ↓ 방출 둘
```

| 갈림 | 언제 · 어떻게 |
|---|---|
| 직접 잡은 콜 | 서버가 판정한 뒤 결재석 없이 곧바로 진행 중으로 올린다. 미리보기로 이미 판정했으면 심사 중에서 곧바로 진행 중으로 올린다 |
| 미리보기 | 결재 기다림까지 가도 내 콜이 아니다. 기사님이 수락하면 심사 중으로 **한 칸 돌아갔다가** 진행 중이 되고, 화면을 떠나면 장부 없이 사라진다 |
| 체험 | 기사님이 KEEP 하든 거절하든 안전취소로 끝난다(서버 기억만) |
| 같은 폰의 원달앱이 새 콜을 선점 | 앞서 심사하던 콜은 안전취소로 끝난다(이미 KEEP 한 콜은 아니다) |
| 원달앱이 «취소를 눌렀다»고 알림 | KEEP 한 진행 중 콜이면 안전취소 · 심사 중 콜이면 안전취소 · 그 밖(상차 완료 콜, 서버에 KEEP 기록이 없는 콜)이면 방출(사무실) |
| 원달앱이 «취소를 못 눌렀다»고 알림 | 상태가 안 바뀐다 — 계약이 남아 있다 |
| 끝난 콜에 KEEP 결재가 옴 | 서버가 진행 중으로 되살리지 않는다 |
| 서버를 다시 켬 | 서버 기억만 있는 세 상태의 콜은 사라진다. 폰이 받았다고 답하지 않은 진행 중 콜도 되살리지 않는다 |
| 예약 | 진행 중이되 보관 날까지 따로 둔다 |
| 되돌리기 | 관제웹 되돌리기로 하차 완료 → 상차 완료 또는 진행 중 · 상차 완료 → 진행 중 |

**끝 상태 약속(정의):** 하차 완료 · 완료 · 안전취소 · 방출 둘은 끝이다. 끝난 콜에는 결재 · 상차 · 하차 보고 · 방출이 닿지 않는다. 예외는 기사님이 잘못 누른 하차 완료를 관제웹에서 되돌리는 것 하나다.

**취소 횟수는 상태가 아니라 끝나는 길에 붙는다.** 셈이 둘이라 숫자가 다를 수 있다(사용설명서 6장 «1DAL 이 따로 센 값»의 근거):
- 배차망 한 판(10회): 서버가 장부의 안전취소 줄을 센다. 미리보기 · 체험은 장부에 안 남아 안 센다.
- 관제웹 폰 줄의 «취소 n»: 콜이 끝나는 세 길(심사 콜 정리 · 결재로 놓음(방출 포함) · 원달앱 비상 보고)에서 오른다. 미리보기 · 체험은 뺀다.

⚠️ 지금 코드가 이 약속을 어길 수 있는 곳이 넷 있다. 고치면 운행 동작이 바뀌므로 **기록만 하고 고치지 않는다**(기사님 «지금은 리팩터링만»):
1. 원달앱이 잡은 인성 · 화물24시 콜에 결재가 없으면, 원달앱이 «취소를 눌렀다»고 알리기 전에 서버가 먼저 안전취소로 적는다. 원달앱이 못 눌렀어도 장부는 취소다.
2. 인성 · 화물24시 미리보기 콜이 시한으로 결재석에서 먼저 사라질 수 있다.
3. 방출한 콜의 상차 · 하차 보고를 되돌리면 진행 중으로 되살아난다.
4. 방출 길에는 끝난 콜 검사가 없다. 단추만이 아니라 짐 불일치 신고 · 현장 상차 취소도 이 길을 탄다.

넷 다 코드로 읽은 사실이고 실제 운행에서 일어나는지는 확인하지 못했다.

### 5-3. 콜의 성질 — 어떤 콜인가

| 성질 | 값 | 한 번 정해지면 안 바뀌나 | 지금 코드 칸 | 장부 |
|---|---|---|---|---|
| 배차망 | 인성 · 화물24시 · 픽커 · 인성플렉스 | 안 바뀐다 | `targetApp` | 있음 |
| 누가 열었나 | 원달앱 / 기사님 | 안 바뀐다 | `openedBy` | 있음 |
| 누가 확정했나 | 아직 없음 / 원달앱 / 기사님 | 한 번 정해진다 | `whoConfirmed`(계산해서 얻는 값) · `type` 일부 | 없음 |
| 그때 모드 | 자동 · 알람 · 직접 · 체험 · 모름(옛 줄) | 안 바뀐다 | `capturedMode` | 있음 |
| 미리보기(확정은 안 하고 판정만 보는 콜) | 예 / 아니오 | 예 → 아니오만 | `isPreview` | 없음 |
| 체험 | 예 / 아니오 | 예 → 아니오(기사님이 직접 확정할 때) | `isSimulated` · `type` 일부 | 없음 |
| 예약 | 보관 날짜 | KEEP 때 정해진다 | `reserved_for` 등 | 있음 |
| 폰이 받았음 | 시각 | 한 번 정해진다. 비어 있으면 서버를 다시 켤 때 그 진행 중 콜을 되살리지 않는다 | `ackedAt` | 있음 |
| 상대가 취소했다고 함 | 예 / 아니오 | 콜의 단계표(상차 · 하차 줄)에 적힌다 | `counterpartCancelled` | 단계표 |
| 정산 | 미정산 / 정산됨 · 미수금 | 바뀐다 | `settlementStatus` · `unpaidAmount` · `settledAt` | 있음 |
| 안전취소 까닭 | 거절 · 시한 · 화면 이탈 · 못 받음 · 원달앱 누름 | 끝날 때 | **칸 없음 — 서버 기록 파일만** | 없음 |

«장부 없음» 칸은 서버를 다시 켜면 모른다. 새 칸을 만들지 않는다(4장 가).

**정의에서 뺀 것(칸은 지우지 않는다):**
- 판정(색 · 점수): 콜의 성질이 아니라 심사 결과다. `order_judgments` 표에 저장된다.
- 합짐 · 급송 · 복귀 목표: 콜의 내용이다. 경로 계산 · 통계가 쓴다.
- 옛 잡은 방식(`capturedVia`): 새 콜마다 비어 있다. 칸을 지우는 일은 기사님이 말씀하실 때만 한다.

### 5-4. 사진 이름의 상태 자리 (`기준페이지_이름표.md` 10장)

| 페이지 | 상태 자리 |
|---|---|
| 새 콜 목록 · 새 콜 화면 | `상태없음` |
| 홈 · 기준 밖 | `없음` |

### 5-5. 콜의 내용 — 주선사 · 퀵사가 올린 값

칸 19개의 이름은 `pageFields.ts` 한 곳에, 칸마다 «어느 화면 어느 자리에서 어떤 글자로 읽나»는 배차망별 정의 표에 있다. 이 문서는 다시 적지 않고 꼭 있어야 하는 값만 적는다(`OrderRequirement.kt`).

| 언제 | 꼭 있어야 하는 값 | 모자라면 |
|---|---|---|
| 원달앱이 목록 줄을 읽을 때 | 상차 · 하차 · 요금 · 상차지거리(픽커 도보는 하차 없어도 됨) | 그 스캔에서만 빼고 다음 스캔에 다시 본다 |
| 원달앱이 상세를 읽은 뒤 | 요금 · 상차 전체 주소 · 하차 전체 주소 | 사진으로 한 번 더 채워 보고, 그래도 모자라면 서버에 올리지 않고 버린다. 이상 기록만 남긴다 |
| 기사님이 먼저 확정한 콜 | 요건으로 버리지 않는다 | 서버가 확정을 진행하고 못 읽은 값은 관제웹에 «직접 채워 주세요»로 표시한다 |

서버도 요금 · 상차 · 하차 같은 셋을 «못 읽음»으로 본다(`detail.ts`).

- **차종:** 기사님 말씀 «차종은 필수». 어디까지 필수인지와 코드는 `차종_기준_계획.md` 에서 정한다. 지금 코드는 필수가 아니다.

## 8. 기사님이 정하실 것

**1. 어디까지 할까요?**
- 부딪히는 문장: «콜 상태를 진행 상태와 성질로 나눠 정의한다» ↔ «새 저장 칸은 합의 뒤에 · 지금은 리팩터링만».
- **가** 말의 뜻만 정하고 틀린 코드 주석만 고친다(추천 · e57856 · onedal-1e 도 가).
- **나** 코드의 칸까지 나눈다. 새 저장 칸이 생긴다.
- **다** 상태 값 이름까지 바꾼다. 앱 · 서버 · 관제웹 · DB 를 함께 올린다.

**2. 안전취소의 까닭을 장부에 남길까요?**
- 부딪히는 문장: «새 저장 칸은 합의 뒤에» ↔ 지금은 서버 기록 파일에만 있어, 보관 기간이 지나면 지워진다.
- **가** 지금은 안 남긴다(추천 · e57856 · onedal-1e 도 가). 사업자가 없어 실제 안전취소 자료가 없다.
- **나** 새 칸을 만든다.

**3. 이 약속을 콜 상태의 약속으로 정할까요?**
- 문장: «하차 완료 · 완료 · 안전취소 · 방출 둘은 끝이다. 끝난 콜에는 결재 · 상차 · 하차 보고 · 방출이 닿지 않는다. 예외는 기사님이 잘못 누른 하차 완료를 관제웹에서 되돌리는 것 하나다.»
- **가** 정한다. 코드가 어길 수 있는 넷은 고치지 않고 기록만 한다(추천 · e57856 · onedal-1e 도 가).
- **나** 고칠 곳을 말씀해 주신다.
